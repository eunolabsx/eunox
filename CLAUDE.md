# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`eunox` is a policy-enforcement proxy for MCP servers (Go, one static binary). It sits between an MCP host and an upstream MCP server, checks every enforced MCP method (`tools/call`, `resources/read`, `resources/subscribe`, `resources/unsubscribe`, `prompts/get`, `sampling/createMessage`) against a YAML capability manifest before forwarding, filters `*/list` responses to permitted entries, and writes every decision to an HMAC-SHA256-signed OCSF JSONL audit log.

## Commands

```bash
make build           # → bin/eunox
make test            # go test -race -count=1 ./...
make lint            # go vet + golangci-lint at CI's pinned version (installs it when PATH has another)
make fmt             # gofmt -w every .go file
make check-fmt       # gofmt-clean check on every .go file (CI-enforced); fix with `make fmt`
make check-license   # Apache-2.0 SPDX header on every .go file (CI-enforced)
make check-notice    # NOTICE lists exactly the binary's third-party modules (CI-enforced)
make coverage        # coverage.out for all packages — CI gates pkg/, internal/ and cmd/ at 80% each
```

Run a single test (standard Go tooling):

```bash
go test -race -count=1 -run 'TestName' ./cmd/eunox/
```

End-to-end demo stack (Docker) — the fastest way to verify a behavior change against a real proxy + mock upstream: `make -C demo up`, then `make -C demo allow|deny|audit`; gateway variant `make -C demo gateway-up`.

## Architecture

Three layers: `cmd/eunox/` is the binary (CLI, transport wiring, PDP wiring); `pkg/` holds the importable engine and supporting libraries; and `internal/` holds subsystems factored out of the binary behind narrow seams — `internal/audit` (the tamper-evident audit log, consumed through the exported `audit.Sink`), `internal/mcp` (the MCP protocol message types plus the JSON-RPC envelope/newline-framing/classification layer — `RPCMsg`, `MsgReader`/`MsgWriter`, `MsgKey`, the response builders — shared by the transports, PDPs, and the CLI's live-upstream probe), `internal/pdp` (the policy decision points: the `PolicyDecisionPoint` contract and the `ManifestPDP`/`JWTPDP`/`AlwaysAllowPDP` implementations), `internal/config` (the config + manifest loading layer: `GatewayConfig` parsing, `LocalManifest` load/validate/merge, schema-version negotiation), `internal/drift` (the startup manifest-drift-comparison policy: `CheckManifestDrift`/`MakeDriftCheck`/`UpstreamTool`/`Warning`/`ParseToolsListResult`/`CheckFunc`, shared by the binary's `validate --live` and the transport runtime), `internal/registry` (the effect-contract corpus format — `Contract`/`LoadCorpus`/`Validate` — plus the attestation trust layer in `attest.go` — `Signature`/`TrustStore`/`LoadTrustStore`/`VerifyAttestations`/`AttestationPayload` — over the shipped corpus in `registry/contracts/`; authoring-time input only, never consulted on the decision path, and no key is ever fetched), `internal/redisutil` (the go-redis TOPOLOGY question both Redis backends ask — `ShardFanOut`/`Topology`/`ClassifyTopology`/`IsNilClient`/`ErrIncompleteFanOut`, where the fan-out it hands back is required to be COMPLETE and go-redis' Ring iterator is not (it skips a shard voted down and returns nil), so the Ring arm is wrapped with the check that turns a partial pass into an error, exported as `WholeRingFanOut` because a consumer whose ring sits behind a decorator can only DECLARE an iterator and the unchecked one is all they otherwise have — hosted below `pkg/callcounter` and `pkg/killswitch` rather than inside either, since a kill-switch-only consumer otherwise linked the whole counter package for a type switch and the next topology question would be answered in a package with no reason to know a keyless SCAN exists), and `internal/transport` (the stdio + HTTP/gateway transport runtime — the proxies, the shared dispatch/forward/enforcement core, the remote-upstream bridge, the route wiring, and the control-token/OAuth-metadata/health endpoints; the binary just wires it). The layering is `internal/mcp` ← `internal/pdp` ← `internal/transport` ← the binary, with `internal/audit` below the transport but deliberately NOT below the PDP layer (the caller-identity adapter that joins the two — validated claims to the `audit.Identity` a record stamps — lives in the binary, `cmd/eunox/audit_identity.go`, which is the one place that already imports both; having `internal/pdp` return the writer's own struct satisfied the `WithIdentity` seam by inverting its arrow rather than removing it, and made every consumer of the PDP layer link the audit writer), and with `internal/config` and `internal/drift` sibling lower layers (`internal/drift` builds on `internal/{config,mcp,pdp}` + `pkg/{capability,enforcement}`) imported by both the CLI and the transport layer; `internal/transport` builds standalone on `internal/{audit,config,drift,mcp,pdp}` + `pkg/*` with zero references back into the binary. `internal/redisutil` is the one arrow that runs the other way — `pkg/{callcounter,killswitch}` import it — and the only `internal/` package that is not factored out of the BINARY: it is factored out of two `pkg/` libraries that both need the same go-redis answer, and it sits in `internal/` rather than `pkg/redisx` because nothing outside the module needs it and the complaint that moved it was precisely that a topology type switch had become published API for the benefit of a consumer that was not itself. It depends on go-redis and the stdlib alone, so it adds no cycle and no reachable API surface.

**Request flow:** host JSON-RPC request → transport layer parses method + arguments → `PolicyDecisionPoint.Decide(...)` → allow: forward to upstream; deny: structured JSON-RPC error back to host (upstream never called) → either way, an audit record is written.

### cmd/eunox

- **Transports** — their own package `internal/transport`; the binary just constructs the proxies (`transport.NewStdioProxy`/`transport.NewHTTPProxyGateway`) and calls `.Start`/`.Serve`. Both constructors first run `wiring.go`'s `requireUsableOptions`, which panics naming any options field holding a TYPED nil: `opts.X == nil` compares the interface, so a wired-but-nil subsystem walked through the absent-case substitution and panicked inside a dependency's goroutine instead. Reflective over the struct rather than a branch per subsystem (a hand-listed guard leaves the next interface field unchecked) and therefore reaching interface-typed fields alone, which is what keeps a legitimately absent `*audit.Sink` constructing; it DESCENDS into struct-kind fields (terminating with no visited set, since Go forbids a struct containing itself by value) so a nested options block cannot inherit "unchecked" — the shape a depth-1 walk stopped covering while the test asserting its coverage stopped asserting on it — and stops at a POINTER, since a pointer field is a subsystem the caller built and its internals are its own package's business, which leaves the map (`Routes`) closed at its own construction site where `NewHTTPProxyGateway` refuses a nil route AND the one interface a route holds; a field reflect will not let it READ (anything reachable only through an unexported name, the read-only flag being propagated to exported fields under it) is SKIPPED rather than refused, since a field no outside caller can set is not the caller-supplied wiring this guard is about — refusing it fired on valid wiring while naming a field that was already exported; substituting a working default is refused for the kill switch in particular, since revocation would silently stop crossing replicas. The subsystems handed over as PARAMETERS rather than options fields (`BuildRoutes`/`LoadUpstreamPDP`'s counter, flow store and kill switch — the three the stdio transport reaches through the second of those alone, since `StdioProxyOptions` carries none of them) take the same refusal through `requireUsable`, named one by one because a parameter list is complete by compilation where a struct field is not. The nilness question itself is NOT this package's: it delegates to `capability.IsNilValue` (`healthSnapshot.fold` and the server-initiated leg's sink ask it too, and `fold` answers a wired-but-nil subsystem DEGRADED, the backstop for anything this package did not construct). The local kind switch beside it is gone — the dependency-weight argument that licenses `internal/redisutil`'s separate copy does not apply to a package that already links `pkg/capability` in dozens of files, and the copy's kind list had drifted WIDER than the shared one, which is the direction that hides a divergence until the first func- or map-typed subsystem. `stdio.go` (`StdioProxy`: host on stdin/stdout, one upstream as subprocess or remote HTTP via `stdio_http_upstream.go`); the `http*.go` files (`HTTPProxy`: MCP Streamable HTTP/SSE, one upstream subprocess per client session, `Mcp-Session-Id` header, loopback-only `/control/kill`) — split by concern into `http.go` (server core: construction + `Serve`), `http_routing.go` (`/mcp` POST/GET/DELETE + `/control/kill`), `http_security.go` (auth, Origin/DNS-rebinding, source-IP, loopback), `http_session.go` (`httpSession` lifecycle, registry, idle reaper, upstream I/O, SSE broadcast; killed-session reclaim runs on the kill's own DELIVERY — `killswitch.Manager.ObserveRevocations` wakes `reclaimOnRevocation`, which re-asks the kill switch about each held session — with the idle reaper's killed arm as the backstop it cannot be, since that reaper does not run at all under `sessionIdleTimeoutMs: 0`), and `http_handlers.go` (upstream-timeout/denial helpers + server-initiated request handling); `record_limiter.go` holds the admission control over the writes a refusal makes at a rate a caller sets — the `recordRateLimiter` token bucket (held per proxy: HTTP's pre-session refusals, and on BOTH transports the `-32022` revision refusal, which stdio writes inline on the serve loop with no other bound at all) and the per-pool `saturationGate` that collapses a `RESOURCE_EXHAUSTED` flood to one record per saturation episode — with the stderr line a refusal writes beside its record bounded separately, in `notice.go`, since a leg can meter no record it writes (an established session's kill records are the tape an emergency stop depends on) and still owe a bound on a per-frame syscall. The two-tier keyed table underneath both is one generic (`tieredBuckets[K]`, held by POINTER by both embedders so a copy shares one table rather than minting a second that aliases its buckets at what the chain then treats as two tiers — the mutexes live in the buckets, so `copylocks` sees nothing): the subtle part — an outer tier that refuses must not lose the inner tier's tally — is the same on either axis. The record buckets are proxy-wide EXCEPT for the four an upstream drives (`upstreamRefusalCategories`), which are per SESSION on HTTP (`newUpstreamRefusalLimiter`, held on the session, carrying that session's own `keyReserve` floor since the table is already per-holder — over the WHOLE upstream-driven set rather than the table's own narrowed one, since a category with no bucket delegates wholly upward and needs its slot at the tier it delegates TO; the notice half cannot hold its floor on the table at all, that table being per ROUTE while its holder is a session): each session has its own upstream, and the shared table let one dead subprocess drain a category's share and elide a sibling session's record that a LIVE in-flight request was lost — the argument each category's own bucket already rests on, one dimension out, and the one `saturationGate` states for its own records. A session's table charges the proxy-wide one as its AGGREGATE parent (`tieredBuckets.parent`) and both tiers must admit, because the split alone multiplies the sustained write rate into the single audit queue by the session count — at the default `maxSessions` that puts the burst past the queue's own depth, under a `--require-audit` that defaults to strict. The session tier decides fairness, the parent holds the total at the pre-split ceiling, a record the parent refuses is pushed back onto the session's tally rather than lost, and a category the session's table has no bucket for is delegated WHOLLY to the parent rather than falling to the floor-rate fallback (which is also what lets a REMOTE-upstream session hold buckets for `remoteUpstreamRefusalCategories` alone — three of the four are driven by a server-initiated request and a remote upstream issues none). The rollup a per-session table produces names its own scope (`suppressedScopeSessionCategory`), since a tally spanning one session stamped with the proxy-wide value reads as spanning every route; see `docs/threat-model-mcp.md` §3.7. How a DIAGNOSTIC is bounded is a per-site declaration too, and — unlike its first form — a MECHANISM rather than a lint: `notice.go` ships the declarations and `admitNotice` READS them at write time to pick the bucket, the direct analogue of `forCategory` on the record half, so a site cannot be declared metered and charge nothing and an UNDECLARED site charges the floor-rate fallback rather than writing free. The declarations are TWO tables, one key kind each: `meteredNotices` maps the `noticeSite` constant a call passes to everything that site declares — its `noticeClass` (which is what lets ONE function hold lines of different classes: `enforcedForwardCore` writes an observe downgrade beside a redaction failure) and its `collapseDisposition` with the reason that answer rests on, both required, since a collapse table of its own could only be an opt-in list and cost `admitNotice` a second string-keyed probe on every line for a window two of fifteen sites hold — and `unmeteredNotices` maps the writing function's QUALIFIED name — the only thing an AST walk can see for a line that never reaches this file, and qualified so the two transports' same-named twins cannot inherit one another's answer — to one of three other bounds (gated on its record's own admission verdict, a one-shot latch, or exempt WITH its reason). The LATCH is a mechanism rather than a lint: `noticeLatch.admitOnce` is a `reserveSlot` claimed against an instant that never advances — the same primitive under the collapse window and the diagnostic floor, so a one-shot reads no clock and costs one atomic load — and a two-way source guard requires every `noticeOnce` site to reach it and every site reaching it to be declared one, which is what removes the three hand-rolled latches (an `atomic.Bool`, and twice a counter compared against 1) that were the shape the metered half's collapse had before it became a declaration. A WINDOW remains metered-only, deliberately: `admitNotice` applies it and an unmetered site never reaches one, so an unmetered site wanting a window holds a `reserveSlot` of its own rather than taking on a peer-driven class budget for a line no peer drives. One map held both key spaces, so a metered entry keyed by a function name was unreachable from the lookup and silently charged the floor bucket; metering is now MEMBERSHIP in the first table rather than a field in either, so that disagreement does not typecheck, and splitting by key kind is not the "two lists that must agree" the single table replaced — the halves answer different questions about disjoint sets of lines. The call-site walk in `notice_bounding_test.go` remains for the two questions a runtime reader cannot answer: a line written through a shape that never reaches the mechanism, and a declaration nothing reaches. The notice budget is no longer one number: it is split by CLASS — `classTraffic` (an account of what a peer or upstream SENT: a refusal, an observe downgrade, a handshake echo), `classFailure` (an account of something that BROKE in transit: an upstream down, a notification POST that failed, a forward with no upstream to forward through) and `classObligation` (a security obligation that did not hold: a `redactFields` directive that could not be applied, a clear that did not commit, a signed receipt contradicting its contract) — so a flood of the cheapest peer-driven line cannot take the last token from the line that says an upstream is down, and an upstream flooding the errors it can produce at will (a generic transit error is free on any call; an obligation failure needs a call that CARRIES one) cannot take it from the line that says one of its obligations failed. What the third class does not buy is stated on the type: a downed flow store or a stale `effect.ref` drives it at the request rate from a conforming peer, so within the class one obligation's failure can still elide another's; and by ROUTE (`UpstreamRoute.notices`, built by `NewHTTPProxyGateway` rather than `BuildRoutes`, since the aggregate a route charges is the PROXY's), so one gateway tenant cannot silence another's. Both aggregates are DERIVED by multiplying a per-key budget up (per class, and per configured route) rather than divided out of a fixed one — the treatment the record categories already had — since integer division floors a route's burst to 1 past two routes and leaves a quiet tenant with less legibility than no split at all. The reachable rate per PEER is unchanged (a peer drives at most one key's budget); the process-wide TOTAL grows with the key count, deliberately — 6 lines/s across three classes where the single bucket was 2/s, times the route count on a gateway — which is a bound the OPERATOR sets rather than one a peer drives. A route's table is built parentless by `BuildRoutes` and re-parented by the proxy, so a route that never reaches one is bounded rather than holding a nil table that falls back to the aggregate sized for all of them. Below the route the tier is a FLOOR rather than buckets (`noticeReserve`, held per `httpSession` and carried on its `noticeWriter`): one reserved line per key per the TABLE's own `reserveEvery` (`noticeReserveInterval` here, `recordReserveInterval` on the record half — the third sizing knob beside rate and burst, per table rather than one package constant, since a floored audit record lands in a queue whose overflow denies the data plane while a floored diagnostic costs terminal legibility, and neither may be sized by moving the other), claimed inside `tieredBuckets.admitWithFloor` at the ONE refusal a table's `floorTier` declares its holder's peers responsible for — for the notice half the table's OWN bucket, since a session SHARES its route's buckets — and taking that bucket's accumulated tally with it, since under a sustained flood the floored line is the next line an operator sees and a count left for "the next admitted line" arrives after the incident. The reserve has TWO key spaces, answering different starvations (the shape `meteredNotices`/`unmeteredNotices` uses, for the same reason): per CLASS for a holder among peers, and per SITE (`floorProtectedSites`, DERIVED from the sites' OWN declarations — the floor disposition is a field on `meteredNotices` rather than a third site-keyed table, so the probe it cost every admitted line for an answer one site of fifteen gives is gone and every metered site must answer, with `floorClassUnprotected` CHECKED against the table's content so protecting a first site in some class fails the build for its class-mates rather than silently demoting them) for the one line a CLASS-MATE's flood must not elide — `siteRedactionFault`, since two of `classObligation`'s sites are drivable at the request rate by a conforming peer against a merely broken deployment, so a fourth class would only move the argument one level finer. Those two are also COLLAPSED at their SOURCE (`collapseWindowed` in `meteredNotices`, whose windows are held per upstream — a route on the gateway, the proxy on stdio — as a `keyReserve[noticeSite]`, the same re-arming primitive the floor is built on, reached inside `admitNotice` ABOVE the bucket so a folded occurrence spends no token and the flood stops existing rather than being survived). A TIME window rather than an episode a success reopens, because the state keys per SOURCE while the faults are per CALL: a success-driven reopen alternated on mixed traffic (more lines than no collapsing, each recovery claim resting on a different subject's evidence) and let an upstream that declined to produce a success mute the site indefinitely. The window is CLAIMED before the bucket — one atomic operation rather than the peek-then-mark composition `saturationGate` needs a mutex for — at the price of an occurrence whose bucket was empty spending the window anyway; and the site floor stays as the backstop for the tier below. The site axis is not about holders at all, so `StdioProxy` holds a site-only reserve (`newNoticeReserve(nil)`) while a proxy, being one holder with no sibling, reserves nothing per class. A floored write is a bypass of the GATE and not of the ACCOUNTING: it DEBITS the bucket that REFUSED (`recordRateLimiter.borrow`, clamped at one burst of debt on the POST-decrement balance), so it displaces the flooder's next write rather than adding to that tier's total — only that tier, since charging the aggregate too would count one write twice, and the aggregate's ceiling holds transitively because each child's own budget bounds every write leaving it. WHICH tier that is comes from the admission's own verdict (`bucketVerdict.refusedBy`) rather than from reaching one level up by hand, because `!ok` means a refusal ANYWHERE above: positionally, a third tier would debit a middle tier that had ADMITTED and leave the refusing one untouched, with `bucket()` recursing happily past it and nothing failing. The TALLY half of the same delivery is `unpushIntermediateTallies`: a tier whose own bucket admitted and whose ancestor then refused pushes its token's worth of tally back on the way UP, before any descendant's floor has decided, so a delivery that then happens leaves every tier between the floor and the refusal reporting a delivered write as one the reader did not see. It is taken back by walking the parent chain to the named refuser rather than by carrying the passed tiers on the verdict, since the verdict is built on every refusal and a slice there allocates per refused frame in the two-tier shape that ships — where the walk terminates on its first comparison and the correction costs nothing. That is what made the same floor affordable on the RECORD half, where a floored write is an audit write and is marked `refusal_record_floored` so an arrival the tier had no room for is distinguishable on the tape. The reserve re-arms per interval rather than per holder LIFETIME, since a lifetime bit is claimed by the first transient and gone when the incident arrives; the interval does not delay an arrival, it only stops one holder claiming repeatedly, and what it gives up is that the bound becomes LIVE holders rather than sessions created. Its instant is the one the ADMISSION sampled (`recordRateLimiter.admit` hands its own `now` back), so a refused frame reads no clock of its own and the floor cannot measure its interval against a different instant than the refill that refused it; the slot stores a `time.Time` rather than unix nanos, since `UnixNano` strips the monotonic reading (an NTP step would then lock every reserve for the length of the step) and leaves no value free to mean "never claimed" (the epoch read as unclaimed forever). A refusal from the AGGREGATE is deliberately not floored on that axis (the route had a token, both tiers already counted the write, and the pressure is other tenants' — flooring it there burned a session's one-per-class reserve on a sibling ROUTE's flood); the RECORD half declares the opposite tier (`floorParentBucket`) and for a reason rather than by symmetry, since a session OWNS its whole record table — its own bucket refusing means it outran its own budget — while its peers contend at the proxy-wide aggregate, which is exactly where a sibling's first `displaced_server_request` was being elided (child and parent are the same rate, so pacing alone left the sibling arriving to find the parent empty). A session's dead upstream drove three `classFailure` sites per frame and elided a SIBLING session's first `upstream error` line, which is the elision the route split closed one tier up; a third tier of buckets is what the RECORD half does at this axis and would buy almost nothing here — at the parent's own rate it paces a flooding session to exactly the rate the route bucket refills at, and as a share it floors to 1/s and a burst of 1 at any realistic `maxSessions`, worse than no split for the single-session case — because what a sibling needs is an ARRIVAL, not a rate. Its bound is the re-arm INTERVAL stated below, not a session count: a holder claims at most one line per key per interval, so the ceiling is LIVE holders rather than sessions created — which is also why `maxSessions: 0` capping nothing does not uncap this. The residual is stated where it is spent: between claims the two sessions share the route's tokens first-come. The rollup names the CLASS and the TIER its count spans, since one bucket serves several sites and the same sentence would otherwise mean one tenant on a gateway and the whole process on stdio — the record half's `suppressed_refusal_scope`, said in a line rather than a field, and on that half the scope now comes from the tier that ANSWERED (`tieredBuckets.admitWithFloor` returns it) rather than from the table the caller happens to hold, since a category delegated wholly to the parent produced a proxy-wide count under a session label. A leg's diagnostic CHANNEL is ONE value (`noticeWriter`: where a line goes, what bounds it, and what floor it may fall back on), not a writer field beside a bucket field that a leg can set half of — the live shape was `serverRequestParams`, whose writer was its own `errOut` while its bucket came from the unblocker it carries. The admission is the ONE entry point (`noticeWriter.admitNotice` returning a `noticeLine`; the eager `noticef` wrapper is gone, so there is no second spelling and no per-site judgment) and EVERY metered site takes it before building its arguments, which are the expensive part of a suppressed line — a bounded method name, a sanitized target, a joined reason list, each escaping to the heap per frame on the flood path the bucket exists for; it hands back a line rather than the bool that shape was first proposed as, since a bool is a peek the mechanism never hears about again and a site pre-gating on one would either spend a second token or skip without counting, which under-states the flood the count exists to report. Every refusal record is written under ONE admission (`categoryRecordLimiter.admitRefusal`), which resolves the holder's floor from the table that holds it — the pre-session path writes its record inline and reached the buckets directly, which agreed with the other spelling only while that table held no floor. Which refusals are metered is a per-category DECLARATION (`refusalDeclarations`: metered, or deliberately exempt WITH its reason) that the bucket table and the budget divisor are derived from — through `sortedKeysWhere`, the ONE filter-and-sort this package's declaration tables share (`declarations.go`), since four hand-written copies of it each sized something load-bearing and a vocabulary that silently omits a key does not fail, it falls to a floor-rate bucket or reserves no slot; the one derivation that PROJECTS values rather than collecting keys stays separate and says why, its dedup being load-bearing where the others need none — with a table test walking the recorder call sites — so a refusal cannot ship with no answer, and neither can one whose call site contradicts its declaration. The DECLARATION is applied by the one admission both spellings of a refusal write go through (`categoryRecordLimiter.admitRefusal`), not at each entry point: an exempt category holds no bucket by design, so an unregistered key on a parentless table falls to the floor-rate `unknown` fallback and reading the exemption at the recorder-resolving spelling alone left the OTHER one throttling an exempt refusal harder than a metered one — the inversion of what the declaration says, under the flood the exemption exists for. A leg RESOLVES its recorder per category through `refusalRecorders.forCategory` (a plain `{rec, limits}` pair, where `limits` is the leg's two buckets held APART from the sink every params struct already carries for its policy records — a second copy of that sink is a wiring fault nothing would catch — and `refusalLimits.recorders` is where the two are put back together; `limits` is a NAMED field rather than an embedded one, since embedding promoted `recorders` onto the resolved pair and let a producer mint one keeping this leg's buckets while pointing at a different tape, which is the hazard holding the sink apart exists to prevent), which reads that declaration — an UNDECLARED category resolving METERED, the bounded direction — rather than holding one recorder for every refusal it can take: the shared notification gate's arms disagree — the pre-session kill record is metered while the two refusals beside it are exempt — so one per-leg thunk handed all three the metered recorder, and an exemption on the record spent a `catKill` token anyway. `forCategory` is the ONE resolver, reached by both framings of the routing refusal (the request-framed one used to be handed an already-resolved recorder that never met the declaration at all); the marker function that stood in for it on that path is gone, since it returned what it was handed and an `auditRecorder` carries no provenance. Two are declared EXEMPT for one stated reason: the fail-closed ROUTING refusal and the enforced-method-as-notification reject, both reachable only by a peer whose other traffic writes policy DENY records at the same one-per-message cost, and a policy verdict may never be admission-controlled. That exemption is scoped to the RECORD: the second clause is what carries it and a stderr line is not a verdict (nor does a policy DENY write one), so the routing refusal's own notice is bounded on the notice bucket with every elided line counted into the next admitted one — the two halves of one refusal, bounded separately and for different reasons. Each transport builds buckets for the categories it charges (`stdioRefusalCategories` is stdio's one) rather than the whole table, with the per-bucket share still taken from the whole declared set. Both transports route enforced requests through one shared `dispatchRequest` (`dispatch.go`: the method→handler mapping and fail-closed default) and the shared deny/forward/record core (`forward.go`: `enforcedForwardCore`/`forwardServerRequest`/`refuseUnroutable`), so the dispatch and enforcement logic live once instead of being hand-mirrored per transport — including the fail-closed routing refusal, whose two framings were the last pair with a bespoke record and now share one producer through that core, with its upstream sink REMOVED (a nil `callUpstream`, which the core AND `dispatchList` read as a MODE) so "never forwarded" survives a reclassification of the code that keeps the observe gate off it — the observe downgrade IS a forward, so a leg with no upstream cannot take it and the refusal stays hard with the code that names the real cause; a stub that FAILED on use looked equivalent and was not, since its error reached `recordUpstreamFailure` and wrote an `UPSTREAM_ERROR` deny for an upstream never contacted. A refusal for a message with no id builds no denial envelope for a caller that must discard one (`refusalResponse`, keyed on the id rather than a threaded flag, so the notification framing inherits it, with `refusalError` applying the same rule to the core's two plain-JSON-RPC-error refusal exits), and the rule is applied once more at the core's own BOUNDARY so all six exits obey it structurally rather than by which helper each reached for — the ALLOW tail included, which was the exception a comment had to remember. Both transports then SKIP a zero message rather than writing it (`mcp.RPCMsg.IsZero`, `writeDispatchResult`): `JSONRPC` has no `omitempty`, so an unconditional write puts the malformed frame `{"jsonrpc":""}` on the wire where nothing should have been sent; the leg that answers a blocked server-initiated initiator lives once too (`server_request_unblock.go`: `serverRequestUnblocker` + `trackServerRequest`, over the one nil-writer disposition `writeToInitiator` — which also BOUNDS the diagnostic every answering site writes, since a dead sink fails all of them at the peer's rate and a bound placed on one caller is one the next site added does not inherit — resolved LAZILY from the upstream's own sink so the holders that only want the tracker — every forwarded request, on a session that displaces nothing — pay nothing for a writer they never call. ANSWERING and RECORDING an answer that did not land are ONE obligation, so the unblocker carries the reporting wiring (`dropReport`: the leg's `refusalRecorders`, its `killSubject`, and this transport's `serverRequestLegs` vocabulary) and every answering site reports from it — the four arms that REFUSE a server-initiated request, and `unblock`'s three callers, which turned on a bool reporting whether the id was HELD rather than whether the answer LANDED and threw the delivery report away: a refusal record describes the refusal, not the delivery, so a destroyed answer left the upstream blocked with nothing on the tape (`catRefusalUndeliverable`, its own bucket since a broken sink needs no tracking, host or delivery to reach). The report is per DISPOSITION rather than per leg, because a destroyed answer eunox produced and a destroyed HOST REPLY are different facts carrying different categories, which is why one leg field could not serve both; `unblock` names its record from the tracker entry the take consumed, since its commonest caller holds a host RESPONSE and a response carries no method. The two params structs that take such a refusal hold that one unblocker rather than a writer, a bucket pair and a leg threaded separately, and both transports' entry-plus-dispatch sequence is one `dispatchServerRequest` in the `hostNotificationGate.admit` mould. The seam is the one the sampling leg's params and the pool's dispatch reach as well — those three fed the same sink from closures over a CONCRETE writer, and a nil `*mcp.MsgWriter` locks its mutex on a nil receiver, so they panicked after their audit record where the seam reports), since the four hand-written copies disagreed about the nil-upstream-writer case; `serialize.go` + `anchor_gate.go` hold the decision turn that orders a flow source's state write before a later sink's read — keyed on the state ANCHOR (the validated `mcp.task_id` under `taskAnchoredState`, the session otherwise) rather than on the connection, so two sessions sharing a task share a turn. BOTH transports resolve that anchor through `enforcement.ResolveStateAnchor`, the same resolver the engine's own key builder uses, so the turn and the state key cannot disagree about a request (stdio's FIFO ticket queues are keyed on it too — it resolves to one anchor today, and keying it is what keeps that from being an assumption held up elsewhere). Whether a policy needs a turn at all is `config.LocalManifest.NeedsDecisionTurn`, called from both transports rather than spelled out at each and DERIVED from the state class each token declares (`capability.TokenStateAccumulation`) rather than from a list of token types; the engine's two skip gates are NOT the transport's business at all: it hands the ENGINE the tokens the policy carries (`config.LocalManifest.PolicyTokens` → `enforcement.WithPolicyTokens`), a fact, and the engine intersects them with its own handler registry. Both registries' keyed-with-refcount lifetime is ONE generic (`keyed_registry.go`: `keyedRegistry[T]` + the embedded `keyedEntry`), with the reclaim trigger supplied by the embedder — the gate drops at its last holder, the FIFO also waits for the tickets it handed out — so a leak or lock-ordering fix has one home rather than two. The stdio server-initiated leg's wait for the turn is BOUNDED (`samplingTurnWait`, as HTTP's is) and its ticket is abandonable — the turn skips a ticket whose waiter gave up. That bound is a `turnWait` PAIR rather than one duration: `perHolder` refuses a waiter only when the request actually HOLDING the turn has held it a whole window without handing off (so a waiter queued behind a moving queue is not refused, which is the property the inline version had for free and concurrent handlers lost), and `total` is the ceiling that keeps "the queue is moving" from meaning forever, since a parked waiter holds a `serverRequestPool` slot. That leg also runs on its OWN goroutine rather than inline on the upstream reader, on BOTH transports, through one shared `serverRequestPool` (`server_request_pool.go`: admission bounded at `maxConcurrentServerRequests`, refusing-plus-recording `RESOURCE_EXHAUSTED` on saturation, plus the teardown `drain`) scoped proxy-wide for stdio and PER SESSION for HTTP: the reader is the only goroutine that delivers upstream responses, so a handler parked on the turn used to stall every in-flight call for the length of the bound, repeatably (HTTP's blast radius is one session rather than the proxy, and under `taskAnchoredState` the turn holder can be a different session sharing the anchor). The cost is that server-initiated requests have NO ordering guarantee among themselves, and each transport's teardown drains them (`awaitServerRequestsDrained` / `releaseSessionState`) before releasing session state. A request reaches its turn through three tiers, every one of them addressed by the RESOLVED anchor rather than by a restatement of how the resolver decides, so all three are correct for any anchor kind rather than for the two that exist: the session's lock-free PIN (the gate for the anchor it resolved at registration, taken in `registerSession`, released by `releaseSessionState`), which serves every request on a session-anchored route and every request of a task-anchored session that stays on one task; the session's own `gateCache` (`session_gate_cache.go`) for the OTHER anchors it resolves, since a session that SPANS tasks — the shape task anchoring exists for — matched the pin on nothing after the move and took the route-wide registry round trip on every enforced call for the rest of its life; and the route registry itself, the always-correct path, reached by a non-serialized route (where it is a no-op) and by a request racing its own session's teardown, after the cache has stopped admitting. Reaching the cap is NOT an overflow into that tier: the cache sheds its least recently used entry and serves the request, so a session cycling wider than the cap pays the cache's bookkeeping on top of the registry round trip rather than a wrong turn (measured, `BenchmarkDecisionTurn_SpanThrashing` against `BenchmarkDecisionTurn_Registry`). The pin is deliberately never RE-pointed: it is read with no lock at all, so moving it means returning the registry reference that is the only thing stopping that gate being reclaimed and rebuilt under a request which read the old pointer and has not yet taken its turn — two gates for one anchor is not slow, it is unserialized. The cache carries the synchronization that hazard needs: a request taking a turn on a cached gate is COUNTED for the whole turn, so eviction (LRU, capped at `maxCachedSessionGates`, because the anchors are validated task claims and one connection must not pin one gate per task it ever touched) never drops a reference in use — an entry with users is RETIRED, removed from the map so nothing new joins it, its reference returned by whichever request leaves last, and `gateCache.close` does the same at teardown for anything that outlives the bounded in-flight drain. On a task-anchored route a session may SPAN anchors — each host request is decided, keyed and serialized on its own — and what pays for that is the leg with no request in scope: `httpSession.noteRequestAnchor` records the span and `spansAnchors` makes the server-initiated leg refuse for the session's life (`session_spans_anchors`), because that leg decides from the claims captured at `initialize` while the host leg decides from each request's, and two tokens differing only in `task_id` would otherwise taint one bucket and peek another. The latch is taken for an ENFORCED request past every gate that can still refuse it — the same predicate the decision turn takes, since nothing else commits anchored state for that leg to peek past — and it is sticky for the session's life, so anything looser disables sampling for the connection permanently: taken above the framing branches, one POST of a frame that is neither request, notification nor response (no id and no method, which decodes fine) did it, as did a reply whose id this proxy never issued; taken above the in-flight cap, one saturating burst did; `initialize` routes through `dispatchRequest` too (its cross-cutting kill gate shared with the other locally-answered methods), with the per-transport response body supplied by an injected `buildInit` responder — only the HTTP *session-creating* `initialize` (no session/dispatchParams yet, and it carries the strict-audit gate) is answered outside the shared dispatcher. Gateway mode (top-level `transport: http` in config) multiplexes N upstreams on one `HTTPProxy`, each at `/mcp/<name>` with its own policy — per-route state lives in `route.go` (`UpstreamRoute`, built by `BuildRoutes`; its `routeSink` wraps the shared `*audit.Sink` and stamps the route name + policy version/digest), config parsing in `internal/config` (`GatewayConfig`; unknown YAML keys rejected; JSON Schema in `schemas/`). The package builds standalone on `internal/{audit,config,drift,mcp,pdp}` + `pkg/*`; the drift-check policy lives in `internal/drift`, and the transport imports it only for the `drift.CheckFunc` hook type (the binary injects `drift.MakeDriftCheck` as that hook, so the runtime calls the opaque hook and never references the comparison). Startup effects that overwrite SHARED last-writer-wins state (the control-token file, the session-kill TTL) run from each transport's own ready hook — `HTTPGatewayOptions.AfterListen` (post-bind) and `StdioProxyOptions.OnReady` (fired inside `Start` once the session is live) — never from the binary before the transport stands, so a proxy that fails to come up cannot clobber a running one. The exported seam the CLI consumes: `NewStdioProxy`/`StdioProxyOptions`, `NewHTTPProxyGateway`/`HTTPGatewayOptions`, `BuildRoutes`/`UpstreamRoute`/`LoadUpstreamPDP`/`LoadEffectReceiptVerifier`/`WrapRoutesWithJWT`/`AnyRouteAccumulatesSharedState`, the `Resolve*` flag resolvers, the control-token + OAuth-metadata helpers, `SetProxyVersion`, and the CLI-probe plumbing (`DoMCPHTTP`, `BuildUpstreamClient`, the revision-selected opener `UpstreamOpenRevision`/`BuildUpstreamOpenerWithID`/`ApplyUpstreamOpenerResult`/`UpstreamOpenerCompletion`/`DeclareUpstreamRevision`/`UpstreamHandshake`, `SessionHeader`, `IsInfraDenialCode`, `MaxUpstreamErrBodyBytes`). a pipelined follow-up; the "dispatches it" half is what keeps the pin from being a wedge, since one id-less `initialize` declaring the revision that removed `initialize` otherwise latched a table with no handshake in it, unrecoverably — and the predicate reads the revision's own dispatch TABLES rather than the method's revision membership, because those two disagree exactly where the wedge lives: a and a `*/list` REQUEST (`unreadParamsReachUpstream`) — since a peer otherwise adds a throwaway duplicate key to make this decoder bail, inherits the context past every gate, and leaves a clean asks — including the server-initiated one, which has no host request in scope and is handed the session's pin as a fact, and which recorded "nothing was negotiated" for a session that had resolved a revision but not pinned one while it answered that by hand), while a declaration that DISAGREES with its context is refused `UNSUPPORTED_PROTOCOL_VERSION` (-32022) rather than re-negotiated — and a refused host RESPONSE also UNBLOCKS the upstream request it would have answered (each transport's negotiation arm, through the one `serverRequestUnblocker`), since a protocol refusal is not an emergency stop and eunox can answer at its own revision without relaying anything the host said. That is the leg's ONE rule — eunox answers a blocked initiator wherever it can do so without acting on a second identity's behalf — and it has exactly two exceptions: a kill drop, deliberately left to be reclaimed with the session it is tearing down, and a reply the SESSION GATES refused, answered only when the sender is PROVABLY the session's own owner (`unblockGateRefusedServerReply` / `senderIsProvenOwner`), because answering completes the initiator's request whether or not the tracked id is consumed and so would hand a second identity a way to abort the owner's pending reply — and "proven" is not "not refused", since the owner binding is vacuous on a session with no bound identity while the audience pin refuses senders that binding never examines. A DISPLACED request — the bounded tracker making room, or an upstream reusing an id — is neither exception and is answered plus recorded at displacement time (metered under `catDisplaced`, since a saturated tracker displaces one per request), taking the LONGEST-WAITING entry rather than an arbitrary one now that the drop actively aborts rather than silently hangs; a request whose own JSON-RPC id exceeds what the tracker retains (`maxTrackedServerReqIDBytes`) is refused at each transport's ENTRY to this leg (`admitServerRequestID`) — above the pool and above the decision, so it costs one record rather than two and no quota slot — while `track` refuses one too, so the bound the constant argues from retention is a property of the thing retaining the bytes rather than of where its callers sit; and so is a host reply DESTROYED because the leg had no upstream sink to relay it through — the take that made it unroutable stays above the writer check for `unblock`'s reason, so the debt is paid on the tape. Every one of those records names its site in the `transport` audit detail through ONE `transportLeg` vocabulary behind one `detailTransport` key (`forward.go`), where two typed enums and a bare string parameter used to land in the same field with nothing stopping two of them minting the same value; and `serverReqTracker.track` — whose return value IS the disposal obligation, which Go does not require a caller to consume — is held to its single disposing wrapper by a source guard rather than by a doc comment. whether a message's declaration has to be HONORABLE for the upstream leg at all is asked per FRAMING (`paramsReachUpstream`), not per method, because a host RESPONSE carries no method to look up and is the one framing relayed to the upstream verbatim, `_meta` included — and the READER is per framing too (`mcp.DeclaredRevisionOf`), since a conforming response has no `params` and a framing-aware gate over a request-shaped reader closes nothing; the upstream side is decided once per route/proxy BEFORE the leg opens, from the operator's `protocolVersion` key (`upstream_open.go`'s `UpstreamOpenRevision`), because that value SELECTS the opener — `initialize`, or `server/discover` on a declaring revision — and a revision derived from a handshake cannot select the opener that performs the handshake. The resolved revision travels on exactly ONE carrier — the context (`capability.WithProtocolRevision`, stamped by each transport's `negotiateHostRevision` and read back by `dispatch.go`'s `requestRevision`) — and the routing tables are derived from that same value the audit sink stamps `protocol_revision` from; it is deliberately NOT also a `dispatchParams` field, because two hand-threaded carriers had opposite zero-value semantics (the field defaulted, the context omitted) and an entry point that set one and forgot the other recorded "no revision decided" for a request it had decided under `2025-11-25`. The empty carrier is resolved to `capability.DefaultRevision` in `requestRevision` alone, so no two dispatch decisions can read it differently; the sink's omission is not a second reading of the same question — a pre-negotiation refusal has to be able to state that nothing was negotiated. The routing tables are DERIVED from `dispatch.go`'s `methodRegistry` — one declaration per method carrying the revisions it exists in (the `TokenSince` pattern), its request handler in one of two typed fields (`Decide` for a PDP-decided method, `Local` for a proxy-answered one, so "enforced but no handler" is unrepresentable), and its notification disposition in ONE `map[string]notificationDisposition` per revision whose zero value IS the fail-closed `notifyUnmapped` — so removal across revisions is expressed by ABSENCE (a method outside the peer's table hits `dispatchUnmapped` exactly as an unknown one does) and an entry declaring no revision fails the build. Every fail-closed routing refusal — both framings — takes its `audit.UnroutableKey` marker (`{reason, revision}`) from one `unroutableReason`, and its audit IDENTIFIER from `auditIdentity`, the rule EVERY refusal with no policy decision behind it shares (the `-32022` revision refusal included), because the code it records is `UNROUTABLE_METHOD` — the JSON-RPC -32001 it used to spell `AUTHORIZATION_FAILED`, a policy code for a message no policy evaluated — whose CLASS is the whole encoding: observe mode downgrades a policy VERDICT and a message the tables cannot route has none, so `capability.DenialInfo.Downgradable` answers false for it structurally rather than because this path builds no `DenialInfo` and never asks, and `IsInfraDenialCode` answers true rather than `eunox suggest` skipping it only because its target happens to be blank. The marker adds which of the three ways it was unroutable, which a code cannot carry. That identifier is dropped for any method RESOLVING a target type (not merely one the revision removed — a notification-framed `tools/list` stamped a tool named after the method). - **Subcommands** — proxy, validate (`--live` diffs manifest against a running upstream; also reports effect-contract coverage and names the unannotated capabilities), init (deny-all starter manifest from live tool list), suggest (proposes manifest tightenings from the audit log), kill, audit-verify, stats, contracts (verifies a local effect-contract corpus, prints an entry's `effect.ref` pin, and — with `--trust-keys` — verifies its signed attestations against a local trust store; `--attest-payload` prints the bytes a publisher signs, since eunox verifies attestations and never mints them. Offline throughout: neither the registry nor any key is fetched), doctor, version. Each lives in its own file (`kill.go`, `audit_verify.go`, `stats.go`, `contracts.go`, `doctor.go`, …); `main.go` holds the dispatch plus the security-critical proxy wiring.

### pkg/

- **`pkg/capability`** — manifest/constraint/condition types, validation, directives (e.g. `redactFields`), JWKS fetching and JWT verification. `revision.go` holds the MCP protocol-revision vocabulary (`Revision`, `PublishedRevisions`, `ParseRevision`, `DefaultRevision`, the `_meta` key, and the context carrier the audit tape's `protocol_revision` field reads) — here rather than in `internal/mcp` because `internal/config` (which parses the operator's pin) and `internal/audit` (which stamps the decided revision) both need it and neither may import that package, the same reason the method-name constants live here. `pep.go` holds the enforcement-point vocabulary (`Binding`/`BindingMCP`, `EnforcementPoint`, `NewEnforcementPoint`) — the audit tape's `pep` stamp, `"<binding>:<id>"`, whose binding half is pinned by the constructor rather than taken as a parameter (eunox enforces at the MCP boundary and nowhere else, so a stamp naming a surface no code in this build polices would be an unfalsifiable claim on a signed tape) and whose operator half is refused rather than sanitized (a repaired name is one the operator cannot join their tapes on, and the accepted set excludes both the `:` the halves join on and the `$` an unexpanded env reference would carry). It lives here for revision.go's reason: `internal/config` parses the operator's name and `internal/audit` stamps it. Condition types are string-discriminated (`allowedValues`, `maxCalls`, `timeWindow`, …; authoritative list in `pkg/capability/condition.go`). `flowlabel.go` holds the information-flow tokens; `effect.go` holds the effect layer (the closed reversibility vocabulary, `EffectContract` + `ResolveEffect`, the `effectClass`/`blastRadius` conditions, the top-level `EffectCeiling`, and `EffectContractDigest` — the content digest a manifest's `effect.ref` pins and the loader verifies LOCALLY, so no registry fetch is on the decision path); `attribution.go` holds the `io.eunolabs.context-manifest` `_meta` interface; `receipt.go` holds the effect-receipt surface (the `io.eunolabs.effect-receipt` result-`_meta` block, its signature verification against an upstream's OWN key domain — never the caller-authenticating JWKS — and the consistency check against the contract the decision used; post-hoc and evidential only, and entirely inert unless an operator configures `effectReceiptKeys` for that upstream). `declassify.go` holds the declassification surface (the `declassify` directive and the `DeclassifyApproval` grant carried on the `mcp.declassify` claim of an already-verified token — the ONLY token that removes a flow label, hence approval-gated and fail-closed to `escalate`; a grant marked `once` is single-use, burned by its mandatory `id` in the engine's anchored ledger), and `declassify_commit.go` the `Declassification` commit handle the decision mints and the second phase consumes — opaque, single-use, carrying its authorized set unexported, so the phase that APPLIES a clear cannot widen what the phase that AUTHORIZED it resolved; `delegation.go` holds delegation attenuation (the RFC 8693 `act` actor chain plus the per-hop `mcp.delegation` grants, and `ValidateDelegationChain`, which REJECTS a token whose hops widen rather than clamping it — every axis narrows in a fixed direction, so consuming the claims needs no experimental gate); `taskvar.go` holds the closed `${task.*}` variable set; `grammar.go` holds the published grammar revisions and `TokenSince`, the one classification lookup — each prototype registry entry declares the revision that introduced it, and `internal/config`'s loader gate reads it rather than keeping tables of its own; `tokenstate.go` holds the second thing every entry declares, `State` — the cross-call state the token's enforcement touches (`StateNone`, `StateAtomic` for a budget admitted through one atomic `AdmitAll`, `StateNonAtomic` for a non-atomic read-then-write) — read through `TokenStateAccumulation`/`ConditionStateAccumulation`/`DirectiveStateAccumulation`, from which both the decision turn's predicate and the multi-instance shared-state advisory are derived; `subsystem.go` holds the third, `Uses` — which OPTIONAL engine facility that enforcement reads (`SubsystemNone`, `SubsystemAntecedentHistory`, `SubsystemFlowLabels`) — read through `TokenUsesEngineSubsystem` and `DeclarationUsesSubsystem` (the one place the unclassified-means-everything rule lives, shared with the handler-side declaration). The engine's two skip gates derive from it, but through the HANDLER REGISTRY rather than through the manifest: the declaration describes the handler this build ships, and `enforcement.WithConditionHandler`/`WithCommittingConditionHandler` can replace any token's handler, so an override that reads the flow store while the token it replaced declares nothing would otherwise have that path skipped out from under it (an override is unclassified unless it implements `enforcement.SubsystemDependent`). All of these are PUBLISHED in `schemaVersion "0.2"` (the batched bump; the `"0.2-draft"` staging string is removed, not aliased) and are NOT part of `0.1` — a `0.1` manifest using one is refused at load. They are documented in `docs/capability-manifest-guide.md` §§5b-5c, `docs/effect-contracts.md`, and `docs/attribution-interface.md`, and mirrored into `schemas/eunox-capability-manifest.schema.json`. The effect-RECEIPT surface in `receipt.go` is the one piece with no manifest token at all: it is gated by an operator explicitly configuring `effectReceiptKeys` for an upstream, a stronger opt-in than a schemaVersion, so it ships enabled-when-configured under either grammar.
- **`pkg/enforcement`** — the decision engine. Conditions are evaluated through a handler registry on `Engine`, whose entries carry a subsystem declaration alongside the handler (`registeredHandler`): a built-in takes it from the token's `pkg/capability` prototype entry, an override from `SubsystemDependent` if it implements it and is UNCLASSIFIED otherwise. An entry holds ONE of two shapes, never both — a pure `ConditionHandler` (`WithConditionHandler`) or a quota-consuming `CommittingConditionHandler` (`WithCommittingConditionHandler`), the latter carrying `PrepareCommit` alone and no `Handle`, so a committing condition has one entry point by construction rather than a second implementation the engine never calls. Its skip/commit contract is asserted in BOTH directions at the one site that consumes a `PrepareCommit` result (`commitDeferredConditions`), and the two violations are answered differently because only one is REPAIRABLE there: a skip the context did not authorize leaves the rest of the deferred set unchecked, so there is no verdict to stand in for it and it hard-denies; a bucket derived under `SkipQuota` is dropped, since the engine owns the only consumption point and dropping it IS the outcome a conforming handler produces for that posture — refusing would turn a third-party handler's bug into a hard outage on the one posture (`--audit`) whose whole contract is that it never blocks. Absorbed is not silent: the violations are named in `capability.EnforceResponse.HandlerFaults` as `{Type, Contract}` pairs — which handler, and which contract it broke, since a report naming only the condition type is unambiguous exactly while one repairable violation exists — the transport stamps them onto whatever record the decision produces (`audit.HandlerFaultKey`, through the one `decisionDetail` fold every below-decision exit shares — the posture that produces a fault is the one that FORWARDS a deny, so an allow-only report would go missing for the constraints whose second condition denies), and `eunox stats` raises them as an ATTENTION line. Those two assertions make the set uniform by construction, which is why there is no post-loop partial-skip guard to keep in agreement with them. The one statement of what a `HardDeny` in this package is FOR — where `WillForwardDeny` answers yes the transport forwards a downgradable verdict and blocks a hard one — lives on `WillForwardDeny` alone, and the forwarding half is pinned by a test in `internal/transport` rather than restated per refusal site. But WHICH refusals resist that downgrade is no longer the bool's question alone: a refusal the engine produced because it could not reach a verdict (an unmodelled condition type, a condition with no usable handler, an unwired or failing counter/store, a nonconforming backend index, a handler's unauthorized skip, a failed state commit) carries `capability.ErrCodeEnforcementError`, whose CLASS (`capability.ClassifyDenialCode`) is the whole encoding: `DenialInfo.Downgradable` folds it with the producer's override and is the ONE question every layer asks (the transport's `isObserveDeny`, the engine's redaction defer, and the PDP's `stamp`/`recordAuditModeAntecedent`/harden legs, which used to predict the transport's answer from the raw bool). Neither denial funnel derives the bool from the class any more — that made the field mean "override OR one of the two non-policy classes", two meanings a third denial constructor could get wrong on its own. Producers set it only to OVERRIDE the class — a policy verdict that must block anyway (`anchorUnresolved`, the two escalations, the descriptionHash pin). Every per-request check is threaded one `evalCtx{req, matched, requestID, now}` rather than the four-value tail seventeen signatures carried, so a new check on this path gets the decision's identity for free; the two exported denial builders reachable with no constraint in hand keep their explicit parameters. `bench_internal_test.go` holds the decision path's benchmarks (per-condition dispatch and its allocation-freeness, the two-pass structure, the anchored-key builders), runnable through `scripts/bench.sh`. `New` derives the two skip gates from that registry, intersected with the tokens the caller declares its policy carries (`WithPolicyTokens` — a fact about the policy; the retired `WithoutAntecedentRecording`/`WithoutFlowLabels` asked a caller for the conclusion, which a manifest-side derivation could get wrong for a replaced handler). The two extension points (`policy`, `custom`) answer from the wired `PolicyEvaluator` when it declares, rather than conservatively; pluggable `Clock`, `CallCounter`, `FlowLabelStore`, `EffectCeiling`, and `PolicyEvaluator` (external PDPs like OPA/Cedar) via functional options. `flowlabel.go` and `effect.go` hold the two axes' handlers; `delegation.go` holds the decision-path half of delegation attenuation (the target gate, the effect-class cap, and the redaction/allow-label composition), and `anchor.go` owns the ANCHOR every piece of accumulated state is keyed on — exported as `StateAnchor`/`ResolveStateAnchor`/`AnchorKind`, because a transport serializing decisions has to key its turn on the same subject the state accrues to and a second reading of "is this task-anchored" is where the two silently diverge (the two ENCODINGS differ on purpose: the engine's counter/store key keeps its session form byte-compatible with pre-anchoring deployments, `StateAnchor.Key()` is the in-process turn-registry key) — the session by default, or the validated `mcp.task_id` claim under `WithTaskAnchoredState` (opt-in; falls back to the session only for a request carrying NO token, refuses an authenticated one whose token carries no `task_id` rather than splitting its state across two buckets, and never shares state on the strength of something the caller did not prove). Every key builder routes through `Engine.anchoredKey`, so a new piece of accumulated state cannot be added under session keying while every existing one follows the task. The `effectCeiling` is NOT a condition: it runs once on the allow tail, after the matched constraint's conditions and BEFORE the session-state commit, so an over-ceiling call leaves neither a phantom `sequenceBlock` antecedent nor a stranded flow label. Both effect conditions and the ceiling read ONE `ResolveEffect` of the matched constraint's contract, threaded through the context, so they cannot disagree about what the call's effect was.
- **`pkg/callcounter`**, **`pkg/killswitch`** — in-memory and Redis backends behind a common interface (Redis enables multi-instance deployments; tests use miniredis). Redis CLUSTER is unsupported and refused rather than documented: `callcounter.NewRedis` returns an error for a `*redis.ClusterClient`/`*redis.Ring` (the library spelling) and the binary refuses a `--redis-addr` pointed at a cluster node after its startup ping (the operator spelling), because `AdmitAll`'s multi-key `EVAL` is otherwise refused with `CROSSSLOT` at the first policy carrying two quota buckets — fail-closed, so invisible until then. `killswitch`'s per-master SCAN stays for a consumer wiring that backend alone, and takes its topology straight from `redisutil.ClassifyTopology` — which returns the topology AND the per-server fan-out together, so a client one package calls sharding while the other has no iterator for it is unrepresentable rather than merely loud (the two hand-written switches this replaced had drifted, and a `*redis.Ring` fell through to a single-node SCAN that loads a partial kill set and reports healthy). The answer is THREE-valued because a concrete-type match has three outcomes: an UNRECOGNIZED type (a decorator, a consumer's own `Cmdable`) proves nothing, and folding it into "not sharding" is what let a wrapper around a cluster client enumerate one shard and report ready — fail-open, silent, on the emergency stop. The two consumers answer it differently, by failure mode: `callcounter.NewRedis` admits it (a sharding client fails loudly and closed at the first multi-bucket `EVAL`'s `CROSSSLOT`), while `killswitch.NewRedis` LATCHES `ErrUnknownTopology`, reported by every reader and writer and fail-closed regardless of `--killswitch-fail-open` — with `WithSingleNodeKeyspace()`/`WithShardFanOut()` as the declaration a consumer that knows what its wrapper wraps supplies, which is what makes refusing a legitimate decorator tolerable. A declaration FILLS an unknown topology and never OVERRIDES a known one — contradicting a recognized client latches `ErrTopologyContradicted` — since honoring it would discard a working fan-out and restore the very partial kill set the refusal exists to prevent, reached through the escape hatch itself. The topology is resolved ONCE at construction, so no enumeration re-asks a question whose answer cannot change — but that is a fact about the CLIENT and says nothing about any one PASS over it, which is the distinction the `*redis.Ring` arm lives in: go-redis skips a shard its heartbeat has voted down and returns nil, so `redisutil` wraps that iterator with a completeness check and a short pass surfaces as `killswitch.ErrIncompleteEnumeration` — bounded by the CONFIGURED shard count widened by the widest the ring has been observed to be, since `SetAddrs` leaves the configured count stale and under-counting is the fail-open direction, and refusing a pass over zero servers outright rather than accepting it as vacuously complete (the residual it cannot close: a ring GROWN while a shard is already down, which go-redis rebalances out of both `Len()` and the iterator with no memory that it existed). `killswitch.RingFanOut` exports the checked iterator for the decorator case, or the declaring option is a way back to the fail-open. Unlike its latched siblings that one is a REFRESH error and honours `WithFailOpen`, because a down shard heals where a wiring fault never does; the residual is `(*Ring).SetAddrs`, which reshapes a ring without writing back to the options the check reads, so a consumer that SHRINKS one at runtime declares its own complete fan-out. A TYPED NIL is classified unknown with no iterator: its per-server iterator is a non-nil func bound to a nil receiver, which would panic inside go-redis on the reconcile goroutine rather than returning the error the definition promises. That guard makes the ITERATOR honest but not the client — go-redis dereferences the receiver before it can build a reply, so every command on a nil client PANICS rather than erroring, and the first to run are `Start`'s `Subscribe` and the reconcile goroutine's `Get`, which is why a guard further down the call graph is unreachable. `redisutil.IsNilClient` (reflect-based over every nilable kind, so it needs no second type list; it answers for a client that IS nil, NOT for a decorator WRAPPING one — reflecting into the embedded field would falsely refuse a wrapper that legitimately forwards elsewhere, and probing would put a network round trip in a constructor that performs none) is therefore asked at each backend's construction seam: `callcounter.NewRedis` returns an error, and `killswitch.NewRedis` — whose signature returns none — LATCHES `ErrNilClient`, which `Start` refuses to launch on and which every reader and writer reports, fail-closed regardless of `--killswitch-fail-open` (fail-open trades revocation for availability during a TRANSIENT outage, and a nil client never heals). `ErrClusterUnsupported` stays in `callcounter`, where the reason for the refusal (the multi-key EVAL) lives. The request-time `CROSSSLOT` backstop matches go-redis' typed sentinel and `HasErrorPrefix`, not the reply text. `killswitch.Manager` carries `HealthStatus` — the readiness question asked with no request in hand, on the seam so a consumer holding the interface can distinguish "not ready" from "backend down" without matching backend-specific sentinels — and the confirmability rule (a backend that cannot confirm its kill set reports the cause from EVERY reader rather than serving a silent all-clear) is stated once on the interface and checked by a cross-backend conformance table. `InMemory`'s zero value is usable: the kill sets are created on first write, where they used to panic. It also carries `ObserveRevocations`: a kill has two effects and only one of them is a read, so a consumer learning of one through `ShouldBlock` alone can DENY the traffic but reclaim nothing the revoked session holds. Both backends notify (Redis from its pub/sub listener AND its reconcile commit, so a dropped publish still reclaims), the callback must not block but MAY call back in — which is a claim about every internal lock and not just the cache one, so BOTH lifecycle locks are released first: the reconcile commit returns the revocations it gained rather than delivering them (`refreshMu` is neither reentrant nor ctx-aware, so a callback reaching a refresh-taking method under it wedged the reconcile goroutine for the process's life and hung `Stop` on `wg.Wait`), and `Start` does the same with the initial snapshot's, since it holds `lifeMu` across its whole body and `Stop` takes that lock, and the `Revocation` is a trigger rather than a work list — the HTTP transport responds by re-asking about the sessions it holds. Every quota admission goes through ONE primitive, `AdmitAll(ctx, []capability.QuotaBucket)`, which admits a whole batch of buckets atomically or none of them. A bucket's `Counted` flag picks its accounting: entry-counting (backing `maxCalls`) or weight-summing (backing `blastRadius`'s cumulative `maxTotal`/`windowSeconds` bound). The two exist for COST, not expressiveness — a count is O(1) in both backends while a weighted total is summed per entry — and a single batch may mix them, so a capability carrying `maxCalls` alongside a cumulative `blastRadius` commits both in one call. What the manifest loader refuses is two buckets of the same kind on the same window (they would share one physical key); `checkDistinctBuckets` is the counter's own runtime backstop for the same shape. A lone `maxCalls` or a lone cumulative `blastRadius` commits through the same primitive as a one-element batch: there is no single-bucket method to drift from it.
- **`pkg/circuitbreaker`** — generic circuit breaker; the only production wiring today guards JWKS endpoint fetches (not upstream MCP calls, which rely on per-call timeouts). `State.Impeded` lives here rather than in a consumer's health endpoint, because what the states MEAN is this package's to define — a transport encoding it read only `StateOpen` and went quiet through most of a sustained outage, fixable only by standing up an `HTTPProxy`. The cache joins that predicate with its OWN staleness in `capability.KeyFetchHealth` (`FetchImpeded` — refreshes refused, so rotation is blocked and an unknown-`kid` token fails now — beside `Status`, the readiness verdict, which is impeded AND no servable set, since the breaker's cooldown is tens of seconds against a five-minute key TTL and degrading on the trip alone drains a fleet that is rejecting nothing). `internal/pdp.(*JWTPDP)` relays that verdict through `HealthStatus() error`, the ONE seam every degradable subsystem answers (`internal/transport`'s `healthReporter`, folded by `healthSnapshot.fold`, whose nil guard is reflect-based because an interface holding a typed nil is not nil and panicked the scrape) — the seam `*audit.Sink` answers too, through the `audit.Health` SAMPLE, so the counters `/healthz` renders and the verdict beside them are one reading and the maintenance carve-out lives with the state machine rather than being remembered by the transport, with each subsystem's DETAIL handed over separately — a seam widened to carry every detail would describe none of them, and reaching through concrete types for one subsystem while asserting an interface for the next is two precedents a third would pick between arbitrarily.

## Load-bearing invariants (from CONTRIBUTING.md)

- **Fail closed.** On any ambiguity — missing manifest, unmapped method, malformed JWT, unset condition argument — deny, with a structured error code (`AUTHORIZATION_FAILED`, `CONDITION_FAILED`, …), and log it. New code paths must preserve this.
- **Audit records are append-only and structured.** Never rewrite a record, never put free-form text in a structured field, never add a top-level field without updating the threat model (`docs/threat-model-mcp.md`).
- **No telemetry / background network activity** without explicit design discussion.
- **Pre-1.0: no backwards-compatibility shims.** Change manifest grammar, audit shape, or config keys cleanly and document the migration. Don't flag back-compat breaks as problems.
- **One static binary on purpose** — new runtime dependencies need strong justification.
- **No emojis in source files or code comments** (README/site are fine).
- Conditions match a specific argument name; never silently match alternatives.

## Conventions

- Every `.go` file starts with the two-line header: `// Copyright 2026 Eunolabs, LLC` + `// SPDX-License-Identifier: Apache-2.0`.
- **Comments explain WHY or HOW, never WHAT.** Delete a comment that just restates the line below it in words — if the code already says it, the comment is noise. Keep or write a comment only for the reason/tradeoff/constraint/bug behind a choice (WHY) or a non-obvious algorithm/ordering/concurrency requirement (HOW); cap it at one or two lines, no preamble, don't restate identifier names. Exported (capitalized) top-level `func`/`type`/`const`/`var` still need a godoc comment starting with their own name (`revive`'s `exported` lint rule requires it) even when there's no WHY/HOW to add — keep that lead-in minimal rather than padding it with restatement. If a comment asserts a rationale you can't verify against the surrounding code, mark it `// TODO: confirm rationale` instead of inventing one. License headers, TODO/FIXME with context, spec/issue links, and security warnings are always kept regardless of this rule.
- Conventional Commits (`feat:`, `fix:`, `sec:`, `perf:`, `refactor:`, `docs:`, `test:`, `ci:`, `chore:`; `!` for breaking). `refactor:` means no behavior change — a restructuring that also fixes observable behavior is a `fix:`. DCO sign-off required: `git commit -s`.
- Tests: new condition types need table-driven tests under `pkg/capability/` (allow + deny + malformed-input cases); new MCP method coverage needs a test in `internal/transport/enforcement_gaps_test.go` — including its PER-REVISION cells (which peer's revision dispatches it, which denies it fail-closed), since revision membership is declared on the method itself; only the table-DERIVATION machinery lives in `internal/transport/dispatch_revision_test.go`, the negotiation rule in `revision_test.go`, and the per-message gate order in `gate_order_test.go`; new audit-record fields need a sign-and-verify round-trip test; changing the duplicate-key scan in `internal/pdp` means keeping it in agreement with the tokenizer oracle in `scan_oracle_test.go` (equivalence table + fuzz targets, and a real fuzz campaign, not just the seeds).
- Every condition/directive discriminator declares THREE things on its `pkg/capability` prototype registry entry: the revision that introduced it (`Since`), the cross-call state its enforcement touches (`State`; see `tokenstate.go` for the rule, and note that an atomic `AdmitAll` budget accumulates but needs no decision turn), and the optional engine subsystems that enforcement reads (`Uses`; see `subsystem.go` — `SubsystemNone`, `SubsystemAntecedentHistory`, `SubsystemFlowLabels`, with the two extension-point tokens declaring everything because what an embedder's evaluator reads is not knowable here). An entry missing any of them fails the build (`TestTokenSince_…`/`TestTokenStateAccumulation_EveryRegisteredTokenDeclaresAClass`/`TestTokenEngineSubsystems_EveryRegisteredTokenDeclaresOne`) and is treated as the strongest class — and as depending on every subsystem — meanwhile. `internal/config`'s `checkTokenRevision` reads `Since` through `capability.TokenSince`, and a token with no `Since` is refused under every revision. A non-discriminator token (`effectCeiling`, a `${task.*}` value) has no registry entry and is gated inside `checkTokenGrammarVersion` instead. Either way it needs a test asserting it is REFUSED under `0.1` — that one gate is what keeps a later revision's predicate from silently widening an earlier one.
- Adding a condition or directive type also means adding a branch to `schemas/eunox-capability-manifest.schema.json`; `cmd/eunox`'s schema drift tests derive their expectation from the condition prototype registry, so a missing branch fails the build rather than shipping an undocumented token.
- Editing a `registry/contracts/` entry means recomputing its `digest`; `go test ./internal/registry/` fails otherwise, and so does any manifest that pinned the old value via `effect.ref`.
- Behavior changes need a docs update in the same PR. Manifest grammar changes also update `docs/capability-manifest-guide.md` and the spec repo (`eunolabs/agent-capability-manifest`). Schema changes update `schemas/` plus a roundtrip test.
- Security vulnerabilities go through `SECURITY.md`, not public issues.
- Never reference issue numbers, bug IDs, or internal milestones (stages, phases, epics, sprints) in code comments, documentation, or site copy. Those references rot and belong in the PR description or commit message only.
