## 1. System Overview

`eunox` is a single binary that sits in-path between an MCP host (Claude Desktop,
an agent runtime, a test harness) and an MCP server (local subprocess or remote HTTP
endpoint). Every policy-relevant JSON-RPC message is evaluated against a policy before
it is forwarded. Calls that violate policy are blocked and logged; calls that are
permitted are forwarded and logged.

Enforcement is not limited to `tools/call`. The proxy evaluates a decision on each of
the MCP method surfaces it understands — `tools/call`, `tools/list`, `resources/read`,
`resources/subscribe`, `resources/unsubscribe`, `resources/list`, `prompts/get`,
`prompts/list`, and
`sampling/createMessage` — and **fails closed on any MCP method it does not map to a
decision** (the message is denied with `AUTHORIZATION_FAILED` rather than blindly
forwarded). The `…/list` surfaces are filtered **in enforce mode**: entries the caller is
not permitted to invoke are removed from the listing before it reaches the host. Methods
outside the mapped set — notably `resources/templates/list` and `completion/complete` —
are therefore denied, not forwarded, so they cannot be used to enumerate names, URI
templates, or argument shapes for entries that `…/list` filtering removed. In **audit
(observe/wiretap) mode**, by contrast, `…/list` returns the *full upstream catalog
unfiltered* — that mode forwards (and merely records) calls it would otherwise deny, so
hiding entries the host can still successfully call would contradict "observe everything,
block nothing"; the kill switch is the only check that still hard-blocks. Operators who
need the host to see only permitted entries must run the route in enforce mode.

```
MCP host → eunox proxy → MCP server (subprocess or remote HTTP)
```

The proxy supports two transports:

| Transport | How the upstream MCP server is reached                                                                       |
| --------- | ------------------------------------------------------------------------------------------------------------ |
| `stdio`   | Upstream is a local subprocess; proxy bridges stdin/stdout                                                   |
| `http`    | Upstream is the proxy's HTTP listener; upstream is a subprocess (default) or a remote URL (`upstreamUrl`) |

Three policy sources can be combined:

| Mode                          | How it is activated                                       | What it enforces                              |
| ----------------------------- | --------------------------------------------------------- | --------------------------------------------- |
| No policy (audit / wiretap)   | No `policy` and no `--jwks-uri`, with `--audit` (stdio host) or `enforcement: audit` (gateway route) | All calls forwarded and logged, none blocked by policy — but an active kill switch hard-blocks even a wiretap route. A gateway route with no policy and no audit posture instead fails closed at startup |
| Manifest PDP                  | route `policy: [manifest.yaml]`                           | Constraint file on disk                       |
| JWT PDP                       | `--jwks-uri` + `--jwt-audience` (required, or `--jwt-allow-any-audience`) + `--jwt-issuer` (required, or `--jwt-allow-any-issuer`) | IdP-issued capability claims in bearer token  |
| Manifest + JWT (intersection) | Both flags set                                            | JWT can only narrow what the manifest permits |

## 2. Trust Boundaries

### 2.1 What the proxy trusts after verification

| Item                                                                      | How trust is established                                                             |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| JWT capability claims (`mcp.capabilities`, `mcp.task_id`, `mcp.agent_id`) | JWT signature verified against the JWKS endpoint; `exp`, `iss`, `aud` validated (signature/issuer/audience validation and the identity claims `mcp.task_id`/`mcp.agent_id` are stable; `mcp.capabilities`-based enforcement is experimental and gated behind `--jwt-experimental-capabilities`, off by default — see §3.5) |
| Manifest policy file contents                                             | Loaded at startup from a local path the operator controls; not re-fetched at runtime |
| Kill-switch state (in-memory or Redis)                                    | Checked on every `Decide()` call before capability evaluation                        |
| Call counter state (in-memory or Redis)                                   | Checked on every `Decide()` call; enforces `maxCalls` conditions                     |

### 2.2 What the proxy verifies on every request

**JWT PDP mode** (`--jwks-uri` set):

0. The JWKS endpoint is fetched over a tamper-resistant channel. `--jwks-uri` must be `https://`; plaintext `http://` is accepted only to a loopback host (no network MITM surface) unless the operator explicitly opts into insecure remote http with `--jwks-allow-insecure-http`. The JWKS is the root of trust for every token, so a plaintext fetch to a remote host — where an on-path attacker could substitute the key set and forge capability claims — fails closed at startup. The same scheme policy is re-applied to every HTTP redirect the JWKS fetch follows, so a valid `https://` endpoint cannot `302` the key fetch onto plaintext remote http (the redirect is refused and the token rejected). A redirect must also stay on the **configured host**: a hop whose target hostname differs from the `--jwks-uri` host is refused **before the request is sent**, even when both are `https://`. Without this, an open-redirect on the legitimate IdP (or a compromised redirector) could bounce the key fetch to an attacker host and substitute the entire key set — forging capability claims for every token — since the scheme check alone passes an `https→https` hop. The port and path may still change (an IdP may relocate its key set within its own host), but the host may not. This floor is enforced twice, independently: the CLI's own default client refuses to follow any redirect at all, and — because `JWKSCacheConfig.Client` is an exported seam a library consumer can override, silently getting Go's default (follow-everything) redirect policy back — a second, response-side same-origin check runs regardless of which client fetched the response, so a caller-supplied `*http.Client` cannot weaken the guarantee. That response-side check compares the final request's host (unchanged since 1.18) **and**, extending it, its scheme: a same-host redirect that downgrades `https` to plaintext `http` is refused exactly like a cross-host one, closing the gap where a scheme-only comparison would have let an IdP's own redirect quietly move the key fetch onto a plaintext channel on its own name.
1. `Authorization: Bearer <token>` header is present and well-formed.
2. JWT signature is valid against one of the keys in the cached JWKS (algorithm restricted to RS256/RS384/RS512, PS256/PS384/PS512, ES256/ES384/ES512, EdDSA — symmetric algorithms are unconditionally rejected).
3. `exp` is present and has not passed (a conservative 10-second clock-skew tolerance is applied by default — `DefaultTokenLeeway`, tunable via `--jwt-leeway`). A token that omits `exp` is rejected — go-jose validates `exp` only when present, so without this an `exp`-less token would never expire, defeating the bearer-token expiry and kill-switch revocation window.
4. `iss` matches `--jwt-issuer`. This is **required** in `--jwks-uri` mode: the proxy refuses to start without it unless the operator explicitly opts out with `--jwt-allow-any-issuer`, so a token from another issuer whose signing key is served by the same JWKS endpoint cannot be replayed against eunox.
5. `aud` contains `--jwt-audience`. This is **required** in `--jwks-uri` mode: the proxy refuses to start without it unless the operator explicitly opts out with `--jwt-allow-any-audience`, so a token minted for another relying party of the same IdP cannot be replayed against eunox. An empty or whitespace-only audience pin is treated as *no* pin and fails closed (every token is rejected regardless of its `aud`) rather than degenerating into a match against a token whose own `aud` is the empty string — the empty value can never be a trusted audience. In gateway mode, where the validator accepts the union of every route's audience, an empty/whitespace entry is dropped from that set for the same reason before a per-route check narrows to the specific route's audience.
6. `mcp.capabilities` claim covers the requested tool name. A token that omits the `mcp.capabilities` claim entirely defers to the route's manifest, which becomes the deciding authority (the JWT carries identity only). On a route with **no** manifest (an unpoliced/wiretap route), there is no backstop to defer to, so an identity-only token is **denied**, not allowed — otherwise any validly signed token that simply leaves the claim out would be granted every target. In effect, enabling JWT mode requires every request to be covered by either a capability claim on the token or a manifest on the route (ADR-0001, amended 2026-06-13). `…/list` filtering composes the same way: an identity-only token on a no-manifest route sees an empty listing.
7. Any condition shorthand in the capability claim (path glob, SQL verb) matches the actual arguments.

When JWT capability-claim enforcement is enabled (`--jwt-experimental-capabilities`), every `mcp.capabilities` entry is structurally validated as the token is first verified — not only when a request happens to match it. A malformed **target-name** glob (e.g. an unclosed `[` character class) is rejected outright (`error_type: invalid_capabilities`), exactly as the manifest loader rejects the same pattern at startup, closing a parity gap: without it a malformed grant would validate cleanly, then silently match nothing at enforce time (`path.Match` treats an invalid pattern as a non-match), producing an inert deny-all that surfaces only as an opaque `AUTHORIZATION_FAILED` — indistinguishable from a target the token simply never listed. (An http(s)-resource claim's `?query` component is exempt, since it is compared literally rather than as a glob. With the flag off — the default — a token that carries any `mcp.capabilities` claim is rejected earlier as `capabilities_disabled`, before any glob is examined, so this structural check applies specifically to the experimental capability-claim mode.)

A token that fails any of these checks is rejected with an opaque `401 Unauthorized` — the go-jose / validation message, which can disclose claim values, the accepted algorithm, the configured issuer, or key-rotation state, is never echoed to the caller. The matching `JWT_INVALID` audit record applies the **same** non-disclosure posture: it records a stable `details.error_type` category (`expired`, `invalid_signature`, `invalid_audience`, `invalid_issuer`, `missing_claims`, `unsupported_version`, `invalid_capabilities`, `malformed_token`, `jwks_unavailable`, …) rather than the raw message, so an operator forwarding the tape to a SIEM gets a fixed code to match on without re-introducing the disclosure the `401` avoids — the same fixed-code-not-free-form-prose discipline applied to upstream error results (§5.5) and audit-detail truncation markers (§6.2). The `jwks_unavailable` category is specifically reserved for a validation that failed because the key set could not be fetched (network error, non-`200`, empty or oversized set, or an open circuit breaker) rather than because the token was bad: the presented token was never checked against a key, so recording it identically to a forged token (`invalid`) would mislead an operator triaging the tape during an IdP/JWKS outage. As with `ORIGIN_REJECTED`, this rejection precedes any session lookup, so the unverified, client-supplied `Mcp-Session-Id` is kept out of the structured `session_id` field and preserved only as the clearly-unverified `details.claimed_session_id`.

**Manifest PDP** (`policy` set):

1. Kill-switch state is not active for this session (checked first, before anything else).
2. A constraint in the manifest covers the request's namespaced `target` (glob match, scoped to the same namespace). Every `target` carries a mandatory namespace prefix — `tool:`, `resource:`, `prompt:`, or `system:` — and matching only happens within a namespace, so a `tool:` constraint can never satisfy a `resource:` request. No matching constraint → deny (`AUTHORIZATION_FAILED`): the manifest is a deny-by-default allowlist, so a target absent from it is rejected, not forwarded.
3. The constraint's `actions` list permits the call (exact match `"call"` / wildcard `"*"`, or semantic category via action resolver). Action–namespace pairing is validated at manifest load: e.g. `tool:` targets reject `read`/`get`/`allow` actions and fail closed at startup.
4. `argumentSchema` validation passes (JSON Schema subset: type, pattern, length, min/max, enum, required, properties, additionalProperties, items). This runs **before** the condition loop, so a structurally invalid call is denied with `INVALID_PARAMS` regardless of any condition outcome. `argumentSchema` is `tool:`-only (SPEC § 3.2.1/3.2.2): it validates a tool-call's argument map, which `resource:`/`prompt:`/`system:` requests do not carry, so one declared on a non-`tool:` target is **rejected at load** — it can never become a declared-but-unenforced guard, the same way a `directives` block on a non-`tool:` target is rejected. The enforcement path fails closed independently as defense in depth: the `resources/read` and `prompts/get` decision paths evaluate conditions through `EvaluateConditions`, which does not run `argumentSchema` validation, so a `resource:`/`prompt:` constraint that carries one (e.g. from a manifest assembled in-process rather than through the loader) is denied with `ENFORCEMENT_ERROR` rather than forwarded with the schema silently skipped.
5. All attached `conditions` pass: `TimeWindow`, `IPRange`, `AllowedOperations`, `AllowedExtensions`, `AllowedTables`, `MaxCalls`, `RecipientDomain`, `AllowedValues`, `Policy`, `Custom`. `conditions` are strictly boolean predicates. Any condition rejection — including a handler whose backend errors, e.g. a `MaxCalls` counter that is unreachable — fails closed with `CONDITION_FAILED` (§5.3). The proxy additionally reserves `ENFORCEMENT_ERROR` (JSON-RPC `-32603`, the internal-error code, distinct from `CONDITION_FAILED` and `CAPABILITY_DENIED`) as a fail-closed guard for an internal engine failure during evaluation; the engine does not currently surface such an error, so this code is not emitted on any reachable path today, but the guard keeps an unexpected internal failure from ever falling open or being mistaken for a policy decision.
6. After the call is allowed, any `directives` on the matched constraint are applied as post-allow obligations (currently `redactFields`). Directives live in a separate `directives` array, not in `conditions`; an unknown directive type fails closed.

When both `--jwks-uri` and `policy` are set, a call must pass **both** checks. The JWT can only narrow what the manifest permits — it cannot expand it.

### 2.3 What the proxy explicitly does not verify

| Item                                          | Why                                                                                              |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Content of LLM prompts or completions         | The proxy operates at the tool-call protocol layer, not the inference layer                      |
| Reason the agent decided to call a tool       | Intent is opaque; the proxy enforces _what_ is called, not _why_                                 |
| Integrity of the MCP server's response        | The proxy forwards upstream responses verbatim (except `redactFields` directive obligations)      |
| Tool description + parameter description text (without descriptionHash) | Tool descriptions and their parameter descriptions flow to the model verbatim; a tampered upstream could inject steering instructions in either. Mitigated by the optional `descriptionHash` pin on exact-name `tool:` entries, which covers both surfaces (§3.7). |
| Upstream `initialize` `instructions` text     | The server's `instructions` field (model-facing guidance returned in the `initialize` handshake) is forwarded to the host verbatim — the same steering/injection surface as tool descriptions, but with no `descriptionHash`-style pin to constrain or detect changes. Captured once per session at handshake; the manifest cannot currently bound it. |
| Integrity of the agent process                | Host OS/container responsibility; the proxy cannot attest client-side code                       |
| Content of tool call arguments (semantically) | The proxy validates argument _shape_ (schema) and specific _values_ (allowedValues), not meaning |
| IdP infrastructure security                   | The proxy trusts JWTs that pass signature verification; IdP compromise is out of scope           |

## 3. Attack Classes Mitigated

### 3.1 Capability Claim Forgery

**Attack:** An attacker crafts or modifies a JWT to include capability claims (`mcp.capabilities`) for tools they are not permitted to call — for example, adding `"write_file"` to a token that was issued with only `"read_file"`.

**Mitigation:** JWT signature validation using the JWKS fetched from `--jwks-uri`. The proxy:

- Accepts only asymmetric algorithms (RS256, RS384, RS512, PS256, PS384, PS512, ES256, ES384, ES512, EdDSA). Symmetric algorithms (HS256, HS384, HS512) and the `none` algorithm are rejected unconditionally by the go-jose/v4 parser.
- Rejects tokens whose `kid` does not appear in the cached JWKS; performs an immediate forced re-fetch in case the IdP rotated keys before falling back to rejection.
- Deduplicates concurrent JWKS fetches using a singleflight implementation, preventing thundering-herd behavior on key rotation.
- Requires an `exp` claim and applies a conservative 10-second clock-skew tolerance by default (`DefaultTokenLeeway`, tunable via `--jwt-leeway`) on its validation; a token with no `exp` (which would never expire) is rejected.

Any modification to the JWT payload invalidates the signature, and the modified token is rejected before its claims are read. Signature/`exp`/`iss`/`aud` validation is stable and always active. Acting on a forged `mcp.capabilities` claim additionally requires the experimental opt-in flag `--jwt-experimental-capabilities`; with the flag off (the default), a token carrying `mcp.capabilities` is rejected at validation regardless of its signature, so the experimental schema is fail-closed.

**Verified-token cache:** signature verification and the claim decodes are the per-request hot path, so a validated token's claims are memoized for a short TTL (30 s, capped at the token's own remaining `exp` lifetime) keyed by the SHA-256 of the raw token; a repeat of the same token within that window skips re-verification. This narrows only the *re-verification* window — it does not widen trust: `exp` is still honored (the cache never outlives the token), and the kill switch, per-route audience, and manifest policy are re-evaluated per call in `Decide` (they are not cached), so a killed session is still blocked on its next call and a revocation cannot be outrun by the cache. The residual exposure is that a token becoming invalid for a reason detectable *only* by re-running signature/`iss`/`aud` verification (e.g. a mid-life JWKS key removal) is still accepted for at most the TTL.

**Residual risk:** A compromised IdP can issue arbitrary tokens that pass signature verification. IdP security is explicitly out of scope (§4.4).

### 3.2 Tool Call Parameter Injection

**Attack:** An agent (or an adversary that has influenced the agent) calls a permitted tool with arguments that exceed the intended scope — for example, calling `read_file` with `path=/etc/shadow` when the policy was intended to permit only `/reports/*`.

**Mitigation (argument schema validation):** The manifest's `argumentSchema` field applies a JSON Schema subset to the actual arguments of every tool call before the call is forwarded. The validator covers: `type`, `pattern` (regexp), `minLength`, `maxLength`, `minimum`, `maximum`, `required`, `enum`, `properties`, `additionalProperties`, `items`, `minItems`, `maxItems`. A call that fails schema validation is denied with code `INVALID_PARAMS` (JSON-RPC `-32602`) before reaching the upstream server, and before any condition is evaluated.

**Mitigation (condition types):** Several built-in condition types enforce argument-level restrictions directly:

| Condition           | What it restricts                                                                                    |
| ------------------- | ---------------------------------------------------------------------------------------------------- |
| `allowedValues`     | Argument value must match one of the allowed strings or globs (e.g., `path` must match `/reports/*`) |
| `allowedOperations` | SQL verb in the named `argument` must be in the permitted set (`SELECT`, not `DROP`)                  |
| `allowedTables`     | Table/column name(s) in the named `argument` must be in the permitted set (matched case-insensitively, like SQL identifiers, so a different-case spelling cannot bypass the allowlist) |
| `allowedExtensions` | File extension of the named path `argument` (a single path or an array of paths) must be permitted   |
| `recipientDomain`   | Email recipients must belong to the permitted domain                                                 |

**Mitigation (JWT condition shorthands):** In JWT PDP mode, capability claim shorthands (JWT schema v0.2) enforce argument-level restrictions inline: `"tool:read_file?path=/reports/*"` restricts the `path` argument to the glob `/reports/*`; `"tool:query_db?op=SELECT"` restricts the SQL operation. Multiple constraints can be `&`-chained in a single shorthand (`"tool:query_db?op=SELECT&table=public.*"`) and are ANDed together; values are URL-decoded before matching. When several capability entries name the same tool, the proxy intersects their per-argument constraints (cross-argument intersection) rather than taking the union, so the narrowest grant wins.

### 3.2.1 Cross-Tool Sequencing (Sequential Exfiltration)

**Attack:** Each tool an agent calls is individually within policy, but a *sequence* of them achieves an outcome the policy intends to prevent. The canonical case is read-then-exfiltrate: the agent calls `read_credentials` (permitted — it has a legitimate use), then `write_external` (permitted — it has a legitimate use), and the pair moves secrets out of the trust boundary. Per-call and per-tool controls (argument restrictions, even `maxCalls: 1` on each tool independently) do not catch this: the read and the write are each a single, in-budget, in-scope call.

**Mitigation (`sequenceBlock` condition):** `sequenceBlock` denies a call when any tool named in its `afterTools` list has already been allowed earlier in the same session. Placing `sequenceBlock(afterTools: [read_credentials])` on `write_external` blocks the external write for the remainder of any session in which credentials were read, while leaving both tools available to sessions that use only one of them (and leaving the harmless reverse order — write, then read — allowed). The decision is session-scoped: call history is keyed by session ID, recorded only on an *allowed* call (a denied antecedent never reaches the upstream and never arms the block), and consulted via a read-only lookup so that testing "did A run?" does not itself count as a call. With no call-counter backend configured, or on a request that carries no session ID, the condition fails closed. A call-counter *fault* also fails closed: an error reading history denies the call, and — critically — an error while *recording* an allowed antecedent is not swallowed. Rather than let a dropped marker cause a later lookup to read a falsely-absent antecedent and fail open, the engine surfaces the write error and denies the call that triggered it with `CONDITION_FAILED` (audit detail `phase: record`). Because every allowed call is recorded so any tool can later serve as an antecedent, a counter-backend fault denies every allowed call in the session for its duration, not only sequence antecedents.

**Residual risk:** The control is per-session. An adversary who can split the read and the write across two *distinct* sessions (e.g. two separate client connections that each obtain their own `Mcp-Session-Id`) is not stopped by a session-scoped rule — defend that case with a per-tool grant that never co-occurs in one policy, or with a JWT whose capability claims grant only one of the two tools per task. The marker also reflects only calls the proxy itself allowed; a tool whose side effect reads credentials without going through a `read_credentials`-named call is not observed.

### 3.3 Session Hijacking via Session-ID Spoofing

**Attack:** A malicious client presents an existing session ID in the `Mcp-Session-Id` HTTP header to impersonate an authenticated session and perform tool calls under that session's policy context.

**Mitigation:** Session IDs are UUID v4 values minted by the proxy at session creation. An attacker who does not know a valid session ID cannot successfully route a request. The proxy validates the session ID against its in-memory session registry on every request; unknown session IDs receive 404.

**Revocation is undone only where the state lives.** `eunox kill --revive <session-id|all> --redis-addr <addr>` removes a session tombstone or deactivates the global switch, and `--revive --agent <agent-id>` removes an agent kill (permanent by design, so the CLI undo is its only remediation short of a library call). It is deliberately available on the **Redis transport only**: the loopback `/control/kill` endpoint is a one-way emergency stop, so a same-host caller that reaches it holding the control token (the residual below) cannot lift the revocation issued against it, and an in-memory kill switch is cleared by restarting the proxy. That one-way constraint is enforced **structurally**, not only by CLI-flag rejection: the endpoint's handle on the kill switch is typed as a kill-only interface exposing `ActivateGlobal` and `KillSession` and nothing else, so a change that generalized the endpoint to accept a revive verb for symmetry with the CLI does not compile rather than landing as a three-line additive diff. The agent dimension is likewise absent from the endpoint by construction — it is reachable only over Redis, so the loopback endpoint's blast radius does not widen with it. Revive grants no privilege that Redis write access did not already carry — anyone who can write the shared state can already delete a `killswitch:session:` key by hand — but note that a kill or revive written over Redis leaves **no record on the proxy's audit tape**: the CLI is a separate process with no sink, so only the `/control/kill` activation is recorded (below), while a Redis-transport revocation is visible on the tape solely through the `KILL_SWITCH` denials that follow it. Treat write access to the shared Redis as equivalent to control of the kill switch, and audit it at the Redis layer (ACLs, a dedicated credential) where that matters. The same channel carries the session-tombstone lifetime the proxy publishes at startup (`killswitch:config:session-kill-ttl`), which the CLI adopts so a revocation is not written with a shorter expiry than the proxy's own kills merely because the two were configured independently; a value planted there by something other than a proxy is rejected as malformed rather than applied, and an explicit `--killswitch-session-ttl` that disagrees resolves to the longer-lived of the two. The published key carries its own **expiry**, refreshed by the running proxy from the reconcile loop it already runs (no new goroutine, ticker, or connection), so a value that is readable at all belongs to a proxy running now. That converts a *stale* value — otherwise indistinguishable from a live one, since the key carries no timestamp or writer identity — into an *absent* one, which the CLI already handles correctly and loudly by falling back to its own lifetime and naming it on stderr; no version, nonce, or reader-side staleness check is needed because the bad state is unrepresentable rather than merely detectable. Re-publishing also makes the disagreement diagnostic reliable rather than startup-only: two differently-configured proxies overwrite each other continuously and each reports the other on its next tick, including the case where the second started long after the first, which no one-shot comparison can catch. The warning is deduplicated on the prior value, so a persistent disagreement is reported once and a changed one again. The reconcile loop's re-publish is a REFRESH and nothing more: it is armed only once an explicit startup publish has been CALLED, so it never becomes the first writer. Called, not succeeded — the startup publish is best-effort by design, and a proxy that booted during a brief outage is one the tick should retry for, which is the self-healing the unconditional SET already provided. That gate is what makes the ready-hook ordering above hold in practice — `Start` (and so the loop) runs before the transport is serving, so an unconditional `SET` on the tick let any startup that survived one reconcile interval before failing publish anyway, and at the 1s interval the flag's own help recommends that was nearly every such failure. **Residual:** a running proxy that loses Redis connectivity for longer than the expiry leaves the key absent until it reconnects — the CLI then uses its own default and says so, the safe direction. A proxy's own `SET` remains best-effort (a failure warns and does not abort startup), and a hostile writer with Redis write access can still plant a fresh-looking value, which is unchanged and already covered by treating Redis write access as equivalent to control of the kill switch. None of this is on the enforcement path: the proxy always applies its own configured TTL to the tombstones it writes.

**Kill-switch binding:** When a session is killed (via `eunox kill <session-id>` or the `/control/kill` API), the session ID is registered in the kill-switch store. Every subsequent `Decide()` call checks kill-switch state first, before evaluating capability conditions. A session whose ID has been killed is denied regardless of whether a valid JWT or manifest policy would otherwise permit the call. This now holds for a policyless wiretap route too: its decision point is wired to the shared kill switch, so an emergency stop halts a forward-and-log route just as it halts a policed one.

The request paths that carry no per-call policy decision — and so bypass `Decide()` — check the kill switch explicitly, so an emergency stop is total: the `*/list` enumerations and the session-creating `initialize` deny on a killed (or globally killed) session before contacting the upstream, and the standalone SSE **GET** notification stream is covered on both open and hold. A killed session cannot **open or re-open** a stream (refused HTTP 403), and a stream **already open** when the kill lands is torn down by the kill path itself: `/control/kill` evicts the session's open SSE streams — per-session for a targeted kill, every session for a global one — by signaling the stream loop to return, so a killed session stops receiving upstream notifications at once instead of lingering on an open channel until the idle reaper or upstream exit closes it. Eviction only detaches the notification listeners: it does not reap the upstream and does not change the kill switch's policy-gate role (the now-streamless session is reaped on the normal idle path, and a reopen is refused by the same 403 check), so the semantics stay "deny everything for a killed session" with the in-flight notification channel now closed as part of that.

Independently of the kill switch, an SSE stream opened with a Bearer token is bounded to that **token's expiry**. The token is validated once, at stream open, so the stream arms a timer at the verified `exp` and ends when the lifetime elapses, forcing the client to re-open — and thus re-validate — with a fresh token. Kill-switch eviction covers administrative revocation; this covers plain expiry, so an expired (or IdP-revoked but not kill-switched) client cannot keep receiving server→client traffic indefinitely on a stream authorized long ago.

The `/control/kill` HTTP endpoint is restricted to loopback addresses only (`127.0.0.1`, `::1`) — any request from a non-loopback source is rejected with 403 — **and** requires an auto-generated control token (SEC-07). Under `--trust-forwarded-for` the loopback check additionally fails closed when the request carries an `X-Forwarded-For` header (the same guard covers `/healthz` and `/metrics`): a reverse proxy fronting the listener presents its own loopback source address on behalf of an off-host client, so the header is treated as proof the request arrived via the proxy and is denied — a directly-connecting local caller never sets it. The loopback check **also** pins the request `Host`, because a loopback *source* alone is satisfied by a victim's own browser after a DNS rebind (the TCP connection still originates on the local host, §3.6), so without the pin attacker JavaScript on a rebound page (`Host: attacker.com`) could read `/healthz` and `/metrics` operational state (session/route counts, audit-degradation and kill-switch health). The pin lives in the shared loopback check, so it covers `/control/kill` as well — that endpoint is gated primarily by its required control token, and the `Host` pin is an additional layer rather than its main defense. What the pin rejects is a foreign **name**, which is what a rebind necessarily presents (the victim's browser still believes it is addressing the attacker's hostname, which is what makes the response same-origin readable). It admits the `checkOrigin` allowlist (the loopback names plus any non-wildcard bind host), any loopback host — literal or alias, so a scrape via `127.0.0.2` or an HTTP/1.0 probe is not broken — and an absent `Host` (HTTP/1.1 requires the header and every browser sends it, so an empty value is a non-browser local caller). A browser cannot be steered into presenting a loopback literal as a rebound page's `Host`: fetching the literal directly is cross-origin, so it carries an `Origin` and the middleware rejects it first. A reverse proxy that fronts these endpoints while rewriting `Host` to an external name is denied — front them on a loopback name, or scrape the listener directly. At startup the proxy mints a 256-bit random token and writes it to a 0600 file (`~/.eunox/control.token` by default, configurable with `--control-token-path`), after the listener binds and under a bounded deadline; `/control/kill` rejects any request whose `X-Eunox-Control-Token` header does not match it (constant-time compare), independently of `listen.authToken` / JWT mode. This closes the gap where a same-host process — e.g. a compromised upstream subprocess, which by design runs on the same host — could trigger the emergency stop merely by reaching the loopback endpoint. The token authenticates the *control* of the kill switch, not the cache stale-ness; `eunox kill` reads the file automatically. A proxy with no control token configured refuses the endpoint (503, fail closed) rather than serving it unauthenticated. The control-token check runs **before** the HTTP method check: a non-`POST` request (e.g. a bare `GET`) is authenticated first, so a caller who has not proven they hold the token gets the same recorded 401 (`CONTROL_AUTH_FAILED`) as any other unauthenticated probe, rather than an unrecorded 405 that confirms the endpoint exists and is enabled a gate earlier — the same asymmetry the loopback-vs-token ordering above already closes, one gate later. A caller who *does* present the valid token but the wrong verb still gets the specific 405 (unrecorded, since they have already proven possession of the token). **Residual:** the 0600 file is readable by the proxy's own UID, so a process compromised *as that same user* with filesystem access can still read it; sandbox the upstream (no read access to the token path) or run it under a distinct UID where that matters.

**Limitation:** The proxy does not implement token binding between the bearer JWT and the session ID. An attacker who learns both a valid JWT and a valid session ID could make requests. This is the tradeoff of the MCP session model; mitigate in high-security environments by setting `listen.authToken` to add a shared secret layer on the proxy's HTTP listener.

### 3.4 Audit Log Tampering

**Attack:** An attacker with local filesystem access modifies or deletes audit records in `~/.eunox/audit.jsonl` to conceal unauthorized tool calls or suppress evidence of policy violations.

**Mitigation (HMAC-SHA256 signing + hash chain):** Each audit record is signed with HMAC-SHA256 using a 256-bit key loaded from `~/.eunox/audit.key`. The HMAC covers the full record JSON — including the record's `seq` and `prev_hmac` chain fields — excluding the `_hmac` field itself. The signature is appended as `"_hmac": "sha256:<hex>"` before the record is written.

Each record additionally carries a monotonic `seq` and a `prev_hmac` holding the `_hmac` of the preceding record, forming a tamper-evident chain (continuous across restarts and rotation; a fresh log's first record carries the `sha256:genesis` sentinel). `eunox audit-verify` recomputes every record's HMAC — catching any field modification — and verifies `prev_hmac` linkage and `seq` contiguity across consecutive records — catching deletion, reordering, and insertion. Because the HMAC is recomputed over the record's modeled fields, a signed record carrying any **unknown top-level field** (one outside the record schema, e.g. an injected `"operator_override"`) is rejected as invalid rather than silently passing — an extra field cannot ride along uncovered by the recomputed signature. Beyond that, a signed record must be in **canonical on-disk form**: verification rebuilds the exact line the writer emits for the fields the record decoded to and requires the bytes to match (§3.4, *Canonical on-disk form*, below), so a byte-level rewrite that still decodes to the signed value — a duplicate top-level key (`{"decision":"allow",…,"decision":"deny",…}`, which last-wins decoding resolves to the signed `deny` while a first-wins consumer reads `allow`), a case-variant spelling of a key (`"Decision"`, which Go's `encoding/json` binds to the same field), an added zero-valued `omitempty` field, an alternate string escape, or inserted whitespace — fails closed. It walks the **entire rotated set as one chain** — every rotated sidecar oldest-first, then the current base log — so the linkage is checked across file boundaries too: deleting an entire interior rotated file is caught because the file after the gap fails to chain onto the file before it (a `prev_hmac` mismatch *and* a `seq` gap), which verifying the current base file in isolation could not detect. Because the chain fields are themselves signed, an attacker without the key cannot rewrite the chain to conceal a removed record:

```
$ eunox audit-verify
Checked 142 record(s): 142 valid, 0 invalid, 0 skipped, 0 unknown-key, 0 unverifiable; 0 chain break(s).

$ eunox audit-verify          # after a record was deleted
CHAIN BREAK at seq 88: prev_hmac does not match the preceding record (a record was deleted, reordered, or inserted)
Checked 141 record(s): 141 valid, 0 invalid, 0 skipped, 0 unknown-key, 0 unverifiable; 1 chain break(s).
# exit status 1
```

The audit key is generated once at first startup using `crypto/rand` (Go's CSPRNG, backed by the OS entropy source) and stored at `~/.eunox/audit.key` with mode `0600`. Loss of the key means existing records cannot be re-verified, but does not affect enforcement.

**File modes are re-tightened on load, not just on creation.** The key file and the audit log are created `0600`, but `O_CREATE` applies that mode *only* when it creates the file — a log or key that already exists is opened/read with its on-disk mode unchanged. So a file left group/world-readable by a looser `umask` on a prior run, a backup restore, or a deliberately pre-created path would otherwise keep that mode. On load the proxy drops any **group/world** access bits from a pre-existing log and key file (and from an active log opened by rotation), preserving the owner bits: e.g. `0644` becomes `0600`, while an operator's deliberately owner-write-only `0200` log is left untouched (so its tail read still fails closed into the chain-resume path rather than being silently re-opened for read). This matters most for the key: a readable HMAC key lets any local user forge records (see Residual risk) — and because a key found group/world-accessible may *already* have been copied, the loose→tight transition is logged as a `SECURITY` warning recommending rotation, not fixed silently. The re-tightening is best-effort with a warning on the rare backend that cannot `chmod` (FAT/exFAT, some CIFS/NFS mounts) — the same backends the key-publish path already tolerates — since refusing to start there is worse than the (HMAC-integrity-protected) log retaining its prior mode.

**The key file is opened under the same symlink guard as every other audit file.** The key is the one audit path whose redirection is unrecoverable: the log is HMAC-protected, so redirecting it is detectable, but whoever chooses the *key* chooses what verifies — a key read through an attacker-planted symlink signs a tape that same attacker can forge at will, and `audit-verify` confirms it. The load, the mode-tightening, and the post-publish re-read therefore refuse a non-regular key path (`Lstat`) and open with `O_NOFOLLOW` where the platform has it, and the tighten works through the **open handle** (`fstat`/`fchmod`) rather than the path — a path-based `stat`+`chmod` pair follows a symlink, so it would re-mode the link's target, and it re-resolves between the two calls, which is a local denial-of-service primitive (dropping `o+r` from an arbitrary file) unrelated to the audit key.

The one deployment shape where a symlinked key is normal rather than an attack is a **projected secret mount** (Kubernetes and equivalents materialize each key as a symlink into a timestamped `..data` directory so the set can be swapped atomically). Set `EUNOX_AUDIT_KEY_ALLOW_SYMLINK=1` there. It is a deliberate, narrow downgrade: the resolved file must still be a regular file (checked through the open handle, so there is no second resolution to race — a device or FIFO stays refused), and what it gives up is only the guarantee that the final path component was not redirected. Prefer mounting the secret's `..data` directory directly, or copying the key to a regular file at startup, and leave it unset.

The key *directory* is created `0700` when the proxy creates it, but a pre-existing key directory is **not** re-tightened: a mode-`0600` key is unreadable by other users regardless of the directory mode (directory perms gate traversal/listing, not file contents), and `--audit-key-path` is explicitly aimed at containerized / multi-instance deployments where the key often lives in a shared or read-only secret mount whose directory mode the operator manages. Narrowing that directory on every load would be collateral the load-bearing key-file tighten does not need.

**Key rotation.** Each record carries a `key_id` — a non-secret digest of the signing key — so that records remain verifiable after the key changes. The key file holds one 64-hex-character key per line (blank lines and `#` comments ignored): the **first** line is the active signing key and any further lines are retired keys retained only for verification. To rotate, prepend a freshly generated key and keep the old one below it. `eunox audit-verify` loads every key in the file, indexes them by `key_id`, and verifies each record against the key that signed it — so a tape that straddles a rotation verifies end to end. A record whose `key_id` names a key absent from the file fails closed; a record with no `key_id` (written before rotation support) is tried against every key, so a tape that straddles the format change verifies the same way the pre-chain format does. The `key_id` is a one-way digest and discloses nothing about the key material.

**Externally-supplied key entropy.** An operator-supplied key — injected via `--audit-key-path` or `EUNOX_AUDIT_KEY_PATH` for containerized or multi-instance deployments — must be a full 256-bit (32-byte) value drawn from a cryptographically secure random source; generate one with `openssl rand -hex 32` (or any CSPRNG) so it matches the entropy of an auto-generated key. The proxy fails closed at startup on an externally-supplied key that does not decode to exactly 32 bytes, and additionally rejects an **all-zero** 32-byte key: zeros are the canonical placeholder a misconfigured deployment supplies (a zeroed or unwritten secret, a value rendered from an unset environment variable), and an all-zero HMAC key carries no entropy — anyone who knows the construction can forge signatures that pass verification, defeating the tamper-evidence control entirely. The check is fail-closed: a weak key is rejected before the proxy starts signing, rather than silently producing a forgeable audit log. Auto-generated keys come from `crypto/rand` and are never affected.

**What the chain does and does not cover.** Modification, interior deletion — of individual records *and* of an entire interior rotated file — reordering, and insertion are detected from the local files alone, because `audit-verify` walks the whole rotated set as one chain (above): a deleted interior file surfaces as a `prev_hmac`/`seq` break where the file after the gap fails to chain onto the file before it. On a **non-rotated** log, leading-record removal is also caught: the first record of a fresh log carries `seq 1` and the `sha256:genesis` sentinel, an invariant `audit-verify` checks, so excising the genuine first record and rewriting the survivor to claim `seq 1` is reported as a `CHAIN BREAK at seq 1` (the rewritten record also fails its per-record HMAC). A `seq 1` record carrying an **empty** `prev_hmac` is flagged the same way, with no exemption: the writer emits either the resumed predecessor's `_hmac` or the genesis sentinel and never an empty string, so an empty one at `seq 1` is the signature of a key-holder truncating the leading records and forging a replacement (see *Unsigned records, and migrating a pre-signing log* below, which removed the one upgrade path that used to produce this shape legitimately). The cases that **cannot** be proven from the local files without an external high-water mark are **trailing truncation** (removing the last N records) and removal of the **leading** records — the oldest records, up to and including whole leading rotated files (which is also exactly what `--audit-retain` prunes deliberately) — because a truncated prefix of the chain is still internally consistent and begins at `seq > 1` indistinguishably from legitimate retention. For tamper evidence against those, ship audit records in real time to an append-only external sink (SIEM, object storage); the chain then lets the sink detect any in-flight gap. When reconciling against that external mark, use the oldest seq `audit-verify` reports as **proven**: the chain walk has to adopt the head record's seq as its anchor before any signature has been checked, so on a log that fails verification the claimed oldest seq is a value the forger picked. `audit-verify` reports the oldest seq covered by a signature it verified, and says so explicitly when the two differ.

**Canonical on-disk form (byte-level tamper evidence).** The HMAC is computed over the record's *decoded and re-marshaled* fields, not over the exact on-disk bytes, so on its own it certifies the **decoded value** and not the byte encoding: any two byte sequences `encoding/json` decodes to the same value verify identically. That is a real gap, because a write-capable attacker without the signing key can rewrite a record's bytes and leave the signature matching while changing what a byte-oriented consumer reads — a **duplicate top-level key** (last-wins decoding keeps the signed value, a first-wins consumer reads the injected one), a **re-spelled key** (`"Decision"` / `"DECISION"`, which Go binds case-insensitively even under `DisallowUnknownFields` and re-marshals back to canonical), a **zero-valued `omitempty` field explicitly present** (`"agent_id":""`, `"audit_only":false`, `"obligations":[]` — the re-marshal drops it again, so it is invisible to the recomputed HMAC), a **redundant `\uXXXX` escape** in a string value (`"deny"` written as `"\u0064eny"`), or **insignificant whitespace** inserted inside the object. Rather than enumerate those vectors, `audit-verify` requires the line to *be* the bytes the writer would have produced: after the strict decode and the re-marshal — and *before* the HMAC comparison, so a byte-rewritten record is reported as non-canonical rather than as a key mismatch — it compares the line against the canonical splice `writeRecord` uses (`signedRecordLine`), in place, without materializing that line. The `_hmac` value on both sides is spelled by the same encoder call, so the writer's form and the verifier's expectation cannot drift apart on the field being compared; the splice *shape* is deliberately expressed twice (the verifier avoids building a line per record), so a change to it has to be mirrored, which a round-trip test enforces. Anything the writer would not have emitted is rejected, which closes the class rather than its currently-known members. This couples tamper evidence to the standard library's exact `json.Marshal` output — but that coupling is already total and unavoidable, because the HMAC is itself computed over `json.Marshal` of the record: an encoding change would break every existing record's *signature* whether or not the bytes are also compared, so the byte comparison adds no fragility that signing did not already carry. Whitespace **outside** the object is trimmed rather than rejected: it can neither add, remove, nor re-spell a field, and callers legitimately differ on whether the terminating newline is included. An unsigned record never reaches this check: it carries no signature to compare against and is rejected as `invalid` first. What remains **out of scope** is a duplicate key *within* the nested `details` object: `details` is a `json.RawMessage` covered byte-exactly by the HMAC, so an attacker cannot edit it, but a `details` blob the caller itself supplied with an internal duplicate (e.g. `{"path":"/etc/passwd","path":"/tmp/safe"}`) is preserved verbatim and verifies — closing that would mean the audit layer walking into and re-validating the caller-supplied map it treats as opaque data by design (see §6.1). A raw-byte consumer reading `details` with different JSON semantics than eunox's decoder should parse it with standard last-wins semantics.

**Resume integrity.** On restart the proxy resumes the chain (next `seq`, `prev_hmac`) from the existing log's last line. That tail is HMAC-verified before it is chained onto: if the last record fails verification — the signature an attacker who truncated to a chosen record or appended a crafted tail cannot produce — the proxy logs a loud warning AND writes a signed, structured `AUDIT_INTEGRITY_FAILURE` marker (a synthetic deny record, like `AUDIT_RECORDS_DROPPED`, carrying the suspect tail's `seq` and `_hmac` in its `details`) as the first record of the new session, so the corruption is not silently carried into the new chain and the detection event is itself part of the tamper-evident trail and any external sink — not merely a transient stderr line that container log rotation can discard. (It warns rather than aborts, consistent with the audit-failure-does-not-block-enforcement tradeoff in §5.4; reconcile against the external sink.) When the configured base log is **empty or absent** on startup — because it was just rotated (the fresh base has no records yet) or a rotation reopen-fallback renamed the base away and never recreated it — the proxy resumes from the most recent rotated sidecar's tail rather than from the empty base, and warns. Resuming from the empty base would otherwise restart the chain at the genesis sentinel and silently orphan every record written before the restart, leaving no detectable gap between the two files. A tail whose final line is only **whitespace** (a stray editor save, or an `echo` appending a blank line) is resolved to the last real record, not mistaken for an empty log — the empty-vs-present distinction is reserved for a genuinely zero-length tail, so a non-empty log can never be misread as empty and restart the chain. When the fallback does reach for a rotated sidecar, an **unreadable *newer*** sidecar is never skipped in favor of an older one (which would reissue the newer file's seqs): the resume fails closed instead — seeding the next `seq` past the on-disk maximum and writing the `chain_resume_failed` marker — exactly as an unreadable base does. The same fail-closed stance covers a log **directory that cannot be listed at all** — any listing error other than a not-yet-created directory (a permission bit, `EIO`, `ESTALE`, or a non-directory parent): it is treated like an unreadable newer sidecar rather than as "no siblings", so it too seeds past the maximum and writes the marker instead of silently rewinding to genesis. That seed is taken across the **whole chain**: the highest `seq` actually read anywhere, *plus* the byte size of every file that could not be read (an unread record occupies at least one byte, so the byte total bounds how many higher `seq`s an unreadable file can hold beyond the readable maximum). Folding the unread bytes **additively** onto the readable maximum — rather than treating any single file's byte size as a global `seq` — seeds past the true on-disk maximum whenever any file in the chain is readable, closing a cross-file under-seed the earlier per-file maximum allowed once the monotonic chain `seq` grew past one sidecar's byte size (after enough rotations, or with a small rotation size). The one residual — a chain whose files are *all* unreadable *and* whose earlier history has been pruned — cannot reconstruct the pruned `seq` span from the surviving bytes and may restart low, but always under the `chain_resume_failed` marker, so the reset is never silent. A log **directory that cannot be listed** bounds the seed even less: the fold then sees only the base log, so the rotated sidecars' `seq`s are simply unknown and new records may collide with `seq`s those files already hold. That is a materially different forensic state from a bounded reseed, so it is stated on the tape — the `chain_resume_failed` marker carries `"seed_unbounded":true` — rather than presented as a confident maximum an auditor would later read as an unexplained duplicate-`seq` cascade. The seed is also **clamped**: the `seq` values it folds are read from disk without HMAC verification (deliberately — this path runs precisely when the chain cannot be verified, and an unverified `seq` can only inflate a counter, never inject a trusted chain link), so a corrupt or planted `{"seq":18446744073709551615}` line would otherwise seed the counter one short of the `uint64` ceiling and make the very next write wrap to 0, reissuing the genesis `seq`. Values above a plausibility ceiling (2^62, unreachable by any real log) are refused and the counter seeded at the ceiling instead, and `writeRecord` additionally refuses to write at all rather than wrap — a counted, warned gap is recoverable, a silently renumbered chain is not. A genuinely **missing** file is the normal brand-new-install case and resumes from genesis silently; but if an **I/O error** (a permission change, `EIO`, NFS `ESTALE`, or a failed `Stat`/`ReadAt` on a present file) prevents reading the tail at all, the chain cannot be safely resumed and restarts from genesis — and this case now writes a signed `AUDIT_INTEGRITY_FAILURE` marker (`"kind":"chain_resume_failed"`, carrying a structured `"reason":"tail_read_failed"` code) too, so an error-induced reset is distinguishable from a legitimate genesis and is not the one chain-reset path left unmarked. The raw OS error — which varies by platform/`errno` and can embed the log file path — is written only to the stderr warning, never into the signed, append-only tape, so `details.reason` stays a fixed code SIEM rules can match across environments rather than free-form prose.

A tail the strict decoder REFUSES — malformed JSON, an unknown top-level field, or trailing bytes — is marked `tail_strict_decode_refused`, not `tail_hmac_mismatch`. Verification strict-decodes before it computes any MAC, so no key ever saw the record: the mismatch marker would assert a comparison that never ran, and point an operator at a tampering remediation for what is most often a malformed or forward-versioned line. The distinction is forensic only — the chain restarts from genesis either way, and the record is never resumed onto. A SIEM rule that treats `tail_hmac_mismatch` as the tamper signal should treat this kind as an integrity event too: an unknown top-level field on the last record is also what a splice looks like, and it is refused before the signature that would have caught it is checked. The marker carries the same `claimed_tail_seq` / `claimed_tail_hmac` facts, from the lenient decode, so a forensic reader can still locate the record.

**Partial trailing write.** A non-clean shutdown (`kill -9`, power loss) can leave bytes after the final newline with no terminating newline of their own — a write interrupted mid-record. Because every complete record ends in a newline, such a non-newline-terminated fragment was never a complete record. On Open the proxy truncates that fragment (which therefore never removes a complete record) so the next append begins at a clean record boundary instead of concatenating onto the orphan and producing a line `audit-verify` cannot parse; it then resumes the chain continuously from the last complete record and writes a signed `AUDIT_INTEGRITY_FAILURE` marker (`"kind":"tail_partial_write_recovered"`, carrying `recovered_bytes`) so the recovery is itself on the tamper-evident trail. This is distinct from a **newline-terminated but unparseable** last record, which is treated as corruption (`"kind":"tail_parse_failure"`, chain restarting from genesis), not a recoverable partial write. Truncating only the unterminated fragment does not weaken truncation detection: an attacker who truncates to a record boundary leaves a newline-terminated tail that is HMAC-verified and reconciled against the external sink exactly as before. A fragment **larger than the tail scan window** with no record boundary inside it is a special case: its last-complete-record boundary cannot be located, so it cannot be safely truncated (dropping the window could delete a complete record whose newline sits just before it). Open therefore fails **closed** — refusing to start until the operator resolves the tail — rather than leaving the orphan and proceeding, which would let the `tail_parse_failure` marker `O_APPEND` directly onto the multi-megabyte orphan, fusing one physical line that trips `audit-verify`'s per-line length bound and buries the marker's own signature.

**Unsigned records, and migrating a pre-signing log.** Every record this proxy writes is signed, so a record carrying no `_hmac` is one of exactly two things: history written before signing existed, or a signed record whose signature an attacker stripped. Nothing in the record distinguishes them, and the second is the *only* edit a write-capable attacker can make without holding the key — so both are refused, on both sides.

On the **write** side, the chain is never resumed onto an unsigned tail. Resuming would seed `seq` and `prev_hmac` from bytes nothing certifies, letting an attacker truncate to a chosen record, append an unsigned record as the new tail, and have the proxy adopt it. Instead an unsigned tail is treated exactly like an unparseable one: the chain restarts from genesis (`seq 1`, `sha256:genesis`) and a signed `AUDIT_INTEGRITY_FAILURE` marker (`"kind":"tail_unsigned"`, carrying the refused tail's `seq`) is written as the first appended record, so the boundary lands on the tamper-evident trail and any external sink rather than only in a transient stderr line. The restart deliberately does **not** inherit the tail's `seq`: an untrusted tail must not be able to inflate the counter. The resulting duplicate `seq` values against the older records are themselves a signal `audit-verify` surfaces.

On the **verify** side, every HMAC-less record is counted `invalid`, wherever it sits in the log and whatever `seq` it carries — treating one as merely `skipped` would make stripping `_hmac` a way to dodge verification, and there is no position or shape that makes an unsigned record certifiable. Unsigned records are also kept out of the chain state, so they cannot poison the `prev_hmac`/`seq` anchor and fabricate (or suppress) breaks for the records around them. A log with no signed record anywhere therefore fails on the `invalid` count alone — closing the wholesale-forgery vector where a write-capable attacker without the key deletes the log and its rotated siblings and rewrites them all in unsigned shape. Relatedly, a record carrying `seq 0` *with* a non-empty `_hmac` is structurally impossible in a correct log (signed records start at `seq 1`) and is rejected as `invalid` regardless of whether its HMAC verifies, closing a forged-`seq-0`-decoy substitution of the genesis record even against a key holder.

**Migration.** There is no compatibility path for a pre-signing log: move it aside before upgrading (`mv audit.jsonl audit.jsonl.pre-hmac`) and let the proxy start a fresh, fully-signed chain. Leaving it in place is safe but noisy — the proxy refuses the tail, starts a new chain, and `audit-verify` exits non-zero with `N invalid` for every pre-signing record until they rotate out. Reconcile that prefix against your external sink; it was never covered by HMAC or chain checks in the first place.

**Rotation integrity.** Size-based rotation renames the active log to a timestamped sidecar before opening a fresh file. The sidecar suffix is a nanosecond-resolution UTC timestamp preceded by a monotonic ordering ordinal with a uniqueness backstop, so two rotations within the same second cannot collide — `os.Rename` atomically replaces an existing target, so a coarser suffix would let the second rotation silently destroy the first sidecar and drop its records outside the chain's coverage. If the rename itself fails (a persistent fault such as a permissions error, a cross-device target, or a disk-full condition affecting only the rename syscall), rotation backs the size counter off by one ~10% burst rather than resetting it to zero, so the active log can grow by at most ~10% of the rotation threshold per failed attempt instead of a full threshold each time — bounding disk growth under a permanently broken rotation while still avoiding a tight retry loop.

**Rotation makes its directory entries durable, not only its data.** `rename(2)` and the fresh base's creation dirty the parent directory inode in cache only, so a power loss after rotation but before that inode is written back replays the directory to its pre-rotation state: the records the fresh base has already `fsync`ed sit in blocks nothing references, restart resumes cleanly from the old tail, and `audit-verify` passes over a log that silently lost every post-rotation record — no attacker required. Rotation therefore `fsync`s the log directory after a successful rename and again once the fresh base is open, the same hazard and the same fix the key publish already handled. Both are best-effort with a warning: a filesystem that refuses directory `fsync` must not wedge rotation.

Three further rotation faults fail closed rather than corrupt the chain or its ordering. (1) The rename is followed by an **fsync of the sidecar before the fresh base opens**; if that fsync fails, rotation *defers the reopen* (entering the same bounded reopen-retry fallback) instead of closing the sidecar's descriptor before its tail is durable — a crash between an un-synced sidecar and an already-created empty base would otherwise lose the sidecar's tail and leave an undetectable chain gap. The bounded reopen-retry itself applies the same rule: when it re-syncs the fallback sidecar before swapping in a fresh base, a failed sync *defers the swap* too, rather than closing the still-un-synced descriptor — so the durability guarantee holds on the fallback-recovery path, not only on clean rotation. (Re-syncing the same descriptor is a bounded best effort — a writeback error is reported to a descriptor at most once — but never completing the swap on a failed sync is the load-bearing half.) (2) The post-rename reopen **refuses a non-regular log path** (a symlink planted in the rename→reopen window) — or a path it cannot `Lstat` for any reason other than genuine absence, since gating the refusal on "stat succeeded" would let a stat fault skip the check and follow a symlink — through a single guard shared with the startup open, so an attacker cannot redirect the tape through a symlink — which would also drop the active log out of `audit-verify`'s regular-file scan, making verification pass without reading a live record. The same symlink guard — the portable `Lstat` refusal plus `O_NOFOLLOW` where the platform has it — covers **every truncating or appending open** on an audit-derived path with no exception, including the sidecar lock file that enforces the single-writer property. (Whole-file *scans* — the resume seq contribution and `audit-verify`'s per-file read — deliberately stay outside it: they read rotated siblings too, and their worst case is a mis-seeded ordinal rather than a redirected write.) Nothing is ever written through that lock handle, but the lock's *exclusivity* is the payload: `flock`/`LockFileEx` applies to whatever the open resolved to, so a link planted at the lock path would send a second instance's lock to a different object, leaving both instances believing they hold the log and appending to it — a forked HMAC chain produced without touching the log file itself. The audit directory is not trusted enough to skip this: `MkdirAll` sets `0700` only on a directory it creates, so a log path pointed at a pre-existing group- or world-writable location carries no mode guarantee. (3) The sidecar's **ordering ordinal is seeded from the existing siblings**; if that directory read was uncertain at startup and stays unreadable at rotation time, rotation is *deferred* (backed off and retried) rather than stamping a stale-low ordinal `1` that would sort before existing higher-ordinal sidecars — mis-ordering retention (deleting the newest first) and feeding cross-file verification out of order.

Deferring is the right call for chain integrity, but a fault that *persists* defers every future rotation, so the size bound is silently voided and the active log grows until the volume fills — at which point writes do start failing and `--require-audit=strict` denies everything. A deferral is therefore **reported**, not merely logged, through the maintenance status (`eunox_audit_maintenance_stalled`, with `auditMaintenanceReason` on `/healthz` naming what to fix) while it is still recoverable; it clears itself as soon as a rotation succeeds. This covers every exit that leaves a rotation attempt incomplete, not only the ordinal-seed case above: an unseedable ordinal, a sidecar name the uniqueness backstop cannot establish as free (it treats a candidate it cannot `Lstat` for any reason other than genuine absence as occupied — the fail-closed choice, since assuming "free" would let the rename clobber a sidecar and its chain tail, so a directory returning `EACCES`/`EIO` on every probe exhausts the backstop and defers rotation exactly as durably as an unseedable ordinal, with the ordinal seed itself looking healthy), a failed rename of the active log, a failed sync of the just-renamed sidecar, and a failed reopen of the fresh base — both the reopen immediately after a clean rename and every bounded retry of it in the fallback-recovery path. Each of those computes its own report at rotation's single reporting exit (mirroring retention's single exit below) rather than at scattered call sites, so an early return added to either path in the future cannot silently skip reporting the way the original gap did.

**Retention (`--audit-retain` / `audit.retainRotated`).** When set, each rotation deletes the oldest rotated sidecars beyond the configured count, bounding disk use (the default, `0`, keeps every sidecar — the historical behaviour). Retention only ever **deletes whole rotated sidecars** matching this log's exact nanosecond-suffix pattern; it never edits a record, never touches the active log, and never touches an unrelated file in the directory. The trade-off is availability of *local* history: deleting the oldest sidecars removes the leading records of the chain, and — as noted above — removal of leading records on a rotated log already cannot be proven from the local files alone. Retention therefore does not weaken what `audit-verify` can prove about the records that remain (modification, interior deletion, reordering, and insertion are still caught), but a deployment that must retain durable history under a retention cap **must** ship records to an append-only external sink in real time; the local tape is explicitly bounded. Because retention runs only on the drainer goroutine at rotation time, it cannot race a concurrent write. Pruning deletes the oldest sidecars first and **stops at the first failed deletion** rather than continuing to a newer one: retention is safe only because it removes a contiguous *oldest* prefix, so continuing past an unlink failure (a Windows sharing violation, `EACCES`, `ESTALE`) could delete a newer sidecar while an older one survived — an interior hole `audit-verify` reads as a `prev_hmac`/`seq` break, indistinguishable from a deleted interior file. A sidecar already gone is not a hole and does not stop the pass; the next rotation retries. An unlink that keeps failing is reported through the same maintenance status as a deferred rotation — the failing sidecar is always the oldest, hence always the first tried, so a permanent fault (an immutable attribute, a read-only mount) breaks the pass at its first entry on every future rotation and voids the retention bound. So is a pass that cannot **list** the sidecars at all: rotation needs only an `Lstat` once its ordinal seed is certain, so a log directory that becomes unlistable *after* startup leaves rotation stamping sidecars that every prune pass then fails to enumerate — retention never runs again and sidecars accumulate unbounded.

The maintenance status is **keyed by subsystem** (rotation, retention) rather than shared between them. The two legs fail independently, and with one shared flag every report of health was a cross-subsystem write: whichever leg ran last decided what the operator saw, so a prune pass finding its own bound satisfied could clear a live rotation stall and return `/healthz` to green while the size bound went unenforced. Each leg now publishes its own status once, at the single exit that decided that pass's outcome, so a recovery in one never clears the other, no exit can leave a status stale, and `auditMaintenanceReason` names which of the two bounds is unenforced — both, when both are.

**Residual risk:** The HMAC key is stored on the same machine as the log file. An attacker with read access to `~/.eunox/audit.key` can forge records (and recompute the chain) that pass verification. For regulated environments requiring tamper evidence against a privileged local attacker, ship audit records to an external sink in real time as above.

### 3.5 Credential Overprivilege

**Attack:** An agent accumulates broader API access than any specific task requires because credentials are issued for the user's full role rather than for the current task's scope.

**Mitigation (JWT PDP mode):** When the IdP is configured to inject `mcp.capabilities` claims into access tokens, the proxy enforces the task-scoped capability set rather than the full role. The JWT (schema v0.2) carries exactly what this agent invocation is permitted to call — `"tool:read_file?path=/reports/*"`, not `"*"`. The capability set is treated as an exhaustive allowlist: any tool not listed is denied with `AUTHORIZATION_FAILED` (JSON-RPC `-32001`). This `mcp.capabilities` enforcement is experimental and requires the opt-in flag `--jwt-experimental-capabilities` (off by default); with the flag off, a token carrying `mcp.capabilities` is rejected at validation (fail closed), so the schema cannot be relied on silently while it is unstable.

**Mitigation (manifest + JWT intersection):** When `policy` is also set, the proxy computes the intersection: a tool call must be permitted by **both** the manifest constraints and the JWT capability claims. The JWT can only restrict what the manifest allows; it cannot expand it. This prevents a misconfigured IdP from accidentally granting broader access than the manifest operator intended. The intersection also requires `--jwt-experimental-capabilities`; when the flag is off the manifest still governs identity-only tokens (`sub`, `mcp.task_id`, `mcp.agent_id`), and a token presenting `mcp.capabilities` is rejected rather than partially enforced.

**Mitigation (MaxCalls condition):** The `maxCalls` condition limits how many times a tool can be called within a sliding time window. For tools that retrieve credentials or sensitive resources, a `maxCalls: 1` limit bounds the privilege exposure window to a single use per session, regardless of token TTL.

### 3.6 Unbounded Tool Call Rate

**Attack:** An agent (or a prompt-injected agent) calls a tool in a tight loop, causing backend resource exhaustion, runaway API costs, or unintended mass operations.

**Mitigation:** The `maxCalls` condition type enforces a call-count ceiling within a configurable sliding window per session. The counter is backed by:

- **In-memory store (default):** Counter resets on proxy restart. Sufficient for single-instance, short-session deployments.
- **Redis store (`--redis-addr`):** Counter survives proxy restarts and is shared across multiple proxy instances running with the same Redis instance. Suitable for persistent or multi-replica deployments.

Counter keys encode `(sessionID, targetType, bareName, windowSeconds)` under a `maxcalls:` prefix. Each component is length-prefixed — `maxcalls:<len>:<sessionID>:<len>:<targetType>:<len>:<bareName>:<len>:<windowSeconds>` — so a component that itself contains the `:` separator cannot forge a different tuple that lands in the same bucket. This matters because `SessionID` is a plain string with no engine-enforced format: the shipped HTTP transport assigns UUIDs (colon-free), but a library caller can supply any value, so the *encoding* — not an assumption that session IDs are colon-free — guarantees the separation. The same length-prefixed encoding backs the `sequenceBlock` `seq:` history markers. The `<targetType>` segment (`tool`, `resource`, `prompt`, taken from `req.Target.Type`) namespaces the bucket by capability type, so a tool named `export` and a prompt named `export` keep independent quotas instead of draining one shared bucket. The `<bareName>` segment is the capability name with any engine prefix (`tool:`, `prompt:`, …) stripped — the same normalization `findMatchingCapability` and the `sequenceBlock` `seq:` history apply — so the prefixed and bare forms of *one* tool (`tool:read_file` and `read_file`) map to a single bucket and a client cannot reset its own quota by toggling the prefix. The trailing `<windowSeconds>` segment gives each window its own bucket, so a capability that layers two `maxCalls` conditions of *different* lengths counts each independently instead of writing both into one shared entry — which inflated the count (and pruned the longer window against the shorter, failing it open); two conditions sharing one `windowSeconds` are rejected at manifest load. This means Redis addresses the *cross-instance* bypass (the same session's quota is visible to all proxy replicas) but does **not** prevent *session-rotation* bypass: a client that opens a fresh MCP session gets a new `Mcp-Session-Id` and therefore a fresh counter, on both backends equally. The session-rotation bypass is a documented residual risk (see `adversarial_test.go` Adv-6).

**In-memory store footprint:** The in-memory counter holds one map entry per distinct `(session, tool)` pair — for both `maxcalls:` keys and the `seq:` markers `sequenceBlock` records — reclaimed only when the periodic cleanup fires (`DefaultCleanupInterval`, 5 minutes). A deployment that mints a fresh session per request (short-lived HTTP connections with UUID `Mcp-Session-Id` values are the common case) accumulates one entry per unique session between cleanup cycles, so the map — and the process heap — peaks at the cleanup boundary; a client able to drive unique session IDs can push that peak high enough to exhaust the heap and OOM the process. The proxy bounds this by default: `--max-call-counter-keys` (1,000,000; set 0 to disable) caps the in-memory key count, and a call under a *new* key past the ceiling is refused rather than growing the map. A key freed by cleanup frees a slot. The *number* of keys is one axis; the *size of each key* is the other, and it is bounded too: `IncrementAndGet` retains only the most-recent `maxEntries` in-window timestamps per key (`recordSessionCall` passes `1`, since a `seq:` marker needs presence, not a count), so a single high-rate antecedent can no longer grow one key's timestamp slice without bound across the 24h history window the way it previously did — the parallel `IncrementAndGet`/`sequenceBlock`-history complement to the admitted-only quota bound below.

Both key namespaces fail **closed** at the ceiling. A refused `maxcalls:` key fails closed: the counter error becomes `CONDITION_FAILED` and the call is denied (`handlers.go`). A refused `seq:` key also fails closed: `recordSessionCall` does **not** swallow the error — consistent with the recording contract described above (§"Mitigation (`sequenceBlock` condition)") and `recordSessionCall`'s own doc in `engine.go`, it surfaces the write error and the engine denies the call that needed the new history key (`CONDITION_FAILED`, audit detail `phase: record`). Swallowing it would leave the antecedent marker unwritten and let a later `sequenceBlock` check read a falsely-absent antecedent and fail open; surfacing it closes that bypass. The consequence at the ceiling is therefore an **availability** impact, not a `sequenceBlock` bypass: under sustained saturation any allowed call in a session that needs a new key is denied while the map is full (and because recording is indiscriminate, that is every allowed call in such a session, not only sequence antecedents). An operator expecting low denial rates under high session churn should choose the Redis backend, whose per-key TTL keeps state off the Go heap so the ceiling is not reached. (The one place a recording error is deliberately swallowed is route-level *audit* mode in `pdp.go`, which forwards regardless and only logs a warning.)

The bound is a memory backstop, not a per-session quota; for sustained high-session-rate deployments prefer the Redis backend (`--redis-addr`), which keeps counter state in Redis with a per-key TTL rather than on the Go heap (so it is unaffected by key count) and therefore does not reach the key ceiling that forces fail-closed denials in the in-memory backend.

**Audit queue back-pressure:** Audit records are enqueued non-blocking into a fixed-size channel; when the channel is full, records are dropped and counted via `DroppedRecords()`. This applies to all denial paths, including unmapped-method denials (`AUTHORIZATION_FAILED`). A client spamming novel MCP methods can saturate the queue and cause subsequent legitimate records to be dropped. Crucially, a drop does **not** vanish from the chain: the drainer writes an explicit, signed `AUDIT_RECORDS_DROPPED` marker into the log before the next record, so `audit-verify` and any external sink see the gap rather than a clean, contiguous chain. Without this marker a flood-induced loss would leave no `seq` gap and no chain break, because the chain head only advances on a successful write — making the loss invisible. Beyond the aggregate `dropped`/`dropped_total` counts, the marker's `details` carries a `by_method_target` breakdown — the dropped record's own method and target were already computed before the enqueue attempt, so they are tallied by (method, target) pair at each of the three drop sites (queue full, over the byte budget, post-close) even though the record's arguments and full content are gone. This is bounded to 32 distinct pairs (further distinct pairs fold into a single `"(other)"` bucket) and is best-effort relative to the aggregate count — the two are updated by separate, unsynchronized counters on the enqueuing goroutine — so a reader should treat the breakdown as directional context (e.g. "the flood concentrated on this one tool") rather than an exact per-bucket reconciliation of `dropped`. Operators should still monitor `DroppedRecords()` and alert when it is non-zero; sustained drops indicate disk I/O pressure or a write flood.

**Shutdown drop window (bounded, counted-but-unchained):** A second, narrow drop path exists during shutdown. `Close()` sets a `closed` flag and closes the record channel under a write lock so an in-flight `record()` send can never race with the close (which would panic with "send on closed channel"); any `record()` that runs after `closed` is set is counted via `DroppedRecords()` and returns without enqueueing. Because the drainer has already written its final `AUDIT_RECORDS_DROPPED` marker and exited by then, these shutdown-window drops are **not** folded into a signed chain marker — they are observable only through a later `DroppedRecords()` read, and the `dropped` total `Close()` prints can itself under-count producers still finishing after `Close()` returns. This is a known, bounded gap (it spans only the graceful-shutdown interval, after the server has stopped accepting new work) and is strictly safer than the prior behaviour, where the same race terminated the process via panic with no graceful flush at all. Operators who require completeness across shutdown should ship records to an external sink (§3.4) and drain it on the high-water mark rather than relying on the local tail.

When the limit is reached, the call is denied with code `RATE_LIMITED` (JSON-RPC `-32003`) and the block is recorded in the audit log. The denial carries a `retryAfter` hint (whole seconds until a slot frees up) so callers can back off. The counter increment is not applied in audit mode (`enforcement: audit`), allowing observation of what would be blocked without affecting the count.

The check-and-record is atomic and applies **only to admitted calls**: an over-limit call is denied without writing a new timestamp (a single mutex for the in-memory backend, a single Lua script for Redis). This closes a self-extending lockout and unbounded-state-growth bug — previously every denied retry was counted, so a client that kept retrying at or above the limit refilled the sliding window indefinitely and drove the counter's backing store (Redis sorted set or in-memory slice) to grow with each retry until the key TTL fired. Because denied calls are no longer recorded, the window now clears `windowSeconds` after the last *admitted* call regardless of how often the client retries, and a rate-limited key's storage shrinks rather than growing. The retained admitted timestamps are themselves bounded by the limit — the quota admission (`AdmitAll`) has no separate `maxEntries` cap, the bound IS the quota, so an in-memory `maxCalls` key holds at most `count` (the configured limit) timestamps per window. A very large quota (hundreds of thousands of calls per window) therefore implies a correspondingly large per-key slice on the Go heap, which is a further reason large-quota deployments should prefer the Redis backend, whose sorted set lives in Redis under a per-key TTL rather than on the heap.

**Multi-`maxCalls` admission is atomic across buckets.** The atomic check-and-record holds *per bucket*, so a *single* `maxCalls` condition is admitted atomically and its limit is exact even under simultaneous requests. When one constraint layers **two or more** `maxCalls` conditions (e.g. 30/minute *and* 500/hour), the engine admits them through a single atomic multi-bucket operation (`CallCounter.AdmitAll`): a call is recorded in **every** bucket only if every bucket has headroom, and otherwise nothing is recorded. On Redis this is one Lua `EVAL` over all the buckets; in memory it is one mutex held across the whole check-and-commit. Two same-session requests that previously raced in the check→commit window can therefore no longer both be admitted — the committed count is exact for single- and multi-condition constraints alike. (An earlier implementation used a non-committing check followed by a separate per-bucket commit, leaving a narrow cross-bucket TOCTOU that could over-admit by up to the number of racing requests; that window is now closed. The single-node Redis client the binary wires evaluates the multi-key script directly. Redis **Cluster is unsupported**: the per-constraint bucket keys carry distinct window suffixes and can hash to different slots, so the script would be refused `CROSSSLOT` — a fail-closed deny, but one discovered at the first two-bucket policy rather than at wiring, so it is refused up front instead: `callcounter.NewRedis` rejects a sharding client, the startup handshake rejects a `--redis-addr` pointed at a cluster node, and a `CROSSSLOT` reaching `AdmitAll` anyway is reported as that same refusal.)

### 3.7 DNS-Rebinding Against the HTTP Listener

**Attack:** The HTTP transport binds to loopback (`127.0.0.1`) by default, so it is not reachable from the network. DNS rebinding circumvents that: a user visits an attacker-controlled web page whose domain initially resolves to the attacker's server and then re-resolves (rebinds) to `127.0.0.1`. JavaScript on that page can then issue requests to `http://attacker-domain:<port>/mcp`, which the browser sends to the locally-listening proxy — the loopback binding alone does not stop it, because the connection genuinely originates on the local host. If `listen.authToken` is unset (or extractable), the page can invoke tools, read resources, or drive `sampling/createMessage` through the user's agent session.

**Mitigation (Origin validation):** Per the MCP Streamable HTTP requirement, the proxy validates the `Origin` header on every HTTP request — `/mcp`, `/control/kill`, and the `.well-known` metadata endpoints alike — through a single middleware choke point so no handler can omit it. A request whose `Origin` does not appear in the allowlist is rejected with `403 Forbidden` and the proxy never reaches the routing, session, or PDP layers; the rejection is recorded in the audit log with code `ORIGIN_REJECTED`. Because this rejection precedes any session lookup or authentication, the unverified, attacker-controlled `Mcp-Session-Id` header is **not** stamped into the structured `session_id` field — doing so would let anyone forge `ORIGIN_REJECTED` records attributed to a victim's session. The structured `session_id` is left empty — and, carrying `omitempty`, is omitted from the record entirely rather than written as an empty string — and the client-claimed value is preserved only as the clearly-unverified `details.claimed_session_id` field, so an operator keeps the correlation hint without conflating it with an authenticated session. The rejected `Origin` itself is recorded in `details.origin`, **length-bounded** (512 bytes, cut on a rune boundary, flagged `details.origin_truncated` when it was not stored verbatim) before it reaches either the tape or stderr — an unauthenticated caller can put roughly a megabyte in that header, so an unbounded copy made every refused request an amplifier for signed-log growth and for a stderr line the refusal-record rate limiter does not gate. The requested `path` on the loopback-only endpoints is bounded the same way. The browser sets `Origin` on exactly the cross-site requests rebinding relies on, so the attacker's page presents its own foreign origin and is blocked.

`ORIGIN_REJECTED` belongs to a family of **pre-policy refusals** recorded so an attack against the transport surface — one that never reaches a PDP decision — still leaves a trace on the tamper-evident tape rather than only an HTTP status or a JSON-RPC error. Two siblings share its pre-session shape exactly: a missing/invalid static Authorization bearer token (`--listen-auth-token`) records `AUTH_FAILED`, and a missing/invalid `X-Eunox-Control-Token` on the loopback emergency-stop endpoint records `CONTROL_AUTH_FAILED`. Like `ORIGIN_REJECTED`, both fire **before any session lookup**, so each records the source IP and the unverified `claimed_session_id` — but **never** the presented credential — and leaves the structured `session_id` empty (stamping the attacker-controlled `Mcp-Session-Id` there would let anyone forge the record against a victim's session). `details.source_ip` is stamped by the shared refusal recorder rather than by each call site, so **every** pre-session refusal carries it by construction; hand-stamping had left it off the two records an incident responder reads first, the unauthenticated Origin probe and the JWT rejection. A fourth, `UNSUPPORTED_MEDIA_TYPE`, is recorded when a POST body is refused for its `Content-Type` (absent, duplicated, or not `application/json` — see the JSON-only body gate below); it carries only `details.header_count`, never the attacker-supplied header value. A fifth, `INVALID_REQUEST`, covers that same gate's malformed-JSON and trailing-data legs (see below); both share this rate-limited path with `ORIGIN_REJECTED` regardless of caller. Their **stamping**, unlike their rate limit, is caller-dependent: on `/control/kill` (no route concept) both fire before any session lookup and are written unstamped, like `ORIGIN_REJECTED`; on `/mcp` the route is already resolved by the time either gate runs (an unknown upstream 404s first), so their record carries that route's `upstream`/`policy_version`/`policy_sha256` stamp — the same treatment the session cap gets below, and for the same reason: a refusal must not be left unstamped merely because most of its siblings are, when the route producing it is already known. A further code, `RESOURCE_EXHAUSTED`, is recorded whenever a request is refused for saturation, at any of the three caps that can refuse one: the concurrent-handler pool (the stdio `hostSem` or the HTTP per-session in-flight cap, on **both** transports), the per-session notification pool, and the proxy-wide session cap. The first two fire on an **already-established session**, so they carry that session's real `session_id` and the refused method, but no `target`: the request is refused before its arguments are parsed, so no tool/resource/prompt name exists yet, and recording the method string as the target would fabricate a phantom one. Both are written **once per saturation episode**, not once per refused request: the first refusal after the pool last had a free slot is recorded, every further refusal while it stays saturated is folded into the next record's `details.suppressed_refusal_count`, and a successful acquire ends the episode so a later saturation records again. That is the signal an operator actually wants (a pool saturated, and by how much) and it closes the availability lever the per-refusal form left open — the notification pool most of all, since a dropped notification costs its sender no upstream round trip and is answered `202 Accepted`, byte-identical to a successful forward, so a flooding client gets no signal to back off. Enough records overflow the sink's bounded queue, and its drop counter is monotonic, so a saturation condition on one session would latch `AuditDegraded()` and — under the default `--require-audit=strict` — deny every enforced call on **every** route for the rest of the process's life. Underneath the episode rule each pool keeps its own small token bucket, so a caller cycling a pool between saturated and drained cannot open episodes faster than the drainer absorbs them. The gates are **per pool, per session**, each with its own scope-stamped rollup: `details.suppressed_refusal_scope` reads `"session"` here, never `"proxy_category"`, so a notification flood cannot elide the request pool's saturation record and the count on one of these records is never mistaken for the cross-route tally described below. The residual — N sessions each writing at the per-pool rate — is proportionate, because saturating a pool costs an authenticated session per-pool-capacity concurrent in-flight calls and each further session costs a full handshake plus its own upstream, bounded independently by the session cap. The **session cap** is the one that fires with no session yet — both halves of it, the pre-spawn slot reservation and the post-establishment `errSessionLimit`, through one helper so the two ways to hit the same cap cannot produce two record shapes. It therefore keeps `session_id` empty and carries the unverified `claimed_session_id` like the pre-session codes, and it stays **rate-limited** with them (it is reachable without an established session, so an unbounded write here would be the same audit-queue flooding primitive the limiter exists to deny) — but it is written through the **route's** sink, so it carries the same `upstream` / `policy_version` / `policy_sha256` stamp as its in-flight-cap sibling rather than being the one saturation record an auditor cannot attribute to a route. That combination — rate-limited *and* possibly route-stamped — is therefore not unique to the session cap: it is shared by `UNSUPPORTED_MEDIA_TYPE` and `INVALID_REQUEST` on `/mcp` too, which is why the rollup names its own scope rather than leaving it to be inferred from whichever record's stamp it happens to ride on (addressed below). One further denial shares the pre-session shape without being a distinct code: the session-creating `initialize`'s per-route audience pin (`AUTHORIZATION_FAILED`, `condition_type: jwtAudience`) fires before any session or upstream exists, reachable by any caller holding one valid token for a *sibling* route's audience (accepted by the gateway's shared union JWT validator) — the same zero-session-required flood shape `ORIGIN_REJECTED` closes, just gated on JWT validity rather than nothing at all. It is rate-limited through its own category (`audience`) for the same reason the session cap is: an unbounded write here is the same audit-queue-flooding primitive, reachable with no session ever created. The session-owner/audience gate re-run on an *existing* session's every action (§3.3) is deliberately **not** included in this bound — reaching it needs a live, unguessable session id a caller cannot mint for a foreign audience, a materially higher bar than the zero-session initialize path.

All of them — plus `DRIFT_REFUSED` (§3.8) — are **non-policy** denial codes: the `suggest` subcommand skips them (they name no policy target), so an off-host bearer/control-token brute-force, a pool-saturation flood against either transport, or a tool-poisoning refusal is visible to an auditor without polluting policy-mining.

**Refusal-record rate limit, and the scope of its rollup.** These records are the only audit writes an *unauthenticated* caller can trigger, so their rate is the attacker's to set: unbounded, a credential spray overflows the audit queue, and because the sink's drop counter is monotonic that latches `AuditDegraded()` for the process lifetime and makes `--require-audit=strict` deny every legitimate call (§5.4). A token bucket bounds them — the first refusals in a burst are written in full, and the next admitted record carries `details.suppressed_refusal_count`, the refusals elided since — so the evidence survives at a write rate the drainer absorbs. The buckets are keyed by refusal **category** (`origin`, `jwt`, `auth`, `control`, `loopback`, `body`, `content_type`, `saturation`, `kill`, `audience`), each proxy-wide across every route. Not one per route: it is the sustained write rate into the single shared audit queue that must be bounded, and a per-route split would multiply the rate an attacker can drive by the size of the route table. But not one bucket for everything either, which is what it was: categories differ enormously in what they cost an attacker to trigger and in what their records are worth to a responder, so a spray of unauthenticated Origin probes — one cheap request each, no credential — absorbed the entire budget and suppressed a **concurrent control-token brute force** into a number on somebody else's record. Categories are code-supplied literals, a fixed handful, so unlike per-source state they are not attacker-sized (the map is capped regardless). Each category holds an even **share** of one aggregate budget (rate and burst each divided by the category count, floored at one token so a share can never divide down to zero and silently stop refilling) rather than a full budget of its own, so the aggregate ceiling an unauthenticated caller can drive stays at or under the pre-split rate — 20/s sustained, burst 50 — for any category count the floor does not dominate (today's ten categories land at 20/s, burst 50 — the floor happens not to bind at this count, since both totals divide evenly); giving every category the full pre-split budget instead (an earlier draft did, briefly) would raise that ceiling to a few hundred records/second with no measurement behind the increase, re-widening exactly the availability bound this section exists to hold. Dividing keeps the property the split was for — no category can silence another — while leaving the aggregate, and the margin under what the drainer absorbs, essentially unchanged. A suppressed refusal is folded into whichever record **of its own category** is admitted next, whatever its route — and the **session cap** above is both rate-limited and route-stamped, so it is the one record that can pair an `upstream` / `policy_version` / `policy_sha256` stamp with a tally that spans every route. A saturation flood against `/mcp/routeA` can surface as a five-figure count on a `RESOURCE_EXHAUSTED` record reading `upstream: routeB`; a SIEM rule keyed on route + code would read thousands of saturation refusals against routeB's policy digest when routeB saw one. Every rolled-up record therefore states its own scope in `details.suppressed_refusal_scope` (`"proxy_category"`: every route, this record's category), so the number is never inferred from the stamp beside it. The count is deliberately **not** spelled `suppressed_count`: that key names the unrelated `*/list` filter statistic (§5.5 — catalog entries the manifest hid) in the same `details` object, and a query written against the bare key would match both routine policy filtering and an unauthenticated refusal flood. A non-zero `suppressed_refusal_count` means a flood, never a lost *policy* decision — no policy decision is ever rate-limited.

**The saturation gates' own rollup is deliberately a separate bucket, per pool per session, not a spoke of the proxy-wide one above.** Sharing it would let a notification flood on ONE session elide the `AUTH_FAILED` / `ORIGIN_REJECTED` records an incident responder reads first, and would make a `RESOURCE_EXHAUSTED` record's `suppressed_refusal_count` a tally spanning sessions and pools it has nothing to do with — exactly the misreading naming the scope exists to prevent, just at the wrong scope. Each pool's own bucket is smaller (burst 20, 5/s refill against the pre-session bucket's 50/20) because episode collapsing already does the heavy lifting: on a healthy proxy the steady-state write rate from this bucket is zero, and even a genuine incident produces a handful of records, so the bucket only needs to bound a caller cycling one pool between saturated and drained faster than the drainer absorbs new episodes. `details.suppressed_refusal_scope` reads `"session"` on every record this bucket rolls up — never `"proxy_category"` — so a reader never has to guess which of the two buckets a given `RESOURCE_EXHAUSTED` record's count came from.

The same **claimed, never asserted** rule reaches one record that is not a pre-session refusal at all. A killed session is torn out of the registry proactively, so its id stops resolving — yet the kill contract is that its requests are denied `KILL_SWITCH` rather than answered with a bare `404` that hides why the session vanished, so that denial is rendered from the raw `Mcp-Session-Id` header of a session the proxy can no longer look up. A caller holding any valid-but-unrelated credential (a route's shared bearer, or any JWT valid for that route's audience) could therefore put an arbitrary — including a real victim's — id in that header and, whenever the kill check fails closed (an active global stop, or a kill-store error), have it signed into `session_id` as fact. It is recorded as `details.claimed_session_id` with `session_id` left empty, exactly like the pre-session family. Which of the two treatments a kill record gets is a **type-level** choice rather than a convention an author has to know: the recorders take a session *subject* that can only be built from an id this proxy established or from the request itself, so a call site added later must state which of the two it holds, and there is no way to spell "this header is verified".

The emergency stop is recorded on **both** sides of the decision. A refused probe of `/control/kill` lands as `CONTROL_AUTH_FAILED` (wrong or missing token) or `LOOPBACK_REJECTED` (off-host source), and a **successful activation** lands as an `allow` record carrying the method `control/kill` and `details.scope` — the killed session id, or `all` for a whole-proxy stop — plus `details.source_ip`. It is written after the kill-store write succeeds — so the tape never attests a stop that did not take effect (a kill-store failure returns `500` and records nothing) — and *before* the SSE eviction and session teardown, which reclaim resources rather than effect the stop. The kill is in force the moment the store write returns, while the teardown waits on every session's close and is bounded only by the shutdown budget, so recording after it left a window in which a crash produced a tape full of `KILL_SWITCH` denials with no activation record to explain them. Without it the tape showed the *consequences* of an emergency stop — a run of `KILL_SWITCH` denials — with no signed evidence of when the stop was tripped or that it was authorized, which is precisely the question an incident reconstruction asks first. The record follows the same non-disclosure rules as the refusal path: the control token is never recorded, and the structured `session_id` is left empty — a global stop addresses no single session, and a targeted one names its session in `details.scope`, where it cannot be mistaken for an authenticated session binding. `control/kill` is deliberately not an MCP method, so `target_type`/`target` stay empty rather than fabricating a phantom target from the method string, and the `suggest` subcommand skips it for the same reason it skips the non-policy denial codes.

Only a **truly absent** `Origin` header is allowed unconditionally — non-browser MCP hosts (the stdio bridge, CLIs) do not send one. Every *present* value must appear in the allowlist, including a present-but-empty `Origin:` and the opaque `null` origin: both are reachable from sandboxed/`file:`/`data:` browser contexts, so neither is trusted by default. The built-in allowlist accepts an origin whose **scheme is `http` or `https`** (case-folded) and whose host is a loopback name (`localhost`, `127.0.0.1`, `[::1]`) or equals the configured `listen.bind` host (a wildcard bind — `0.0.0.0` / `::` — does not widen the allowlist). Restricting the host-set path to the web-origin schemes keeps it inside the RFC 6454 serialized-origin grammar (`scheme://host[:port]`): a non-web scheme (`file://localhost`), a scheme-relative reference (`//localhost`, empty scheme), or any other scheme on a trusted host is **not** trusted by default, matching the opt-in posture already applied to `null`. Operators serving a trusted browser front-end add its origin via `listen.allowedOrigins` (full origins, e.g. `https://app.example.com`, matched case-insensitively); a genuine `file:`/sandboxed front-end that needs the `null` (or a non-`http(s)`) origin must opt in explicitly by listing it there. An unparseable, hostless, or non-`http(s)` `Origin` fails closed.

**Second layer (JSON-only request bodies):** both POST endpoints — `/mcp` and `/control/kill` — require a request `Content-Type` of `application/json` (parameters such as `charset` are accepted; the media type is matched case-insensitively) and reject anything else with `415 Unsupported Media Type`, failing closed on an absent, unparseable, or duplicated header. This is defence in depth behind the `Origin` check rather than a second copy of it. The browser's CORS rules make a POST carrying `text/plain`, `application/x-www-form-urlencoded`, or `multipart/form-data` a **simple request**: it is dispatched with no preflight, so a page on any local port can emit one and simply ignore the response it is not allowed to read. Every *session-bound* `/mcp` POST already forces a preflight through its custom `Mcp-Session-Id` header, and `/control/kill` through `X-Eunox-Control-Token`; the sessionless `initialize` POST — the one request that legitimately carries no custom header, and the one that spawns an upstream subprocess — was the remaining shape that could reach a handler without one. Requiring a JSON content type puts it behind a preflight too, so the `Origin` check is no longer the only control standing between a same-host page and a session-creating POST. Conformant MCP clients already send the header (the Streamable HTTP transport requires it), so no honest host is affected. The refusal **is** recorded on the tape, as `UNSUPPORTED_MEDIA_TYPE`, through the same rate-limited bucket that carries `ORIGIN_REJECTED`: the gate sits behind the transport credential on both endpoints — `listen.authToken`/JWT for `/mcp`, the control token for `/control/kill` — so where either is configured this is an *authenticated* caller's refusal, and where neither is, the token bucket is exactly what makes an anonymous caller's refusals safe to write. Only the header *count* is recorded, never the attacker-supplied value. A duplicated header additionally prints a one-line `[eunox] SECURITY:` diagnostic, because a reverse proxy that re-adds `Content-Type` is the one way an operator trips this through no fault of their client, and a silent 415 on every POST is otherwise near-impossible to diagnose. The same shared decode path also rejects a body that passes the content-type gate but fails to parse as JSON, or that carries a trailing token after one valid JSON value (a `400`, guarding against a smuggled second value such as a legitimate `{"sessionId":"..."}` followed by `{"all":true}`); both legs are now recorded too, as `INVALID_REQUEST`, through the same rate-limited bucket — a malformed or multi-value body on either endpoint is the same class of transport-surface probe as a rejected `Content-Type`, and was previously the one refusal on this path visible only as an HTTP status. Both codes are written on `/control/kill` exactly as described above (unstamped, no route to name); on `/mcp` both are written through the **already-resolved route's** sink — `handleMCP` 404s an unknown upstream before either gate runs, so by the time a `/mcp` body reaches them the route is not merely knowable but already known, and leaving the record unstamped would misrepresent that as a pre-route refusal like `ORIGIN_REJECTED` or `JWT_INVALID`, which genuinely fire first.

**Residual risk:** Origin validation defends the browser-driven rebinding path specifically. A non-browser process running on the same host can still craft requests with an allowed `Origin` (or none); for `/mcp` that local-process threat is mitigated by `listen.authToken`, and for `/control/kill` by the loopback-source check **plus** the required control token (§3.3, SEC-07) — so a same-host process can no longer trigger the emergency stop without reading the 0600 token file. Binding to a non-loopback interface (`--unsafe-bind-all`) widens exposure beyond what Origin validation addresses and should be paired with `authToken` and network controls.

### 3.8 Tool Description Poisoning (Tool Poisoning)

**Attack:** A compromised or malicious MCP server returns a `tools/list` response in which the `description` field of a permitted tool contains injected instructions. The model reads the description before deciding whether and how to call the tool; a poisoned description can steer the agent toward specific call patterns, supply fake argument examples, or include override instructions that redirect the model's behavior across all tools in scope (cross-tool steering).

This class was described by Invariant Labs (2025) and applies even after eunox's list filtering: filtering removes unauthorized tools, but within the allowed set the model still sees whatever the upstream sends.

**Mitigation — description hash pinning (`descriptionHash`):**

Exact-name `tool:` constraints in the manifest may carry an optional `descriptionHash: sha256:<hex>` field. The hash covers a tool's full **model-facing instruction surface** — its top-level description, the root `inputSchema`'s own description, *and* the description of **every** input parameter, at any depth, under **any** subschema-valued JSON Schema keyword: `properties`/`patternProperties`, array `items`/`prefixItems` (single and tuple), `$defs`/`definitions`, `dependentSchemas`/`dependencies` (draft 2019-09 and its draft-07 predecessor), the `allOf`/`anyOf`/`oneOf` combinators, and the applicator keywords (`additionalProperties`, `unevaluatedProperties`, `propertyNames`, `contains`, `not`, `if`/`then`/`else`, `contentSchema`, …). A parameter description is fed to the model exactly like the top-level description, so a poisoning payload moved into *any* description string — including one buried under an applicator keyword — must not evade the pin. The per-location path keys are length-prefixed and framed so two distinct locations can never collide (a property literally named `$defs` cannot mask the real `$defs` section). Recursion into the schema is depth-bounded and fails closed past the bound (an adversarial deeply-nested schema forces a distinct hash rather than exhausting the stack). The structural shape of the parameters (names, types, `required`) is deliberately excluded so this always-fatal pin does not fire on benign schema evolution; that divergence is covered separately by FM-6 (below). When set:

1. **At startup (drift check):** `CheckManifestDrift` computes the SHA-256 of the live description and parameter descriptions from `tools/list` (via `ComputeToolHash`) and compares it against the pinned hash. A mismatch is classified as **FM-5** and aborts proxy startup unconditionally — it is not gated by `--strict-drift`. The finding is logged to stderr before the abort so operators see which tool changed. If `tools/list` is unavailable at startup and any pinned hash exists in the manifest, startup is also aborted — the proxy cannot confirm description integrity. When the drift check runs **per session** (the HTTP/gateway transport probes the upstream on each new session, and the stdio transport at session start), a refusal additionally writes a signed `DRIFT_REFUSED` audit record before the session is torn down, so the tool-poisoning event lands on the tamper-evident trail (and any external sink) rather than only on stderr and a generic `500`. Following the `JWT_INVALID` non-disclosure discipline, the record carries the stable `DRIFT_REFUSED` category, not the raw drift reason (which names the drifted tools); that reason stays on stderr where `CheckManifestDrift` already logs it.

2. **At runtime (list filtering):** When the proxy filters `tools/list` responses, any tool entry whose live description does not match the pinned hash is excluded from the filtered response. The model never sees the poisoned description and therefore does not invoke the tool. As each `tools/list` response is walked, the proxy also records the SHA-256 of each tool's live description.

   This recording pass is a security control, not best-effort bookkeeping: when any pin exists, a `tools/list` the proxy cannot reduce to a comparable hash for a pinned tool **fails closed** by sticky-poisoning the affected pin(s). It matters most on an observe (`--audit`) route, where the catalog is forwarded verbatim and this pass is the only thing arming the mid-session pin. One shared pass arms the pins for both the observe route and the enforce-mode filter, so the two cannot diverge, and it runs to completion **before** any filtering — a poison discovered at the last entry must already be visible to the keep decision for the first, or the emitted catalog could advertise a tool whose call leg then hard-denies.

   The decisive detail is that the proxy and the host may not read the same bytes the same way, so what "cannot be reduced to a comparable hash" means is deliberately wide:

   - **Duplicate keys**, at the top level or nested inside a hashed parameter description. `encoding/json` keeps the last value, so `{"description":"<INJECT>","description":"<CLEAN>"}` hashes clean while a first-key-wins host renders the injection.
   - **Case-variant sibling keys.** Go binds object keys to struct fields *case-insensitively* and keeps the last match, so `{"description":"<INJECT>","Description":"<CLEAN>"}` also hashes clean while a case-sensitive host (`JSON.parse`, the Python SDK) renders the injection. Top-level keys are therefore compared **case-folded**; nested keys, which decode into an exact-keyed map, are compared exactly — sibling schema properties differing only by case are legal and honest.
   - **An entry that will not decode** into the hashed surface, or whose name is duplicated or case-variant (which would let it present one name to the proxy and another to the host).
   - **An ambiguous envelope** — undecodable, an undecodable `tools` array, or a duplicate or case-variant `tools` key.

   The scan captures each value's raw bytes rather than tokenizing them, so an adversarial float64-overflowing number (`1e999`) cannot error the walk and shield a later duplicate, and its depth bound is kept deliberately **looser** than the hashed surface's own bound so an honest deeply-nested schema is resolved by a hash mismatch rather than a spurious duplicate verdict.

   Blast radius is scoped to the evidence: an ambiguity confined to one entry poisons only the pinned names *that entry could present*, so an unrelated malformed entry cannot disable pins it never named; only a whole-response ambiguity poisons every pin. This matters because the mark is sticky until restart and one per-route policy is shared across every session. A plainly absent `tools` key is not ambiguous — a host renders no tools from it — so it poisons nothing.

**Mitigation (Tier-2 interface pinning — automatic, no manifest entry required):** `descriptionHash` covers only the tools an operator remembered to pin, which leaves the poisoning surface open on every unpinned tool. Tier-2 closes that by **auto-baselining the advertised surface of every tool a session sees** — the same `ComputeToolHash` over the same model-facing bytes — and re-diffing it on every later `tools/list`. A tool whose surface changes mid-session is a **pin break**: a hard `AUTHORIZATION_FAILED` on the call leg (not downgradable under `--audit`) and hidden from `tools/list`, so the catalog a host is shown never advertises a tool its call leg will reject. The break is sticky within the session, because an upstream that rotates a description back would otherwise re-open the call leg for a host still holding the rewritten copy.

The baseline is scoped **per session** and released on teardown. Within a session, an advertised surface changing is anomalous — servers evolve across restarts, not mid-conversation — while a per-process baseline would let one session on a shared per-route PDP poison every other session until restart. Recovery from a false positive is therefore a new session, not an operator intervention, which is why Tier-2 ships on by default with no off switch: the blast radius of a wrong verdict is one session, and an off switch is a fail-open an operator would reach for exactly once. A tools/list entry whose bytes cannot be trusted to decode to what a host renders cannot be baselined at all, so it fails closed by breaking the names it could be presenting; an unreadable envelope breaks every tool the session had baselined.

Adds and removes are **advisory**, not breaks: MCP supports a changing tool list explicitly (`notifications/tools/list_changed`) and a new tool is still gated by the manifest allowlist, so denying on one would be a false positive with no security gain. An added tool is baselined on sight, and a removed tool's baseline is retained — so a tool that disappears and returns with a rewritten surface still breaks.

**Honest limit:** Tier-2 is pure **metadata** comparison. It catches description poisoning and silent interface drift. It does **not** catch a rug pull where the advertised interface is unchanged and only the upstream's *behavior* differs; that is behavioral, detecting it would mean watching server behavior, and eunox verifies attestations rather than monitoring servers (§4.5). The break's own log line states this non-coverage inline so an operator reading it cannot mistake Tier-2 for a general anti-tamper guarantee. See `docs/interface-pinning-tier2.md`.

3. **At runtime (call leg):** `tools/call` enforcement (`ManifestPDP.Decide`) also checks `descriptionHash` for a pinned exact-name `tool:` constraint, against the description most recently observed at the list-filter step. If the upstream rewrites a tool's description **after the session started** and the host re-lists, the changed description is recorded and a subsequent `tools/call` to that tool — even one issued by name without re-listing — is denied (`AUTHORIZATION_FAILED`), closing the gap where the list filter hid the tool but the call leg still forwarded it. The pin is keyed off the pinned **name** and evaluated **before** capability selection, so it fires even when no constraint is selected for the caller (a principal-scoped pinned entry whose claims do not match, or a shadowing non-pinned sibling): a genuine poisoning stays a hard `AUTHORIZATION_FAILED` rather than falling through to a downgradable no-match/action deny that an observe route would forward to the poisoned upstream. A description not yet observed via `tools/list` is **not** denied on the call leg: the startup drift check (step 1) already verified every pin against the live upstream before the session was handed to the host, and is fatal on mismatch, so the start-time verification is authoritative until a `tools/list` re-observes the tool. Once a pinned tool has been observed poisoned, the deny is **sticky**: a later `tools/list` returning the clean description does **not** re-open the call leg, and the tool stays hidden from the list, until the proxy restarts. This is deliberately fail-closed for a pin — in HTTP mode one per-route policy is shared across every session's upstream instance, so without the sticky mark an honest session serving the clean description could otherwise clear the record and re-admit a concurrent session whose upstream instance is still poisoned. A legitimately changed-then-reverted pinned description therefore requires a restart (or an updated pin). Only `tools/list` carries descriptions to record this way; `resource:` and `prompt:` targets do not support `descriptionHash`.

4. **In `validate --live`:** The FM-5 finding appears in the WARNINGS section of the drift report, counted in the exit-1 summary.

**Populating hashes:** `eunox init --pin-descriptions` computes and embeds `descriptionHash` for every tool it discovers, so the operator gets a ready-to-review manifest with descriptions already pinned to the current upstream.

**Scope and coverage:**

`descriptionHash` is only supported on exact-name `tool:` targets. The manifest loader rejects the field on `resource:`, `prompt:`, and glob targets:

- **resource:/prompt: rejected at load** — FM-5 startup verification fetches `tools/list` only; a `descriptionHash` on a non-tool target would create a false sense of protection with no startup enforcement. These target types are not currently supported and the manifest loader will error.
- **Glob targets rejected at load** — a single hash cannot represent the description of every tool a glob like `tool:read_*` might match. Use exact-name entries with `--pin-descriptions` to get coverage.

| What `descriptionHash` covers | What it does not cover |
| ----------------------------- | ---------------------- |
| Description text, the root `inputSchema` description, **and every parameter description**, at any depth under any subschema-valued keyword (`properties`/`patternProperties`, `items`/`prefixItems`, `$defs`/`definitions`, `dependentSchemas`/`dependencies`, `allOf`/`anyOf`/`oneOf`, and applicators like `additionalProperties`/`propertyNames`/`contains`/`not`/`if`/`then`/`else`) of individually named `tool:` entries | Structural `inputSchema` shape (names/types/`required` — see FM-6); response body of `tools/call` |
| Startup FM-5 check (tools/list at proxy start) | Resources and prompts (would require fetching their list surfaces at startup) |
| Runtime: tools removed from filtered `tools/list` on mismatch | Description content inside `tools/call` results (not currently inspected) |

**Structural drift (FM-6):** The description hash intentionally ignores the parameter *shape*. To catch a tool whose argument surface changes, a constraint may declare an `argumentSchema`; at startup and in `validate --live`, FM-6 warns when the live `inputSchema` grows a parameter a **closed** schema (`additionalProperties: false`) did not declare — a new, unreviewed argument — or when a declared parameter's concrete type changes incompatibly. The check applies only to **exact-name `tool:` targets** (like the description pin): a glob's single `argumentSchema` cannot be a closed enumeration of every tool it matches, so running the added-parameter check against a glob would systematically false-positive. It recurses into nested object parameters (a new field under a nested `additionalProperties: false` is caught with a dotted path like `options.exfil_to`). It does *not* fire on a parameter a condition already references (the operator reviewed it), on a *disappeared* declared parameter (that is FM-3), or on a policy-compatible type change such as `number`→`integer` (an integer validates against a number schema). `eunox init` scaffolds `additionalProperties: false` so the added-parameter check is armed out of the box; relax it for a tool that legitimately takes open-ended arguments. Unlike FM-5, FM-6 is advisory by default and fatal only under `--strict-drift`, because benign schema evolution is common. Pairing `argumentSchema` with `additionalProperties: false` also fails the dangerous *call* closed at enforce time, regardless of whether the structural change was noticed.

**Recommended defense stack:** description pinning is one layer. Pair it with:
- **Supply-chain pinning:** pin the MCP server binary hash or container image digest in your deployment manifest so the server itself cannot be silently replaced.
- **Model-layer guardrails:** semantic content scanners (Invariant, Lakera, etc.) for instructions that bypass token-level checks.

**Residual risk:** An operator who has not set `descriptionHash` receives no protection from this mechanism. Use `eunox init --pin-descriptions` to populate hashes automatically from a live upstream, then review the generated manifest before committing it.

### 3.9 Transport Resource Exhaustion (HTTP listener and stdio→HTTP bridge)

**Attack:** §3.6 bounds the *backend* call rate; this class is exhaustion of the *proxy's own* memory, goroutines, and upstream connections by a host that drives the transport rather than the tool surface. Two paths are unbounded without explicit caps:

- **SSE subscriber fan-out per session.** A client opens many concurrent `GET /mcp` streams against a single `Mcp-Session-Id`. Each stream registers a subscriber channel (16-slot buffer) on the session, so the per-session subscriber list and its buffers grow with the number of open streams — memory the `maxSessions` cap does not bound, because it is all charged to one session.
- **Fire-and-forget POSTs on the stdio→remote-HTTP bridge.** The bridge that lets a stdio host reach an HTTP upstream POSTs each host request/notification on its own goroutine and returns before the POST completes. A pipelining host can spawn an unbounded number of in-flight POSTs, each holding a request body and an upstream connection (the response buffer is only 64 deep).
- **Unbounded handler goroutines on the stdio host loop.** The stdio proxy dispatches each host request to its own goroutine so the read loop stays free to route the host's replies to server-initiated requests. Without a cap, a pipelining host — especially against an upstream that never answers under `--upstream-timeout=0` — grows handler goroutines and the `hostToUp`/`byUpstreamID` maps without bound, since each in-flight request holds a map entry until it completes or times out.
- **Concurrent session *establishment* past `maxSessions`.** The cap bounded sessions that had finished REGISTERING, but establishment — upstream spawn, `initialize` handshake, drift `tools/list` probe — runs for up to `sessionStartTimeout` before registration. A registry-only pre-check therefore admitted every concurrent `initialize` arriving against an empty registry: each spawned an upstream subprocess/connection, and only `maxSessions` of them registered while the rest were torn down *after* their handshake. PID/FD/memory exhaustion despite the cap, repeatable every window, and contradicting the flag's own documented "refused with `503` rather than spawning". Reachable pre-authentication on an unauthenticated non-loopback bind.
- **Unbounded in-flight requests per HTTP session.** The network-exposed HTTP transport dispatches each enforced `POST /mcp` into a handler goroutine that allocates a reply channel plus `hostToUp`/`byUpstreamID` map entries and blocks in the upstream round-trip. `maxSessions` bounds session count and `maxSubsPerSession` bounds SSE streams, but per-session *request* concurrency was uncapped, so after one `initialize` a client POSTing concurrently on many connections — especially against a slow/silent upstream under `--upstream-timeout=0` — grew goroutines and per-session map entries without bound. This is the same failure the stdio `hostSem` prevents, on the more-exposed transport.

**Mitigation:**

- **Per-session SSE subscriber cap (`maxSubsPerSession`, 8).** `handleMCPGet` registers the subscriber *before* writing the `200`/SSE headers and rejects an over-cap stream with `429 Too Many Requests` (an error status is still possible because no `200` has been written yet). This bounds the per-session subscriber list and per-subscriber buffer independent of `maxSessions`. A well-behaved host opens a single stream for the session lifetime; a disconnect frees the slot. The same list is what server-initiated requests (`sampling/createMessage`) scan for a single recipient, so capping it also bounds that scan.
- **Bounded per-chunk SSE write deadline.** The cap above only bounds slot *count*; it relies on each slot eventually freeing. A stuck reader (a TCP zero/tiny receive window that never drains, not a clean disconnect) could otherwise defeat that: once the 16-slot subscriber buffer and the kernel send buffer fill, the next delivery `Write` blocks indefinitely, parking the goroutine outside its `select` so it observes neither kill-eviction, idle-reap, nor context cancel — pinning the goroutine and permanently consuming a `maxSubsPerSession` slot. An attacker opening 8 zero-window streams per session could wedge every slot and block legitimate notification delivery. The delivery loop therefore re-arms a bounded write deadline (`sseWriteTimeout`) before each `sseWriteChunk`-sized write instead of clearing the connection deadline permanently, so the deadline measures forward progress rather than whole-frame wall-clock (a slow-but-progressing reader is not killed mid-frame; a no-progress reader still trips it). It returns on any write or flush error — which runs the unsubscribe/drain defer that frees the slot — and, for a server-initiated request consumed from the buffer before the failed write, replies an error to the upstream itself so that request does not hang until the idle reaper. A keepalive comment frame, emitted once immediately at stream open and then every `sseKeepaliveInterval`, re-arms the deadline on an otherwise-idle stream so a wedged reader is detected within `sseKeepaliveInterval + sseWriteTimeout` (and from stream open, not only after the first interval) rather than only at the next upstream notification.
- **Single response-write deadline rule (floored at `httpWriteTimeout`).** Every response-write deadline on the HTTP transport is armed by one helper (`rearmWriteDeadline`, its Duration spelling, and the teardown spelling that doubles a `--shutdown-timeout` budget for a leg waiting on two sequential teardown bounds), whose window is the leg's own budget plus slack, never shorter than `httpWriteTimeout`. Hand-written per-leg windows are what produced the original defect in this area: a leg reaching its own write with the entry deadline already past drops the response for an operation that in fact succeeded, which is worst on the kill endpoint, where the operator reads a failure for an emergency stop that took effect. The floor is load-bearing on its own — a write deadline bounds how long the *client* may take to read a response, which is unrelated to how long the *upstream* was given, so a deployment running a small `--upstream-timeout` no longer gets a proportionally small window for its writes (a 50 ms upstream budget used to arm just over five seconds at handler entry). One consequence is deliberate and worth stating rather than leaving implicit: the entry deadline is also the Slowloris backstop over the pre-dispatch writes (the 202 ack, an early 4xx, a kill or audience denial), so a deployment running `--upstream-timeout` well below 30s now gives a slow-reading client the 30s floor there too instead of its own smaller budget. That is the intended trade — those writes are a few hundred bytes on a connection the server can close, and the alternative is a deployment-specific window on a leg whose duration has nothing to do with the upstream budget. The per-chunk SSE deadline is deliberately NOT this rule: it is a forward-progress bound re-armed per write, and folding it into the response-write helper would kill a slow-but-progressing reader mid-frame.
- **Bridge in-flight POST cap (`maxInflightPosts`, 64).** A semaphore bounds concurrent POST goroutines on the bridge: once the cap is reached the next spawn blocks until a slot frees (backpressure) rather than growing without bound, and drops on bridge close. The cap matches the 64-slot response buffer so the two limits do not fight. The bound is fail-safe — the acquire also unblocks on the per-call context (so `--upstream-timeout` still cancels) and on bridge shutdown — and because the bridge never delivers server-initiated requests, backpressuring host writes cannot wedge the read loop against a slot that never frees.
- **Stdio host-request in-flight cap (`maxConcurrentHostRequests`, 256).** `serveHost` acquires a non-blocking semaphore slot before dispatching each request goroutine and releases it when the handler returns; on saturation it replies a structured, retryable server-busy error (JSON-RPC `-32000`) to the host instead of spawning. The acquire is deliberately non-blocking — the read loop must keep routing host replies to server-initiated requests, so it can never stall on a full pool — so unlike the bridge POST cap this one sheds the excess request rather than back-pressuring the producer. This bounds handler goroutines and the `hostToUp`/`byUpstreamID` maps even under `--upstream-timeout=0` against a silent upstream.
- **HTTP per-session in-flight request cap (`maxConcurrentSessionRequests`, 256).** `handleSessionPost` acquires a non-blocking per-session semaphore before dispatching each enforced request and releases it when dispatch returns; on saturation it replies the same retryable server-busy error (JSON-RPC `-32000`) instead of spawning, the HTTP analogue of the stdio `hostSem`. This bounds handler goroutines and the per-session `hostToUp`/`byUpstreamID` maps on the network-exposed transport even under `--upstream-timeout=0`. `initialize` answers locally without an upstream round-trip and is not subject to the cap. Related: an in-flight enforced request also defers the idle reaper (tracked per session), so a legitimately long-running call is not torn down mid-flight while `lastActive` sits stale.
- **Reservation-based session cap.** The `maxSessions` slot is taken *before* the upstream is spawned and held across the whole of establishment, so the cap counts registered sessions **plus** those still establishing. Over-cap `initialize` requests are refused with `503` without starting anything, which is what the flag documented all along. The reservation has exactly one owner — the request handler takes it and releases it unconditionally on every path, and registration does not consume it — because establishment can fail *after* the session registers (the startup drift refusal registers, probes, then tears down): a second releaser cannot know whether the slot it is dropping is its own, and dropping a concurrently-establishing session's slot silently re-admits the over-spawn. Between registration and release a session is counted twice, which errs toward refusing one extra `initialize` rather than admitting one too many.
- **Bounded upstream subprocess write (sampling + write-wedge deadlock).** A sampling-capable subprocess upstream that issues `sampling/createMessage` and then stops draining its stdin while awaiting the reply can fill the pipe buffer, blocking a proxy→upstream write. Because the framed writer serializes writes under one mutex held across the blocking pipe write, that wedged write used to hold both the writer mutex and — on stdio, whose single serve loop is the sole router of host responses to server-initiated requests — a wire-ordering-barrier slot; a subsequent host notification then parked the serve loop on the barrier, and the sampling reply that would unblock the upstream sat behind the parked loop, hanging the session until SIGINT. The subprocess writer now carries a per-write deadline of `--upstream-timeout` (`mcp.NewMsgWriterWithTimeout`): a wedged write returns `ErrUpstreamWriteTimeout` and poisons the writer (a timed-out write can flush a partial frame and desync the newline framing, so the stream is not reused). Poisoning keys on the **byte count**, not on the deadline: any write that flushes only part of its frame — EPIPE from an upstream that died mid-write, ENOSPC, a signal interrupting a write larger than `PIPE_BUF` — desyncs the framing identically and latches the writer the same way. Poisoning invokes a teardown hook (`killUpstream` / the session's subprocess kill) that fires regardless of which write path first wedged — request, host->upstream notification, or the serve loop's server-reply relay — so the upstream is reaped and the session recovers instead of hanging, and the recovery is not limited to the request path. Deadline support is probed once at construction: where the platform rejects a pipe write deadline the bound is left unarmed and a one-time warning is logged, so the operator learns `--upstream-timeout` does not bound writes there rather than silently retaining the deadlock. `ErrUpstreamWriteTimeout` is classified as `UPSTREAM_TIMEOUT` (not the generic `UPSTREAM_ERROR`) on the host-facing error and audit record; a non-deadline partial frame carries a distinct sentinel (`ErrFrameDesync`) and is classified as `UPSTREAM_ERROR`, so an upstream that crashed mid-write is not recorded on the tape as a timeout with a fabricated duration — or, under `--upstream-timeout=0`, as having exceeded a deadline that does not exist. Under `--upstream-timeout=0` the write is intentionally unbounded (the operator's opt-out), and the interruptible barrier wait remains the residual "recoverable by shutdown" backstop. The stdio **host** writer (stdout) carries the same poison latch but no deadline, so it is constructed with its own teardown hook: its writes are fire-and-forget at every call site, and without an owner a single partial write would latch it silently — the proxy would go on deciding and forwarding allowed calls upstream, with real side effects, while every response was dropped and the host hung.

**Residual risk:** Both bounds are fixed memory/goroutine backstops, not per-tenant quotas. They cap a *single* session/bridge; aggregate exhaustion across many sessions is bounded separately by `maxSessions` and the idle-session reaper. A host that opens streams up to the cap on many sessions is still bounded by `maxSessions × maxSubsPerSession`.

### 3.10 Enforced-Method Smuggling via Notification Framing

**Attack:** JSON-RPC distinguishes a *request* (carries an `id`, expects a response) from a *notification* (no `id`, fire-and-forget) purely structurally — `IsNotification()` is `id == nil && method != ""`, with no allowlist restricting which methods may legitimately take notification form. `tools/call`, `resources/read`, `resources/subscribe`, `resources/unsubscribe`, and `prompts/get` are always requests in a well-formed MCP session, but nothing rejected one of these framed as a notification instead: a host omitting the `id` field on an otherwise-normal `tools/call` body caused the message to be routed to each transport's fire-and-forget notification-forwarding path (stdio's `forwardHostNotification`, the HTTP transport's notification branch in `handleSessionPost`), which forwarded it to the upstream verbatim after only a kill-switch check — never reaching `dispatchRequest`, so the PDP decision was skipped and no audit record (allow or deny) was written. A lenient upstream MCP server that processes notification-framed method calls would execute the tool the manifest would otherwise have denied, invisibly to the audit trail and to `--require-audit=strict`.

**Mitigation:** Both transports check the notification's method against the same enforced-method set `dispatchRequest` routes on for that peer's protocol revision (`methodRegistry` / `isEnforcedMethod`, `internal/transport/dispatch.go`) before forwarding. A match is denied and recorded (`INVALID_REQUEST`) instead of forwarded — the request never reaches the upstream, and the denial is a signed audit record like any other enforced-path deny. The check and its record live in a single shared gate (`hostNotificationGate.admit`) both transports call for every host notification, so the two cannot independently drift out of sync — nor can they drift in the ORDER they apply it, since that gate also carries the swallowed set, the kill check and the unmapped default in their one canonical sequence.

**Residual risk:** The denial record uses the raw method name as both the audit identifier and the target (mirroring `malformedDeny`'s pre-existing convention for params rejected before the PDP is consulted, since a notification-framed call's real target argument is not parsed) — for `prompts/get` this yields a `target` of `"get"` rather than a real prompt name. A consumer that keys off `denial_code` (as `suggest` already does via `IsInfraDenialCode`) is unaffected; a hand-rolled consumer that does not filter infrastructure-fault codes could misread this as a denied call to a tool/resource/prompt literally named after the bare method suffix.

### 3.11 Argument Smuggling via Duplicate JSON Keys

**Attack:** A request's `params` object could carry the same key twice — at the params root (`{"name":"safe","name":"dangerous"}`) or inside `arguments` at any depth (`{"path":"/safe","path":"/etc/shadow"}`). Go's `encoding/json` keeps the **last** value, so the PDP authorized one value while the transport forwards the caller's **original** params bytes verbatim to the upstream, and a first-key-wins parser (common outside Go) then acts on the **other** value. At the params root this is **tool-name** smuggling — the policy matches the manifest entry for one tool while the upstream dispatches another; inside `arguments` it is argument smuggling past an `allowedValues` / `argumentSchema` guard.

The same divergence arises from keys that are not byte-identical but differ only by **case fold** (`{"name":"dangerous","Name":"safe"}`). `encoding/json` binds object keys to struct fields by a case-folding match and keeps the last, so the proxy resolves `name` to `"safe"` and authorizes it, while a case-sensitive upstream reads the literal `name` key and acts on `"dangerous"`. A byte-exact duplicate check does not see these as duplicates at all, which makes the fold variant the more dangerous of the two.

**Mitigation:** The shared params decode (`mcp.DecodeParams`, the chokepoint the `tools/call`, `resources/read`, `resources/subscribe`, `resources/unsubscribe`, and `prompts/get` dispatchers all use) rejects a colliding object key at **any** nesting depth before decoding, failing closed — the dispatchers already treat a `DecodeParams` error as an `INVALID_REQUEST` deny with a signed audit record. Collision is judged by **Unicode simple fold**, not byte equality, so both the exact and the case-variant form are refused; the fold is a real simple-fold rather than a lower-casing, because U+017F (long s) folds onto `s` for the decoder while `strings.ToLower` leaves it distinct. The fold applies at every depth, not only at the struct-bound root, because the forwarded bytes are decoded by an upstream whose binding shape the proxy does not control — the cost is refusing an object that deliberately carries case-distinct siblings, which is a denial rather than a bypass. Rejecting rather than silently normalizing to last-wins is what keeps the **enforced view and the forwarded bytes in agreement**: the proxy never has to guess which value a differently-behaving upstream will read.

**Scope:** This covers the **request** direction. Response-direction `*/list` filtering is a separate control (§3.8); a duplicate or case-variant key in an upstream's list envelope is not addressed here.

### 3.12 Consequential Action Within Granted Capabilities

**Attack:** Every control above decides whether a call is *permitted*. None of them decides whether it is *survivable*. An agent acting on untrusted input — a support ticket, a scraped page, a returned tool result — can be steered into an action that is fully inside its granted capabilities and catastrophic anyway: `DROP TABLE customers` through a `query_db` whose `allowedOperations` legitimately includes `DROP`; a $5,000 refund through a refund tool whose whole purpose is refunds; four hundred individually-permitted small transfers. Identity says yes, the argument allowlist says yes, and the damage is in the **consequence**. This is the case per-call authorization structurally cannot reach, because there is no per-call fact that is wrong.

**Mitigation (effect contracts + a tool-agnostic ceiling):** A constraint may declare an **effect contract**: what a call to this target *does* — its reversibility class (`reversible` / `compensable` / `irreversible`), its blast radius (a fixed magnitude or the value of a named argument; a list contributes its length), whether it is idempotent, and what action compensates it. The **argument-parameterized** form makes effect a function of the call's own arguments as a *static decision table* — `SELECT` reversible, `DROP` irreversible — resolved on the decision path with no callout and no inference from payload content.

Two per-target conditions gate on that contract (`effectClass`, `blastRadius`), and a top-level **`effectCeiling`** additionally checks **every** allowed action against a consequence bound keyed on effect properties, never on tool identity. That placement is the control: a per-target condition guards only the targets someone remembered to write one for, so the tool nobody thought about is the one with no gate; the ceiling inverts it. Approval is triggered by *irreversibility or blast radius alone* — `requireCompensation` enriches an escalation already triggered by one of those with a `no_compensating_action` reason; it never independently turns an allowed call into an escalation (§3.12 below).

**The fail-closed default is what makes it work.** A target with **no** contract resolves to irreversible and unquantified, so it exceeds any ceiling and escalates — annotating a tool is what buys it out of maximum friction, and an unannotated one costs approval friction by default with no configuration. Likewise a call whose blast radius cannot be established is denied by a `blastRadius` bound rather than read as zero: an action whose size is unknown must not be treated as small. And `compensable` requires a declared compensating action **at load**, so the class cannot decay into a softer word for irreversible and slip past the gate — "there is an undo" is exactly how an irreversible action gets waved through. `effectCeiling`'s `requireCompensation` is checked the same way: it applies only to an action already *above* `maxEffectClass`, so `maxEffectClass` must be set to a class below `irreversible` (the top of the vocabulary, which nothing can ever be classified above) — both an unset bound and `maxEffectClass: irreversible` load-fail as a control that reads as active but can never fire, checked at load for a manifest and, for the exported ceiling seam that bypasses the loader, at evaluation.

**`escalate` is a refusal, not a pending state.** The in-path proxy holds no approval workflow (approval is the control-plane surface), so with none wired an escalation resolves fail-closed to *not forwarded*. Every forward gate in the proxy tests `!= DecisionAllow`, so this holds structurally rather than by a check that could be forgotten. It is a hard refusal with `AuditOnly` deliberately unset, so a route running `--audit` cannot turn "needs human approval" into "performed anyway, logged" — the one downgrade that would defeat the control entirely.

**Audit.** An escalation is recorded with `decision: escalate` — an additive value of the existing `decision` field, not a new top-level field, so the signed-record schema is unchanged and `audit-verify`'s unknown-field rejection still holds. The value is **derived inside the sink from the `ESCALATION_REQUIRED` denial code** rather than passed alongside it, so no call site can stamp one without the other. Its `details` carry the consequence inputs (`effect_class`, `blast_radius`, `compensating_action`, `ceiling_exceeded`, `annotated`) and the session's accumulated flow labels under `carried_labels` — the top-level field is reserved for allow records, but an escalation is the one refusal a human is expected to act on, and *which provenance produced this* is the first thing they need. That is what ties the who-may-know axis to the what-may-break one on a single record. `eunox stats` tallies escalations separately, as the operator's approval queue rather than a policy defect.

**Ordering.** The ceiling runs after the matched constraint's conditions and **before** the session-state commit, so an over-ceiling call leaves neither a phantom `sequenceBlock` antecedent nor a stranded flow label — the same rule a hard deny obeys, for the same reason: it was never forwarded.

**Effect receipts — verifying an attestation, not watching a server.** A contract is an assertion, and nothing above checks whether a server behaves as it says. A server MAY close that loop itself: it publishes, in a tool RESULT's `_meta` under `io.eunolabs.effect-receipt`, a compact JWS carrying the same vocabulary a contract does (`tool`, `class`, `blastRadius`, `unit`, `compensatingAction`, `iat`). eunox verifies the signature against the key domain configured for **that upstream** (`effectReceiptKeys`, a local JWKS file read once at startup — never fetched), checks the statement against the contract the pre-call decision resolved, and records the verdict in `details.effect_receipt` (`verified` / `inconsistent` / `unverified` / `malformed`) with the attested values beside it. It rides the existing `details` field, so the signed-record schema is unchanged and `audit-verify`'s unknown-field rejection still holds.

The key domain is **distinct from the caller-authenticating JWKS** by design: a receipt is the upstream's statement about its own behavior, closer to package signing than to an access token, so tying it to the token issuer that authenticates callers would let any party who can mint a caller token also mint attestations about a server. Four properties are load-bearing. It is **verification only** — the declared block is read and nothing else, with no egress watching and no payload inference (§4.5). It **fails closed on trust**: an unsigned or unverifiable receipt earns nothing and puts **none** of its claims on the tape, and a receipt silent about a dimension the contract quantified records `inconsistent` rather than `verified`, because a forged "reversible, 1 row" recorded as fact would invert the control. It is **post-hoc, never retroactive**: the call already happened, so an inconsistency is evidence and an input to future friction, never a refusal taken after the side effect. And it costs **nothing when unconfigured** — no key domain means no parse and no record, so a non-supporting server changes nothing. Consistency is one-directional (a server reporting a smaller or less consequential action than declared is honoring the bound the decision was made against), and a contract that could not be resolved before the call has no bound to exceed, which is the genuinely runtime-dynamic case receipts uniquely carry. **Residual:** `iat` plus a freshness window BOUNDS replay rather than eliminating it — eliminating it needs a nonce eunox supplies on the request leg. That is adequate only while a receipt grants no friction reduction, which is the case today: nothing consumes a verdict as an authorization input. Any future mechanism that lets a receipt lower a bar must close the replay window first.

**Scope and honest limits.** This does not re-implement resource-layer RBAC; it covers the contextually-poisoned and the cumulatively-catastrophic-but-individually-permitted cases, over a database's own grants rather than instead of them. A contract is an **assertion** — by the operator's manifest, or copied from a reviewed registry entry and hash-pinned — and nothing here observes whether a server behaves as its contract says (§4.5); a receipt verifies what the server ITSELF states, which is a different claim and is recorded as such. The argument-parameterized table's verb matching is the same coarse first-token rule `allowedOperations` uses, with the same documented limit that it is not a SQL parser. Cumulative **velocity** ("no more than $2,000 an hour") IS expressible, via `blastRadius`'s `maxTotal`/`windowSeconds` pair over a weighted sliding-window sum (`CallCounter.AdmitAll` over a weight-summing bucket — the same seam `maxCalls` uses with an entry-counting one, not a second accounting system). Its bounds are the counter's: the budget is per `(session, target)`, an over-limit call records nothing (so a burst of refusals cannot extend its own lockout), a call whose weight cannot move the total is admitted without being recorded (zero was otherwise unbounded), the commit runs AFTER the effect ceiling so a call the ceiling refuses spends no budget, an unquantifiable call fails it rather than contributing 0 to the sum, and a bound above 2^53 is refused at load (compared in arbitrary precision, so it cannot round its way in) because the Redis backend's Lua arithmetic is float64 and would enforce a threshold nobody authored. Fractional magnitudes ARE summable — currency is the motivating case — within that double-precision contract. A cumulative bound and a `maxCalls` DO compose on one capability — "how much" and "how many" are different questions about the same call — because the two accountings are admitted in one atomic backend call, so neither spends the other's budget on a call the other denies; what is a load error is two bounds of the same kind on one window, which would share a physical bucket and halve the limit the manifest states.

### 3.13 Self-Service Declassification (Laundering a Flow Label)

**Attack:** Information-flow control (§3.2.1's cross-session sibling — the `flowLabel` sink over `labelOutput` sources) holds only while taint accumulates monotonically. Real policies need a way to *drop* a label: a review step, a redaction pass, a sanitizing transform whose whole point is that the data leaving it is no longer PII. The moment such a step exists, it is the single highest-value target in the flow layer — an injected agent that can invoke it clears its own taint and every downstream sink opens. Every other flow token fails toward more denials; this one fails toward more allows, so it is the only place in the layer where a bug is a leak rather than an outage.

**Mitigation (`declassify` + a verified human approval):** A `declassify` directive names the labels an action clears, and the clear happens **only** when the request carries a human approval covering every one of those labels at that exact target. With no covering approval the call is refused with `ESCALATION_REQUIRED` — it is **not** forwarded-without-clearing, because forwarding it would let an author write a declassification the proxy never performs and leave the next sink denying for a reason the policy says should not apply. The refusal is a **hard** one with `AuditOnly` unset, so a route running `--audit` cannot turn "no human has approved dropping this label" into "performed anyway, logged" — the same non-negotiable the effect ceiling's escalation carries, and the stronger case of the two: the forward would not merely perform the action, it would perform it while also clearing the taint that would have stopped the next one.

**The approval's key domain is the operator's, not the upstream's.** An approval rides the `mcp.declassify` claim of a token the proxy has *already* verified for signature, issuer, audience, and expiry against the operator-configured JWKS. That is the same reasoning that governs effect receipts in §3.12, applied in the opposite direction: a receipt is the *upstream's* statement about itself and therefore needs a key domain distinct from the caller-authenticating JWKS, while an approval is a statement by the *operator's own* identity plane and therefore belongs on exactly that JWKS. Neither reuses the audit tape's HMAC key, which attests eunox's own records and nothing else. No new trust root is introduced, and no fetch lands on the decision path.

**Scope rules, each fail-closed.** The grant's `target` is matched **literally** — a glob is refused at the token boundary, because a pattern would widen one human approval across every matching action, inverting how a glob fails in a policy allowlist. Its `labels` must be a **superset** of what the directive clears; a partial grant escalates rather than clearing the covered subset, since half-clearing leaves the operator believing a label is gone while a later sink still sees it. `approver` is **mandatory**: an approval with no accountable human is not human approval. A malformed grant rejects the **token**, rather than evaluating to a grant that covers nothing — which would turn an IdP template mistake into a permanent, invisible escalation loop with no error to grep for. And a request with no token carries no approvals at all, so a deployment with no approval integration escalates every declassification by default.

**Composition, and the host transport.** A wrapping PDP (the JWT layer) can refuse a call on its own terms and short-circuit above the manifest PDP, so the approval check would never run — and that refusal is a SOFT deny an `--audit` route downgrades to a forward. `HardenRefusal` therefore replaces such a refusal with the declassify escalation, exactly as it does for the effect ceiling: adding a token can never make a call run that the same manifest hard-refuses without one. Separately, an approval can only arrive on a validated JWT, which needs an HTTP listener — so a `declassify` directive on a **stdio host** is unsatisfiable by construction and is refused at startup rather than escalating on every call forever, the same posture the audience-pin check takes for the same reason.

**Ordering and atomicity.** The approval check runs on the allow tail, after the matched constraint's conditions and after the effect ceiling, but **before** the deferred-condition commit and the flow/antecedent write — so a refused declassification spends no quota slot, writes no `sequenceBlock` antecedent, and leaves the session's label set exactly as it found it.

**The clear is two-phase, and the second phase runs after the call.** The decision *authorizes* the clear and burns a single-use grant; it does not remove a label. The removal happens once the call has actually run and its (redacted) response is deliverable — past the last gate that could still refuse it, before the record that reports it.

That split is a security property, not bookkeeping. The transport releases the decision turn immediately after the PDP decision, deliberately, so the slow upstream forward is not held under it. A clear applied *inside* the decision was therefore visible to every concurrent decision for the **whole upstream round trip** — bounded only by `--upstream-timeout`, and by nothing at all when that is `0` — so a second request decided in that window read an already-clean label set, and a sink the taint existed to stop could be **allowed and forwarded while the sanitizing call was still in flight**. No compensating undo could close that: the undo ran after the round trip, which is after the window it was meant to cover.

**The second phase takes a handle, not a label set.** What the decision hands back is an opaque, single-use authorization carrying the labels it resolved; the commit accepts nothing else. That is what makes the bound above structural rather than documented: the first phase is where every gate lives — the approval's scope, the escalation, the single-use ledger — so a second phase that accepted an arbitrary list was an unauthorized clear primitive, and an embedder holding an engine could remove any label it named with no approval presented, no grant burned, and nothing on the tape to say so. The handle also carries the obligation: a caller that never commits leaves the session as tainted as it found it (fail-closed, a later sink over-blocks), and the one cost of forgetting — a single-use grant spent on a clear that never lands — is exactly what `_eunox_declassify_spent_approval_id` makes reconcilable. The burn deliberately stays with the decision even so: two concurrent decisions get two handles, so no per-handle flag could make a grant single-use across them, and the atomic ledger admission is what does.

Deferring the removal *removes* that window rather than narrowing it: the labels are never absent until the call that clears them has completed. `labelOutput` keeps committing inside the decision, and is safe there for the mirror reason — a call that taints and then fails leaves *extra* taint, which over-blocks. The **burn** of a single-use grant likewise stays with the decision, because it is the atomic test that makes "once" mean once and two callers must not both be able to reach it.

**Two things stop the deferral from opening the mirror race.** Removing a label a round trip after deciding to is only safe if it cannot remove a *different* call's taint, and the naive form of this fix does exactly that: a source read decided while the sanitizing call is in flight commits a fresh label, and a clear that re-reads the anchor at commit time then deletes it — brand-new tainted data laundered by an approval granted before that read existed, which a set store cannot detect afterwards because one occurrence of `pii` is indistinguishable from another.

So, first: **what to clear is a decision-time fact.** The authorized labels are intersected against what the anchor is carrying *inside* the decision's critical section, and the commit removes exactly that set without re-reading anything. A label asserted after the decision is not in it. This also means a no-op clear is resolved before the call is even forwarded — nothing is pending, no store round trip happens, and no declassification reaches the tape — and that `labels_cleared` can no longer disagree with the `carried_labels` on its own record.

Second: **a declassifying call keeps the decision turn** until its commit is done, so no second decision on the same state interleaves between the two phases at all. Every other call still releases before the forward. The cost is head-of-line blocking on that anchor for the length of one declassifying call, bounded by `--upstream-timeout` — which is the reason a deployment using `declassify` should not set that to `0`.

**The turn is keyed on the state anchor, not on the connection.** It has to be: under `WithTaskAnchoredState` the label set is keyed on the validated task, and two sessions can share one task, so a per-*session* turn did not span the state it was ordering — a source read on session B could interleave with a declassifying call on session A. The proxy hands out one turn per anchor (the validated `mcp.task_id` where the route anchors on the task, the session otherwise), resolved through the same claim lookup the engine's own key builder uses so the turn and the key cannot disagree. Under the default session anchoring the key *is* the session, so an operator who has not enabled task anchoring sees exactly the per-session mutual exclusion this replaces. The anchor is read from the **validated** token only; resolving it from an unverified one would let a caller choose which turn it takes, and therefore choose not to share one.

**A task-anchored session's sampling sink is refused when the session spans tasks.** A session has two legs that decide, and only one of them has a request in scope: the host leg reads the current request's validated claims, while the server-initiated leg — which has no host request at all — reads the claims captured at `initialize`. The session-owner pin compares issuer and subject, so it accepts two tokens differing only in `mcp.task_id`, and under `taskAnchoredState` that is two different state anchors on one session: a `labelOutput` source records its taint under the *request's* task, the sampling sink peeks the *session's*, finds it clean, and forwards the egress the label existed to stop. The anchor-keyed turn cannot catch that — the sampling leg's turn and its state key agree with each other and both disagree with the host leg; the turn's guarantee holds, it is the wrong key.

The refusal lands on the SINK rather than on the request. Each host request is decided, keyed and serialized on the anchor its own token names, which is correct however many the session spans — and spanning is a shape an operator legitimately needs, since an agent runtime multiplexing several tasks over one long-lived connection is normal and the whole reason task anchoring exists is that a task outlives a connection. What cannot be decided that way is the leg with no request in scope: which task a `sampling/createMessage` belongs to is genuinely undetermined there, and MCP defines no correlation field an upstream could use to say (one would also be an upstream-supplied input choosing which task's taint the sink peeks, which is the same fail-open with an extra step). So from the first request that resolves a second anchor, every server-initiated decision on that session is refused (`CONDITION_FAILED`, `condition_type: flowLabel`, `reason: session_spans_anchors`), STICKY for the session's life — the taint written under the other anchor outlives the request that wrote it — and hard, so an `--audit` route cannot downgrade it into the forward it prevents. A client needing sampling on such a route keeps one session per task; a client multiplexing tasks keeps every other guarantee and loses that one feature, loudly and on the tape. Routes that do not anchor on the task are unaffected: every request on such a session resolves that session, so no session can span anything.

**The turn is not something a session's reader may wait on indefinitely.** The server-initiated leg (`sampling/createMessage`) is decided on the session's single upstream-reader goroutine, which is also the only goroutine that delivers upstream responses — so waiting there for a turn held across another call's upstream round trip stalls every in-flight request on that session, and under task anchoring the holder can be a different session. That leg takes the turn with a bound and refuses the sampling request when it cannot get it: sampling is deny-by-default, so refusing one request is the cheap side of that trade, and deciding without the turn would be the fail-open the turn exists to close. It also does not COMMIT a declassification at all — "the host received the request" is not "the sanitizing action ran", and a server-initiated request is answered out of band — so a decision reaching it with a clear pending is refused rather than committed on delivery.

On **stdio** that wait was a deadlock rather than a stall, and the bound is what closes it. There the leg runs inline on the reader that must deliver the very response the turn holder is waiting for, so a declassifying host call and one `sampling/createMessage` arriving mid-clear wedge each other: it unwound when `--upstream-timeout` fired and **never** under `--upstream-timeout=0`. It did not require sampling to be permitted, either — the turn is taken before the sampling decision runs, so any upstream could wedge a `declassify`-using stdio proxy by emitting one such request at the right moment, including one the policy denies sampling to. Bounding it there needed the FIFO ticket to be genuinely **abandonable**: that transport serves its turns in proxy-receipt order, so a ticket taken and then dropped would have left a hole every later request on the anchor waited behind, trading a bounded stall for an unbounded one. The turn now skips an abandoned ticket, and both transports answer "what happens when the turn is held by a declassifying call" the same way.

**And on stdio the leg does not run on the reader at all.** The bound above turns a deadlock into a stall; it does not bound how OFTEN an upstream may provoke one. Because that reader is the proxy's only response-delivery path, an upstream emitting one `sampling/createMessage` per in-flight declassifying call cost the whole session the length of the bound each time — latency landing on calls with nothing to do with sampling, scaling with the call rate rather than with anything the operator configured, and requiring no sampling grant to trigger. Each server-initiated request is therefore handled on its **own goroutine**, so a handler waiting for the turn blocks only itself, with the bound kept as the backstop. Three things come with that. It needs a **concurrency bound of its own** — the upstream-facing twin of the host-request cap — so an upstream that emits requests faster than the host answers them cannot grow goroutines without limit; on saturation the request is refused to the upstream with a retryable server-busy error and the refusal is recorded (`RESOURCE_EXHAUSTED`), so a flood is visible on the tape rather than only on the wire. It gives up the **receipt ordering** those requests previously had by accident: two the upstream emits back to back may now reach the host in either order, and one may be overtaken by a notification received after it. Nothing in MCP orders independent server-initiated requests (a response is correlated to its request by id), and host-initiated traffic keeps every ordering guarantee it had — its receipt order is fixed where tickets are reserved, and its request/notification barrier is unaffected — but a future server-initiated method that *did* need ordering would have to establish it rather than inherit it. And teardown now **drains** those handlers before releasing session state, since draining the reader no longer implies they have finished: one still running would otherwise write its audit record into a closed sink, or read flow state that was just cleared. The HTTP transport keeps the bound alone: there the same shape costs one session's response path rather than the proxy's only one.

**Residual, across instances.** The turn is in-process. Two eunox instances sharing one Redis backend hold independent turns for the same task, so the interleaving above remains possible *between* instances. Closing it needs a distributed lease held across an upstream round trip — a store round trip on every declassifying call, and a new failure mode when the lease expires mid-flight — which is a different trade from the one this layer makes elsewhere; it is not implemented. What bounds the damage in that deployment is the decision-time intersection, which is a property of the decision rather than of any lock: the other instance's commit removes only labels *it* observed, so a label asserted after its decision survives. What it can still clear is a label both were carrying, which is the reading a shared task arguably asks for — the task is one unit of work, and an approved sanitization of its context clears its taint. Stated rather than implied away.

The commit runs on a context detached from the request's cancellation but **not** from its values. Both halves are load-bearing: a client that disconnects while its response is being assembled cancels the request context, and a context-honouring store would then drop the clear for a call that really ran; and the state anchor resolves from the request's validated claims, so a fully detached context would clear the *session* key for a task-anchored call — leaving the task tainted while deleting a label the session never asked to drop, and reporting success.

**Audit.** An approved declassification is an **allow** carrying three additive top-level fields — `labels_cleared`, `approver`, and the control plane's `approval_id` — which appear together or not at all and which no other record shape carries — that is what makes it a distinguishable event on the tape rather than an allow that quietly dropped a label. **All three are covered by the record HMAC**, so neither the cleared set, nor the approving human, nor the approval identifier can be rewritten after the fact. `approval_id` is a first-class signed field like the other two, *not* a `details` key: it is the value that joins a tape entry back to the approval workflow that produced it, so a consumer that looked for `details.approval_id` would find nothing and lose exactly the reconciliation the field exists for. `labels_cleared` reports what the **commit** actually changed (the intersection with what the anchor was carrying), not what was authorized: an approval to clear a label the session never held is a permitted no-op that stamps no approver, because the tape must not record a declassification that did not happen. `eunox stats` counts declassifications separately, as the other half of the approval queue.

**A declassification that is authorized and then refused.** Three gates below the decision refuse a call without delivering a response: the `--require-audit=strict` gate, an upstream transport failure, and a redaction failure. None of them commits the clear, so the labels were never removed and there is nothing to undo. They differ on whether the sanitizing action HAPPENED, which is a separate question from whether the response was delivered: the strict gate blocks before the forward, a transport failure can follow a side effect that already landed, and the redaction gate is reached only after a reply came back — so only there can the proxy sometimes say the action executed, and only when that reply passes the same success test the commit path uses (a reply flagged `isError`, one carrying an error member beside a result, or bytes this build cannot interpret all read as "did not happen"). The session is exactly as tainted as the calls it actually made.

Two facts still reach the tape, in `details`, on the refusal record — and on the record for a call that ran but failed, which is handled identically. `_eunox_declassify_not_applied` names the labels the approved clear did not remove, so a reader can tell this from a call that never asked for one; on the redaction-failure gate a third joins them, `_eunox_declassify_result_withheld`, whenever that gate's reply shows the action having succeeded — the one exit where the proxy can say it executed. `_eunox_declassify_spent_approval_id` names a **single-use** grant the decision burned, which stays burned — the burn is atomic with the decision and has no un-burn, so a refused call spends the operator's one-shot approval and they must mint another. Both keys carry the reserved `_eunox_` prefix, because two of the four declassification detail keys ride an **allow** record whose `details` is the caller's own argument map in audit mode, and `eunox suggest` mines that map as argument names. The prefix alone is not enough, though — a client can *send* an argument with that name. So the transport quarantines any caller argument in eunox's reserved namespace under `_eunox_reserved_arguments` before the record is built: the argument is preserved (an auditor should see what was really sent) but cannot land where it reads as a statement the proxy made. Without that, any caller could forge the `ATTENTION` line `eunox stats` raises on `_eunox_declassify_commit_failed`, or bury a real one under repetitions, on a proxy where no declassification ever ran.

**Detail keys, one provenance each.** `_eunox_declassify_spent_approval_id` says a one-shot grant was burned — on a clean clear, a no-op clear, and a refused call alike, because the grant is spent in all three. `_eunox_declassify_not_applied` says a refusal below the decision meant the clear never ran (benign: nothing is under-tainted). `_eunox_declassify_result_withheld` says the action EXECUTED and eunox dropped its result. It is stamped only at the redaction-failure gate and only when that gate's reply passes the same success test the commit path uses, because the three gates below the decision are not one case and the mere presence of a result body is not evidence the transform ran — an upstream can return one flagged `isError`, or a result beside an error member, and have redaction fail on it. It normally rides beside the not-applied key, but stands alone on a no-op clear under a single-use grant, where the decision authorized labels the anchor was not carrying. The clear is still withheld (the result never reached the host, so nothing sanitized entered the session), but the burned `once` grant then costs a re-minted approval for a proxy- or manifest-side defect, and this key is the difference between that approval retrying the work and re-delivering work already done. `_eunox_declassify_commit_failed` says the call **ran** and the clear could not be applied — never a second commit of one decision, which is a proxy wiring fault reported as one, because there the clear *did* land and telling an operator to re-approve it would be an alert wrong in the unsafe direction. None of them reuses `approval_id`, the top-level signed field reserved for a declassification that actually took effect: one key must not appear on the tape with two provenances. That separation is carried by the authorization handle rather than by each producer remembering it — a decision that authorized no clear mints a handle that can only name the grant it burned, so the field reserved for a clear that took effect is not something a refusal can populate at all.

**The commit runs only when the call SUCCEEDED.** "A response came back" is not "the transform happened": a sanitize whose upstream answers with a JSON-RPC error, or with an MCP tool result flagged `isError`, is delivered to the host and is not a transport failure — so it reaches the commit with nothing sanitized. Dropping the taint there would forward the next egress on the strength of a step that failed. Such a call is treated exactly as a refused one: nothing is cleared, and the record says the approved clear did not take effect. Ambiguity (bytes that do not decode, a non-object result) reads as failure.

**Residual — one, and it now fails closed.** The commit can fault: the call ran, its response is in hand and is not withheld for a bookkeeping failure, and the label stays. The session then holds taint the policy says the action dropped, so a later sink **over-blocks** until the operator retries under a new approval. That is the opposite direction from the residual it replaces — labels gone for a call that never ran, which admitted the next egress the label existed to stop — and it is why the session is *not* marked sticky-untrusted on this path: there is no longer any state in which the proxy knows a session's taint is missing, and quarantining a session whose taint is fully intact would be a self-inflicted outage with no security gain. `eunox stats` counts it and calls it out; `_eunox_declassify_commit_failed` is the key to alert on.

**Single-use grants (`once`).** A grant is replayable by default, and `once: true` makes it single-use: the proxy burns it on the first call that clears with it, and every later presentation is refused `approval_consumed` rather than clearing again. Five properties keep it fail-closed. The burn is keyed by the grant's **`id`**, which `once` therefore makes mandatory — a content key would let two genuinely distinct human decisions collide, and a grant with nothing to burn would silently behave as a standing one, so it rejects the token instead. It is scoped to **nothing else**: not the session, not the task. Anchoring the ledger made "once" mean once-per-anchor, and session lifetime is entirely under the caller's control, so a burn a teardown could reclaim would have made the advertised property hold in no default deployment. The grant is burned **even when the clear is a no-op**, because burning only on a clear that changed something would make it replayable by ordering (present it once while clean, acquire the taint, present it again to the clear that matters). The burn is written **with the decision** and therefore always before the clear, which the second phase applies only once the call has run — so a fault can leave a grant spent for a clear that did not happen (over-refusal, the safe direction) but never a label dropped by a grant still marked live. There is deliberately **no refund**: the un-burn an earlier design performed was itself a fail-open, because the antecedent-fault deny it fired on is soft, so an `--audit` route forwarded the call *and* handed the grant back; a commit that spent a single-use grant now takes the HARD declassify deny whether or not a label moved. Because a spent grant can outlive the clear it authorized, every call that burns one stamps `details._eunox_declassify_spent_approval_id` — on the allow and on any refusal below the decision — so "which of my outstanding one-shot approvals are still live?" is answerable from the tape, which `approval_id` alone could not do (it appears only when the clear changed something). The burn is **atomic** — one admission against a one-slot bucket through the call counter's single `AdmitAll` primitive, so two callers that both observe the grant as live cannot both spend it; a check-then-act against the flow store could not promise that, which is why the ledger moved off it. And a ledger read fault **escalates** while a write fault **hard-denies**, so an unreachable backend is not the way to replay every one-shot grant in a token. The one bound worth stating plainly: the counter is windowed, so a burn is remembered for **seven days** and not forever. That window is no longer a residual, because the other half of the bound is enforced at the TOKEN boundary — a `once` grant riding a token whose remaining lifetime exceeds the window is **rejected at validation**, naming the grant. The burn is written no earlier than the moment the token is presented, so a window this long always outlives a token admitted under that bound: a grant this proxy accepts cannot go live again while the token carrying it is still usable. A deployment that wants long-lived tokens keeps standing grants (replayable for the token's lifetime by design, bounded by literal target scoping and `exp`) or mints a short-lived token per approval.

**Residual — what remains.** `once` bounds how many times an approval is *usable*; it does not bound who holds the token. A token stolen before its grant is spent still spends it, and a standing grant (`once` unset, which stays expressible for an operator whose control plane already mints a short-lived token per approval) remains replayable for that token's lifetime, bounded by literal target scoping and `exp`. The burn's **retention is seven days**, but a token is not admitted if it could outlive that: the boundary refuses a `once` grant whose token's remaining lifetime exceeds the window, so the replay the retention once permitted is closed by construction rather than by operator discipline. What is left is the retention's other consequence — a `once` grant simply cannot be carried on a token valid for longer than a week, which is a refusal at validation rather than a silent weakening. Short-lived per-approval tokens remain the recommended practice.

### 3.14 Cross-PEP State Evasion (Restarting the Task on the Far Side of a Hop)

**Attack:** Every accumulated enforcement state — flow-label taint, `sequenceBlock` antecedents, `maxCalls` and cumulative `blastRadius` budgets, spent one-shot declassify grants — is keyed on the **session**. That is correct for one proxy in front of one host↔upstream pair, and it is also a boundary an agent can step over: delegate the work to a sub-agent that reaches a second enforcement point, or re-enter through a fresh session, and the far side starts with a clean label set, an empty antecedent history, and a full budget. A source read on one hop and the sink it feeds on the next are, to the proxy, two unrelated sessions — so §3.2.1's "for all flows" claim spans one enforcement point and no more, and a per-session quota is a per-*reconnect* quota.

**Mitigation (`taskAnchoredState`).** The same state is keyed on the caller's validated `mcp.task_id` claim instead of on its session, so it accrues to the TASK and survives a hop. Three properties keep it from widening anything:

- **Opt-in.** It changes what every budget in the policy means (a `maxCalls` of 20 becomes 20 per task rather than 20 per connection) and makes two sessions share a label set. That is a semantic change to the operator's policy, not one to make on their behalf.
- **The anchor is a validated claim.** `task_id` is one of the reserved `input.claims` keys filled authoritatively from the verified token, which a same-named custom claim cannot shadow — so an agent cannot choose which task's budget it spends, the one way this could widen anything.
- **It falls back to the session for an unauthenticated caller, and REFUSES an authenticated one it cannot anchor.** A request with no token is anchored exactly as it is today — the failure direction is "no sharing" (the current behavior), not "shared with everyone" (a bypass and a denial-of-service at once). A request that presented a token carrying no `task_id` is denied `MISSING_CONTEXT` instead: on an HTTP host each request carries its own `Authorization` header, so falling back there would let ONE caller split its own state across two buckets by alternating tokens, and every direction of that split is a fail-open (taint written under the task key is invisible to a sink read under the session key; a spent budget is refilled; an antecedent is hidden).

The key encoding keeps the two anchors disjoint — a task-anchored key carries the anchor kind as its own length-prefixed component, so a task and a session with the same name address different buckets — and a session-anchored key is byte-for-byte what it was before the option existed, so an operator who does not enable it cannot be affected by it, including mid-rollout against a shared Redis backend.

**Concurrency.** A task key is reachable from two sessions at once, and the transport's decision lock is per-SESSION — so the flow-label rollback (which removes the labels a faulted call added, computed from a snapshot taken under one session's lock) stands down for a request whose state is TASK-keyed. It is the request's key that decides, not the route's mode: a token-less caller on a task-anchored route is still session-keyed, its lock does span its key, and standing down there would strand a label for a hazard that cannot arise. Removing a label a concurrent session legitimately deposited would leave the task untainted for a source read that really happened, a fail-open on precisely the claim the anchor extends. The label is stranded instead, which over-blocks a later sink.

**Reclamation.** Task-anchored state deliberately outlives the session that wrote it, so session teardown does not reclaim it: clearing it on disconnect would restore exactly the boundary the anchor exists to cross, and would let an agent launder a task's taint by reconnecting. What reclaims it is an **idle bound**, enabled on both backends in this mode — a label set is released after 24 hours with nothing touching it — refreshed by every `labelOutput` write AND every sink read, so it measures the anchor's INACTIVITY rather than its taint's age. That distinction is what keeps it from being the window this store exists to avoid: an active task never loses its provenance however long it runs, and only an anchor nothing will ever ask about again is released. It is scoped to this MODE and no wider: a session-anchored key already has a reclamation path in the transport's teardown, and expiring it would age a taint out from under a session that is merely quiet — inactive is not abandoned — so the default backend expires nothing, exactly as before. `--max-call-counter-keys` remains an ADMISSION ceiling behind all of it, never a reaper; the store warns as the live count approaches it, and at it a new anchor's first labelled call is denied (over-blocking, never a bypass) rather than the process being wedged there for good. Redis remains the supported backend for a MULTI-INSTANCE deployment of this mode — a task's state has to be visible to every enforcement point handling the task, which per-process stores cannot do — and the proxy prints a startup notice when the option is on with no `--redis-addr`.

**Residual.** The anchor is only as good as the IdP's task discipline: two logically distinct workstreams minted with one `task_id` share one budget, which over-restricts (the safe direction) but is worth stating.

### 3.15 Delegation Widening (A Sub-Agent Broader Than Its Delegator)

**Attack:** An agent that hands work to a sub-agent is handing over authority. Without a mechanism, the sub-agent presents its own token and gets whatever the manifest grants that identity — which may be more than its delegator held, and is certainly not *less*. The dangerous shape is a quarantined worker: an agent given a deliberately narrow job (scrape a page, summarize a document) that, once injected, reaches every sink the manifest allows its principal. `principal` scoping answers which caller a capability applies to; nothing answered what is left of a caller's authority after it delegates.

**Mitigation (RFC 8693 `act` + `mcp.delegation`).** Two claims on an already-verified token carry the chain: `act` (the actor identities, nested most-recent-outermost per §4.1) and `mcp.delegation` (the per-hop grants, delegator-first). Each grant narrows along a fixed direction per axis — `targets` shrink, `labels` grow, `allowLabels` shrink, `redactFields` grow, `maxEffectClass` does not rise. Three of the five are also ASSERTED at the token boundary, and a hop that moves one of those the other way **rejects the token** rather than being clamped, because the operator's whole reason for minting a chain is that "the delegate is no broader than its delegator" is checkable rather than conventional. The asserted three are the ones whose value reads as a claim of authority — "I may reach these", "I may carry taint into these sinks", "I may cause up to this" — where declaring more than the delegator held is visible nonsense. `labels` and `redactFields` are the other kind: a hop declaring them imposes something on ITSELF, the decision path unions both across every hop, and neither can widen by construction. Asserting them anyway demanded that every hop restate every ancestor's values and rejected the whole TOKEN when one did not, which is a monotonicity check denying a monotone chain.

That assertion is not what the enforcement rests on. The decision path applies **every** hop's grant, not only the most attenuated, so a chain whose monotonicity check was somehow skipped still cannot let hop 3 reach what hop 1 forbade. Two independent checks, neither depending on the other being right.

**Why no experimental gate.** Every axis narrows, so a build that honors these claims can only deny more than one that ignores them — there is no fail-open direction to gate against. This is the opposite of `mcp.capabilities`, which *replaces* the authorization surface and therefore must be refused outright when its enforcement is disabled.

**Decoding.** A claim-borne grant is decoded strictly, because every one of these narrows something and a grant that parses to something WEAKER than it reads is an invisible loss of a control an operator believes is in force. Three JSON shapes produce exactly that and none is caught by decoding into a struct: an unknown member (`targts` decodes to NO target restriction), an explicit null (`"targets": null` is a nil pointer, which this grammar reads as unrestricted; `"once": null` is a standing approval), and a duplicate key (`targets` beside `Targets` is one field to the decoder, last one wins, so which takes effect depends on member order). All three reject the TOKEN — the loud failure, where an IdP template mistake becomes a caller who cannot authenticate rather than a caller whose narrowing quietly evaporated. The duplicate scan folds keys through the same `FoldJSONKey` the JSON-RPC envelope and `tools/list` scans use, so the three cannot drift on what "the same key" means. The one deliberate relaxation is on the `act` object, whose identity-descriptive members (`iss`, `client_id`) are admitted by NAME: RFC 8693 defines an actor as a set of claims identifying it, a token-exchange IdP routinely writes the actor's issuer beside its subject, and refusing that denied every request on such a token.

The same duplicate-key ambiguity exists ONE LAYER OUT from a grant's own fields — in which claim object gets selected in the first place. The token's top-level `act`/`mcp` claims and the `mcp` block's own `capabilities`/`declassify`/`delegation`/`task_id`/`agent_id`/`v` members are bound by a PLAIN struct unmarshal (the standard library's, run once at the token boundary before any per-grant decoder sees anything), which folds field names and keeps the last collision exactly as a naive grant decode would — so `{"mcp":{"delegation":[{narrow}],"Delegation":[{wide}]}}` hands the per-grant decoder only the WIDE array, with no sign a narrower candidate ever existed. This is validated too (`capability.ClaimMembers`), watching only the small set of names this build reads — a JWT legitimately carries claims for other audiences, and an ambiguity in one this build never touches is not this build's business to refuse a token over.

**Quarantine.** `allowLabels: []` on a hop reduces the effective sink allow-set to empty by intersection, so a delegate sharing a tainted task reaches **no labeled sink at all**, however it is injected and whatever tool it is tricked into calling. `labels: ["untrusted"]` is the complementary half: the delegate's calls carry that taint because its delegator decided so, not because the delegate cared to declare it. Delegated `targets` are matched **literally** — a glob is refused, for the same reason a declassify approval's target is literal.

**Ordering.** The target gate runs before the constraint's conditions (it does not depend on them) and the effect-class gate runs with the ceiling, both before any state commit — so a call refused for exceeding its delegation spends no quota, writes no antecedent, and leaves the label set untouched. A delegate cannot drain its own task's budget by making calls it was never allowed to make.

**Coverage.** The target gate is applied by every enforced method and by every list filter — including the paths that never reach the enforcement engine and would otherwise have been silently unbound: `sampling/createMessage` (which builds its own request — the same omission the JWT layer already found and closed for `mcp.capabilities`, since sampling is the one method that drives the HOST's model and therefore the one a quarantined delegate most wants), `resources/unsubscribe` (authorized by match alone — this gate is authority rather than metering, so it commits nothing and cannot deny a cancel by spending a budget), and a JWT-only or wiretap route (no manifest engine at all, and precisely the route class where the token is present and the manifest is not — its list filters gate too, so the catalog a delegate is shown never disagrees with what its call leg permits). The refusal is constructed in ONE place, so a call refused off the engine path carries the same code, condition type and details as one refused on it.

The delegated `maxEffectClass` composes onto a wrapping layer's short-circuited refusal, but LAST — after the effect ceiling and the unapproved-declassification check, which is the reverse of the full path's order. What it contributes is attribution, not hardness: a delegation refusal is downgradable by design, so composing one can only ever replace one soft refusal with another, and what changes is that the tape names the axis and the hop instead of carrying the wrapping layer's generic `AUTHORIZATION_FAILED`. Because it is the one composed verdict that is *not* hard, it must never preempt one that is — hence last. (It composed nothing at all until the two halves of that path were reconciled: the same path applied the chain's `redactFields` to the response it forwarded while taking the verdict as though the caller held no chain, so a delegated caller over its hop's cap got a refusal hardened by the ceiling and not by the cap. One chain per call is now resolved once and threaded into both halves.) The TARGET gate the JWT layer runs does compose too, and for a stronger reason: because its refusal is downgradable, an `--audit` route FORWARDS it, and a refusal assembled above the inner PDP carries none of the redaction obligations, interface-pin break, or ceiling verdict that PDP would have contributed to that forward. Without the composition, adding a chain that only ever narrows made the same request forward unredacted and past a broken pin.

**Audit.** A delegated call is attributable whether it is allowed or refused. Every record for a call on a token carrying an actor chain stamps the top-level `delegate` (the identity currently holding the token — the outermost `act` actor) and `delegation_depth`, both HMAC-covered like every other field: `user_id` names the human the token is *for*, who on a delegated call invoked nothing directly, so without them a delegated ALLOW — precisely the record an investigator most needs to attribute ("which sub-agent actually invoked `tool:wire_transfer`") — was indistinguishable from one the human made. The terminal actor plus a depth rather than the whole actor list is a deliberate size trade; the full chain lives in the token. A delegation REFUSAL additionally carries `condition_type: delegation` with `delegation: true`, a machine-readable `reason`, and the `delegate` that blocked it in the denial details — with a chain several hops deep, "not permitted" says nothing about which delegator's grant to widen, and the blocking hop is not necessarily the acting one. A flow denial caused by forced taint records `delegated_labels` separately from `carried_labels` (observed) and `declared_labels` (client-asserted), so the tape can answer *why* a call was tainted; `allowLabels` on such a record is the effective set the check ran against, not the manifest's. List results are filtered by the chain too, so the catalog a delegate is shown never advertises an action its call leg will refuse.

**Residual.** A delegation refusal is downgradable by `--audit`, deliberately: it is an authorization verdict like the manifest's own no-match deny, and an observe route exists to show what enforcement would do on a chain being rolled out. The chain is also only as good as the minting side — eunox consumes tokens and never mints them, so a control plane that issues a delegate the same grant as its delegator has expressed no attenuation, and the proxy has nothing to enforce. What the proxy guarantees is that a chain claiming to narrow actually does.

---

### 3.16 Protocol-Revision Confusion (Reaching Another Revision's Method Table)

**Threat.** eunox speaks two MCP revisions, and they do not have the same method set:
2025-11-25 has `initialize`, `ping`, and the `resources/subscribe` pair; 2026-07-28
removes all of them and declares its protocol version in each request's `_meta`
(`io.modelcontextprotocol/protocolVersion`). Once routing is revision-scoped, the
revision a request is decided under selects which methods exist for it — so a caller
that can influence that value can choose the table its request is matched against.
Two shapes matter: declaring a revision this build does not speak (does the request
fall back to a permissive default?), and declaring one revision inside a context
opened at another (a mid-context flip).

**Mitigation.**

- **Omission never widens.** A request declaring no revision inherits the revision its
  context negotiated, and a context that negotiated none resolves to `2025-11-25` — the
  surface eunox already shipped. There is no path by which leaving a declaration out
  reaches a method set the peer did not negotiate.
- **A mid-context flip is refused, not honored.** A context pins its revision from its
  FIRST resolved message, and a later request declaring a different one is denied
  `UNSUPPORTED_PROTOCOL_VERSION` (-32022) and recorded. A peer that changes its declared
  revision mid-context is indistinguishable from one probing for the more permissive
  table, so this fails closed rather than re-negotiating (ADR-0006). The pin is
  deliberately NOT taken from the `initialize` response: a peer on a revision that removed
  the handshake would never pin at all — leaving this refusal inert for exactly the
  revision that mandates per-request declarations — and that placement also wrote the pin
  from a handler goroutine the message loop read for the next request, a check-then-act
  window the value being atomic concealed.
- **An unspoken revision dispatches nothing.** A declared revision outside the published
  set is refused; internally, a revision with no tables resolves to empty tables rather
  than borrowing another revision's, so even a wiring fault denies rather than widens.
- **Removal is expressed by absence.** Each method declares the revisions it exists in,
  once, and the routing tables are derived from those declarations — including the
  notification dispositions, which are one map per revision whose ZERO VALUE is the
  fail-closed "unmapped": a method with no entry cannot be reached by any other path. A method outside
  the requesting peer's tables falls to the same fail-closed default (`dispatchUnmapped`,
  `AUTHORIZATION_FAILED`, recorded) that already covers unknown methods — there is no
  second removal mechanism that could disagree with the first. A declaration naming no
  revision fails the build.
- **The decision is on the tape, from the same value that routed it.** Every record stamps
  `protocol_revision` (§6.1) in the signed body, so an auditor can separate "policy refused
  this" from "this method does not exist in the revision that peer negotiated". The routing
  tables are selected by READING THAT SAME CARRIER (the request context, via
  `requestRevision`) rather than by a second copy threaded beside it, so a record cannot
  name a revision the dispatcher did not route by, or stay silent about one it did. The
  refusal itself is recorded under the `UNSUPPORTED_PROTOCOL_VERSION` code.
- **The gate order is fixed and asserted.** Revision negotiation runs ahead of the
  revocation check on both transports, because a message whose revision is unresolved has
  no method table to be looked up in. The consequence is bounded and deliberate: a revoked
  session's bad-version probe is recorded as `UNSUPPORTED_PROTOCOL_VERSION` rather than
  `KILL_SWITCH` — a labelling difference on a message refused either way, which contacts no
  upstream, mutates no state, and is rate-limited like every other caller-driven refusal.
  Because that difference is SIEM-facing during an emergency stop, the ordering and its
  exception are pinned by tests on both transports rather than left to prose.

**Residual risk.** The revision a peer declares is still the peer's own claim; eunox
constrains which table that claim can select and records the choice, but does not
authenticate it. Since every revision's table is deny-by-default over the same manifest,
selecting a different table can only ever *remove* methods, never grant one policy did
not permit.

**Test coverage.** `internal/transport/dispatch_revision_test.go` (per-revision exact
table sets; the undeclared-membership build gate; an unspoken revision dispatching
nothing; the registry-derived handshake revision), `internal/transport/revision_test.go`
(the negotiation table, including both flip directions and the malformed-params case that
must NOT be relabeled as a version failure),
`internal/transport/enforcement_gaps_test.go` (the per-revision method cells: which peer's
revision dispatches a method and which denies it fail-closed, in both framings),
`internal/transport/gate_order_test.go` (the gate order and its labelling exception, on
both transports; the single-carrier property),
`internal/transport/revision_wire_test.go` (byte-stable old-revision responses),
`internal/transport/integration_test.go` (end-to-end through a real proxy and upstream),
`internal/audit/protocol_revision_test.go` (sign-and-verify round-trip plus the tamper
leg).

## 4. Explicit Out-of-Scope Threats

These attack classes are outside the proxy's enforcement boundary. This is not a gap to be filled — it reflects that these threats require controls at a different layer.

### 4.1 Prompt Injection

**What it is:** Malicious instructions embedded in data the LLM reads (documents, API responses, database records) cause the agent to issue tool calls that the legitimate user did not intend.

**Why it is out of scope:** The proxy enforces _what the agent is permitted to call_, not _why the agent decided to call it_. A prompt-injected call to `read_file("/reports/Q4.pdf")` is indistinguishable from a legitimate one at the JSON-RPC layer, and will be allowed if the capability token permits it.

**What the proxy does reduce (but does not eliminate):** By scoping capabilities to specific resources and argument patterns, the proxy limits the blast radius of a successful injection. An injected agent cannot call tools not listed in its manifest constraints; the additional narrowing to a per-token `mcp.capabilities` scope applies only when the experimental flag `--jwt-experimental-capabilities` is enabled (off by default).

**Recommended complementary control:** Input sanitization and content scanning at the application layer before feeding external data to the agent. The proxy is a last line of defense on tool calls, not a substitute for application-level sanitization.

---

### 4.2 Model Jailbreak

**What it is:** Adversarial prompting causes the LLM to disregard its system prompt or produce harmful outputs.

**Why it is out of scope:** Jailbreak is a property of the model's response to inputs. The proxy does not inspect model inputs or outputs. As with prompt injection (§4.1), the proxy reduces blast radius by enforcing capability constraints on whatever the jailbroken model instructs the agent to call.

---

### 4.3 Client-Side Agent Code Compromise

**What it is:** An attacker compromises the agent process — the Python runtime, the Node.js process, the container — and extracts the bearer JWT or the session ID from memory.

**Why it is out of scope:** The proxy cannot attest the integrity of a client process. Process isolation and host security are the responsible controls here.

**What the proxy does reduce:** Short-lived JWTs bound by `exp` limit the useful window of a stolen token. The kill-switch provides immediate revocation once compromise is detected.

---

### 4.4 IdP Compromise

**What it is:** The identity provider that issues JWTs with `mcp.capabilities` claims is compromised, allowing an attacker to mint arbitrary tokens.

**Why it is out of scope:** The proxy trusts any JWT that passes signature verification against the IdP's JWKS. An attacker who can issue valid signed JWTs from the IdP can call any tool they include in the capability claims. The proxy is not in a position to second-guess the IdP's issuance decisions.

**Mitigation the manifest provides:** When `policy` is also configured, the manifest acts as a second envelope. Even a fully compromised IdP cannot grant more than the manifest allows, because the intersection logic ensures the manifest is the ceiling.

---

### 4.5 Backend Service Vulnerabilities

**What it is:** A backend that the proxy forwards authorized calls to contains its own vulnerability — SQL injection, IDOR, privilege escalation within the backend service.

**Why it is out of scope:** The proxy enforces capability policy in front of backends. It does not perform DAST or runtime security testing of the backends it proxies to. Backends are responsible for their own internal security posture.

---

### 4.6 Enforcement-Point Bypass (Direct-to-Upstream Connection)

**What it is:** The entire model assumes the MCP host is configured to reach the upstream *through* eunox. A host — or a compromised, misconfigured, or simply uncooperative agent — that opens a connection **directly** to the upstream MCP server bypasses the proxy completely: no policy decision, no `*/list` filtering, no audit record. A proxy that clients are merely *configured* to use governs only the clients that choose to use it.

**Why it is out of scope:** eunox is in-path only where the deployment places it in-path. A binary cannot compel a client to route through it; it is an enforcement *point*, not a self-interposing one. Whether eunox is a **mandatory chokepoint** or an **optional convenience** is a property of the surrounding environment — network, identity, and endpoint controls — not something the proxy can assert about itself. This is the same class of boundary as client-side process integrity (§4.3): the proxy enforces what passes through it and makes no claim about traffic that does not.

**What establishes the chokepoint:** A direct connection needs three things — a **credential** the upstream accepts, a **network path** to the upstream, and a **place to run** the client. Remove any one and the bypass fails. Enterprises establish interposition with deployment controls across those three planes:

- **Credential control (the strongest, most portable lever).** Make eunox the only holder or minter of a usable upstream credential. Do not distribute upstream secrets to clients; for per-caller identity, mint short-lived, audience-locked, delegated tokens per request (the upstream-credential delegation model). A client that connects directly then holds no token the upstream will honor — the bypass is *unauthenticated*. Because this is enforced at the IdP/upstream, it holds even on devices and networks the operator does not control.
- **Network egress control.** Route outbound traffic through an egress firewall or forward proxy that permits the upstream's endpoint only from eunox's identity; resolve the upstream's hostname to eunox internally (split-horizon DNS); or have the upstream IP-allowlist eunox. The bypass is then *unroutable* — but only within a managed network.
- **Endpoint control.** For local (stdio) upstreams there is no network chokepoint, so the control is the device: MDM-pushed, locked client configuration users cannot repoint; no upstream secrets provisioned locally; application allowlisting that blocks unapproved MCP server binaries. The bypass is then *unconfigurable*.

These compose: an upstream that accepts only eunox-minted, eunox-delegated credentials, reachable only from eunox's network identity, with client config locked and no local secrets, makes a direct connection simultaneously unauthenticated, unroutable, and unconfigurable. See the [deployment-hardening guide](./deployment-hardening.md) for the concrete patterns (including the GitHub case).

**What the proxy contributes:** Two things. First, eunox *enables* the credential-control lever — it can be deployed as the sole credential holder, and its upstream-credential delegation can mint per-request short-lived tokens so there is no reusable secret on any client to bypass with. Second, eunox's tamper-evident audit log (§3.4) is the basis for bypass **detection**: reconcile eunox's records against the upstream's own audit log — any upstream activity with no corresponding eunox record is access that skipped the gateway. Detection is the compensating control wherever prevention is incomplete (unmanaged or off-network endpoints).

**Residual risk:** A fully unmanaged endpoint — a personal device, an agent running outside the corporate network — cannot be *prevented* from attempting a direct connection. Credential control denies it a usable token and audit reconciliation surfaces any residual access, but a deployment that distributes long-lived upstream credentials to clients and relies only on client configuration to route through eunox has established a *cooperative* boundary, not an *enforcement* one. Treat "the host is configured to use eunox" as an assumption to be enforced by the controls above, not a given.

## Coverage Map: OWASP Top 10 for Agentic Applications (2026)

The [OWASP Top 10 for Agentic Applications](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/) (ASI01–ASI10, published December 2025) catalogues risk for the *whole* agentic stack — model, memory, planning, identity, tool execution, and multi-agent coordination. eunox is a single control at one layer of that stack: the MCP tool-call boundary. It therefore provides **deep, direct** coverage of the tool-execution and privilege risks, **runtime containment** for several others, and is **out of scope** for the model-internal and human/multi-agent risks that require controls elsewhere. A "10/10 coverage" claim would be misleading for a focused enforcement point; the honest map is below.

Coverage levels: **Direct** — a primary design goal, enforced per call; **Containment** — does not prevent the root cause but bounds the blast radius from the MCP boundary; **Out of scope** — requires controls at a different layer (cross-referenced to §4 where applicable).

| OWASP risk | Coverage | How eunox relates |
| --- | --- | --- |
| **ASI01 — Agent Goal Hijack** | Containment | The hijack itself (prompt injection / goal manipulation) is out of scope (§4.1). The default-deny allowlist plus per-argument and per-session conditions bound what a hijacked agent can actually *do* through MCP — it cannot call tools or reach arguments outside the manifest. |
| **ASI02 — Tool Misuse & Exploitation** | **Direct** | The core competency. `allowedOperations` (SQL verb allowlisting), `allowedValues`/`argumentSchema` (argument constraints), and `maxCalls` turn the canonical misuse cases — `DROP TABLE`, path traversal, mass operations — into per-call denials (§3.2, §3.6). |
| **ASI03 — Identity & Privilege Abuse** | **Direct** | Least-privilege by construction: a manifest capability allowlist, claim-forgery rejection (§3.1), and per-session scoping. The additional narrowing by JWT capability claims intersected with the manifest so a token can only *restrict* (§3.5) is experimental and opt-in via `--jwt-experimental-capabilities` (off by default); the stable, always-active basis is the manifest allowlist plus verified identity claims. |
| **ASI04 — Agentic Supply Chain** | Containment | Runtime containment of an untrusted or compromised MCP server you did not write: enforcement lives *outside* the server process where it cannot be switched off, `*/list` filtering hides forbidden tools, and `descriptionHash` pins against tool-description poisoning (§3.8). It does not vet build-time dependencies — that is a different layer. |
| **ASI05 — Unexpected Code Execution (RCE)** | Containment | Gates *access* to exec/eval/shell/SQL tools and constrains their arguments (`allowedOperations`, `argumentSchema`); a dangerous tool absent from the manifest cannot be called at all. It does not sandbox the execution that an allowed call performs (no privilege rings / process isolation). |
| **ASI06 — Memory & Context Poisoning** | Containment (partial) | Gates `resources/read` and writes to memory-backed MCP servers, and `redactFields` masks sensitive fields in responses before they enter context. Tool-description poisoning — a context-poisoning vector on the MCP channel — is directly pinned (§3.8). It does not manage agent memory or RAG stores themselves. |
| **ASI07 — Insecure Inter-Agent Communication** | Out of scope | eunox governs host↔MCP-server traffic, not agent↔agent / A2A protocols. |
| **ASI08 — Cascading Failures** | Containment | Per-session `maxCalls` ceilings (§3.6), kill-switch revocation, and the fail-closed posture (§5) bound runaway loops and limit cascade on the MCP path. It is not an orchestration-level resilience system. |
| **ASI09 — Human-Agent Trust Exploitation** | Out of scope | eunox has no human-interaction or approval layer (contrast: SDKs offering a `require_approval` action). Allow/deny is mechanical, not a human-in-the-loop workflow. |
| **ASI10 — Rogue Agents** | Containment | Out-of-process deny-by-default means a rogue agent cannot bypass policy on the MCP channel; the tamper-evident audit log gives attribution (§3.4) and the kill-switch contains an identified session. It is blind to rogue activity on channels other than the MCP servers it fronts. |

**Summary:** direct, per-call coverage of **ASI02** and **ASI03**; runtime containment for **ASI01, ASI04, ASI05, ASI06, ASI08, ASI10**; out of scope for **ASI07** and **ASI09**. The pattern is consistent with eunox's role — it is the enforcement point for *what an agent may do through MCP tools*, deliberately narrow, and most effective when paired with model-layer (input scanning), identity-layer (IdP), and orchestration-layer controls for the risks above that it only contains or does not see.

## 5. Failure Modes and Resilience Posture

The proxy defaults to **fail-closed**: when a dependency required for a security decision is unavailable, the default is to deny rather than allow. The exceptions are documented explicitly below, with the security tradeoff stated plainly.

### 5.1 Proxy Crash

**Observed behavior:** The process exits. The upstream MCP server receives no further traffic. No tool calls are forwarded.

**Security posture:** Fail-closed by nature of being in the request path. The agent runtime receives a connection error and the task fails.

**Recovery:** Restart the proxy binary. In-memory state (call counters, kill-switch) is reset on restart. If persistence is required, configure `--redis-addr` before deploying.

---

### 5.2 JWKS Endpoint Unreachable

**Observed behavior:** The proxy uses its in-process JWKS cache. Tokens signed with a key that is in the cache are accepted normally. Tokens whose `kid` is not in the cache trigger a force-refresh attempt; if the re-fetch fails, the token is rejected with 401. The resulting `JWT_INVALID` audit record carries `details.error_type: jwks_unavailable` (see §2.2) — distinct from the categories that mark a genuinely bad token — so an operator triaging the tape can tell "the key infrastructure was down and a possibly-valid token was rejected" apart from "a forged or expired token was rejected". The fetch failure itself (network error, non-`200`, empty/oversized key set, or an open circuit breaker) is what carries the category up through the validation path.

**Cache TTL:** 5 minutes by default (configurable). When the cache expires and the endpoint is still unreachable, the next token validation that requires a key not in the cache will fail closed.

**Security posture:** Cached-then-fail-closed. A proxy that has already fetched the JWKS can continue to enforce for up to the cache TTL without the IdP being reachable. This is intentional: it prevents an IdP outage from causing an immediate enforcement outage. However, key rotation events that require a new `kid` are blocked during the outage window.

**Recovery:** JWKS endpoint recovery is transparent. The next forced re-fetch (triggered by a token with a `kid` not in cache) restores normal operation immediately.

---

### 5.3 Redis Unavailable (When `--redis-addr` Is Configured)

When Redis is configured, it backs two enforcement functions:

| Function           | Redis unavailable behavior                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------------------- |
| `MaxCalls` counter | The counter increment errors; the `MaxCalls` condition fails closed and the call is denied with `CONDITION_FAILED` |
| Kill-switch state  | **Fails closed by default:** once a refresh fails, the proxy denies any request whose kill-switch state it cannot confirm (`KILL_SWITCH_ERROR`). Serving the last successfully refreshed snapshot instead is opt-in via `--killswitch-fail-open`. |

The Redis backing is deliberately thin. The proxy uses the standard Redis client directly — there is no circuit breaker, failover, or partitioned-state layer in front of it (the earlier `redisfailover`, Redis-backed circuit-breaker, and partitioned kill-switch packages were removed in an earlier cleanup as over-engineered). Redis is a single optional dependency for shared, restart-surviving state; the fail-closed and last-snapshot behaviors below are what guard a Redis outage.

**Security implication of kill-switch fallback:** The Redis kill-switch maintains an in-process snapshot refreshed two ways — immediately on each pub/sub event, and on a fixed-interval reconciliation timer (`defaultReconcileInterval`) that re-reads the authoritative Redis state regardless of pub/sub. The hot decision path reads that snapshot rather than making a live Redis call. A kill-switch that was activated _before_ Redis became unavailable (and had been refreshed into the snapshot) remains active. A kill-switch activated _after_ Redis became unavailable, or whose pub/sub event was lost (pub/sub is at-most-once), is observed on the next successful reconciliation tick once Redis recovers — it no longer depends on a pub/sub event being delivered, which closes the "lost event is never reconciled" gap. **During the outage itself the switch fails _closed_ by default** (ADR-0003): once a refresh fails, `ShouldBlock()` denies any request whose state it cannot confirm (`KILL_SWITCH_ERROR`, via the `ErrBackendUnreachable` sentinel — the wrapped Redis error is not leaked to clients) until the next successful refresh, so an unconfirmable revocation is never bypassed. Operators who prefer data-plane availability over guaranteed revocation during a partition can opt into the prior behaviour with `--killswitch-fail-open`, which serves the last snapshot instead; for immediate propagation independent of Redis, run a local proxy instance per host with its own in-memory kill-switch. The Redis kill switch exposes `HealthStatus()` (non-nil ⟹ the last snapshot refresh failed); operators should poll it and alert so a Redis partition — a partial data-plane outage in the default mode, a widening revocation-latency window under `--killswitch-fail-open` — is visible rather than discovered during an incident.

**Security implication of MaxCalls denial:** When Redis is unavailable, `MaxCalls` conditions fail closed — calls are denied rather than allowed without a counter check. This is conservative and may cause false positives during Redis outages, but it prevents unbounded call rates.

**Recovery:** Redis recovery is transparent. The Redis-backed stores resume their normal role immediately.

---

### 5.4 Audit Log Write Failure

**Observed behavior:** If writing an audit record fails (disk full, permission error, file descriptor limit), the loss is surfaced three ways: a one-shot stderr warning (subsequent write errors are suppressed to avoid a flood under a sustained outage),

```
[eunox] WARNING: audit record write failed — the audit trail is now incomplete; check disk space and I/O ...
```

a monotonic counter exposed as the `eunox_audit_write_failures_total` metric (and the `auditWriteFailed` field on `/healthz`), and — for a write failure that persists to the final `Sync`/`Close` — a **non-zero process exit**. This counter is deliberately distinct from `eunox_audit_dropped_records_total` (queue back-pressure on a healthy file): a non-zero write-failures count means the backing file itself is unwritable, so audit coverage is degrading even though the queue kept up. Enforcement continues. The tool call result (allow or deny) is still applied to the upstream and returned to the client. The audit record for that call is lost.

Unlike a queue-back-pressure drop, a write failure **cannot** be recorded with an in-chain `AUDIT_RECORDS_DROPPED`-style marker, because the file that marker would be written to is the thing that is failing. The chain head is intentionally not advanced on a failed write, so the chain stays internally consistent (no spurious break), and the loss is surfaced out of band via the metric and exit code instead.

**Security tradeoff — documented explicitly:** Audit log write failure does not block enforcement. This is a deliberate design decision: dropping production traffic because the local audit log is full would be worse than a partial audit trail gap in most deployment contexts. Operators who require guaranteed audit completeness should:

1. Monitor disk space on the machine running the proxy.
2. Ship audit records to an external sink (SIEM, object storage) by tailing `~/.eunox/audit.jsonl` with a log shipper.
3. Set the `--audit-rotate-size` flag to match available disk space (default: 100 MiB auto-rotation).

Use `eunox audit-verify` to detect HMAC verification failures and chain breaks in existing records. The `seq`/`prev_hmac` chain (§3.4) flags an interior gap left by a dropped or deleted record; a record missing from the very end of the log cannot be distinguished from "never written" without an external high-water mark. A line that is itself corrupt (fails JSON decode) is counted as `invalid` by its per-record HMAC check but is excluded from the chain linkage, so it does not fabricate a spurious chain break against the following intact record.

#### 5.4.1 Fail-open on the allow path

**The allow path is fail-open with respect to durable audit.** A permitted (`allow`) request is recorded only **after** the call has already been forwarded and the upstream has answered: in the shared forward core (`internal/transport/forward.go`, `enforcedForwardCore`) the proxy forwards the authorized request, reads the upstream response, and only then calls `RecordAllow(...)`. `RecordAllow` does not write to disk synchronously — it does struct init plus a **non-blocking** channel send onto the bounded (4096-slot) audit queue (`internal/audit/audit.go`, `Sink.Record`), and a separate drainer goroutine serializes, signs, and writes the record later. Consequently the call's effect on the upstream is **never** blocked on, reversed by, or conditioned on the record reaching disk. Under any of:

- **Full queue** — the non-blocking send finds the channel full and the record is dropped (counted in `dropped`); or
- **Write error** — the record dequeues but the drainer's write/`Sync` fails (disk full, permission error, `EIO`); or
- **Process loss** — the proxy exits or is killed with records still queued,

an `allow` can be forwarded and applied to the upstream with **no durable on-disk record of the decision**. This is the same documented tradeoff as §5.4 (audit failure never blocks enforcement), stated explicitly for the allow path: the security control that is weakened is *audit completeness*, not *enforcement* — a denied call is still denied, the forwarded call still happened, only the tape entry may be missing.

**Existing mitigations (the loss is observable, not silent):**

- A **back-pressure drop** is made tamper-evident in-band: when the drainer next runs after the queue had been full, it writes a signed `AUDIT_RECORDS_DROPPED` chain marker (§3.6) recording how many records were lost, so a verifier sees that a gap occurred even though the individual records are gone.
- Two distinct counters expose the two loss modes: `eunox_audit_dropped_records_total` (queue back-pressure on a healthy file) and `eunox_audit_write_failures_total` (the backing file itself is unwritable), plus the one-shot stderr warnings and the `/healthz` `auditWriteFailed` field (§5.4).
- A write failure that persists to the final `Sync`/`Close` causes a **non-zero process exit**, so a deployment that treats the proxy's exit status as health will notice.
- `--require-audit` is three-state and **defaults to `strict`** (below): a proxy started without the flag fails closed on audit loss. `--require-audit=on` gates only **sink-open at startup** (the proxy refuses to start if it cannot open the audit log/key) but does **not** make the per-record allow path block on a durable write; `--require-audit=off` makes even the startup check best-effort (warn and run unaudited). A bare `--require-audit`, like the omitted default, is `strict`.

**Operators requiring guaranteed completeness** have two complementary options. First, ship records to an append-only external sink in real time (§5.4, step 2); the chain then lets the sink detect any in-flight gap that the local counters/marker also flag. Second, keep the default `--require-audit=strict` (rather than relaxing to `=on`/`=off`) to fail the local data plane closed the moment coverage degrades:

**`--require-audit=strict` (the runtime fail-closed gate).** Strict mode promotes `--require-audit` from a startup-only check into a runtime gate over the *forward* path. Before the proxy forwards an authorized request — every enforced method (`tools/call`, `resources/read`, `resources/subscribe`, `resources/unsubscribe`, `prompts/get`, and `sampling/createMessage`) and every `*/list` enumeration — the shared core (`enforcedForwardCore` / `dispatchList`, and both the allow and audit-mode observe legs of the sampling path in `forwardServerRequest`) consults `Sink.AuditDegraded()`. Once either loss counter has incremented (`dropped > 0` from queue back-pressure, or `writeFailures > 0` from a failed write/`Sync`), the call is denied fail-closed with the `AUDIT_UNAVAILABLE` code (JSON-RPC `-32603`, the internal-error class — distinct from the `-32001/-32002/-32003` policy codes) and the upstream is **not contacted** (for sampling, the upstream initiator receives the `AUDIT_UNAVAILABLE` error and the request is not forwarded to the host). The deny is itself recorded best-effort; its structured audit `details` carry only discrete counts (`dropped_count`, `write_failure_count` — present only when non-zero), never free-form prose. The human-readable degradation reason is reserved for the host-facing error response and the one-shot stderr warning, keeping the structured audit field value-free.

On the HTTP/gateway transport the session-creating `initialize` is gated the same way: spawning or contacting an upstream is a privileged side effect, so once the trail is degraded a new session is refused with `AUDIT_UNAVAILABLE` rather than starting an upstream whose creation and subsequent traffic could go partly unrecorded. (The stdio transport answers `initialize` from cached capabilities and starts its single upstream before any traffic, so it has no equivalent per-call side effect to gate.)

**What the gate does and does not guarantee.** The gate is **retrospective**: `AuditDegraded()` reads the cumulative `dropped`/`writeFailures` counters, which reflect only *already-completed* calls, and a call's own allow record is enqueued *after* the upstream answers. So the **boundary call** — the first call whose own record is the one lost (and, under concurrency, any call already in flight when the queue first saturates) — is still forwarded *and* loses its record; only the *next* call observes `degraded` and is denied. The accurate guarantee is therefore: **after the first lost record is observed, every subsequent forward is denied** — not that *no* call is ever forwarded unaudited. Closing the boundary window entirely would require a synchronous/blocking allow path (forward only after the record is durably written), which trades far more data-plane latency than the residual one-record window is worth; it is intentionally not done. Operators who need a zero-loss guarantee must combine strict mode with the real-time external sink (option one above), whose chain detects the boundary record's gap.

**Immediate boundary-call diagnostic.** While the window above cannot be closed without the blocking path, the boundary call does not have to be invisible until the next unrelated request trips the gate. Around each of its own `RecordAllow`/`RecordDeny` calls, the forward core reads `AuditDegraded()` once immediately before and once immediately after; if the trail was healthy going in and degraded coming out, that call's own record is plausibly the one just lost, and an immediate `SECURITY` line to stderr names the call rather than waiting for a later request's `AUDIT_UNAVAILABLE` denial to be the first sign. This is a diagnostic, not a new enforcement point — the boundary call is still forwarded either way — and it is best-effort: concurrent in-flight calls at the exact transition instant may each observe the flip and each warn, which is acceptable since every such call is a genuine candidate for the boundary, not a false positive on unrelated activity.

The gate is also **coarse and sticky by design**: it keys on the cumulative loss counters, so a single drop or write error denies every subsequent forward for the lifetime of the process (the counters only ever increase). This trades data-plane availability for audit completeness — the deliberate inverse of the relaxed `--require-audit=off`/`=on` posture — and is the right choice wherever an unauditable privileged call is worse than a denied one (the compliance/forensics case), which is why it is the default. Deployments that prefer availability over audit completeness opt down with `--require-audit=on` (startup-fatal only) or `--require-audit=off` (best-effort). A hard policy deny is unaffected (it already returns without forwarding); strict mode also overrides route-level **audit/wiretap** forwarding when the trail is degraded, since an observation that cannot be recorded has no audit value. The unenforced server-initiated passthroughs (`roots/list`, `elicitation/create`, …) are not gated — they carry no policy decision — so the gate's scope is exactly the enforced decision paths, `*/list`, and the HTTP session-creating `initialize`. Strict mode implies `--require-audit` (a sink that cannot open at startup is still fatal), so the runtime gate never runs without a sink. The "now denying forwards" stderr warning fires **once**, on the healthy→degraded transition; each denied call's durable signal is its `AUDIT_UNAVAILABLE` record, not a per-request log line.

### 5.5 Upstream MCP Server Unavailable

**Observed behavior:** If the upstream subprocess fails to start or a remote `upstreamUrl` is unreachable, the session initialization fails and the client receives an HTTP 500 with the error message. On the HTTP transport, session initialization — the initialize handshake and the startup drift probe — is bounded by a per-initialize deadline (the session-start budget, separate from `--upstream-timeout`), so a hung upstream cannot pin the handler goroutine or leave an unkillable orphan process.

For in-session failures (upstream dies or hangs after initialization), any method that attempts to reach the upstream — enforced methods and `*/list` discovery methods alike — returns a JSON-RPC error and an audit record is written with one of the infrastructure denial codes:

- `UPSTREAM_ERROR` — the upstream failed (exited, transport error, malformed response).
- `UPSTREAM_TIMEOUT` — the upstream did not respond within `--upstream-timeout`. This per-request bound is applied centrally to every host-initiated upstream round-trip (tool calls, reads, and the `*/list` discovery methods) on both transports, and to notification forwarding to a remote HTTP upstream. It deliberately does **not** govern session-start work (the initialize handshake and drift probe), which has its own session-start budget so a tight `--upstream-timeout` cannot by itself fail session establishment.
- `REQUEST_CANCELED` — the host abandoned the request before the upstream responded; the upstream is not implicated.

These records are never marked `audit_only`: the error returned to the host is an enforced outcome even when the route runs in audit mode. Infrastructure codes are distinct from policy denial codes, and the `suggest` subcommand ignores records carrying them when drafting manifests.

**Security posture:** Fail-closed on upstream errors. An unreachable upstream does not cause the proxy to bypass enforcement — it causes the call to be denied with an infrastructure error code distinct from policy denial codes.

Distinct from an infrastructure failure is a **completed** round-trip in which the upstream chose to return a JSON-RPC `error` *result* (the call reached the upstream, which answered with an error rather than a result). The proxy authorized and forwarded that call, so its decision is recorded as an honest `allow` — the `decision` field records the proxy's policy verdict, not the upstream's outcome — but the `allow` record carries a `_eunox_upstream_error_code` entry in `details` so a forwarded upstream error is not indistinguishable from a clean success on the tape. Only the numeric JSON-RPC error code is recorded; the upstream's error *message* is never copied into the audit record, which could otherwise leak sensitive content from the upstream's response. The key is underscore-prefixed, in the same reserved namespace as `_eunox_truncated` (below), so in the ordinary case it is merged flat alongside the caller's real tool arguments with no risk of colliding with one — a tool argument literally named `upstream_error_code` (bare, no prefix) is ordinary caller data and is recorded and mined like any other argument. On the rare call whose real argument is literally named the reserved key's own underscore-prefixed string, the merge nests the caller's arguments under an `"arguments"` wrapper instead of overwriting them with the injected code (mirroring the guard the bare key needed before the rename); `suggest`'s argument mining resolves this nested shape the same way it did before.

**List-enumeration filter counts.** A `*/list` allow record (`tools/list`, `resources/list`, `prompts/list`) carries three machine-readable counts in `details`: `upstream_count` (entries the upstream returned), `filtered_count` (entries that survived policy filtering and were delivered to the host), and `suppressed_count` (`upstream_count − filtered_count`, the entries the manifest hid). Without these, an `allow` for `tools/list` looks identical whether the upstream returned 100 tools with 99 filtered by policy or genuinely returned an empty list — an auditor investigating why a client sees no tools could not tell aggressive filtering from upstream emptiness, and could not reconstruct the effective permission surface at a point in time from the tamper-evident chain. In route-level observe (audit) mode the manifest filter is bypassed, so `filtered_count == upstream_count` and `suppressed_count == 0`; the record additionally carries `observe_mode: true` in `details` so a reader can tell a zero suppressed count caused by *bypassed* filtering from one caused by an all-permitting manifest (an enforce-mode record omits the key). The counts are entry tallies only; no tool/resource/prompt names are recorded. `suppressed_count` here means catalog entries hidden by policy on an `allow`; the refusal rate limiter's unrelated rollup on a transport-surface `deny` is spelled `suppressed_refusal_count` (§3.7) so the two cannot be matched by one query.

### 6.2 What the proxy logs — mode dependency

Argument-value capture depends on both the operating mode and the decision outcome.

**Allow records — route-level observe mode only:** when the proxy runs in route-level observe mode (the `--audit` flag on the `proxy` subcommand, or `enforcement: audit` under `defaults:` / per-route `enforcement:` in a gateway config), allowed-call records include the **full argument map** in the `details` field. In enforce mode (the default) and in per-entry `enforcement: audit` without a route-level override, allowed-call records contain no argument values.

**Argument size is bounded before enqueue.** Because observe mode captures arguments verbatim, a single tool call with a multi-megabyte argument (a `write_file` body, a base64 blob, a large text corpus) would otherwise produce one audit record larger than the `audit-verify` scanner buffer and the chain-resume tail window — making `audit-verify` fail with `token too long` (skipping every later record) and the chain resume from a stale fragment after a restart. To keep records bounded, any single string value over 512 KiB is replaced with a size-marked placeholder — a binary (`[]byte`) value is measured by its base64-encoded length, the size it actually occupies once serialized into the record — and if the whole `details` map still marshals over 1 MiB it is replaced with a single `_eunox_truncated` marker carrying a structured `{"reason": …}` code (plus the numeric `bytes`/`cap` facts) rather than a free-form prose string, so consumers key on a stable code. This bounds the record well under the scanner limit while keeping the truncation visible; it caps individual value size, never the number or set of records. The bound is applied on the request goroutine **before** the record is placed on the audit queue, not in the background drainer afterward, so the bounded queue cannot retain up to `auditChannelSize` un-truncated multi-MiB argument clones.

**The record envelope is bounded too.** The `details` cap covers only the argument map; the record's envelope strings are bounded separately. `target` is derived verbatim from the attacker-controlled tool name (`params.name`) or resource URI (`params.uri`), and an unrecognized raw method is preserved as `method` — both are written even on the deny path (e.g. an unknown tool), and an incoming request is allowed up to 4 MiB. An unbounded `target` could fill nearly the whole body and push the serialized line past the 4 MiB `audit-verify` scanner buffer and chain-resume tail window — the same failure the `details` cap prevents, reached through the envelope instead. `target` and a raw `method` are therefore truncated to 8 KiB with a visible marker. The `obligations` array is bounded the same way: directives such as `redactFields` emit one obligation per match, so a manifest with many (or deliberately crafted) long redact paths could otherwise drive the array large enough to push the line past the 4 MiB window on its own. The array is capped at 64 KiB of serialized length — the kept prefix is retained in order and a single `obligations_truncated:N` sentinel records the omitted count, so the truncation is visible and the record stays structurally valid. The `agent_id`, `task_id`, `user_id`, and `delegate` fields are bounded the same way: all come from a validated JWT's `mcp.agent_id`/`mcp.task_id` claims, its `sub` subject, and its `act` actor chain, whose structure is checked but whose length is not, so a misconfigured or compromised IdP could otherwise stamp a multi-megabyte claim and push the line past the 4 MiB window without any change to the proxy config. Each is truncated to 8 KiB with a visible marker. With the 1 MiB `details` cap, the 64 KiB `obligations` cap, the `session_id` explicitly capped at 256 bytes (in HTTP mode it comes from the client-controlled `Mcp-Session-Id` header, so it is bounded like `target`/`method` rather than trusted to be a server-minted UUID), the 8 KiB `agent_id`/`task_id`/`user_id` caps, and every other envelope field bounded by its source (policy digest, request id), this makes the full serialized record provably far below the 4 MiB window. Each of these same fields (`target`, an unrecognized `method`, `session_id`, `agent_id`, `task_id`, `user_id`) is also normalized to valid UTF-8 before it is ever marshaled — not for size, but because `encoding/json.Marshal` is not idempotent across a decode-then-re-encode round trip for a string holding invalid UTF-8 (it writes a lone invalid byte as the literal escape text `\ufffd` the first time, but decoding that and re-marshaling the resulting valid U+FFFD rune emits its raw UTF-8 bytes instead), which broke the round-trip both the HMAC recompute and the canonical-form check (§3.4) depend on for exactly these attacker/IdP-controlled fields — a client-supplied `Mcp-Session-Id` with a single stray invalid byte was enough to make a genuine, never-tampered record fail verification.

**Denial records — all modes:** denial records always include `denial.Details`, a condition-specific object written for compliance and forensic purposes. For conditions such as `allowedValues` this object contains the **specific argument value** that triggered the denial (e.g., `{"argument": "sql", "value": "<the rejected query>", "allowedValues": [...]}`). This applies in both enforce mode and audit mode. Operators must therefore treat `audit.jsonl` as potentially sensitive regardless of mode — the file may contain individual argument values extracted from denied calls.

**A denial's `details` are bounded far more tightly than an allow's.** The argument-echo above is the one place caller-controlled bytes cross from a *rejected* request into the signed tape, and nothing bounds a tool-call argument before the condition check runs — so an unbounded echo made each denied call a kilobyte-per-byte lever on signed-log growth, at whatever rate an agent can trigger condition denials. This is the same amplifier closed for the rejected `Origin` header and the loopback endpoints' `path` (§4.4), reached post-authentication through a tool argument instead of pre-authentication through a header. Four caps apply to every denial's `details`, and they are enforced at the single point every enforcement deny passes through rather than at each condition handler's own object, so a handler added later inherits them by construction: any single string value is truncated at **512 bytes** with the same visible `...[eunox: truncated, N bytes]` marker used elsewhere; the map as a whole is bounded by an **8 KiB** budget charged across every key and scalar the walk visits, which bounds an argument that decoded to a large *container* whose elements are each individually small; nesting is bounded at **8 levels**, which bounds a chain of empty containers that would cost nothing against the byte budget; and the number of *top-level* keys is capped at **16** (the 8 KiB budget divided by the 512-byte per-key floor — the point past which the per-key share alone stopped bounding the map, since it floors rather than continuing to shrink). Keys are kept in ascending order up to that count; the rest are folded into a single `_eunox_elided` entry naming how many were dropped, the same convention a partly-elided nested object uses one level down. A value dropped by the byte budget or the depth bound is replaced with the fixed marker string `[eunox: elided]`, a partly-elided object gains one `_eunox_elided` entry naming how many entries were dropped, and a partly-elided array ends in one `[eunox: N of M elements elided]` entry — fixed codes rather than free-form prose, the same discipline applied to `_eunox_truncated` above and to upstream error results (§5.5). Keys are walked in sorted order so that *which* entries survive an exhausted budget is deterministic: two identical denied calls write identical details, rather than differing by Go's randomized map iteration in a way an operator or a diffing SIEM rule would read as a difference in the requests. Every string is also normalized to valid UTF-8 for the same round-trip-idempotency reason the envelope fields are (above). These caps are diagnostic bounds on a *deny* echo, deliberately much tighter than the 512 KiB / 1 MiB caps an audit-mode *allow* gets: an allow record in observe mode is the record of what was actually forwarded, while a deny's details exist to make the refusal actionable. They are also a **separate** mechanism from those caps rather than a replacement — the sink's own bounds still apply to every record from every source.

Denial codes and condition types are bounded the same way (8 KiB, as for `target`). For the built-in engine both are compile-time constants, but a deployment wiring an external policy evaluator (§6.5) receives them as operator-supplied strings from that evaluator's response.

| ------------------------------------ | ---------------------------------- | -------------------------------------------------- | ----------------------------------------------------- |
| Full tool argument map               | Not written                        | Written in `details` (oversized values size-capped, §6.2) — **treat log as sensitive** | Not written                                |

**Two records on an observed-and-forwarded denial.** When a per-entry `enforcement: audit` constraint (or route-level audit mode) produces a *would-be denial* that is then forwarded, the proxy writes **two** records for that one request: first a `deny` record (`audit_only: true`) capturing the verdict and its `denial_code`/`details`, then — after the upstream call returns — an `allow` record (`audit_only: true`) capturing the forwarded outcome and any obligations. This is intentional: the deny record preserves the policy verdict for `stats`/`suggest` and forensics, while the allow record reflects what the host actually received. Both carry `audit_only: true`, which together with the matching `target`/`method` distinguishes the pair from a genuine allow or a genuine enforced deny. SIEM correlation rules that treat an allow+deny pair on the same target as an anomaly should exclude records where `audit_only` is `true`. A hard-blocked kill-switch denial is **not** forwarded and therefore produces a single enforced `deny` record (never marked `audit_only`).

### 6.3 Response redaction via the `redactFields` directive

`redactFields` is a post-allow **directive**, not a condition. When a matched constraint carries a `redactFields` entry in its `directives` array (e.g., `directives: [{"type": "redactFields", "fields": ["$.ssn", "$.card_number"]}]`), the proxy **masks** those dot-path fields in the tool call _result_ returned to the MCP host before forwarding it: each matched field keeps its key, but its value is replaced by the placeholder string `"[redacted]"`. The redaction is applied to JSON text content blocks, the `structuredContent` object, and the result envelope itself, recursing into array elements — so a declared field sitting directly on a top-level result key is masked, not only one nested inside a sibling key's value. A single-segment path naming an MCP-reserved component is left to that component's own handling (masking the whole component wholesale would produce a result a conformant host cannot decode); a dotted path through one resolves to the leaf it names. Redaction fails the whole response closed (internal error `-32603`, never forwarding unredacted data) only on a **structural or resource guard** — the response envelope is not parseable JSON (or carries trailing data), the `content` array or one of its items has a structurally unverifiable shape, a value nests deeper than a fixed redaction depth bound, or re-serialization fails. It does **not** fail closed over string *content* it merely cannot parse as JSON (see the accepted residual below).

Because an obligation is a property of the **matched constraint**, not of the allow *decision*, `redactFields` is also applied when an **observe-mode deny is downgraded to a forwarded call** — a condition, `argumentSchema`, or action-check failure under an `enforcement: audit` constraint **or a route running `--audit`** still returns the upstream response to the host, so it is masked exactly as a genuine allow would be. Dropping the obligation on that path would forward the very fields the manifest marked for redaction; the downgraded deny therefore carries the constraint's `redactFields` obligations, and the transport applies them before the forwarded response reaches the host.

Both halves of that union matter, and they are computed in one place so they cannot drift: gating only on the per-constraint `enforcement: audit` flag would leak on the standard whole-route `--audit` deployment, where individual constraints are *not* marked audit-only. The test is also `!= allow` rather than `== deny`, matching the transport's own fail-closed gate — a response with an unset decision is forwarded there, so gating on `== deny` here would let it through unredacted.

A **no-match** deny (no constraint selected for this caller — e.g. a principal-scoped entry whose claims the caller does not satisfy) is downgradable too, so a route running `--audit` forwards it. It carries the `redactFields` declared by **every entry naming that target**, regardless of principal scoping: no entry was selected, and any entry declaring a field of this target redactable is reason enough to mask it on a response about to be forwarded. On an enforce route the same deny blocks, so it carries nothing.

A **hard** deny (kill-switch, a tool-poisoning `descriptionHash` mismatch, an engine-error) is never forwarded, so it carries no obligations.

The fill happens at **two** layers, deliberately. The enforcement engine stamps the obligations onto every downgradable deny it produces — the condition, `argumentSchema`, record-fault, and no-match paths — so the property holds for a direct caller of the exported `Engine.ValidateAction`/`EvaluateConditions` (an external embedder), which never reaches the PDP. The `ManifestPDP` remains a backstop for anything the engine did not attach and supplies the richer manifest view for its own paths. Both read the downgradable test from one place (`enforcement.WillForwardDeny`, which the transport's `isObserveDeny` mirrors), so neither can widen the set the other narrows. A `HardDeny` carries none.

One layer above this, `JWTPDP` short-circuits its own denials before the manifest layer runs, so the inner PDP never evaluates and three things it would have contributed have to be supplied explicitly at the seam every short-circuiting deny already passes through: the inner manifest's **obligations** (else an `--audit` route forwards the response unredacted), the **interface-pin** break (§3.8), and the **effect ceiling** (§3.12). Each was the same defect in a different currency — turning the JWT on removed a guarantee, inverting the rule that a token may only ever *restrict*. The ceiling needed a narrower answer than the other two: both pin reads are pure lookups against state an earlier `tools/list` armed, but reaching the ceiling the normal way means running the matched constraint's conditions, and some of those **commit** (`maxCalls` consumes a window slot, `labelOutput` writes a flow label, `sequenceBlock` writes an antecedent). Replaying them for a call that is already refused and will never be forwarded would leave exactly the phantom state the ordering below exists to prevent, so the composed verdict goes through a **non-committing** seam that evaluates the ceiling and nothing else, after the structural gates the real path applies before one could be reached (no ceiling configured, no constraint selected for this caller, or a constraint that does not permit this action). Where a *condition* would have denied first, the composed refusal is the ceiling's — harder than the manifest's, and the safe direction for a call being refused either way.

**Mask, not strip — disclosure posture.** Redaction replaces the value and **retains the key**; it does not delete the key. The host therefore learns that the named field was *present* (and at what path) but never its contents. This is a deliberate choice over stripping the key outright: a stable response shape avoids breaking hosts that expect the field to exist, at the cost of disclosing the field's *presence*. The masked value is a fixed sentinel (`"[redacted]"`) carrying none of the original data — whatever the original type (string, number, object, array), the field becomes that string. Because the sentinel is always a string, masking a field a tool's `outputSchema` declares as a number, object, or array yields a value that no longer matches that schema, so a host that validates `structuredContent` against `outputSchema` may reject the result — another reason to redact such fields **upstream**. Where a field's very existence is sensitive and must not be disclosed, redact it **upstream** so the proxy never sees it.

A redaction target (`$.ssn`, `user.card_number`) is a key inside a JSON object, so the **text-content posture** turns on whether a block parses cleanly as JSON. A block that parses cleanly as a single JSON object or array is redacted; a block that is **not** a clean JSON document — genuine free-form text (an error string, a `[ERROR] …` log line, a bare scalar), **malformed** JSON (`{"ssn":"…",}`, `{"ssn":"…"`, a truncated `[{"ssn":"…"}`), a status-prefixed body (`OK {"ssn":"…"}`), or JSON **embedded in surrounding prose** (`result: {"ssn":"…"}`) — has no addressable JSON key and is **forwarded unchanged**. `redactFields` redacts valid JSON only and never fails the response closed over string *content* it cannot parse, so adding it never blocks a tool that returns plain-text or partially-JSON output.

**Accepted residual (fail-open on unparseable content).** Forwarding unparseable string bodies unchanged is a deliberate availability/precision trade-off, and its cost is an explicit fail-open: a named field hidden inside a **malformed** JSON container that still carries it (a truncated `{"ssn":"…"`), or inside JSON **embedded in prose**, is **not** redacted and reaches the host. The structural-key smuggling vector is still closed for *clean* JSON — a **clean** container reached through any number of nested JSON-string-encoding layers (`{"data":"{\"ssn\":\"…\"}"}`, or that same string encoded again, and again) is unwrapped at every layer, redacted, and re-serialized, up to a bounded depth, so an upstream cannot evade redaction by double- or triple-encoding well-formed JSON. `redactFields` is therefore a control over **cleanly-structured** JSON fields only, at any string-encoding depth; data that may arrive malformed or prose-embedded must still be redacted **upstream**, at the tool/server that produces it. (Redacting JSON embedded in surrounding prose is not currently supported.)

**Ambiguous object keys fail closed.** The redaction walk decodes the result with `encoding/json`, which resolves a duplicate object key **last-wins**, while a host is free to resolve it **first-wins** (`JSON.parse` and the Python SDK both do). That divergence is a bypass on its own, and a silent one: an upstream answering `{"content":[…],"data":{"ssn":"…"},"data":{}}` under `redactFields: ["data.ssn"]` presents this layer an empty `data`, so no path matches, nothing changes, the ORIGINAL bytes are forwarded byte-for-byte — and the audit record reports the obligation applied while the host renders the ssn. The response path therefore runs the same streaming key scan the request path (`rejectDuplicateJSONKeys`) and the `*/list` filters already apply, and denies the response when it fires: **a duplicate key at any depth**, or **a case-variant collision on a key this redaction depends on resolving** — a segment of a redact path (`data` alongside `Data` under `redactFields: ["data.ssn"]`, where the masking walk looks its segments up exactly), or one of the result envelope's protocol-reserved keys (`content` alongside `Content`, on which `ApplyRedactObligs` dispatches exactly: the canonical spelling gets the content-array pass with its fail-closed guards on resource items and anomalous shapes, while a variant would fall to the lenient generic sibling walk, so `{"content":[],"Content":[{"type":"resource",…}]}` would pass the strict pass over an empty array and the lenient one over the payload). Both rules apply at every depth, so the verdict does not depend on whether a value happened to be wrapped in an array. The scan also runs on a JSON container unwrapped from a text item or a doubly-encoded string, because the envelope-level scan cannot see keys that only become keys once this layer decodes the string — without it the identical smuggle works one layer down.

A third rule covers the case the first two structurally cannot: a **lone** case variant of a result-envelope key, with no canonical sibling to collide with. `{"Content":[{"type":"resource",…}]}` folds to a reserved name but collides with nothing, so it tripped neither rule; it then missed the exact-match dispatch (`result["content"]` is not `result["Content"]`) and fell to the generic sibling walk, which carries no resource-body guard, no content-item shape checks, and drops dotted paths under its own prefixes. Nothing matched, so the ORIGINAL bytes were forwarded while the tape reported the obligation applied — and a case-insensitive consumer (the Go MCP SDK's struct binding, .NET's `PropertyNameCaseInsensitive`) bound the variant as the real content. Any top-level key that folds to one of the six protocol-reserved envelope names (`content`, `structuredContent`, `isError`, `contents`, `messages`, `_meta`) without being spelled canonically now denies the response. The cost to an honest upstream is nil: a spec-conformant server does not spell a protocol key any other way.

The case-variant rule is deliberately **narrower here than on the request and `*/list` paths**, which fold every key at the struct-bound level. Their fold is derived from `encoding/json` binding keys to a Go **struct** case-insensitively, which makes any case-variant sibling a divergence. Nothing on the redaction path is struct-bound — the envelope and every unwrapped leaf decode into `map[string]interface{}`, whose keys are exact, exactly as any host that renders JSON as data sees them — so carrying the wider rule over refused honest responses (a payload with both `Report` and `report` under an obligation naming neither) with no divergence behind the refusal. Scoping it to the names above keeps the guard where a resolution really differs. The residual cost is over-refusal on a case-variant pair of a named key *nested* below the root, where only the envelope-level dispatch strictly cares — a denial, never a bypass.

**JSON-RPC error channel.** Redaction operates on a tool-call **result**. When the upstream answers an allowed call with a JSON-RPC **error** instead, there is no result to mask, and the free-form `error.data` payload cannot be verified against the result-shaped redact paths — an adversarial or misconfigured upstream could otherwise smuggle a declared-redactable value to the host through `error.data`. Rather than forward it unredacted, the proxy **strips `error.data`** (fails closed) whenever a `redactFields` obligation is attached to the call; the error `code` and `message` still reach the host, and the obligation is **not** stamped as discharged in the audit record (so the tape never claims a redaction that did not run).

Redaction affects the data the MCP host sees, not the audit log. The allow record's `obligations` array records each applied obligation as a token — `redactFields:<path>`, one per masked field path (a bare `redactFields` when the directive lists no path) — so the tape shows *which* fields were masked. These are the operator-defined field *names* from the manifest, never the masked *values*; the upstream response itself is never written to the log in any mode (§6.2), so a redacted value cannot leak there. The record may still capture request *argument* values depending on mode and outcome (§6.2). This lets operators control what the MCP host receives while the audit trail retains the redaction provenance.

### 6.4 Data residency in default configuration

**eunox sends no telemetry and never phones home.** It opens no analytics,
usage-reporting, or update-check connections of its own. The only outbound
connections it makes are the ones the operator configures: the upstream MCP
server (when it is a remote HTTP upstream), the JWKS endpoint (when `--jwks-uri`
is set), and Redis (when `--redis-addr` is set). Adding any background network
activity requires an explicit design discussion (see
[CONTRIBUTING.md](../CONTRIBUTING.md)).

In the default configuration, all data stays on the machine running the proxy:

| Data               | Location                             |
| ------------------ | ------------------------------------ |
| Audit records      | `~/.eunox/audit.jsonl` (local file)  |
| HMAC signing key   | `~/.eunox/audit.key` (local file)    |
| Kill-switch state  | In-process memory                    |
| Call counter state | In-process memory                    |
| JWKS cache         | In-process memory                    |
| Policy manifest    | Local file path provided by operator |

When `--redis-addr` is configured, kill-switch and call-counter state are persisted to the Redis instance at that address. When a remote `upstreamUrl` is configured, tool call requests are forwarded to that URL (with the `upstreamAuthHeader` if provided). The remote-upstream HTTP client does **not** follow redirects: an MCP JSON-RPC POST has no legitimate redirect, and Go strips only `Authorization`/`Cookie` on a cross-host redirect, so a custom-named `upstreamAuthHeader` (e.g. `X-Api-Key`) would otherwise be replayed verbatim to whatever host a compromised upstream named in a `30x` `Location` — leaking the credential. A `30x` from the upstream is surfaced as an error instead. No other data is transmitted externally by the proxy.

**Credential redaction in error paths and diagnostics.** A remote `upstreamUrl` can carry a credential in userinfo (`https://user:pass@host`), in a query/fragment (`?api_key=…`, `#access_token=…`), or **in the path** — for whole families of endpoints the path *is* the secret (a Slack incoming webhook `…/services/T…/B…/<secret>`, a Telegram bot URL `…/bot<token>/…`, a presigned object URL). Every path that surfaces such a URL routes it through a redactor, and there are deliberately **two**, chosen by where the output lands:

- **Log-facing** (`capability.RedactURLForLog`) — config-validation errors, the live-upstream probe's `*url.Error`, the JWKS startup banner, and the operational stderr lines that name the upstream (session start on both transports, the remote-upstream notice, a failed session-teardown DELETE). It keeps `scheme://host` and drops **everything** else: userinfo, the whole query, the fragment, and the path (replaced with `/[redacted]`). These land in the systemd journal, container stdout, or a CI log — commonly a lower protection tier than the config file the secret came from. The most likely way a webhook URL reaches a *validation* error is a scheme typo, which parses cleanly: keeping the path would print the whole secret. An authority-less value (a scheme-less `upstreamUrl`, which `url.Parse` accepts with host and path together) keeps its host, so the message still names an endpoint. A credential it can see but cannot locate — a userinfo containing `/`, which puts the authority boundary inside the password — collapses to a fixed placeholder rather than a partial echo.
- **Bundle-facing** (`config.RedactURL`) — the `doctor` support bundle's audit tail and its non-upstream URL config fields. It scrubs userinfo and every query *value* but preserves query parameter **names** and the **path**, which is load-bearing there: the audit tail records which resource URIs were allowed and denied, so the path is the content being audited, and an RFC 9728 resource URI or authorization server is a published identifier whose route (`/mcp/github` vs `/mcp/jira`) is the diagnostic point.

  **`upstreamUrl` is the exception**: inside the bundle it takes the *log-facing* redactor, path included. It is the one config field that is routinely a webhook endpoint whose path is the entire credential, no allowlist of field *names* can catch that (the field name is legitimate), and the bundle is explicitly produced to be pasted into a bug report — the highest-exposure sink in the binary. The host still identifies the upstream.

This matters most for the **live probe**: a connection failure surfaces a Go `*url.Error` whose text the standard library scrubs only of the userinfo *password* — the username and the entire query string still print (as does the full credential, password included, from a `url.Parse`-fatal endpoint, which the standard library does not scrub at all). Both redactors handle the hierarchical, opaque (`scheme:user:pass@host`, including an opaque body that itself embeds a later `://`), scheme-less, and unparseable forms and fail safe (never return the raw value) on anything they cannot fully scrub. The `doctor` bundle additionally fails closed on an audit record whose `details` is a non-object JSON value, redacting it wholesale rather than emitting it verbatim.

**Generated-file handling (`init` / `suggest`).** `eunox init` and `eunox suggest` write their output at mode `0600`, refuse to overwrite a pre-existing file unless `--force` is passed (so a hand-edited manifest is not silently clobbered), and — because `O_CREATE` applies a mode only on creation — re-tighten the mode to `0600` on an intentional overwrite. This is load-bearing for `init --config-output`, whose generated config can embed a cleartext `--upstream-auth-header` credential: writing it into a pre-existing group/world-readable file would otherwise leave that credential exposed.

**Env-ref misdirection fails closed.** `audit.log` and `audit.keyPath` accept `${VAR}` references like the credential/URL config fields. An **unset** reference survives expansion as literal `${VAR}` text, which would silently write the tamper-evident tape (or its HMAC signing key) to a path literally named `${VAR}` — a fail-open on the core integrity artifact. The loader now rejects an unset reference in either field at startup, mirroring the fail-closed guard the `upstreamUrl`/credential fields already had. The same guard covers `listen.allowedOrigins` (an unset reference there boots cleanly and then matches no real `Origin`, so a browser client gets a bare 403 with nothing on stderr tying it to the config) and a stdio upstream's `command`/`args` (an unset reference there fails at *exec* time on the first session rather than at startup, so the operator learns of a config typo from a client's failed handshake).

The `command`/`args` leg is restricted to the **braced** `${VAR}` spelling, and so — since 1.47 — is the EXPANSION of those fields, along with everything after the first `?`/`#` of an `upstreamUrl`. Those two fields are arbitrary subprocess argv rather than a URL, and a bare `$word` is ordinary literal content there — an OData `?$filter=`, a regex `$anchor`, a jq expression, or anything the child interpolates itself. Applying the broader bare-`$` rule the `upstreamUrl` guard uses would refuse to *start* a config that works today, blaming a variable the operator never wrote; `${VAR}` is unambiguous intent to substitute. Note the guard's COVERAGE is still a per-field list, so a field is guarded only once it is added to it — though every guarded field now reads its grammar from the field's own declaration, so a guard and an expansion cannot disagree about what a `$` means there. Most of the unguarded rest happen to fail at startup for their own reasons (a `${VAR}` in `name` fails the route-name pattern, in `bind` fails `net.Listen`, in `policy` fails manifest loading, in `trustedProxyCIDRs` fails CIDR parsing), which is why the remaining gaps are quiet rather than loud.

### 6.5 Verified JWT claims at the policy-evaluator boundary

When a `policy` condition delegates to an external evaluator (the library-only `WithPolicyEvaluator` extension point — OPA/Cedar/etc.; the stock binary embeds none and denies `policy` conditions fail-closed), the proxy serializes the request into the standard Rego `input` document and hands it to that evaluator. `input.claims` carries the **entire** top-level claim set of the verified JWT — not only the four eunox-canonical fields (`sub`, `iss`, `task_id`, `agent_id`) but every other claim the IdP issued, including the nested `mcp` object and any PII the token happens to carry (`email`, `name`, group/role lists, …). A policy that restricts on an arbitrary IdP claim requires this; the trade-off is that whatever the IdP puts in the token now crosses the proxy→evaluator boundary on every evaluation, where before this change only the four fields did.

This is bounded and does not change the audit or data-residency posture:

- **Verification-gated.** The claim set is assembled only after the token's signature is verified, so an unsigned or invalid token contributes nothing.
- **Audit log unaffected.** Only the validated `agent_id`/`task_id`/`user_id` (the `sub` subject) reach an audit record (§6.1); `input.claims` is never written to `audit.jsonl`.
- **Stays where the evaluator runs.** A `PolicyEvaluator` is in-process operator code (§6.4 lists no policy-evaluator egress). Claims leave the host only if that operator-supplied evaluator itself forwards them — e.g. to an OPA sidecar. Operators wiring an external evaluator should treat `input.claims` as potentially PII-bearing and scope what their evaluator transmits accordingly.
