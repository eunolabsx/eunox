## 1. System Overview

`eunox` is a single binary that sits in-path between an MCP host (Claude Desktop,
an agent runtime, a test harness) and an MCP server (local subprocess or remote HTTP
endpoint). Every policy-relevant JSON-RPC message is evaluated against a policy before
it is forwarded. Calls that violate policy are blocked and logged; calls that are
permitted are forwarded and logged.

Enforcement is not limited to `tools/call`. The proxy evaluates a decision on each of
the MCP method surfaces it understands — `tools/call`, `tools/list`, `resources/read`,
`resources/subscribe`, `resources/list`, `prompts/get`, `prompts/list`, and
`sampling/createMessage` — and **fails closed on any MCP method it does not map to a
decision** (the message is denied with `AUTHORIZATION_FAILED` rather than blindly
forwarded). The `…/list` surfaces are filtered **in enforce mode**: entries the caller is
not permitted to invoke are removed from the listing before it reaches the host. Methods
outside the mapped set — notably `resources/templates/list` and `completion/complete` —
are therefore denied, not forwarded, so they cannot be used to enumerate names, URI
templates, or argument shapes for entries that `…/list` filtering removed. In **audit
(observe/wiretap) mode**, by contrast, `…/list` returns the *full upstream catalog
unfiltered* — that mode forwards (and merely records) calls it would otherwise deny, so
hiding entries the host can still successfully call would contradict "observe everything,
block nothing"; the kill switch is the only check that still hard-blocks. Operators who
need the host to see only permitted entries must run the route in enforce mode.

```
MCP host → eunox proxy → MCP server (subprocess or remote HTTP)
```

The proxy supports two transports:

| Transport | How the upstream MCP server is reached                                                                       |
| --------- | ------------------------------------------------------------------------------------------------------------ |
| `stdio`   | Upstream is a local subprocess; proxy bridges stdin/stdout                                                   |
| `http`    | Upstream is the proxy's HTTP listener; upstream is a subprocess (default) or a remote URL (`upstreamUrl`) |

Three policy sources can be combined:

| Mode                          | How it is activated                                       | What it enforces                              |
| ----------------------------- | --------------------------------------------------------- | --------------------------------------------- |
| No policy (audit / wiretap)   | No `policy` and no `--jwks-uri`, with `--audit` (stdio host) or `enforcement: audit` (gateway route) | All calls forwarded and logged, none blocked by policy — but an active kill switch hard-blocks even a wiretap route. A gateway route with no policy and no audit posture instead fails closed at startup |
| Manifest PDP                  | route `policy: [manifest.yaml]`                           | Constraint file on disk                       |
| JWT PDP                       | `--jwks-uri` + `--jwt-audience` (required, or `--jwt-allow-any-audience`) + `--jwt-issuer` (required, or `--jwt-allow-any-issuer`) | IdP-issued capability claims in bearer token  |
| Manifest + JWT (intersection) | Both flags set                                            | JWT can only narrow what the manifest permits |

## 2. Trust Boundaries

### 2.1 What the proxy trusts after verification

| Item                                                                      | How trust is established                                                             |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| JWT capability claims (`mcp.capabilities`, `mcp.task_id`, `mcp.agent_id`) | JWT signature verified against the JWKS endpoint; `exp`, `iss`, `aud` validated (signature/issuer/audience validation and the identity claims `mcp.task_id`/`mcp.agent_id` are stable; `mcp.capabilities`-based enforcement is experimental and gated behind `--jwt-experimental-capabilities`, off by default — see §3.5) |
| Manifest policy file contents                                             | Loaded at startup from a local path the operator controls; not re-fetched at runtime |
| Kill-switch state (in-memory or Redis)                                    | Checked on every `Decide()` call before capability evaluation                        |
| Call counter state (in-memory or Redis)                                   | Checked on every `Decide()` call; enforces `maxCalls` conditions                     |

### 2.2 What the proxy verifies on every request

**JWT PDP mode** (`--jwks-uri` set):

0. The JWKS endpoint is fetched over a tamper-resistant channel. `--jwks-uri` must be `https://`; plaintext `http://` is accepted only to a loopback host (no network MITM surface) unless the operator explicitly opts into insecure remote http with `--jwks-allow-insecure-http`. The JWKS is the root of trust for every token, so a plaintext fetch to a remote host — where an on-path attacker could substitute the key set and forge capability claims — fails closed at startup. The same scheme policy is re-applied to every HTTP redirect the JWKS fetch follows, so a valid `https://` endpoint cannot `302` the key fetch onto plaintext remote http (the redirect is refused and the token rejected). A redirect must also stay on the **configured host**: a hop whose target hostname differs from the `--jwks-uri` host is refused **before the request is sent**, even when both are `https://`. Without this, an open-redirect on the legitimate IdP (or a compromised redirector) could bounce the key fetch to an attacker host and substitute the entire key set — forging capability claims for every token — since the scheme check alone passes an `https→https` hop. The port and path may still change (an IdP may relocate its key set within its own host), but the host may not.
1. `Authorization: Bearer <token>` header is present and well-formed.
2. JWT signature is valid against one of the keys in the cached JWKS (algorithm restricted to RS256/RS384/RS512, PS256/PS384/PS512, ES256/ES384/ES512, EdDSA — symmetric algorithms are unconditionally rejected).
3. `exp` is present and has not passed (a conservative 10-second clock-skew tolerance is applied by default — `DefaultTokenLeeway`, tunable via `--jwt-leeway`). A token that omits `exp` is rejected — go-jose validates `exp` only when present, so without this an `exp`-less token would never expire, defeating the bearer-token expiry and kill-switch revocation window.
4. `iss` matches `--jwt-issuer`. This is **required** in `--jwks-uri` mode: the proxy refuses to start without it unless the operator explicitly opts out with `--jwt-allow-any-issuer`, so a token from another issuer whose signing key is served by the same JWKS endpoint cannot be replayed against eunox.
5. `aud` contains `--jwt-audience`. This is **required** in `--jwks-uri` mode: the proxy refuses to start without it unless the operator explicitly opts out with `--jwt-allow-any-audience`, so a token minted for another relying party of the same IdP cannot be replayed against eunox. An empty or whitespace-only audience pin is treated as *no* pin and fails closed (every token is rejected regardless of its `aud`) rather than degenerating into a match against a token whose own `aud` is the empty string — the empty value can never be a trusted audience. In gateway mode, where the validator accepts the union of every route's audience, an empty/whitespace entry is dropped from that set for the same reason before a per-route check narrows to the specific route's audience.
6. `mcp.capabilities` claim covers the requested tool name. A token that omits the `mcp.capabilities` claim entirely defers to the route's manifest, which becomes the deciding authority (the JWT carries identity only). On a route with **no** manifest (an unpoliced/wiretap route), there is no backstop to defer to, so an identity-only token is **denied**, not allowed — otherwise any validly signed token that simply leaves the claim out would be granted every target. In effect, enabling JWT mode requires every request to be covered by either a capability claim on the token or a manifest on the route (ADR-0001, amended 2026-06-13). `…/list` filtering composes the same way: an identity-only token on a no-manifest route sees an empty listing.
7. Any condition shorthand in the capability claim (path glob, SQL verb) matches the actual arguments.

When JWT capability-claim enforcement is enabled (`--jwt-experimental-capabilities`), every `mcp.capabilities` entry is structurally validated as the token is first verified — not only when a request happens to match it. A malformed **target-name** glob (e.g. an unclosed `[` character class) is rejected outright (`error_type: invalid_capabilities`), exactly as the manifest loader rejects the same pattern at startup, closing a parity gap: without it a malformed grant would validate cleanly, then silently match nothing at enforce time (`path.Match` treats an invalid pattern as a non-match), producing an inert deny-all that surfaces only as an opaque `AUTHORIZATION_FAILED` — indistinguishable from a target the token simply never listed. (An http(s)-resource claim's `?query` component is exempt, since it is compared literally rather than as a glob. With the flag off — the default — a token that carries any `mcp.capabilities` claim is rejected earlier as `capabilities_disabled`, before any glob is examined, so this structural check applies specifically to the experimental capability-claim mode.)

A token that fails any of these checks is rejected with an opaque `401 Unauthorized` — the go-jose / validation message, which can disclose claim values, the accepted algorithm, the configured issuer, or key-rotation state, is never echoed to the caller. The matching `JWT_INVALID` audit record applies the **same** non-disclosure posture: it records a stable `details.error_type` category (`expired`, `invalid_signature`, `invalid_audience`, `invalid_issuer`, `missing_claims`, `unsupported_version`, `invalid_capabilities`, `malformed_token`, `jwks_unavailable`, …) rather than the raw message, so an operator forwarding the tape to a SIEM gets a fixed code to match on without re-introducing the disclosure the `401` avoids — the same fixed-code-not-free-form-prose discipline applied to upstream error results (§5.5) and audit-detail truncation markers (§6.2). The `jwks_unavailable` category is specifically reserved for a validation that failed because the key set could not be fetched (network error, non-`200`, empty or oversized set, or an open circuit breaker) rather than because the token was bad: the presented token was never checked against a key, so recording it identically to a forged token (`invalid`) would mislead an operator triaging the tape during an IdP/JWKS outage. As with `ORIGIN_REJECTED`, this rejection precedes any session lookup, so the unverified, client-supplied `Mcp-Session-Id` is kept out of the structured `session_id` field and preserved only as the clearly-unverified `details.claimed_session_id`.

**Manifest PDP** (`policy` set):

1. Kill-switch state is not active for this session (checked first, before anything else).
2. A constraint in the manifest covers the request's namespaced `target` (glob match, scoped to the same namespace). Every `target` carries a mandatory namespace prefix — `tool:`, `resource:`, `prompt:`, or `system:` — and matching only happens within a namespace, so a `tool:` constraint can never satisfy a `resource:` request. No matching constraint → deny (`AUTHORIZATION_FAILED`): the manifest is a deny-by-default allowlist, so a target absent from it is rejected, not forwarded.
3. The constraint's `actions` list permits the call (exact match `"call"` / wildcard `"*"`, or semantic category via action resolver). Action–namespace pairing is validated at manifest load: e.g. `tool:` targets reject `read`/`get`/`allow` actions and fail closed at startup.
4. `argumentSchema` validation passes (JSON Schema subset: type, pattern, length, min/max, enum, required, properties, additionalProperties, items). This runs **before** the condition loop, so a structurally invalid call is denied with `INVALID_PARAMS` regardless of any condition outcome. `argumentSchema` is `tool:`-only (SPEC § 3.2.1/3.2.2): it validates a tool-call's argument map, which `resource:`/`prompt:`/`system:` requests do not carry, so one declared on a non-`tool:` target is **rejected at load** — it can never become a declared-but-unenforced guard, the same way a `directives` block on a non-`tool:` target is rejected. The enforcement path fails closed independently as defense in depth: the `resources/read` and `prompts/get` decision paths evaluate conditions through `EvaluateConditions`, which does not run `argumentSchema` validation, so a `resource:`/`prompt:` constraint that carries one (e.g. from a manifest assembled in-process rather than through the loader) is denied with `ENFORCEMENT_ERROR` rather than forwarded with the schema silently skipped.
5. All attached `conditions` pass: `TimeWindow`, `IPRange`, `AllowedOperations`, `AllowedExtensions`, `AllowedTables`, `MaxCalls`, `RecipientDomain`, `AllowedValues`, `Policy`, `Custom`. `conditions` are strictly boolean predicates. Any condition rejection — including a handler whose backend errors, e.g. a `MaxCalls` counter that is unreachable — fails closed with `CONDITION_FAILED` (§5.3). The proxy additionally reserves `ENFORCEMENT_ERROR` (JSON-RPC `-32603`, the internal-error code, distinct from `CONDITION_FAILED` and `CAPABILITY_DENIED`) as a fail-closed guard for an internal engine failure during evaluation; the engine does not currently surface such an error, so this code is not emitted on any reachable path today, but the guard keeps an unexpected internal failure from ever falling open or being mistaken for a policy decision.
6. After the call is allowed, any `directives` on the matched constraint are applied as post-allow obligations (currently `redactFields`). Directives live in a separate `directives` array, not in `conditions`; an unknown directive type fails closed.

When both `--jwks-uri` and `policy` are set, a call must pass **both** checks. The JWT can only narrow what the manifest permits — it cannot expand it.

### 2.3 What the proxy explicitly does not verify

| Item                                          | Why                                                                                              |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Content of LLM prompts or completions         | The proxy operates at the tool-call protocol layer, not the inference layer                      |
| Reason the agent decided to call a tool       | Intent is opaque; the proxy enforces _what_ is called, not _why_                                 |
| Integrity of the MCP server's response        | The proxy forwards upstream responses verbatim (except `redactFields` directive obligations)      |
| Tool description + parameter description text (without descriptionHash) | Tool descriptions and their parameter descriptions flow to the model verbatim; a tampered upstream could inject steering instructions in either. Mitigated by the optional `descriptionHash` pin on exact-name `tool:` entries, which covers both surfaces (§3.7). |
| Upstream `initialize` `instructions` text     | The server's `instructions` field (model-facing guidance returned in the `initialize` handshake) is forwarded to the host verbatim — the same steering/injection surface as tool descriptions, but with no `descriptionHash`-style pin to constrain or detect changes. Captured once per session at handshake; the manifest cannot currently bound it. |
| Integrity of the agent process                | Host OS/container responsibility; the proxy cannot attest client-side code                       |
| Content of tool call arguments (semantically) | The proxy validates argument _shape_ (schema) and specific _values_ (allowedValues), not meaning |
| IdP infrastructure security                   | The proxy trusts JWTs that pass signature verification; IdP compromise is out of scope           |

## 3. Attack Classes Mitigated

### 3.1 Capability Claim Forgery

**Attack:** An attacker crafts or modifies a JWT to include capability claims (`mcp.capabilities`) for tools they are not permitted to call — for example, adding `"write_file"` to a token that was issued with only `"read_file"`.

**Mitigation:** JWT signature validation using the JWKS fetched from `--jwks-uri`. The proxy:

- Accepts only asymmetric algorithms (RS256, RS384, RS512, PS256, PS384, PS512, ES256, ES384, ES512, EdDSA). Symmetric algorithms (HS256, HS384, HS512) and the `none` algorithm are rejected unconditionally by the go-jose/v4 parser.
- Rejects tokens whose `kid` does not appear in the cached JWKS; performs an immediate forced re-fetch in case the IdP rotated keys before falling back to rejection.
- Deduplicates concurrent JWKS fetches using a singleflight implementation, preventing thundering-herd behavior on key rotation.
- Requires an `exp` claim and applies a conservative 10-second clock-skew tolerance by default (`DefaultTokenLeeway`, tunable via `--jwt-leeway`) on its validation; a token with no `exp` (which would never expire) is rejected.

Any modification to the JWT payload invalidates the signature, and the modified token is rejected before its claims are read. Signature/`exp`/`iss`/`aud` validation is stable and always active. Acting on a forged `mcp.capabilities` claim additionally requires the experimental opt-in flag `--jwt-experimental-capabilities`; with the flag off (the default), a token carrying `mcp.capabilities` is rejected at validation regardless of its signature, so the experimental schema is fail-closed.

**Verified-token cache:** signature verification and the claim decodes are the per-request hot path, so a validated token's claims are memoized for a short TTL (30 s, capped at the token's own remaining `exp` lifetime) keyed by the SHA-256 of the raw token; a repeat of the same token within that window skips re-verification. This narrows only the *re-verification* window — it does not widen trust: `exp` is still honored (the cache never outlives the token), and the kill switch, per-route audience, and manifest policy are re-evaluated per call in `Decide` (they are not cached), so a killed session is still blocked on its next call and a revocation cannot be outrun by the cache. The residual exposure is that a token becoming invalid for a reason detectable *only* by re-running signature/`iss`/`aud` verification (e.g. a mid-life JWKS key removal) is still accepted for at most the TTL.

**Residual risk:** A compromised IdP can issue arbitrary tokens that pass signature verification. IdP security is explicitly out of scope (§4.4).

### 3.2 Tool Call Parameter Injection

**Attack:** An agent (or an adversary that has influenced the agent) calls a permitted tool with arguments that exceed the intended scope — for example, calling `read_file` with `path=/etc/shadow` when the policy was intended to permit only `/reports/*`.

**Mitigation (argument schema validation):** The manifest's `argumentSchema` field applies a JSON Schema subset to the actual arguments of every tool call before the call is forwarded. The validator covers: `type`, `pattern` (regexp), `minLength`, `maxLength`, `minimum`, `maximum`, `required`, `enum`, `properties`, `additionalProperties`, `items`, `minItems`, `maxItems`. A call that fails schema validation is denied with code `INVALID_PARAMS` (JSON-RPC `-32602`) before reaching the upstream server, and before any condition is evaluated.

**Mitigation (condition types):** Several built-in condition types enforce argument-level restrictions directly:

| Condition           | What it restricts                                                                                    |
| ------------------- | ---------------------------------------------------------------------------------------------------- |
| `allowedValues`     | Argument value must match one of the allowed strings or globs (e.g., `path` must match `/reports/*`) |
| `allowedOperations` | SQL verb in the named `argument` must be in the permitted set (`SELECT`, not `DROP`)                  |
| `allowedTables`     | Table/column name(s) in the named `argument` must be in the permitted set (matched case-insensitively, like SQL identifiers, so a different-case spelling cannot bypass the allowlist) |
| `allowedExtensions` | File extension of the named path `argument` (a single path or an array of paths) must be permitted   |
| `recipientDomain`   | Email recipients must belong to the permitted domain                                                 |

**Mitigation (JWT condition shorthands):** In JWT PDP mode, capability claim shorthands (JWT schema v0.2) enforce argument-level restrictions inline: `"tool:read_file?path=/reports/*"` restricts the `path` argument to the glob `/reports/*`; `"tool:query_db?op=SELECT"` restricts the SQL operation. Multiple constraints can be `&`-chained in a single shorthand (`"tool:query_db?op=SELECT&table=public.*"`) and are ANDed together; values are URL-decoded before matching. When several capability entries name the same tool, the proxy intersects their per-argument constraints (cross-argument intersection) rather than taking the union, so the narrowest grant wins.

### 3.2.1 Cross-Tool Sequencing (Sequential Exfiltration)

**Attack:** Each tool an agent calls is individually within policy, but a *sequence* of them achieves an outcome the policy intends to prevent. The canonical case is read-then-exfiltrate: the agent calls `read_credentials` (permitted — it has a legitimate use), then `write_external` (permitted — it has a legitimate use), and the pair moves secrets out of the trust boundary. Per-call and per-tool controls (argument restrictions, even `maxCalls: 1` on each tool independently) do not catch this: the read and the write are each a single, in-budget, in-scope call.

**Mitigation (`sequenceBlock` condition):** `sequenceBlock` denies a call when any tool named in its `afterTools` list has already been allowed earlier in the same session. Placing `sequenceBlock(afterTools: [read_credentials])` on `write_external` blocks the external write for the remainder of any session in which credentials were read, while leaving both tools available to sessions that use only one of them (and leaving the harmless reverse order — write, then read — allowed). The decision is session-scoped: call history is keyed by session ID, recorded only on an *allowed* call (a denied antecedent never reaches the upstream and never arms the block), and consulted via a read-only lookup so that testing "did A run?" does not itself count as a call. With no call-counter backend configured, or on a request that carries no session ID, the condition fails closed. A call-counter *fault* also fails closed: an error reading history denies the call, and — critically — an error while *recording* an allowed antecedent is not swallowed. Rather than let a dropped marker cause a later lookup to read a falsely-absent antecedent and fail open, the engine surfaces the write error and denies the call that triggered it with `CONDITION_FAILED` (audit detail `phase: record`). Because every allowed call is recorded so any tool can later serve as an antecedent, a counter-backend fault denies every allowed call in the session for its duration, not only sequence antecedents.

**Residual risk:** The control is per-session. An adversary who can split the read and the write across two *distinct* sessions (e.g. two separate client connections that each obtain their own `Mcp-Session-Id`) is not stopped by a session-scoped rule — defend that case with a per-tool grant that never co-occurs in one policy, or with a JWT whose capability claims grant only one of the two tools per task. The marker also reflects only calls the proxy itself allowed; a tool whose side effect reads credentials without going through a `read_credentials`-named call is not observed.

### 3.3 Session Hijacking via Session-ID Spoofing

**Attack:** A malicious client presents an existing session ID in the `Mcp-Session-Id` HTTP header to impersonate an authenticated session and perform tool calls under that session's policy context.

**Mitigation:** Session IDs are UUID v4 values minted by the proxy at session creation. An attacker who does not know a valid session ID cannot successfully route a request. The proxy validates the session ID against its in-memory session registry on every request; unknown session IDs receive 404.

**Kill-switch binding:** When a session is killed (via `eunox kill <session-id>` or the `/control/kill` API), the session ID is registered in the kill-switch store. Every subsequent `Decide()` call checks kill-switch state first, before evaluating capability conditions. A session whose ID has been killed is denied regardless of whether a valid JWT or manifest policy would otherwise permit the call. This now holds for a policyless wiretap route too: its decision point is wired to the shared kill switch, so an emergency stop halts a forward-and-log route just as it halts a policed one.

The request paths that carry no per-call policy decision — and so bypass `Decide()` — check the kill switch explicitly, so an emergency stop is total: the `*/list` enumerations and the session-creating `initialize` deny on a killed (or globally killed) session before contacting the upstream, and the standalone SSE **GET** notification stream is covered on both open and hold. A killed session cannot **open or re-open** a stream (refused HTTP 403), and a stream **already open** when the kill lands is torn down by the kill path itself: `/control/kill` evicts the session's open SSE streams — per-session for a targeted kill, every session for a global one — by signaling the stream loop to return, so a killed session stops receiving upstream notifications at once instead of lingering on an open channel until the idle reaper or upstream exit closes it. Eviction only detaches the notification listeners: it does not reap the upstream and does not change the kill switch's policy-gate role (the now-streamless session is reaped on the normal idle path, and a reopen is refused by the same 403 check), so the semantics stay "deny everything for a killed session" with the in-flight notification channel now closed as part of that.

Independently of the kill switch, an SSE stream opened with a Bearer token is bounded to that **token's expiry**. The token is validated once, at stream open, so the stream arms a timer at the verified `exp` and ends when the lifetime elapses, forcing the client to re-open — and thus re-validate — with a fresh token. Kill-switch eviction covers administrative revocation; this covers plain expiry, so an expired (or IdP-revoked but not kill-switched) client cannot keep receiving server→client traffic indefinitely on a stream authorized long ago.

The `/control/kill` HTTP endpoint is restricted to loopback addresses only (`127.0.0.1`, `::1`) — any request from a non-loopback source is rejected with 403 — **and** requires an auto-generated control token (SEC-07). Under `--trust-forwarded-for` the loopback check additionally fails closed when the request carries an `X-Forwarded-For` header (the same guard covers `/healthz` and `/metrics`): a reverse proxy fronting the listener presents its own loopback source address on behalf of an off-host client, so the header is treated as proof the request arrived via the proxy and is denied — a directly-connecting local caller never sets it. The loopback check **also** pins the request `Host`, because a loopback *source* alone is satisfied by a victim's own browser after a DNS rebind (the TCP connection still originates on the local host, §3.6), so without the pin attacker JavaScript on a rebound page (`Host: attacker.com`) could read `/healthz` and `/metrics` operational state (session/route counts, audit-degradation and kill-switch health). The pin lives in the shared loopback check, so it covers `/control/kill` as well — that endpoint is gated primarily by its required control token, and the `Host` pin is an additional layer rather than its main defense. What the pin rejects is a foreign **name**, which is what a rebind necessarily presents (the victim's browser still believes it is addressing the attacker's hostname, which is what makes the response same-origin readable). It admits the `checkOrigin` allowlist (the loopback names plus any non-wildcard bind host), any loopback host — literal or alias, so a scrape via `127.0.0.2` or an HTTP/1.0 probe is not broken — and an absent `Host` (HTTP/1.1 requires the header and every browser sends it, so an empty value is a non-browser local caller). A browser cannot be steered into presenting a loopback literal as a rebound page's `Host`: fetching the literal directly is cross-origin, so it carries an `Origin` and the middleware rejects it first. A reverse proxy that fronts these endpoints while rewriting `Host` to an external name is denied — front them on a loopback name, or scrape the listener directly. At startup the proxy mints a 256-bit random token and writes it to a 0600 file (`~/.eunox/control.token` by default, configurable with `--control-token-path`); `/control/kill` rejects any request whose `X-Eunox-Control-Token` header does not match it (constant-time compare), independently of `listen.authToken` / JWT mode. This closes the gap where a same-host process — e.g. a compromised upstream subprocess, which by design runs on the same host — could trigger the emergency stop merely by reaching the loopback endpoint. The token authenticates the *control* of the kill switch, not the cache stale-ness; `eunox kill` reads the file automatically. A proxy with no control token configured refuses the endpoint (503, fail closed) rather than serving it unauthenticated. **Residual:** the 0600 file is readable by the proxy's own UID, so a process compromised *as that same user* with filesystem access can still read it; sandbox the upstream (no read access to the token path) or run it under a distinct UID where that matters.

**Limitation:** The proxy does not implement token binding between the bearer JWT and the session ID. An attacker who learns both a valid JWT and a valid session ID could make requests. This is the tradeoff of the MCP session model; mitigate in high-security environments by setting `listen.authToken` to add a shared secret layer on the proxy's HTTP listener.

### 3.4 Audit Log Tampering

**Attack:** An attacker with local filesystem access modifies or deletes audit records in `~/.eunox/audit.jsonl` to conceal unauthorized tool calls or suppress evidence of policy violations.

**Mitigation (HMAC-SHA256 signing + hash chain):** Each audit record is signed with HMAC-SHA256 using a 256-bit key loaded from `~/.eunox/audit.key`. The HMAC covers the full record JSON — including the record's `seq` and `prev_hmac` chain fields — excluding the `_hmac` field itself. The signature is appended as `"_hmac": "sha256:<hex>"` before the record is written.

Each record additionally carries a monotonic `seq` and a `prev_hmac` holding the `_hmac` of the preceding record, forming a tamper-evident chain (continuous across restarts and rotation; a fresh log's first record carries the `sha256:genesis` sentinel). `eunox audit-verify` recomputes every record's HMAC — catching any field modification — and verifies `prev_hmac` linkage and `seq` contiguity across consecutive records — catching deletion, reordering, and insertion. Because the HMAC is recomputed over the record's modeled fields, a signed record carrying any **unknown top-level field** (one outside the record schema, e.g. an injected `"operator_override"`) is rejected as invalid rather than silently passing — an extra field cannot ride along uncovered by the recomputed signature. A signed record with a **duplicate top-level key** is likewise rejected: JSON decoding is last-wins, so an attacker could otherwise prepend a duplicate (e.g. `{"decision":"allow",…,"decision":"deny",…}`) that re-marshals to the signed value and passes the HMAC while a first-wins consumer (a SIEM, `jq`, a raw-line grep) reads the attacker's injected value — verification walks the top-level object and fails closed on any repeated key. The repeat test is by **canonical field**, not exact string: Go's `encoding/json` binds object keys to struct fields case-insensitively, so a case-variant spelling (`{"Decision":"allow",…,"decision":"deny",…}`) also feeds the single `Decision` field and re-marshals to the signed value — verification normalizes each key to the field it binds to before the duplicate check, so a case-variant duplicate is rejected exactly like an exact-case one. It walks the **entire rotated set as one chain** — every rotated sidecar oldest-first, then the current base log — so the linkage is checked across file boundaries too: deleting an entire interior rotated file is caught because the file after the gap fails to chain onto the file before it (a `prev_hmac` mismatch *and* a `seq` gap), which verifying the current base file in isolation could not detect. Because the chain fields are themselves signed, an attacker without the key cannot rewrite the chain to conceal a removed record:

```
$ eunox audit-verify
Checked 142 record(s): 142 valid, 0 invalid, 0 skipped; 0 chain break(s).

$ eunox audit-verify          # after a record was deleted
CHAIN BREAK at seq 88: prev_hmac does not match the preceding record (a record was deleted, reordered, or inserted)
Checked 141 record(s): 141 valid, 0 invalid, 0 skipped; 1 chain break(s).
# exit status 1
```

The audit key is generated once at first startup using `crypto/rand` (Go's CSPRNG, backed by the OS entropy source) and stored at `~/.eunox/audit.key` with mode `0600`. Loss of the key means existing records cannot be re-verified, but does not affect enforcement.

**File modes are re-tightened on load, not just on creation.** The key file and the audit log are created `0600`, but `O_CREATE` applies that mode *only* when it creates the file — a log or key that already exists is opened/read with its on-disk mode unchanged. So a file left group/world-readable by a looser `umask` on a prior run, a backup restore, or a deliberately pre-created path would otherwise keep that mode. On load the proxy drops any **group/world** access bits from a pre-existing log and key file (and from an active log opened by rotation), preserving the owner bits: e.g. `0644` becomes `0600`, while an operator's deliberately owner-write-only `0200` log is left untouched (so its tail read still fails closed into the chain-resume path rather than being silently re-opened for read). This matters most for the key: a readable HMAC key lets any local user forge records (see Residual risk) — and because a key found group/world-accessible may *already* have been copied, the loose→tight transition is logged as a `SECURITY` warning recommending rotation, not fixed silently. The re-tightening is best-effort with a warning on the rare backend that cannot `chmod` (FAT/exFAT, some CIFS/NFS mounts) — the same backends the key-publish path already tolerates — since refusing to start there is worse than the (HMAC-integrity-protected) log retaining its prior mode.

The key *directory* is created `0700` when the proxy creates it, but a pre-existing key directory is **not** re-tightened: a mode-`0600` key is unreadable by other users regardless of the directory mode (directory perms gate traversal/listing, not file contents), and `--audit-key-path` is explicitly aimed at containerized / multi-instance deployments where the key often lives in a shared or read-only secret mount whose directory mode the operator manages. Narrowing that directory on every load would be collateral the load-bearing key-file tighten does not need.

**Key rotation.** Each record carries a `key_id` — a non-secret digest of the signing key — so that records remain verifiable after the key changes. The key file holds one 64-hex-character key per line (blank lines and `#` comments ignored): the **first** line is the active signing key and any further lines are retired keys retained only for verification. To rotate, prepend a freshly generated key and keep the old one below it. `eunox audit-verify` loads every key in the file, indexes them by `key_id`, and verifies each record against the key that signed it — so a tape that straddles a rotation verifies end to end. A record whose `key_id` names a key absent from the file fails closed; a record with no `key_id` (written before rotation support) is tried against every key, so a tape that straddles the format change verifies the same way the pre-chain format does. The `key_id` is a one-way digest and discloses nothing about the key material.

**Externally-supplied key entropy.** An operator-supplied key — injected via `--audit-key-path` or `EUNOX_AUDIT_KEY_PATH` for containerized or multi-instance deployments — must be a full 256-bit (32-byte) value drawn from a cryptographically secure random source; generate one with `openssl rand -hex 32` (or any CSPRNG) so it matches the entropy of an auto-generated key. The proxy fails closed at startup on an externally-supplied key that does not decode to exactly 32 bytes, and additionally rejects an **all-zero** 32-byte key: zeros are the canonical placeholder a misconfigured deployment supplies (a zeroed or unwritten secret, a value rendered from an unset environment variable), and an all-zero HMAC key carries no entropy — anyone who knows the construction can forge signatures that pass verification, defeating the tamper-evidence control entirely. The check is fail-closed: a weak key is rejected before the proxy starts signing, rather than silently producing a forgeable audit log. Auto-generated keys come from `crypto/rand` and are never affected.

**What the chain does and does not cover.** Modification, interior deletion — of individual records *and* of an entire interior rotated file — reordering, and insertion are detected from the local files alone, because `audit-verify` walks the whole rotated set as one chain (above): a deleted interior file surfaces as a `prev_hmac`/`seq` break where the file after the gap fails to chain onto the file before it. On a **non-rotated** log, leading-record removal is also caught: the first record of a fresh log carries `seq 1` and the `sha256:genesis` sentinel, an invariant `audit-verify` checks, so excising the genuine first record and rewriting the survivor to claim `seq 1` is reported as a `CHAIN BREAK at seq 1` (the rewritten record also fails its per-record HMAC). A `seq 1` record carrying an **empty** `prev_hmac` is flagged the same way unless it is preceded in the chain by the unsigned legacy records of a pre-chain upgrade (see *Upgrading from a pre-chain log* below): a legitimate legacy resume always sits behind those records, so a bare empty-`prev_hmac` `seq 1` record with no legacy predecessor is the signature of a key-holder truncating the leading records and forging a replacement — closing a gap where that one form previously bypassed the genesis check. The cases that **cannot** be proven from the local files without an external high-water mark are **trailing truncation** (removing the last N records) and removal of the **leading** records — the oldest records, up to and including whole leading rotated files (which is also exactly what `--audit-retain` prunes deliberately) — because a truncated prefix of the chain is still internally consistent and begins at `seq > 1` indistinguishably from legitimate retention. For tamper evidence against those, ship audit records in real time to an append-only external sink (SIEM, object storage); the chain then lets the sink detect any in-flight gap.

**Decoded-value vs. raw-byte tamper evidence (raw-consumer requirement).** The HMAC is recomputed over the record's *decoded and re-marshaled* fields, not over the exact on-disk bytes, so verification certifies the **decoded value**, not the byte encoding. Two byte sequences that `encoding/json` decodes to the same value therefore verify identically. Three specific manifestations are closed as fail-closed hard rejects because they change what a differently-behaving consumer reads: a **duplicate top-level key** (above), an **unknown top-level field**, and a **zero-valued `omitempty` field explicitly present** (e.g. `"agent_id":""`, `"audit_only":false`, `"obligations":[]`) — `writeRecord`'s `omitempty` never emits one of these fields holding its zero value (it omits the key entirely instead, per the same tag re-marshal drops it under), so an on-disk zero value for one of them can only have been appended after signing; `audit-verify` rejects it exactly like a duplicate key or unknown field, not silently through the normal re-marshal-and-compare path. The residual, un-rejected members of the same class are byte edits that decode to the *same* value under standard last-wins JSON — a redundant `\uXXXX` escape in a string field (`"rm_rf"` written as `"rm_rf"`), or insignificant whitespace/number-format changes in a struct-typed field — which re-marshal to the signed value and pass verification, yet a consumer that reads the raw line differently than Go's `encoding/json` (a first-wins or raw-scanning parser, a `grep`/regex over the raw bytes, some SIEM ingest paths) could read a different surface. This is inherent to signing the decoded projection rather than the exact bytes; RFC 8259 explicitly calls duplicate-name and escaping behavior implementation-defined. **Any raw-byte consumer of the audit tape MUST parse it with standard last-wins JSON semantics (or normalize before matching) rather than scan the raw bytes**, so that what it reads matches what the HMAC certified. The `details` field is a `json.RawMessage` covered as bytes, so its own bytes are byte-exact against the signed value — an edit to *those* bytes (a duplicate key, added whitespace, or a re-escaped string *inside* `details`) changes the HMAC input and is caught like any other byte edit to a signed field; the requirement above applies to the struct-typed fields (`decision`, `target`, `method`, `session_id`, `identifier`, …), not to `details`. What is **not** checked is a duplicate key *within* the nested `details` object at the semantic level: `rejectDuplicateTopLevelKeys` deliberately walks only the top-level object (nested objects inside `details` are the signed `RawMessage` and are not re-inspected), so a `details` blob written with an internal duplicate key (e.g. `{"path":"/etc/passwd","path":"/tmp/safe"}`) is preserved verbatim, HMAC-covered as those exact bytes, and verifies — but it still carries the same first-wins-vs-last-wins ambiguity for a raw-byte consumer reading `details` with different JSON semantics than `eunox`'s decoder. That consumer is covered by the same raw-byte-consumer requirement above; closing it at the signing layer would mean walking into and re-validating the caller-supplied `details` map's own key spelling, which the audit layer treats as opaque data by design (see §6.1). Closing the escaping/whitespace vector at the byte level would require verification to reproduce the writer's exact `json.Marshal` output and byte-compare, coupling tamper evidence to the standard library's precise encoding — a fragility (a stdlib formatting change would false-positive every legitimate record) that is not worth taking on for a residual that a conformant JSON consumer is already immune to.

**Resume integrity.** On restart the proxy resumes the chain (next `seq`, `prev_hmac`) from the existing log's last line. That tail is HMAC-verified before it is chained onto: if the last record fails verification — the signature an attacker who truncated to a chosen record or appended a crafted tail cannot produce — the proxy logs a loud warning AND writes a signed, structured `AUDIT_INTEGRITY_FAILURE` marker (a synthetic deny record, like `AUDIT_RECORDS_DROPPED`, carrying the suspect tail's `seq` and `_hmac` in its `details`) as the first record of the new session, so the corruption is not silently carried into the new chain and the detection event is itself part of the tamper-evident trail and any external sink — not merely a transient stderr line that container log rotation can discard. (It warns rather than aborts, consistent with the audit-failure-does-not-block-enforcement tradeoff in §5.4; reconcile against the external sink.) When the configured base log is **empty or absent** on startup — because it was just rotated (the fresh base has no records yet) or a rotation reopen-fallback renamed the base away and never recreated it — the proxy resumes from the most recent rotated sidecar's tail rather than from the empty base, and warns. Resuming from the empty base would otherwise restart the chain at the genesis sentinel and silently orphan every record written before the restart, leaving no detectable gap between the two files. A tail whose final line is only **whitespace** (a stray editor save, or an `echo` appending a blank line) is resolved to the last real record, not mistaken for an empty log — the empty-vs-present distinction is reserved for a genuinely zero-length tail, so a non-empty log can never be misread as empty and restart the chain. When the fallback does reach for a rotated sidecar, an **unreadable *newer*** sidecar is never skipped in favor of an older one (which would reissue the newer file's seqs): the resume fails closed instead — seeding the next `seq` past the on-disk maximum and writing the `chain_resume_failed` marker — exactly as an unreadable base does. That seed is taken across the **whole chain** (base *and* every rotated sidecar), so a small just-rotated base cannot under-seed below a sidecar's higher `seq` and reissue it. A genuinely **missing** file is the normal brand-new-install case and resumes from genesis silently; but if an **I/O error** (a permission change, `EIO`, NFS `ESTALE`, or a failed `Stat`/`ReadAt` on a present file) prevents reading the tail at all, the chain cannot be safely resumed and restarts from genesis — and this case now writes a signed `AUDIT_INTEGRITY_FAILURE` marker (`"kind":"chain_resume_failed"`, carrying a structured `"reason":"tail_read_failed"` code) too, so an error-induced reset is distinguishable from a legitimate genesis and is not the one chain-reset path left unmarked. The raw OS error — which varies by platform/`errno` and can embed the log file path — is written only to the stderr warning, never into the signed, append-only tape, so `details.reason` stays a fixed code SIEM rules can match across environments rather than free-form prose.

**Partial trailing write.** A non-clean shutdown (`kill -9`, power loss) can leave bytes after the final newline with no terminating newline of their own — a write interrupted mid-record. Because every complete record ends in a newline, such a non-newline-terminated fragment was never a complete record. On Open the proxy truncates that fragment (which therefore never removes a complete record) so the next append begins at a clean record boundary instead of concatenating onto the orphan and producing a line `audit-verify` cannot parse; it then resumes the chain continuously from the last complete record and writes a signed `AUDIT_INTEGRITY_FAILURE` marker (`"kind":"tail_partial_write_recovered"`, carrying `recovered_bytes`) so the recovery is itself on the tamper-evident trail. This is distinct from a **newline-terminated but unparseable** last record, which is treated as corruption (`"kind":"tail_parse_failure"`, chain restarting from genesis), not a recoverable partial write. Truncating only the unterminated fragment does not weaken truncation detection: an attacker who truncates to a record boundary leaves a newline-terminated tail that is HMAC-verified and reconciled against the external sink exactly as before. A fragment **larger than the tail scan window** with no record boundary inside it is a special case: its last-complete-record boundary cannot be located, so it cannot be safely truncated (dropping the window could delete a complete record whose newline sits just before it). Open therefore fails **closed** — refusing to start until the operator resolves the tail — rather than leaving the orphan and proceeding, which would let the `tail_parse_failure` marker `O_APPEND` directly onto the multi-megabyte orphan, fusing one physical line that trips `audit-verify`'s per-line length bound and buries the marker's own signature.

**Upgrading from a pre-chain log.** A log written before signing/chaining support has no `_hmac` on its records. When the proxy resumes from such a tail, the first record it appends carries `prev_hmac: ""` — the empty `_hmac` of the legacy predecessor it is chaining onto — rather than the `sha256:genesis` sentinel (which marks only the first record of a brand-new log). `audit-verify` reconstructs the same empty link from the legacy record, so the upgrade boundary shows **no spurious chain break**. Because that empty-`prev_hmac` `seq 1` record is always preceded by its legacy predecessor, it is verified through the ordinary prev-link check, not the first-record genesis check — so the genesis check can still flag a bare empty-`prev_hmac` `seq 1` record that has *no* legacy predecessor (a leading-truncation forgery) without false-positiving the legitimate upgrade.

Because resuming onto an unsigned (legacy) tail is exempt from the tail HMAC check above, it is also the one resume an attacker with log-write access can perform without the signing key (truncate to a chosen record, append an unsigned record as the new tail). It is legitimate exactly once — on the first restart after a pre-chain upgrade — so the proxy records it in-band: when it chains onto a legacy tail it writes a signed `AUDIT_INTEGRITY_FAILURE` marker (`"kind":"legacy_tail_resumed"`, carrying the resumed tail's `seq`) as the first appended record. The boundary is then on the tamper-evident trail and any external sink rather than only a transient stderr line. A *recurring* `legacy_tail_resumed` marker on a log that has already been chained is suspicious (a genuine upgrade boundary occurs once), and should be reconciled against the external sink.

The legacy records themselves remain individually unverifiable: they were never signed, so `VerifyRecord` counts each as `invalid` (treating an unsigned record as merely `skipped` would let an attacker strip `_hmac` to dodge verification — `invalid` is the fail-closed call). Genuine legacy records are exempted from the per-record HMAC count (bucketed as `legacy`, not `invalid`) **only at the head of a log, before any signed record**. This exemption is **not** restricted to `seq 0`: the writer's own resume rule (above) is deliberately seq-independent — a pre-chain tail can carry any stale `seq` value inherited from before the chain existed, not only the `seq 0` shape a fresh, never-yet-chained log also produces — so `audit-verify` accepts an HMAC-less head record regardless of its `seq`, matching the writer's model rather than disagreeing with it. The exemption is scoped to *before any signed record* deliberately: an HMAC-less record appearing *after* a signed record is not a real pre-chain record — the chain was already active — so it is a forged "legacy" record spliced into a signed chain and is counted `invalid` (failing the verdict) rather than laundered through the legacy bucket. Likewise, a record carrying `seq 0` *with* a non-empty `_hmac` is structurally impossible in a correct log (legacy records have no `_hmac`; signed records start at `seq 1`); it is rejected as `invalid` regardless of whether its HMAC verifies, closing a forged-`seq-0`-decoy substitution of the genesis record even against a key holder. Because `audit-verify` exits non-zero whenever any record is `invalid`, a log with genuine head-legacy records will still **exit non-zero after an upgrade** — printing `N invalid … 0 chain break(s)` — until the pre-chain records rotate out of the log. That is expected: only the signed records appended after the upgrade are covered by HMAC and chain checks. Operators upgrading a long-lived log should expect the `invalid` count (not a chain break) to persist until rotation, and reconcile against the external sink in the meantime.

**Residual: a stripped-HMAC head record is caught, but sometimes only indirectly.** Because the head-legacy exemption cannot distinguish (from the record's content alone) a genuine pre-chain record from a signed record an attacker tampered with *and* stripped the `_hmac` from before any other signed record exists to anchor against, such a tampered head record is bucketed `legacy`, not `invalid` — the same ambiguity already accepted for a genuine `seq 0` legacy tail (this is the one splice an attacker with log-write access can make without the key, see above). The verdict still fails overall, just via a different signal than a direct per-record `invalid`: if a later genuine signed record's `prev_hmac` references the tampered record's *original* (pre-strip) `_hmac`, the mismatch surfaces as a `CHAIN BREAK` at the *following* record rather than an `invalid` at the tampered one; if the tampered record is the only one in the log, the all-legacy `UNANCHORED` check (below) fires instead. Either way `audit-verify` still exits non-zero — this is a loss of diagnostic precision (which record is blamed), not a fail-open — but an operator reconciling a `CHAIN BREAK` should check the record immediately *before* the flagged one, not only the flagged one itself.

A log that is legacy *end to end* — every record unsigned, no signed record anywhere — is a distinct case: when a verification key is configured it carries no signature to check at all, so `audit-verify` reports it `UNANCHORED` and fails the verdict rather than passing it. This closes a wholesale-forgery vector where a write-capable attacker without the signing key deletes the log and its rotated siblings and rewrites them entirely in legacy shape; a legitimate legacy→signed upgrade always leaves at least one signed record (the `legacy_tail_resumed` marker or a fresh-chain genesis record), so an all-legacy log under a held key is never a normal state. The `UNANCHORED` verdict keys on *every* record being legacy (`legacy == total`), so it closes only the strictly-all-legacy rewrite; it does **not** close the narrower residual where the attacker **preserves one genuine signed record** to keep `legacy < total`. Concretely, a write-capable attacker without the key can keep the genuine `seq 1` genesis record (it verifies as-is), trailing-truncate the signed records after it (`seq 2..N` — undetectable locally without an external high-water mark, per *What the chain does and does not cover*), and prepend forged unsigned legacy records carrying fabricated allow decisions: the forged head buckets as `legacy` (never HMAC-checked), the legacy→genesis transition is accepted, the genesis verifies, and because `legacy != total` the `UNANCHORED` guard does not fire. This is the same "legacy records are individually unverifiable" boundary as trailing truncation and leading-record removal above, and cannot be closed from the local files alone (it is not a regression — the pre-`UNANCHORED` verdict also passed it; `UNANCHORED` strictly narrows the vector). The closure is the same as for every truncation residual: an append-only external sink with a high-water mark, which the chain then lets detect the gap.

**Rotation integrity.** Size-based rotation renames the active log to a timestamped sidecar before opening a fresh file. The sidecar suffix is a nanosecond-resolution UTC timestamp preceded by a monotonic ordering ordinal with a uniqueness backstop, so two rotations within the same second cannot collide — `os.Rename` atomically replaces an existing target, so a coarser suffix would let the second rotation silently destroy the first sidecar and drop its records outside the chain's coverage. If the rename itself fails (a persistent fault such as a permissions error, a cross-device target, or a disk-full condition affecting only the rename syscall), rotation backs the size counter off by one ~10% burst rather than resetting it to zero, so the active log can grow by at most ~10% of the rotation threshold per failed attempt instead of a full threshold each time — bounding disk growth under a permanently broken rotation while still avoiding a tight retry loop.

Three further rotation faults fail closed rather than corrupt the chain or its ordering. (1) The rename is followed by an **fsync of the sidecar before the fresh base opens**; if that fsync fails, rotation *defers the reopen* (entering the same bounded reopen-retry fallback) instead of closing the sidecar's descriptor before its tail is durable — a crash between an un-synced sidecar and an already-created empty base would otherwise lose the sidecar's tail and leave an undetectable chain gap. (2) The post-rename reopen **refuses a non-regular log path** (a symlink planted in the rename→reopen window), matching the startup open guard, so an attacker cannot redirect the tape through a symlink — which would also drop the active log out of `audit-verify`'s regular-file scan, making verification pass without reading a live record. (3) The sidecar's **ordering ordinal is seeded from the existing siblings**; if that directory read was uncertain at startup and stays unreadable at rotation time, rotation is *deferred* (backed off and retried) rather than stamping a stale-low ordinal `1` that would sort before existing higher-ordinal sidecars — mis-ordering retention (deleting the newest first) and feeding cross-file verification out of order.

**Retention (`--audit-retain` / `audit.retainRotated`).** When set, each rotation deletes the oldest rotated sidecars beyond the configured count, bounding disk use (the default, `0`, keeps every sidecar — the historical behaviour). Retention only ever **deletes whole rotated sidecars** matching this log's exact nanosecond-suffix pattern; it never edits a record, never touches the active log, and never touches an unrelated file in the directory. The trade-off is availability of *local* history: deleting the oldest sidecars removes the leading records of the chain, and — as noted above — removal of leading records on a rotated log already cannot be proven from the local files alone. Retention therefore does not weaken what `audit-verify` can prove about the records that remain (modification, interior deletion, reordering, and insertion are still caught), but a deployment that must retain durable history under a retention cap **must** ship records to an append-only external sink in real time; the local tape is explicitly bounded. Because retention runs only on the drainer goroutine at rotation time, it cannot race a concurrent write. Pruning deletes the oldest sidecars first and **stops at the first failed deletion** rather than continuing to a newer one: retention is safe only because it removes a contiguous *oldest* prefix, so continuing past an unlink failure (a Windows sharing violation, `EACCES`, `ESTALE`) could delete a newer sidecar while an older one survived — an interior hole `audit-verify` reads as a `prev_hmac`/`seq` break, indistinguishable from a deleted interior file. A sidecar already gone is not a hole and does not stop the pass; the next rotation retries.

**Residual risk:** The HMAC key is stored on the same machine as the log file. An attacker with read access to `~/.eunox/audit.key` can forge records (and recompute the chain) that pass verification. For regulated environments requiring tamper evidence against a privileged local attacker, ship audit records to an external sink in real time as above.

### 3.5 Credential Overprivilege

**Attack:** An agent accumulates broader API access than any specific task requires because credentials are issued for the user's full role rather than for the current task's scope.

**Mitigation (JWT PDP mode):** When the IdP is configured to inject `mcp.capabilities` claims into access tokens, the proxy enforces the task-scoped capability set rather than the full role. The JWT (schema v0.2) carries exactly what this agent invocation is permitted to call — `"tool:read_file?path=/reports/*"`, not `"*"`. The capability set is treated as an exhaustive allowlist: any tool not listed is denied with `AUTHORIZATION_FAILED` (JSON-RPC `-32001`). This `mcp.capabilities` enforcement is experimental and requires the opt-in flag `--jwt-experimental-capabilities` (off by default); with the flag off, a token carrying `mcp.capabilities` is rejected at validation (fail closed), so the schema cannot be relied on silently while it is unstable.

**Mitigation (manifest + JWT intersection):** When `policy` is also set, the proxy computes the intersection: a tool call must be permitted by **both** the manifest constraints and the JWT capability claims. The JWT can only restrict what the manifest allows; it cannot expand it. This prevents a misconfigured IdP from accidentally granting broader access than the manifest operator intended. The intersection also requires `--jwt-experimental-capabilities`; when the flag is off the manifest still governs identity-only tokens (`sub`, `mcp.task_id`, `mcp.agent_id`), and a token presenting `mcp.capabilities` is rejected rather than partially enforced.

**Mitigation (MaxCalls condition):** The `maxCalls` condition limits how many times a tool can be called within a sliding time window. For tools that retrieve credentials or sensitive resources, a `maxCalls: 1` limit bounds the privilege exposure window to a single use per session, regardless of token TTL.

### 3.6 Unbounded Tool Call Rate

**Attack:** An agent (or a prompt-injected agent) calls a tool in a tight loop, causing backend resource exhaustion, runaway API costs, or unintended mass operations.

**Mitigation:** The `maxCalls` condition type enforces a call-count ceiling within a configurable sliding window per session. The counter is backed by:

- **In-memory store (default):** Counter resets on proxy restart. Sufficient for single-instance, short-session deployments.
- **Redis store (`--redis-addr`):** Counter survives proxy restarts and is shared across multiple proxy instances running with the same Redis instance. Suitable for persistent or multi-replica deployments.

Counter keys encode `(sessionID, targetType, bareName, windowSeconds)` under a `maxcalls:` prefix. Each component is length-prefixed — `maxcalls:<len>:<sessionID>:<len>:<targetType>:<len>:<bareName>:<len>:<windowSeconds>` — so a component that itself contains the `:` separator cannot forge a different tuple that lands in the same bucket. This matters because `SessionID` is a plain string with no engine-enforced format: the shipped HTTP transport assigns UUIDs (colon-free), but a library caller can supply any value, so the *encoding* — not an assumption that session IDs are colon-free — guarantees the separation. The same length-prefixed encoding backs the `sequenceBlock` `seq:` history markers. The `<targetType>` segment (`tool`, `resource`, `prompt`, taken from `req.Target.Type`) namespaces the bucket by capability type, so a tool named `export` and a prompt named `export` keep independent quotas instead of draining one shared bucket. The `<bareName>` segment is the capability name with any engine prefix (`tool:`, `prompt:`, …) stripped — the same normalization `findMatchingCapability` and the `sequenceBlock` `seq:` history apply — so the prefixed and bare forms of *one* tool (`tool:read_file` and `read_file`) map to a single bucket and a client cannot reset its own quota by toggling the prefix. The trailing `<windowSeconds>` segment gives each window its own bucket, so a capability that layers two `maxCalls` conditions of *different* lengths counts each independently instead of writing both into one shared entry — which inflated the count (and pruned the longer window against the shorter, failing it open); two conditions sharing one `windowSeconds` are rejected at manifest load. This means Redis addresses the *cross-instance* bypass (the same session's quota is visible to all proxy replicas) but does **not** prevent *session-rotation* bypass: a client that opens a fresh MCP session gets a new `Mcp-Session-Id` and therefore a fresh counter, on both backends equally. The session-rotation bypass is a documented residual risk (see `adversarial_test.go` Adv-6).

**In-memory store footprint:** The in-memory counter holds one map entry per distinct `(session, tool)` pair — for both `maxcalls:` keys and the `seq:` markers `sequenceBlock` records — reclaimed only when the periodic cleanup fires (`DefaultCleanupInterval`, 5 minutes). A deployment that mints a fresh session per request (short-lived HTTP connections with UUID `Mcp-Session-Id` values are the common case) accumulates one entry per unique session between cleanup cycles, so the map — and the process heap — peaks at the cleanup boundary; a client able to drive unique session IDs can push that peak high enough to exhaust the heap and OOM the process. The proxy bounds this by default: `--max-call-counter-keys` (1,000,000; set 0 to disable) caps the in-memory key count, and a call under a *new* key past the ceiling is refused rather than growing the map. A key freed by cleanup frees a slot. The *number* of keys is one axis; the *size of each key* is the other, and it is bounded too: `IncrementAndGet` retains only the most-recent `maxEntries` in-window timestamps per key (`recordSessionCall` passes `1`, since a `seq:` marker needs presence, not a count), so a single high-rate antecedent can no longer grow one key's timestamp slice without bound across the 24h history window the way it previously did — the parallel `IncrementAndGet`/`sequenceBlock`-history complement to the admitted-only `IncrementIfBelow` bound below.

Both key namespaces fail **closed** at the ceiling. A refused `maxcalls:` key fails closed: the counter error becomes `CONDITION_FAILED` and the call is denied (`handlers.go`). A refused `seq:` key also fails closed: `recordSessionCall` does **not** swallow the error — consistent with the recording contract described above (§"Mitigation (`sequenceBlock` condition)") and `recordSessionCall`'s own doc in `engine.go`, it surfaces the write error and the engine denies the call that needed the new history key (`CONDITION_FAILED`, audit detail `phase: record`). Swallowing it would leave the antecedent marker unwritten and let a later `sequenceBlock` check read a falsely-absent antecedent and fail open; surfacing it closes that bypass. The consequence at the ceiling is therefore an **availability** impact, not a `sequenceBlock` bypass: under sustained saturation any allowed call in a session that needs a new key is denied while the map is full (and because recording is indiscriminate, that is every allowed call in such a session, not only sequence antecedents). An operator expecting low denial rates under high session churn should choose the Redis backend, whose per-key TTL keeps state off the Go heap so the ceiling is not reached. (The one place a recording error is deliberately swallowed is route-level *audit* mode in `pdp.go`, which forwards regardless and only logs a warning.)

The bound is a memory backstop, not a per-session quota; for sustained high-session-rate deployments prefer the Redis backend (`--redis-addr`), which keeps counter state in Redis with a per-key TTL rather than on the Go heap (so it is unaffected by key count) and therefore does not reach the key ceiling that forces fail-closed denials in the in-memory backend.

**Audit queue back-pressure:** Audit records are enqueued non-blocking into a fixed-size channel; when the channel is full, records are dropped and counted via `DroppedRecords()`. This applies to all denial paths, including unmapped-method denials (`AUTHORIZATION_FAILED`). A client spamming novel MCP methods can saturate the queue and cause subsequent legitimate records to be dropped. Crucially, a drop does **not** vanish from the chain: the drainer writes an explicit, signed `AUDIT_RECORDS_DROPPED` marker into the log before the next record, so `audit-verify` and any external sink see the gap rather than a clean, contiguous chain. Without this marker a flood-induced loss would leave no `seq` gap and no chain break, because the chain head only advances on a successful write — making the loss invisible. Beyond the aggregate `dropped`/`dropped_total` counts, the marker's `details` carries a `by_method_target` breakdown — the dropped record's own method and target were already computed before the enqueue attempt, so they are tallied by (method, target) pair at each of the three drop sites (queue full, over the byte budget, post-close) even though the record's arguments and full content are gone. This is bounded to 32 distinct pairs (further distinct pairs fold into a single `"(other)"` bucket) and is best-effort relative to the aggregate count — the two are updated by separate, unsynchronized counters on the enqueuing goroutine — so a reader should treat the breakdown as directional context (e.g. "the flood concentrated on this one tool") rather than an exact per-bucket reconciliation of `dropped`. Operators should still monitor `DroppedRecords()` and alert when it is non-zero; sustained drops indicate disk I/O pressure or a write flood.

**Shutdown drop window (bounded, counted-but-unchained):** A second, narrow drop path exists during shutdown. `Close()` sets a `closed` flag and closes the record channel under a write lock so an in-flight `record()` send can never race with the close (which would panic with "send on closed channel"); any `record()` that runs after `closed` is set is counted via `DroppedRecords()` and returns without enqueueing. Because the drainer has already written its final `AUDIT_RECORDS_DROPPED` marker and exited by then, these shutdown-window drops are **not** folded into a signed chain marker — they are observable only through a later `DroppedRecords()` read, and the `dropped` total `Close()` prints can itself under-count producers still finishing after `Close()` returns. This is a known, bounded gap (it spans only the graceful-shutdown interval, after the server has stopped accepting new work) and is strictly safer than the prior behaviour, where the same race terminated the process via panic with no graceful flush at all. Operators who require completeness across shutdown should ship records to an external sink (§3.4) and drain it on the high-water mark rather than relying on the local tail.

When the limit is reached, the call is denied with code `RATE_LIMITED` (JSON-RPC `-32003`) and the block is recorded in the audit log. The denial carries a `retryAfter` hint (whole seconds until a slot frees up) so callers can back off. The counter increment is not applied in audit mode (`enforcement: audit`), allowing observation of what would be blocked without affecting the count.

The check-and-record is atomic and applies **only to admitted calls**: an over-limit call is denied without writing a new timestamp (a single mutex for the in-memory backend, a single Lua script for Redis). This closes a self-extending lockout and unbounded-state-growth bug — previously every denied retry was counted, so a client that kept retrying at or above the limit refilled the sliding window indefinitely and drove the counter's backing store (Redis sorted set or in-memory slice) to grow with each retry until the key TTL fired. Because denied calls are no longer recorded, the window now clears `windowSeconds` after the last *admitted* call regardless of how often the client retries, and a rate-limited key's storage shrinks rather than growing. The retained admitted timestamps are themselves bounded by the limit — `IncrementIfBelow` has no separate `maxEntries` cap, so an in-memory `maxCalls` key holds at most `count` (the configured limit) timestamps per window. A very large quota (hundreds of thousands of calls per window) therefore implies a correspondingly large per-key slice on the Go heap, which is a further reason large-quota deployments should prefer the Redis backend, whose sorted set lives in Redis under a per-key TTL rather than on the heap.

**Multi-`maxCalls` admission is atomic across buckets.** The atomic check-and-record holds *per bucket*, so a *single* `maxCalls` condition is admitted atomically and its limit is exact even under simultaneous requests. When one constraint layers **two or more** `maxCalls` conditions (e.g. 30/minute *and* 500/hour), the engine admits them through a single atomic multi-bucket operation (`CallCounter.IncrementIfAllBelow`): a call is recorded in **every** bucket only if every bucket has headroom, and otherwise nothing is recorded. On Redis this is one Lua `EVAL` over all the buckets; in memory it is one mutex held across the whole check-and-commit. Two same-session requests that previously raced in the check→commit window can therefore no longer both be admitted — the committed count is exact for single- and multi-condition constraints alike. (An earlier implementation used a non-committing check followed by a separate per-bucket commit, leaving a narrow cross-bucket TOCTOU that could over-admit by up to the number of racing requests; that window is now closed. The single-node Redis client the binary wires evaluates the multi-key script directly; a Redis-Cluster deployment would need the per-constraint bucket keys to share a slot.)

### 3.7 DNS-Rebinding Against the HTTP Listener

**Attack:** The HTTP transport binds to loopback (`127.0.0.1`) by default, so it is not reachable from the network. DNS rebinding circumvents that: a user visits an attacker-controlled web page whose domain initially resolves to the attacker's server and then re-resolves (rebinds) to `127.0.0.1`. JavaScript on that page can then issue requests to `http://attacker-domain:<port>/mcp`, which the browser sends to the locally-listening proxy — the loopback binding alone does not stop it, because the connection genuinely originates on the local host. If `listen.authToken` is unset (or extractable), the page can invoke tools, read resources, or drive `sampling/createMessage` through the user's agent session.

**Mitigation (Origin validation):** Per the MCP Streamable HTTP requirement, the proxy validates the `Origin` header on every HTTP request — `/mcp`, `/control/kill`, and the `.well-known` metadata endpoints alike — through a single middleware choke point so no handler can omit it. A request whose `Origin` does not appear in the allowlist is rejected with `403 Forbidden` and the proxy never reaches the routing, session, or PDP layers; the rejection is recorded in the audit log with code `ORIGIN_REJECTED`. Because this rejection precedes any session lookup or authentication, the unverified, attacker-controlled `Mcp-Session-Id` header is **not** stamped into the structured `session_id` field — doing so would let anyone forge `ORIGIN_REJECTED` records attributed to a victim's session. The structured `session_id` is left empty — and, carrying `omitempty`, is omitted from the record entirely rather than written as an empty string — and the client-claimed value is preserved only as the clearly-unverified `details.claimed_session_id` field, so an operator keeps the correlation hint without conflating it with an authenticated session. The browser sets `Origin` on exactly the cross-site requests rebinding relies on, so the attacker's page presents its own foreign origin and is blocked.

Only a **truly absent** `Origin` header is allowed unconditionally — non-browser MCP hosts (the stdio bridge, CLIs) do not send one. Every *present* value must appear in the allowlist, including a present-but-empty `Origin:` and the opaque `null` origin: both are reachable from sandboxed/`file:`/`data:` browser contexts, so neither is trusted by default. The built-in allowlist accepts an origin whose **scheme is `http` or `https`** (case-folded) and whose host is a loopback name (`localhost`, `127.0.0.1`, `[::1]`) or equals the configured `listen.bind` host (a wildcard bind — `0.0.0.0` / `::` — does not widen the allowlist). Restricting the host-set path to the web-origin schemes keeps it inside the RFC 6454 serialized-origin grammar (`scheme://host[:port]`): a non-web scheme (`file://localhost`), a scheme-relative reference (`//localhost`, empty scheme), or any other scheme on a trusted host is **not** trusted by default, matching the opt-in posture already applied to `null`. Operators serving a trusted browser front-end add its origin via `listen.allowedOrigins` (full origins, e.g. `https://app.example.com`, matched case-insensitively); a genuine `file:`/sandboxed front-end that needs the `null` (or a non-`http(s)`) origin must opt in explicitly by listing it there. An unparseable, hostless, or non-`http(s)` `Origin` fails closed.

**Residual risk:** Origin validation defends the browser-driven rebinding path specifically. A non-browser process running on the same host can still craft requests with an allowed `Origin` (or none); for `/mcp` that local-process threat is mitigated by `listen.authToken`, and for `/control/kill` by the loopback-source check **plus** the required control token (§3.3, SEC-07) — so a same-host process can no longer trigger the emergency stop without reading the 0600 token file. Binding to a non-loopback interface (`--unsafe-bind-all`) widens exposure beyond what Origin validation addresses and should be paired with `authToken` and network controls.

### 3.8 Tool Description Poisoning (Tool Poisoning)

**Attack:** A compromised or malicious MCP server returns a `tools/list` response in which the `description` field of a permitted tool contains injected instructions. The model reads the description before deciding whether and how to call the tool; a poisoned description can steer the agent toward specific call patterns, supply fake argument examples, or include override instructions that redirect the model's behavior across all tools in scope (cross-tool steering).

This class was described by Invariant Labs (2025) and applies even after eunox's list filtering: filtering removes unauthorized tools, but within the allowed set the model still sees whatever the upstream sends.

**Mitigation — description hash pinning (`descriptionHash`):**

Exact-name `tool:` constraints in the manifest may carry an optional `descriptionHash: sha256:<hex>` field. The hash covers a tool's full **model-facing instruction surface** — its top-level description, the root `inputSchema`'s own description, *and* the description of **every** input parameter, at any depth, under **any** subschema-valued JSON Schema keyword: `properties`/`patternProperties`, array `items`/`prefixItems` (single and tuple), `$defs`/`definitions`, `dependentSchemas`/`dependencies` (draft 2019-09 and its draft-07 predecessor), the `allOf`/`anyOf`/`oneOf` combinators, and the applicator keywords (`additionalProperties`, `unevaluatedProperties`, `propertyNames`, `contains`, `not`, `if`/`then`/`else`, `contentSchema`, …). A parameter description is fed to the model exactly like the top-level description, so a poisoning payload moved into *any* description string — including one buried under an applicator keyword — must not evade the pin. The per-location path keys are length-prefixed and framed so two distinct locations can never collide (a property literally named `$defs` cannot mask the real `$defs` section). Recursion into the schema is depth-bounded and fails closed past the bound (an adversarial deeply-nested schema forces a distinct hash rather than exhausting the stack). The structural shape of the parameters (names, types, `required`) is deliberately excluded so this always-fatal pin does not fire on benign schema evolution; that divergence is covered separately by FM-6 (below). When set:

1. **At startup (drift check):** `CheckManifestDrift` computes the SHA-256 of the live description and parameter descriptions from `tools/list` (via `ComputeToolHash`) and compares it against the pinned hash. A mismatch is classified as **FM-5** and aborts proxy startup unconditionally — it is not gated by `--strict-drift`. The finding is logged to stderr before the abort so operators see which tool changed. If `tools/list` is unavailable at startup and any pinned hash exists in the manifest, startup is also aborted — the proxy cannot confirm description integrity.

2. **At runtime (list filtering):** When the proxy filters `tools/list` responses, any tool entry whose live description does not match the pinned hash is excluded from the filtered response. The model never sees the poisoned description and therefore does not invoke the tool. As each `tools/list` response is walked, the proxy also records the SHA-256 of each tool's live description.

   This recording pass is a security control, not best-effort bookkeeping: when any pin exists, a `tools/list` the proxy cannot reduce to a comparable hash for a pinned tool **fails closed** by sticky-poisoning the affected pin(s). It matters most on an observe (`--audit`) route, where the catalog is forwarded verbatim and this pass is the only thing arming the mid-session pin. One shared pass arms the pins for both the observe route and the enforce-mode filter, so the two cannot diverge, and it runs to completion **before** any filtering — a poison discovered at the last entry must already be visible to the keep decision for the first, or the emitted catalog could advertise a tool whose call leg then hard-denies.

   The decisive detail is that the proxy and the host may not read the same bytes the same way, so what "cannot be reduced to a comparable hash" means is deliberately wide:

   - **Duplicate keys**, at the top level or nested inside a hashed parameter description. `encoding/json` keeps the last value, so `{"description":"<INJECT>","description":"<CLEAN>"}` hashes clean while a first-key-wins host renders the injection.
   - **Case-variant sibling keys.** Go binds object keys to struct fields *case-insensitively* and keeps the last match, so `{"description":"<INJECT>","Description":"<CLEAN>"}` also hashes clean while a case-sensitive host (`JSON.parse`, the Python SDK) renders the injection. Top-level keys are therefore compared **case-folded**; nested keys, which decode into an exact-keyed map, are compared exactly — sibling schema properties differing only by case are legal and honest.
   - **An entry that will not decode** into the hashed surface, or whose name is duplicated or case-variant (which would let it present one name to the proxy and another to the host).
   - **An ambiguous envelope** — undecodable, an undecodable `tools` array, or a duplicate or case-variant `tools` key.

   The scan captures each value's raw bytes rather than tokenizing them, so an adversarial float64-overflowing number (`1e999`) cannot error the walk and shield a later duplicate, and its depth bound is kept deliberately **looser** than the hashed surface's own bound so an honest deeply-nested schema is resolved by a hash mismatch rather than a spurious duplicate verdict.

   Blast radius is scoped to the evidence: an ambiguity confined to one entry poisons only the pinned names *that entry could present*, so an unrelated malformed entry cannot disable pins it never named; only a whole-response ambiguity poisons every pin. This matters because the mark is sticky until restart and one per-route policy is shared across every session. A plainly absent `tools` key is not ambiguous — a host renders no tools from it — so it poisons nothing.

3. **At runtime (call leg):** `tools/call` enforcement (`ManifestPDP.Decide`) also checks `descriptionHash` for a pinned exact-name `tool:` constraint, against the description most recently observed at the list-filter step. If the upstream rewrites a tool's description **after the session started** and the host re-lists, the changed description is recorded and a subsequent `tools/call` to that tool — even one issued by name without re-listing — is denied (`AUTHORIZATION_FAILED`), closing the gap where the list filter hid the tool but the call leg still forwarded it. The pin is keyed off the pinned **name** and evaluated **before** capability selection, so it fires even when no constraint is selected for the caller (a principal-scoped pinned entry whose claims do not match, or a shadowing non-pinned sibling): a genuine poisoning stays a hard `AUTHORIZATION_FAILED` rather than falling through to a downgradable no-match/action deny that an observe route would forward to the poisoned upstream. A description not yet observed via `tools/list` is **not** denied on the call leg: the startup drift check (step 1) already verified every pin against the live upstream before the session was handed to the host, and is fatal on mismatch, so the start-time verification is authoritative until a `tools/list` re-observes the tool. Once a pinned tool has been observed poisoned, the deny is **sticky**: a later `tools/list` returning the clean description does **not** re-open the call leg, and the tool stays hidden from the list, until the proxy restarts. This is deliberately fail-closed for a pin — in HTTP mode one per-route policy is shared across every session's upstream instance, so without the sticky mark an honest session serving the clean description could otherwise clear the record and re-admit a concurrent session whose upstream instance is still poisoned. A legitimately changed-then-reverted pinned description therefore requires a restart (or an updated pin). Only `tools/list` carries descriptions to record this way; `resource:` and `prompt:` targets do not support `descriptionHash`.

4. **In `validate --live`:** The FM-5 finding appears in the WARNINGS section of the drift report, counted in the exit-1 summary.

**Populating hashes:** `eunox init --pin-descriptions` computes and embeds `descriptionHash` for every tool it discovers, so the operator gets a ready-to-review manifest with descriptions already pinned to the current upstream.

**Scope and coverage:**

`descriptionHash` is only supported on exact-name `tool:` targets. The manifest loader rejects the field on `resource:`, `prompt:`, and glob targets:

- **resource:/prompt: rejected at load** — FM-5 startup verification fetches `tools/list` only; a `descriptionHash` on a non-tool target would create a false sense of protection with no startup enforcement. These target types are not currently supported and the manifest loader will error.
- **Glob targets rejected at load** — a single hash cannot represent the description of every tool a glob like `tool:read_*` might match. Use exact-name entries with `--pin-descriptions` to get coverage.

| What `descriptionHash` covers | What it does not cover |
| ----------------------------- | ---------------------- |
| Description text, the root `inputSchema` description, **and every parameter description**, at any depth under any subschema-valued keyword (`properties`/`patternProperties`, `items`/`prefixItems`, `$defs`/`definitions`, `dependentSchemas`/`dependencies`, `allOf`/`anyOf`/`oneOf`, and applicators like `additionalProperties`/`propertyNames`/`contains`/`not`/`if`/`then`/`else`) of individually named `tool:` entries | Structural `inputSchema` shape (names/types/`required` — see FM-6); response body of `tools/call` |
| Startup FM-5 check (tools/list at proxy start) | Resources and prompts (would require fetching their list surfaces at startup) |
| Runtime: tools removed from filtered `tools/list` on mismatch | Description content inside `tools/call` results (not currently inspected) |

**Structural drift (FM-6):** The description hash intentionally ignores the parameter *shape*. To catch a tool whose argument surface changes, a constraint may declare an `argumentSchema`; at startup and in `validate --live`, FM-6 warns when the live `inputSchema` grows a parameter a **closed** schema (`additionalProperties: false`) did not declare — a new, unreviewed argument — or when a declared parameter's concrete type changes incompatibly. The check applies only to **exact-name `tool:` targets** (like the description pin): a glob's single `argumentSchema` cannot be a closed enumeration of every tool it matches, so running the added-parameter check against a glob would systematically false-positive. It recurses into nested object parameters (a new field under a nested `additionalProperties: false` is caught with a dotted path like `options.exfil_to`). It does *not* fire on a parameter a condition already references (the operator reviewed it), on a *disappeared* declared parameter (that is FM-3), or on a policy-compatible type change such as `number`→`integer` (an integer validates against a number schema). `eunox init` scaffolds `additionalProperties: false` so the added-parameter check is armed out of the box; relax it for a tool that legitimately takes open-ended arguments. Unlike FM-5, FM-6 is advisory by default and fatal only under `--strict-drift`, because benign schema evolution is common. Pairing `argumentSchema` with `additionalProperties: false` also fails the dangerous *call* closed at enforce time, regardless of whether the structural change was noticed.

**Recommended defense stack:** description pinning is one layer. Pair it with:
- **Supply-chain pinning:** pin the MCP server binary hash or container image digest in your deployment manifest so the server itself cannot be silently replaced.
- **Model-layer guardrails:** semantic content scanners (Invariant, Lakera, etc.) for instructions that bypass token-level checks.

**Residual risk:** An operator who has not set `descriptionHash` receives no protection from this mechanism. Use `eunox init --pin-descriptions` to populate hashes automatically from a live upstream, then review the generated manifest before committing it.

### 3.9 Transport Resource Exhaustion (HTTP listener and stdio→HTTP bridge)

**Attack:** §3.6 bounds the *backend* call rate; this class is exhaustion of the *proxy's own* memory, goroutines, and upstream connections by a host that drives the transport rather than the tool surface. Two paths are unbounded without explicit caps:

- **SSE subscriber fan-out per session.** A client opens many concurrent `GET /mcp` streams against a single `Mcp-Session-Id`. Each stream registers a subscriber channel (16-slot buffer) on the session, so the per-session subscriber list and its buffers grow with the number of open streams — memory the `maxSessions` cap does not bound, because it is all charged to one session.
- **Fire-and-forget POSTs on the stdio→remote-HTTP bridge.** The bridge that lets a stdio host reach an HTTP upstream POSTs each host request/notification on its own goroutine and returns before the POST completes. A pipelining host can spawn an unbounded number of in-flight POSTs, each holding a request body and an upstream connection (the response buffer is only 64 deep).
- **Unbounded handler goroutines on the stdio host loop.** The stdio proxy dispatches each host request to its own goroutine so the read loop stays free to route the host's replies to server-initiated requests. Without a cap, a pipelining host — especially against an upstream that never answers under `--upstream-timeout=0` — grows handler goroutines and the `pending`/`byUpstreamID` maps without bound, since each in-flight request holds a map entry until it completes or times out.
- **Unbounded in-flight requests per HTTP session.** The network-exposed HTTP transport dispatches each enforced `POST /mcp` into a handler goroutine that allocates a reply channel plus `pending`/`byUpstreamID` map entries and blocks in the upstream round-trip. `maxSessions` bounds session count and `maxSubsPerSession` bounds SSE streams, but per-session *request* concurrency was uncapped, so after one `initialize` a client POSTing concurrently on many connections — especially against a slow/silent upstream under `--upstream-timeout=0` — grew goroutines and per-session map entries without bound. This is the same failure the stdio `hostSem` prevents, on the more-exposed transport.

**Mitigation:**

- **Per-session SSE subscriber cap (`maxSubsPerSession`, 8).** `handleMCPGet` registers the subscriber *before* writing the `200`/SSE headers and rejects an over-cap stream with `429 Too Many Requests` (an error status is still possible because no `200` has been written yet). This bounds the per-session subscriber list and per-subscriber buffer independent of `maxSessions`. A well-behaved host opens a single stream for the session lifetime; a disconnect frees the slot. The same list is what server-initiated requests (`sampling/createMessage`) scan for a single recipient, so capping it also bounds that scan.
- **Bounded per-chunk SSE write deadline.** The cap above only bounds slot *count*; it relies on each slot eventually freeing. A stuck reader (a TCP zero/tiny receive window that never drains, not a clean disconnect) could otherwise defeat that: once the 16-slot subscriber buffer and the kernel send buffer fill, the next delivery `Write` blocks indefinitely, parking the goroutine outside its `select` so it observes neither kill-eviction, idle-reap, nor context cancel — pinning the goroutine and permanently consuming a `maxSubsPerSession` slot. An attacker opening 8 zero-window streams per session could wedge every slot and block legitimate notification delivery. The delivery loop therefore re-arms a bounded write deadline (`sseWriteTimeout`) before each `sseWriteChunk`-sized write instead of clearing the connection deadline permanently, so the deadline measures forward progress rather than whole-frame wall-clock (a slow-but-progressing reader is not killed mid-frame; a no-progress reader still trips it). It returns on any write or flush error — which runs the unsubscribe/drain defer that frees the slot — and, for a server-initiated request consumed from the buffer before the failed write, replies an error to the upstream itself so that request does not hang until the idle reaper. A keepalive comment frame, emitted once immediately at stream open and then every `sseKeepaliveInterval`, re-arms the deadline on an otherwise-idle stream so a wedged reader is detected within `sseKeepaliveInterval + sseWriteTimeout` (and from stream open, not only after the first interval) rather than only at the next upstream notification.
- **Bridge in-flight POST cap (`maxInflightPosts`, 64).** A semaphore bounds concurrent POST goroutines on the bridge: once the cap is reached the next spawn blocks until a slot frees (backpressure) rather than growing without bound, and drops on bridge close. The cap matches the 64-slot response buffer so the two limits do not fight. The bound is fail-safe — the acquire also unblocks on the per-call context (so `--upstream-timeout` still cancels) and on bridge shutdown — and because the bridge never delivers server-initiated requests, backpressuring host writes cannot wedge the read loop against a slot that never frees.
- **Stdio host-request in-flight cap (`maxConcurrentHostRequests`, 256).** `serveHost` acquires a non-blocking semaphore slot before dispatching each request goroutine and releases it when the handler returns; on saturation it replies a structured, retryable server-busy error (JSON-RPC `-32000`) to the host instead of spawning. The acquire is deliberately non-blocking — the read loop must keep routing host replies to server-initiated requests, so it can never stall on a full pool — so unlike the bridge POST cap this one sheds the excess request rather than back-pressuring the producer. This bounds handler goroutines and the `pending`/`byUpstreamID` maps even under `--upstream-timeout=0` against a silent upstream.
- **HTTP per-session in-flight request cap (`maxConcurrentSessionRequests`, 256).** `handleSessionPost` acquires a non-blocking per-session semaphore before dispatching each enforced request and releases it when dispatch returns; on saturation it replies the same retryable server-busy error (JSON-RPC `-32000`) instead of spawning, the HTTP analogue of the stdio `hostSem`. This bounds handler goroutines and the per-session `pending`/`byUpstreamID` maps on the network-exposed transport even under `--upstream-timeout=0`. `initialize` answers locally without an upstream round-trip and is not subject to the cap. Related: an in-flight enforced request also defers the idle reaper (tracked per session), so a legitimately long-running call is not torn down mid-flight while `lastActive` sits stale.
- **Bounded upstream subprocess write (sampling + write-wedge deadlock).** A sampling-capable subprocess upstream that issues `sampling/createMessage` and then stops draining its stdin while awaiting the reply can fill the pipe buffer, blocking a proxy→upstream write. Because the framed writer serializes writes under one mutex held across the blocking pipe write, that wedged write used to hold both the writer mutex and — on stdio, whose single serve loop is the sole router of host responses to server-initiated requests — a wire-ordering-barrier slot; a subsequent host notification then parked the serve loop on the barrier, and the sampling reply that would unblock the upstream sat behind the parked loop, hanging the session until SIGINT. The subprocess writer now carries a per-write deadline of `--upstream-timeout` (`mcp.NewMsgWriterWithTimeout`): a wedged write returns `ErrUpstreamWriteTimeout` and poisons the writer (a timed-out write can flush a partial frame and desync the newline framing, so the stream is not reused). Poisoning invokes a teardown hook (`killUpstream` / the session's subprocess kill) that fires regardless of which write path first wedged — request, host->upstream notification, or the serve loop's server-reply relay — so the upstream is reaped and the session recovers instead of hanging, and the recovery is not limited to the request path. Deadline support is probed once at construction: where the platform rejects a pipe write deadline the bound is left unarmed and a one-time warning is logged, so the operator learns `--upstream-timeout` does not bound writes there rather than silently retaining the deadlock. `ErrUpstreamWriteTimeout` is classified as `UPSTREAM_TIMEOUT` (not the generic `UPSTREAM_ERROR`) on the host-facing error and audit record. Under `--upstream-timeout=0` the write is intentionally unbounded (the operator's opt-out), and the interruptible barrier wait remains the residual "recoverable by shutdown" backstop.

**Residual risk:** Both bounds are fixed memory/goroutine backstops, not per-tenant quotas. They cap a *single* session/bridge; aggregate exhaustion across many sessions is bounded separately by `maxSessions` and the idle-session reaper. A host that opens streams up to the cap on many sessions is still bounded by `maxSessions × maxSubsPerSession`.

### 3.10 Enforced-Method Smuggling via Notification Framing

**Attack:** JSON-RPC distinguishes a *request* (carries an `id`, expects a response) from a *notification* (no `id`, fire-and-forget) purely structurally — `IsNotification()` is `id == nil && method != ""`, with no allowlist restricting which methods may legitimately take notification form. `tools/call`, `resources/read`, `resources/subscribe`, and `prompts/get` are always requests in a well-formed MCP session, but nothing rejected one of these framed as a notification instead: a host omitting the `id` field on an otherwise-normal `tools/call` body caused the message to be routed to each transport's fire-and-forget notification-forwarding path (stdio's `forwardHostNotification`, the HTTP transport's notification branch in `handleSessionPost`), which forwarded it to the upstream verbatim after only a kill-switch check — never reaching `dispatchRequest`, so the PDP decision was skipped and no audit record (allow or deny) was written. A lenient upstream MCP server that processes notification-framed method calls would execute the tool the manifest would otherwise have denied, invisibly to the audit trail and to `--require-audit=strict`.

**Mitigation:** Both transports check the notification's method against the same enforced-method set `dispatchRequest` routes on (`decideMethodHandlers` / `isEnforcedMethod`, `internal/transport/dispatch.go`) before forwarding. A match is denied and recorded (`INVALID_REQUEST`) instead of forwarded — the request never reaches the upstream, and the denial is a signed audit record like any other enforced-path deny. The check and its record are a single shared function (`denyEnforcedMethodNotification`) both transports call, so the two cannot independently drift out of sync.

**Residual risk:** The denial record uses the raw method name as both the audit identifier and the target (mirroring `malformedDeny`'s pre-existing convention for params rejected before the PDP is consulted, since a notification-framed call's real target argument is not parsed) — for `prompts/get` this yields a `target` of `"get"` rather than a real prompt name. A consumer that keys off `denial_code` (as `suggest` already does via `IsInfraDenialCode`) is unaffected; a hand-rolled consumer that does not filter infrastructure-fault codes could misread this as a denied call to a tool/resource/prompt literally named after the bare method suffix.

### 3.11 Argument Smuggling via Duplicate JSON Keys

**Attack:** A request's `params` object could carry the same key twice — at the params root (`{"name":"safe","name":"dangerous"}`) or inside `arguments` at any depth (`{"path":"/safe","path":"/etc/shadow"}`). Go's `encoding/json` keeps the **last** value, so the PDP authorized one value while the transport forwards the caller's **original** params bytes verbatim to the upstream, and a first-key-wins parser (common outside Go) then acts on the **other** value. At the params root this is **tool-name** smuggling — the policy matches the manifest entry for one tool while the upstream dispatches another; inside `arguments` it is argument smuggling past an `allowedValues` / `argumentSchema` guard.

The same divergence arises from keys that are not byte-identical but differ only by **case fold** (`{"name":"dangerous","Name":"safe"}`). `encoding/json` binds object keys to struct fields by a case-folding match and keeps the last, so the proxy resolves `name` to `"safe"` and authorizes it, while a case-sensitive upstream reads the literal `name` key and acts on `"dangerous"`. A byte-exact duplicate check does not see these as duplicates at all, which makes the fold variant the more dangerous of the two.

**Mitigation:** The shared params decode (`mcp.DecodeParams`, the chokepoint the `tools/call`, `resources/read`, `resources/subscribe`, and `prompts/get` dispatchers all use) rejects a colliding object key at **any** nesting depth before decoding, failing closed — the dispatchers already treat a `DecodeParams` error as an `INVALID_REQUEST` deny with a signed audit record. Collision is judged by **Unicode simple fold**, not byte equality, so both the exact and the case-variant form are refused; the fold is a real simple-fold rather than a lower-casing, because U+017F (long s) folds onto `s` for the decoder while `strings.ToLower` leaves it distinct. The fold applies at every depth, not only at the struct-bound root, because the forwarded bytes are decoded by an upstream whose binding shape the proxy does not control — the cost is refusing an object that deliberately carries case-distinct siblings, which is a denial rather than a bypass. Rejecting rather than silently normalizing to last-wins is what keeps the **enforced view and the forwarded bytes in agreement**: the proxy never has to guess which value a differently-behaving upstream will read.

**Scope:** This covers the **request** direction. Response-direction `*/list` filtering is a separate control (§3.8); a duplicate or case-variant key in an upstream's list envelope is not addressed here.

## 4. Explicit Out-of-Scope Threats

These attack classes are outside the proxy's enforcement boundary. This is not a gap to be filled — it reflects that these threats require controls at a different layer.

### 4.1 Prompt Injection

**What it is:** Malicious instructions embedded in data the LLM reads (documents, API responses, database records) cause the agent to issue tool calls that the legitimate user did not intend.

**Why it is out of scope:** The proxy enforces _what the agent is permitted to call_, not _why the agent decided to call it_. A prompt-injected call to `read_file("/reports/Q4.pdf")` is indistinguishable from a legitimate one at the JSON-RPC layer, and will be allowed if the capability token permits it.

**What the proxy does reduce (but does not eliminate):** By scoping capabilities to specific resources and argument patterns, the proxy limits the blast radius of a successful injection. An injected agent cannot call tools not listed in its manifest constraints; the additional narrowing to a per-token `mcp.capabilities` scope applies only when the experimental flag `--jwt-experimental-capabilities` is enabled (off by default).

**Recommended complementary control:** Input sanitization and content scanning at the application layer before feeding external data to the agent. The proxy is a last line of defense on tool calls, not a substitute for application-level sanitization.

---

### 4.2 Model Jailbreak

**What it is:** Adversarial prompting causes the LLM to disregard its system prompt or produce harmful outputs.

**Why it is out of scope:** Jailbreak is a property of the model's response to inputs. The proxy does not inspect model inputs or outputs. As with prompt injection (§4.1), the proxy reduces blast radius by enforcing capability constraints on whatever the jailbroken model instructs the agent to call.

---

### 4.3 Client-Side Agent Code Compromise

**What it is:** An attacker compromises the agent process — the Python runtime, the Node.js process, the container — and extracts the bearer JWT or the session ID from memory.

**Why it is out of scope:** The proxy cannot attest the integrity of a client process. Process isolation and host security are the responsible controls here.

**What the proxy does reduce:** Short-lived JWTs bound by `exp` limit the useful window of a stolen token. The kill-switch provides immediate revocation once compromise is detected.

---

### 4.4 IdP Compromise

**What it is:** The identity provider that issues JWTs with `mcp.capabilities` claims is compromised, allowing an attacker to mint arbitrary tokens.

**Why it is out of scope:** The proxy trusts any JWT that passes signature verification against the IdP's JWKS. An attacker who can issue valid signed JWTs from the IdP can call any tool they include in the capability claims. The proxy is not in a position to second-guess the IdP's issuance decisions.

**Mitigation the manifest provides:** When `policy` is also configured, the manifest acts as a second envelope. Even a fully compromised IdP cannot grant more than the manifest allows, because the intersection logic ensures the manifest is the ceiling.

---

### 4.5 Backend Service Vulnerabilities

**What it is:** A backend that the proxy forwards authorized calls to contains its own vulnerability — SQL injection, IDOR, privilege escalation within the backend service.

**Why it is out of scope:** The proxy enforces capability policy in front of backends. It does not perform DAST or runtime security testing of the backends it proxies to. Backends are responsible for their own internal security posture.

---

### 4.6 Enforcement-Point Bypass (Direct-to-Upstream Connection)

**What it is:** The entire model assumes the MCP host is configured to reach the upstream *through* eunox. A host — or a compromised, misconfigured, or simply uncooperative agent — that opens a connection **directly** to the upstream MCP server bypasses the proxy completely: no policy decision, no `*/list` filtering, no audit record. A proxy that clients are merely *configured* to use governs only the clients that choose to use it.

**Why it is out of scope:** eunox is in-path only where the deployment places it in-path. A binary cannot compel a client to route through it; it is an enforcement *point*, not a self-interposing one. Whether eunox is a **mandatory chokepoint** or an **optional convenience** is a property of the surrounding environment — network, identity, and endpoint controls — not something the proxy can assert about itself. This is the same class of boundary as client-side process integrity (§4.3): the proxy enforces what passes through it and makes no claim about traffic that does not.

**What establishes the chokepoint:** A direct connection needs three things — a **credential** the upstream accepts, a **network path** to the upstream, and a **place to run** the client. Remove any one and the bypass fails. Enterprises establish interposition with deployment controls across those three planes:

- **Credential control (the strongest, most portable lever).** Make eunox the only holder or minter of a usable upstream credential. Do not distribute upstream secrets to clients; for per-caller identity, mint short-lived, audience-locked, delegated tokens per request (the upstream-credential delegation model). A client that connects directly then holds no token the upstream will honor — the bypass is *unauthenticated*. Because this is enforced at the IdP/upstream, it holds even on devices and networks the operator does not control.
- **Network egress control.** Route outbound traffic through an egress firewall or forward proxy that permits the upstream's endpoint only from eunox's identity; resolve the upstream's hostname to eunox internally (split-horizon DNS); or have the upstream IP-allowlist eunox. The bypass is then *unroutable* — but only within a managed network.
- **Endpoint control.** For local (stdio) upstreams there is no network chokepoint, so the control is the device: MDM-pushed, locked client configuration users cannot repoint; no upstream secrets provisioned locally; application allowlisting that blocks unapproved MCP server binaries. The bypass is then *unconfigurable*.

These compose: an upstream that accepts only eunox-minted, eunox-delegated credentials, reachable only from eunox's network identity, with client config locked and no local secrets, makes a direct connection simultaneously unauthenticated, unroutable, and unconfigurable. See the [deployment-hardening guide](./deployment-hardening.md) for the concrete patterns (including the GitHub case).

**What the proxy contributes:** Two things. First, eunox *enables* the credential-control lever — it can be deployed as the sole credential holder, and its upstream-credential delegation can mint per-request short-lived tokens so there is no reusable secret on any client to bypass with. Second, eunox's tamper-evident audit log (§3.4) is the basis for bypass **detection**: reconcile eunox's records against the upstream's own audit log — any upstream activity with no corresponding eunox record is access that skipped the gateway. Detection is the compensating control wherever prevention is incomplete (unmanaged or off-network endpoints).

**Residual risk:** A fully unmanaged endpoint — a personal device, an agent running outside the corporate network — cannot be *prevented* from attempting a direct connection. Credential control denies it a usable token and audit reconciliation surfaces any residual access, but a deployment that distributes long-lived upstream credentials to clients and relies only on client configuration to route through eunox has established a *cooperative* boundary, not an *enforcement* one. Treat "the host is configured to use eunox" as an assumption to be enforced by the controls above, not a given.

## Coverage Map: OWASP Top 10 for Agentic Applications (2026)

The [OWASP Top 10 for Agentic Applications](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/) (ASI01–ASI10, published December 2025) catalogues risk for the *whole* agentic stack — model, memory, planning, identity, tool execution, and multi-agent coordination. eunox is a single control at one layer of that stack: the MCP tool-call boundary. It therefore provides **deep, direct** coverage of the tool-execution and privilege risks, **runtime containment** for several others, and is **out of scope** for the model-internal and human/multi-agent risks that require controls elsewhere. A "10/10 coverage" claim would be misleading for a focused enforcement point; the honest map is below.

Coverage levels: **Direct** — a primary design goal, enforced per call; **Containment** — does not prevent the root cause but bounds the blast radius from the MCP boundary; **Out of scope** — requires controls at a different layer (cross-referenced to §4 where applicable).

| OWASP risk | Coverage | How eunox relates |
| --- | --- | --- |
| **ASI01 — Agent Goal Hijack** | Containment | The hijack itself (prompt injection / goal manipulation) is out of scope (§4.1). The default-deny allowlist plus per-argument and per-session conditions bound what a hijacked agent can actually *do* through MCP — it cannot call tools or reach arguments outside the manifest. |
| **ASI02 — Tool Misuse & Exploitation** | **Direct** | The core competency. `allowedOperations` (SQL verb allowlisting), `allowedValues`/`argumentSchema` (argument constraints), and `maxCalls` turn the canonical misuse cases — `DROP TABLE`, path traversal, mass operations — into per-call denials (§3.2, §3.6). |
| **ASI03 — Identity & Privilege Abuse** | **Direct** | Least-privilege by construction: a manifest capability allowlist, claim-forgery rejection (§3.1), and per-session scoping. The additional narrowing by JWT capability claims intersected with the manifest so a token can only *restrict* (§3.5) is experimental and opt-in via `--jwt-experimental-capabilities` (off by default); the stable, always-active basis is the manifest allowlist plus verified identity claims. |
| **ASI04 — Agentic Supply Chain** | Containment | Runtime containment of an untrusted or compromised MCP server you did not write: enforcement lives *outside* the server process where it cannot be switched off, `*/list` filtering hides forbidden tools, and `descriptionHash` pins against tool-description poisoning (§3.8). It does not vet build-time dependencies — that is a different layer. |
| **ASI05 — Unexpected Code Execution (RCE)** | Containment | Gates *access* to exec/eval/shell/SQL tools and constrains their arguments (`allowedOperations`, `argumentSchema`); a dangerous tool absent from the manifest cannot be called at all. It does not sandbox the execution that an allowed call performs (no privilege rings / process isolation). |
| **ASI06 — Memory & Context Poisoning** | Containment (partial) | Gates `resources/read` and writes to memory-backed MCP servers, and `redactFields` masks sensitive fields in responses before they enter context. Tool-description poisoning — a context-poisoning vector on the MCP channel — is directly pinned (§3.8). It does not manage agent memory or RAG stores themselves. |
| **ASI07 — Insecure Inter-Agent Communication** | Out of scope | eunox governs host↔MCP-server traffic, not agent↔agent / A2A protocols. |
| **ASI08 — Cascading Failures** | Containment | Per-session `maxCalls` ceilings (§3.6), kill-switch revocation, and the fail-closed posture (§5) bound runaway loops and limit cascade on the MCP path. It is not an orchestration-level resilience system. |
| **ASI09 — Human-Agent Trust Exploitation** | Out of scope | eunox has no human-interaction or approval layer (contrast: SDKs offering a `require_approval` action). Allow/deny is mechanical, not a human-in-the-loop workflow. |
| **ASI10 — Rogue Agents** | Containment | Out-of-process deny-by-default means a rogue agent cannot bypass policy on the MCP channel; the tamper-evident audit log gives attribution (§3.4) and the kill-switch contains an identified session. It is blind to rogue activity on channels other than the MCP servers it fronts. |

**Summary:** direct, per-call coverage of **ASI02** and **ASI03**; runtime containment for **ASI01, ASI04, ASI05, ASI06, ASI08, ASI10**; out of scope for **ASI07** and **ASI09**. The pattern is consistent with eunox's role — it is the enforcement point for *what an agent may do through MCP tools*, deliberately narrow, and most effective when paired with model-layer (input scanning), identity-layer (IdP), and orchestration-layer controls for the risks above that it only contains or does not see.

## 5. Failure Modes and Resilience Posture

The proxy defaults to **fail-closed**: when a dependency required for a security decision is unavailable, the default is to deny rather than allow. The exceptions are documented explicitly below, with the security tradeoff stated plainly.

### 5.1 Proxy Crash

**Observed behavior:** The process exits. The upstream MCP server receives no further traffic. No tool calls are forwarded.

**Security posture:** Fail-closed by nature of being in the request path. The agent runtime receives a connection error and the task fails.

**Recovery:** Restart the proxy binary. In-memory state (call counters, kill-switch) is reset on restart. If persistence is required, configure `--redis-addr` before deploying.

---

### 5.2 JWKS Endpoint Unreachable

**Observed behavior:** The proxy uses its in-process JWKS cache. Tokens signed with a key that is in the cache are accepted normally. Tokens whose `kid` is not in the cache trigger a force-refresh attempt; if the re-fetch fails, the token is rejected with 401. The resulting `JWT_INVALID` audit record carries `details.error_type: jwks_unavailable` (see §2.2) — distinct from the categories that mark a genuinely bad token — so an operator triaging the tape can tell "the key infrastructure was down and a possibly-valid token was rejected" apart from "a forged or expired token was rejected". The fetch failure itself (network error, non-`200`, empty/oversized key set, or an open circuit breaker) is what carries the category up through the validation path.

**Cache TTL:** 5 minutes by default (configurable). When the cache expires and the endpoint is still unreachable, the next token validation that requires a key not in the cache will fail closed.

**Security posture:** Cached-then-fail-closed. A proxy that has already fetched the JWKS can continue to enforce for up to the cache TTL without the IdP being reachable. This is intentional: it prevents an IdP outage from causing an immediate enforcement outage. However, key rotation events that require a new `kid` are blocked during the outage window.

**Recovery:** JWKS endpoint recovery is transparent. The next forced re-fetch (triggered by a token with a `kid` not in cache) restores normal operation immediately.

---

### 5.3 Redis Unavailable (When `--redis-addr` Is Configured)

When Redis is configured, it backs two enforcement functions:

| Function           | Redis unavailable behavior                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------------------- |
| `MaxCalls` counter | The counter increment errors; the `MaxCalls` condition fails closed and the call is denied with `CONDITION_FAILED` |
| Kill-switch state  | **Fails closed by default:** once a refresh fails, the proxy denies any request whose kill-switch state it cannot confirm (`KILL_SWITCH_ERROR`). Serving the last successfully refreshed snapshot instead is opt-in via `--killswitch-fail-open`. |

The Redis backing is deliberately thin. The proxy uses the standard Redis client directly — there is no circuit breaker, failover, or partitioned-state layer in front of it (the earlier `redisfailover`, Redis-backed circuit-breaker, and partitioned kill-switch packages were removed in an earlier cleanup as over-engineered). Redis is a single optional dependency for shared, restart-surviving state; the fail-closed and last-snapshot behaviors below are what guard a Redis outage.

**Security implication of kill-switch fallback:** The Redis kill-switch maintains an in-process snapshot refreshed two ways — immediately on each pub/sub event, and on a fixed-interval reconciliation timer (`defaultReconcileInterval`) that re-reads the authoritative Redis state regardless of pub/sub. The hot decision path reads that snapshot rather than making a live Redis call. A kill-switch that was activated _before_ Redis became unavailable (and had been refreshed into the snapshot) remains active. A kill-switch activated _after_ Redis became unavailable, or whose pub/sub event was lost (pub/sub is at-most-once), is observed on the next successful reconciliation tick once Redis recovers — it no longer depends on a pub/sub event being delivered, which closes the "lost event is never reconciled" gap. **During the outage itself the switch fails _closed_ by default** (ADR-0003): once a refresh fails, `ShouldBlock()` denies any request whose state it cannot confirm (`KILL_SWITCH_ERROR`, via the `ErrBackendUnreachable` sentinel — the wrapped Redis error is not leaked to clients) until the next successful refresh, so an unconfirmable revocation is never bypassed. Operators who prefer data-plane availability over guaranteed revocation during a partition can opt into the prior behaviour with `--killswitch-fail-open`, which serves the last snapshot instead; for immediate propagation independent of Redis, run a local proxy instance per host with its own in-memory kill-switch. The Redis kill switch exposes `HealthStatus()` (non-nil ⟹ the last snapshot refresh failed); operators should poll it and alert so a Redis partition — a partial data-plane outage in the default mode, a widening revocation-latency window under `--killswitch-fail-open` — is visible rather than discovered during an incident.

**Security implication of MaxCalls denial:** When Redis is unavailable, `MaxCalls` conditions fail closed — calls are denied rather than allowed without a counter check. This is conservative and may cause false positives during Redis outages, but it prevents unbounded call rates.

**Recovery:** Redis recovery is transparent. The Redis-backed stores resume their normal role immediately.

---

### 5.4 Audit Log Write Failure

**Observed behavior:** If writing an audit record fails (disk full, permission error, file descriptor limit), the loss is surfaced three ways: a one-shot stderr warning (subsequent write errors are suppressed to avoid a flood under a sustained outage),

```
[eunox] WARNING: audit record write failed — the audit trail is now incomplete; check disk space and I/O ...
```

a monotonic counter exposed as the `eunox_audit_write_failures_total` metric (and the `auditWriteFailed` field on `/healthz`), and — for a write failure that persists to the final `Sync`/`Close` — a **non-zero process exit**. This counter is deliberately distinct from `eunox_audit_dropped_records_total` (queue back-pressure on a healthy file): a non-zero write-failures count means the backing file itself is unwritable, so audit coverage is degrading even though the queue kept up. Enforcement continues. The tool call result (allow or deny) is still applied to the upstream and returned to the client. The audit record for that call is lost.

Unlike a queue-back-pressure drop, a write failure **cannot** be recorded with an in-chain `AUDIT_RECORDS_DROPPED`-style marker, because the file that marker would be written to is the thing that is failing. The chain head is intentionally not advanced on a failed write, so the chain stays internally consistent (no spurious break), and the loss is surfaced out of band via the metric and exit code instead.

**Security tradeoff — documented explicitly:** Audit log write failure does not block enforcement. This is a deliberate design decision: dropping production traffic because the local audit log is full would be worse than a partial audit trail gap in most deployment contexts. Operators who require guaranteed audit completeness should:

1. Monitor disk space on the machine running the proxy.
2. Ship audit records to an external sink (SIEM, object storage) by tailing `~/.eunox/audit.jsonl` with a log shipper.
3. Set the `--audit-rotate-size` flag to match available disk space (default: 100 MiB auto-rotation).

Use `eunox audit-verify` to detect HMAC verification failures and chain breaks in existing records. The `seq`/`prev_hmac` chain (§3.4) flags an interior gap left by a dropped or deleted record; a record missing from the very end of the log cannot be distinguished from "never written" without an external high-water mark. A line that is itself corrupt (fails JSON decode) is counted as `invalid` by its per-record HMAC check but is excluded from the chain linkage, so it does not fabricate a spurious chain break against the following intact record.

#### 5.4.1 Fail-open on the allow path

**The allow path is fail-open with respect to durable audit.** A permitted (`allow`) request is recorded only **after** the call has already been forwarded and the upstream has answered: in the shared forward core (`internal/transport/forward.go`, `enforcedForwardCore`) the proxy forwards the authorized request, reads the upstream response, and only then calls `RecordAllow(...)`. `RecordAllow` does not write to disk synchronously — it does struct init plus a **non-blocking** channel send onto the bounded (4096-slot) audit queue (`internal/audit/audit.go`, `Sink.Record`), and a separate drainer goroutine serializes, signs, and writes the record later. Consequently the call's effect on the upstream is **never** blocked on, reversed by, or conditioned on the record reaching disk. Under any of:

- **Full queue** — the non-blocking send finds the channel full and the record is dropped (counted in `dropped`); or
- **Write error** — the record dequeues but the drainer's write/`Sync` fails (disk full, permission error, `EIO`); or
- **Process loss** — the proxy exits or is killed with records still queued,

an `allow` can be forwarded and applied to the upstream with **no durable on-disk record of the decision**. This is the same documented tradeoff as §5.4 (audit failure never blocks enforcement), stated explicitly for the allow path: the security control that is weakened is *audit completeness*, not *enforcement* — a denied call is still denied, the forwarded call still happened, only the tape entry may be missing.

**Existing mitigations (the loss is observable, not silent):**

- A **back-pressure drop** is made tamper-evident in-band: when the drainer next runs after the queue had been full, it writes a signed `AUDIT_RECORDS_DROPPED` chain marker (§3.6) recording how many records were lost, so a verifier sees that a gap occurred even though the individual records are gone.
- Two distinct counters expose the two loss modes: `eunox_audit_dropped_records_total` (queue back-pressure on a healthy file) and `eunox_audit_write_failures_total` (the backing file itself is unwritable), plus the one-shot stderr warnings and the `/healthz` `auditWriteFailed` field (§5.4).
- A write failure that persists to the final `Sync`/`Close` causes a **non-zero process exit**, so a deployment that treats the proxy's exit status as health will notice.
- `--require-audit` is three-state and **defaults to `strict`** (below): a proxy started without the flag fails closed on audit loss. `--require-audit=on` gates only **sink-open at startup** (the proxy refuses to start if it cannot open the audit log/key) but does **not** make the per-record allow path block on a durable write; `--require-audit=off` makes even the startup check best-effort (warn and run unaudited). A bare `--require-audit`, like the omitted default, is `strict`.

**Operators requiring guaranteed completeness** have two complementary options. First, ship records to an append-only external sink in real time (§5.4, step 2); the chain then lets the sink detect any in-flight gap that the local counters/marker also flag. Second, keep the default `--require-audit=strict` (rather than relaxing to `=on`/`=off`) to fail the local data plane closed the moment coverage degrades:

**`--require-audit=strict` (the runtime fail-closed gate).** Strict mode promotes `--require-audit` from a startup-only check into a runtime gate over the *forward* path. Before the proxy forwards an authorized request — every enforced method (`tools/call`, `resources/read`, `resources/subscribe`, `prompts/get`, and `sampling/createMessage`) and every `*/list` enumeration — the shared core (`enforcedForwardCore` / `dispatchList`, and both the allow and audit-mode observe legs of the sampling path in `forwardServerRequest`) consults `Sink.AuditDegraded()`. Once either loss counter has incremented (`dropped > 0` from queue back-pressure, or `writeFailures > 0` from a failed write/`Sync`), the call is denied fail-closed with the `AUDIT_UNAVAILABLE` code (JSON-RPC `-32603`, the internal-error class — distinct from the `-32001/-32002/-32003` policy codes) and the upstream is **not contacted** (for sampling, the upstream initiator receives the `AUDIT_UNAVAILABLE` error and the request is not forwarded to the host). The deny is itself recorded best-effort; its structured audit `details` carry only discrete counts (`dropped_count`, `write_failure_count` — present only when non-zero), never free-form prose. The human-readable degradation reason is reserved for the host-facing error response and the one-shot stderr warning, keeping the structured audit field value-free.

On the HTTP/gateway transport the session-creating `initialize` is gated the same way: spawning or contacting an upstream is a privileged side effect, so once the trail is degraded a new session is refused with `AUDIT_UNAVAILABLE` rather than starting an upstream whose creation and subsequent traffic could go partly unrecorded. (The stdio transport answers `initialize` from cached capabilities and starts its single upstream before any traffic, so it has no equivalent per-call side effect to gate.)

**What the gate does and does not guarantee.** The gate is **retrospective**: `AuditDegraded()` reads the cumulative `dropped`/`writeFailures` counters, which reflect only *already-completed* calls, and a call's own allow record is enqueued *after* the upstream answers. So the **boundary call** — the first call whose own record is the one lost (and, under concurrency, any call already in flight when the queue first saturates) — is still forwarded *and* loses its record; only the *next* call observes `degraded` and is denied. The accurate guarantee is therefore: **after the first lost record is observed, every subsequent forward is denied** — not that *no* call is ever forwarded unaudited. Closing the boundary window entirely would require a synchronous/blocking allow path (forward only after the record is durably written), which trades far more data-plane latency than the residual one-record window is worth; it is intentionally not done. Operators who need a zero-loss guarantee must combine strict mode with the real-time external sink (option one above), whose chain detects the boundary record's gap.

**Immediate boundary-call diagnostic.** While the window above cannot be closed without the blocking path, the boundary call does not have to be invisible until the next unrelated request trips the gate. Around each of its own `RecordAllow`/`RecordDeny` calls, the forward core reads `AuditDegraded()` once immediately before and once immediately after; if the trail was healthy going in and degraded coming out, that call's own record is plausibly the one just lost, and an immediate `SECURITY` line to stderr names the call rather than waiting for a later request's `AUDIT_UNAVAILABLE` denial to be the first sign. This is a diagnostic, not a new enforcement point — the boundary call is still forwarded either way — and it is best-effort: concurrent in-flight calls at the exact transition instant may each observe the flip and each warn, which is acceptable since every such call is a genuine candidate for the boundary, not a false positive on unrelated activity.

The gate is also **coarse and sticky by design**: it keys on the cumulative loss counters, so a single drop or write error denies every subsequent forward for the lifetime of the process (the counters only ever increase). This trades data-plane availability for audit completeness — the deliberate inverse of the relaxed `--require-audit=off`/`=on` posture — and is the right choice wherever an unauditable privileged call is worse than a denied one (the compliance/forensics case), which is why it is the default. Deployments that prefer availability over audit completeness opt down with `--require-audit=on` (startup-fatal only) or `--require-audit=off` (best-effort). A hard policy deny is unaffected (it already returns without forwarding); strict mode also overrides route-level **audit/wiretap** forwarding when the trail is degraded, since an observation that cannot be recorded has no audit value. The unenforced server-initiated passthroughs (`roots/list`, `elicitation/create`, …) are not gated — they carry no policy decision — so the gate's scope is exactly the enforced decision paths, `*/list`, and the HTTP session-creating `initialize`. Strict mode implies `--require-audit` (a sink that cannot open at startup is still fatal), so the runtime gate never runs without a sink. The "now denying forwards" stderr warning fires **once**, on the healthy→degraded transition; each denied call's durable signal is its `AUDIT_UNAVAILABLE` record, not a per-request log line.

### 5.5 Upstream MCP Server Unavailable

**Observed behavior:** If the upstream subprocess fails to start or a remote `upstreamUrl` is unreachable, the session initialization fails and the client receives an HTTP 500 with the error message. On the HTTP transport, session initialization — the initialize handshake and the startup drift probe — is bounded by a per-initialize deadline (the session-start budget, separate from `--upstream-timeout`), so a hung upstream cannot pin the handler goroutine or leave an unkillable orphan process.

For in-session failures (upstream dies or hangs after initialization), any method that attempts to reach the upstream — enforced methods and `*/list` discovery methods alike — returns a JSON-RPC error and an audit record is written with one of the infrastructure denial codes:

- `UPSTREAM_ERROR` — the upstream failed (exited, transport error, malformed response).
- `UPSTREAM_TIMEOUT` — the upstream did not respond within `--upstream-timeout`. This per-request bound is applied centrally to every host-initiated upstream round-trip (tool calls, reads, and the `*/list` discovery methods) on both transports, and to notification forwarding to a remote HTTP upstream. It deliberately does **not** govern session-start work (the initialize handshake and drift probe), which has its own session-start budget so a tight `--upstream-timeout` cannot by itself fail session establishment.
- `REQUEST_CANCELED` — the host abandoned the request before the upstream responded; the upstream is not implicated.

These records are never marked `audit_only`: the error returned to the host is an enforced outcome even when the route runs in audit mode. Infrastructure codes are distinct from policy denial codes, and the `suggest` subcommand ignores records carrying them when drafting manifests.

**Security posture:** Fail-closed on upstream errors. An unreachable upstream does not cause the proxy to bypass enforcement — it causes the call to be denied with an infrastructure error code distinct from policy denial codes.

Distinct from an infrastructure failure is a **completed** round-trip in which the upstream chose to return a JSON-RPC `error` *result* (the call reached the upstream, which answered with an error rather than a result). The proxy authorized and forwarded that call, so its decision is recorded as an honest `allow` — the `decision` field records the proxy's policy verdict, not the upstream's outcome — but the `allow` record carries a `_eunox_upstream_error_code` entry in `details` so a forwarded upstream error is not indistinguishable from a clean success on the tape. Only the numeric JSON-RPC error code is recorded; the upstream's error *message* is never copied into the audit record, which could otherwise leak sensitive content from the upstream's response. The key is underscore-prefixed, in the same reserved namespace as `_eunox_truncated` (below), so in the ordinary case it is merged flat alongside the caller's real tool arguments with no risk of colliding with one — a tool argument literally named `upstream_error_code` (bare, no prefix) is ordinary caller data and is recorded and mined like any other argument. On the rare call whose real argument is literally named the reserved key's own underscore-prefixed string, the merge nests the caller's arguments under an `"arguments"` wrapper instead of overwriting them with the injected code (mirroring the guard the bare key needed before the rename); `suggest`'s argument mining resolves this nested shape the same way it did before.

**List-enumeration filter counts.** A `*/list` allow record (`tools/list`, `resources/list`, `prompts/list`) carries three machine-readable counts in `details`: `upstream_count` (entries the upstream returned), `filtered_count` (entries that survived policy filtering and were delivered to the host), and `suppressed_count` (`upstream_count − filtered_count`, the entries the manifest hid). Without these, an `allow` for `tools/list` looks identical whether the upstream returned 100 tools with 99 filtered by policy or genuinely returned an empty list — an auditor investigating why a client sees no tools could not tell aggressive filtering from upstream emptiness, and could not reconstruct the effective permission surface at a point in time from the tamper-evident chain. In route-level observe (audit) mode the manifest filter is bypassed, so `filtered_count == upstream_count` and `suppressed_count == 0`; the record additionally carries `observe_mode: true` in `details` so a reader can tell a zero suppressed count caused by *bypassed* filtering from one caused by an all-permitting manifest (an enforce-mode record omits the key). The counts are entry tallies only; no tool/resource/prompt names are recorded.

### 6.2 What the proxy logs — mode dependency

Argument-value capture depends on both the operating mode and the decision outcome.

**Allow records — route-level observe mode only:** when the proxy runs in route-level observe mode (the `--audit` flag on the `proxy` subcommand, or `enforcement: audit` under `defaults:` / per-route `enforcement:` in a gateway config), allowed-call records include the **full argument map** in the `details` field. In enforce mode (the default) and in per-entry `enforcement: audit` without a route-level override, allowed-call records contain no argument values.

**Argument size is bounded before enqueue.** Because observe mode captures arguments verbatim, a single tool call with a multi-megabyte argument (a `write_file` body, a base64 blob, a large text corpus) would otherwise produce one audit record larger than the `audit-verify` scanner buffer and the chain-resume tail window — making `audit-verify` fail with `token too long` (skipping every later record) and the chain resume from a stale fragment after a restart. To keep records bounded, any single string value over 512 KiB is replaced with a size-marked placeholder — a binary (`[]byte`) value is measured by its base64-encoded length, the size it actually occupies once serialized into the record — and if the whole `details` map still marshals over 1 MiB it is replaced with a single `_eunox_truncated` marker carrying a structured `{"reason": …}` code (plus the numeric `bytes`/`cap` facts) rather than a free-form prose string, so consumers key on a stable code. This bounds the record well under the scanner limit while keeping the truncation visible; it caps individual value size, never the number or set of records. The bound is applied on the request goroutine **before** the record is placed on the audit queue, not in the background drainer afterward, so the bounded queue cannot retain up to `auditChannelSize` un-truncated multi-MiB argument clones.

**The record envelope is bounded too.** The `details` cap covers only the argument map; the record's envelope strings are bounded separately. `target` is derived verbatim from the attacker-controlled tool name (`params.name`) or resource URI (`params.uri`), and an unrecognized raw method is preserved as `method` — both are written even on the deny path (e.g. an unknown tool), and an incoming request is allowed up to 4 MiB. An unbounded `target` could fill nearly the whole body and push the serialized line past the 4 MiB `audit-verify` scanner buffer and chain-resume tail window — the same failure the `details` cap prevents, reached through the envelope instead. `target` and a raw `method` are therefore truncated to 8 KiB with a visible marker. The `obligations` array is bounded the same way: directives such as `redactFields` emit one obligation per match, so a manifest with many (or deliberately crafted) long redact paths could otherwise drive the array large enough to push the line past the 4 MiB window on its own. The array is capped at 64 KiB of serialized length — the kept prefix is retained in order and a single `obligations_truncated:N` sentinel records the omitted count, so the truncation is visible and the record stays structurally valid. The `agent_id`, `task_id`, and `user_id` fields are bounded the same way: all come from a validated JWT's `mcp.agent_id`/`mcp.task_id` claims and its `sub` subject, whose structure is checked but whose length is not, so a misconfigured or compromised IdP could otherwise stamp a multi-megabyte claim and push the line past the 4 MiB window without any change to the proxy config. Each is truncated to 8 KiB with a visible marker. With the 1 MiB `details` cap, the 64 KiB `obligations` cap, the `session_id` explicitly capped at 256 bytes (in HTTP mode it comes from the client-controlled `Mcp-Session-Id` header, so it is bounded like `target`/`method` rather than trusted to be a server-minted UUID), the 8 KiB `agent_id`/`task_id`/`user_id` caps, and every other envelope field bounded by its source (policy digest, request id), this makes the full serialized record provably far below the 4 MiB window.

**Denial records — all modes:** denial records always include `denial.Details`, a condition-specific object written for compliance and forensic purposes. For conditions such as `allowedValues` this object contains the **specific argument value** that triggered the denial (e.g., `{"argument": "sql", "value": "<the rejected query>", "allowedValues": [...]}`). This applies in both enforce mode and audit mode. Operators must therefore treat `audit.jsonl` as potentially sensitive regardless of mode — the file may contain individual argument values extracted from denied calls.

| Data                                 | Allow record (enforce mode)        | Allow record (route-level audit mode)              | Denial record (any mode)                              |
| ------------------------------------ | ---------------------------------- | -------------------------------------------------- | ----------------------------------------------------- |
| Full tool argument map               | Not written                        | Written in `details` (oversized values size-capped, §6.2) — **treat log as sensitive** | Not written                                |
| Condition-specific argument excerpt  | N/A (no denial)                    | N/A (no denial)                                    | Written in `details` (e.g., rejected value) — **sensitive** |
| Bearer JWT content                   | Not written                        | Not written                                        | Not written                                           |
| `listen.authToken` value             | Not written                        | Not written                                        | Not written                                           |
| `upstreamAuthHeader` value           | Not written                        | Not written                                        | Not written                                           |
| `--redis-password` value             | Not written                        | Not written                                        | Not written                                           |
| Upstream MCP server responses        | Not written                        | Not written                                        | Not written (enforced denials never reach upstream; observed denials are forwarded but the response is not captured) |
| HMAC key (`~/.eunox/audit.key`)      | Not written                        | Not written                                        | Not written                                           |

**Two records on an observed-and-forwarded denial.** When a per-entry `enforcement: audit` constraint (or route-level audit mode) produces a *would-be denial* that is then forwarded, the proxy writes **two** records for that one request: first a `deny` record (`audit_only: true`) capturing the verdict and its `denial_code`/`details`, then — after the upstream call returns — an `allow` record (`audit_only: true`) capturing the forwarded outcome and any obligations. This is intentional: the deny record preserves the policy verdict for `stats`/`suggest` and forensics, while the allow record reflects what the host actually received. Both carry `audit_only: true`, which together with the matching `target`/`method` distinguishes the pair from a genuine allow or a genuine enforced deny. SIEM correlation rules that treat an allow+deny pair on the same target as an anomaly should exclude records where `audit_only` is `true`. A hard-blocked kill-switch denial is **not** forwarded and therefore produces a single enforced `deny` record (never marked `audit_only`).

### 6.3 Response redaction via the `redactFields` directive

`redactFields` is a post-allow **directive**, not a condition. When a matched constraint carries a `redactFields` entry in its `directives` array (e.g., `directives: [{"type": "redactFields", "fields": ["$.ssn", "$.card_number"]}]`), the proxy **masks** those dot-path fields in the tool call _result_ returned to the MCP host before forwarding it: each matched field keeps its key, but its value is replaced by the placeholder string `"[redacted]"`. The redaction is applied to JSON text content blocks and the `structuredContent` object in the upstream response, recursing into array elements. Redaction fails the whole response closed (internal error `-32603`, never forwarding unredacted data) only on a **structural or resource guard** — the response envelope is not parseable JSON (or carries trailing data), the `content` array or one of its items has a structurally unverifiable shape, a value nests deeper than a fixed redaction depth bound, or re-serialization fails. It does **not** fail closed over string *content* it merely cannot parse as JSON (see the accepted residual below).

Because an obligation is a property of the **matched constraint**, not of the allow *decision*, `redactFields` is also applied when an **observe-mode deny is downgraded to a forwarded call** — a condition, `argumentSchema`, or action-check failure under an `enforcement: audit` constraint **or a route running `--audit`** still returns the upstream response to the host, so it is masked exactly as a genuine allow would be. Dropping the obligation on that path would forward the very fields the manifest marked for redaction; the downgraded deny therefore carries the constraint's `redactFields` obligations, and the transport applies them before the forwarded response reaches the host.

Both halves of that union matter, and they are computed in one place so they cannot drift: gating only on the per-constraint `enforcement: audit` flag would leak on the standard whole-route `--audit` deployment, where individual constraints are *not* marked audit-only. The test is also `!= allow` rather than `== deny`, matching the transport's own fail-closed gate — a response with an unset decision is forwarded there, so gating on `== deny` here would let it through unredacted.

A **no-match** deny (no constraint selected for this caller — e.g. a principal-scoped entry whose claims the caller does not satisfy) is downgradable too, so a route running `--audit` forwards it. It carries the `redactFields` declared by **every entry naming that target**, regardless of principal scoping: no entry was selected, and any entry declaring a field of this target redactable is reason enough to mask it on a response about to be forwarded. On an enforce route the same deny blocks, so it carries nothing.

A **hard** deny (kill-switch, a tool-poisoning `descriptionHash` mismatch, an engine-error) is never forwarded, so it carries no obligations.

Two layers above this remain **out of scope** and are tracked as known gaps: `JWTPDP` short-circuits its own denials before the manifest layer runs, so a JWT-side deny on a `--audit` route still forwards without obligations; and `Engine.ValidateAction`/`EvaluateConditions` return audit-mode denials to external embedders without them.

**Mask, not strip — disclosure posture.** Redaction replaces the value and **retains the key**; it does not delete the key. The host therefore learns that the named field was *present* (and at what path) but never its contents. This is a deliberate choice over stripping the key outright: a stable response shape avoids breaking hosts that expect the field to exist, at the cost of disclosing the field's *presence*. The masked value is a fixed sentinel (`"[redacted]"`) carrying none of the original data — whatever the original type (string, number, object, array), the field becomes that string. Because the sentinel is always a string, masking a field a tool's `outputSchema` declares as a number, object, or array yields a value that no longer matches that schema, so a host that validates `structuredContent` against `outputSchema` may reject the result — another reason to redact such fields **upstream**. Where a field's very existence is sensitive and must not be disclosed, redact it **upstream** so the proxy never sees it.

A redaction target (`$.ssn`, `user.card_number`) is a key inside a JSON object, so the **text-content posture** turns on whether a block parses cleanly as JSON. A block that parses cleanly as a single JSON object or array is redacted; a block that is **not** a clean JSON document — genuine free-form text (an error string, a `[ERROR] …` log line, a bare scalar), **malformed** JSON (`{"ssn":"…",}`, `{"ssn":"…"`, a truncated `[{"ssn":"…"}`), a status-prefixed body (`OK {"ssn":"…"}`), or JSON **embedded in surrounding prose** (`result: {"ssn":"…"}`) — has no addressable JSON key and is **forwarded unchanged**. `redactFields` redacts valid JSON only and never fails the response closed over string *content* it cannot parse, so adding it never blocks a tool that returns plain-text or partially-JSON output.

**Accepted residual (fail-open on unparseable content).** Forwarding unparseable string bodies unchanged is a deliberate availability/precision trade-off, and its cost is an explicit fail-open: a named field hidden inside a **malformed** JSON container that still carries it (a truncated `{"ssn":"…"`), or inside JSON **embedded in prose**, is **not** redacted and reaches the host. The structural-key smuggling vector is still closed for *clean* JSON — a **clean** container reached through any number of nested JSON-string-encoding layers (`{"data":"{\"ssn\":\"…\"}"}`, or that same string encoded again, and again) is unwrapped at every layer, redacted, and re-serialized, up to a bounded depth, so an upstream cannot evade redaction by double- or triple-encoding well-formed JSON. `redactFields` is therefore a control over **cleanly-structured** JSON fields only, at any string-encoding depth; data that may arrive malformed or prose-embedded must still be redacted **upstream**, at the tool/server that produces it. (Redacting JSON embedded in surrounding prose is not currently supported.)

**JSON-RPC error channel.** Redaction operates on a tool-call **result**. When the upstream answers an allowed call with a JSON-RPC **error** instead, there is no result to mask, and the free-form `error.data` payload cannot be verified against the result-shaped redact paths — an adversarial or misconfigured upstream could otherwise smuggle a declared-redactable value to the host through `error.data`. Rather than forward it unredacted, the proxy **strips `error.data`** (fails closed) whenever a `redactFields` obligation is attached to the call; the error `code` and `message` still reach the host, and the obligation is **not** stamped as discharged in the audit record (so the tape never claims a redaction that did not run).

Redaction affects the data the MCP host sees, not the audit log. The allow record's `obligations` array records each applied obligation as a token — `redactFields:<path>`, one per masked field path (a bare `redactFields` when the directive lists no path) — so the tape shows *which* fields were masked. These are the operator-defined field *names* from the manifest, never the masked *values*; the upstream response itself is never written to the log in any mode (§6.2), so a redacted value cannot leak there. The record may still capture request *argument* values depending on mode and outcome (§6.2). This lets operators control what the MCP host receives while the audit trail retains the redaction provenance.

### 6.4 Data residency in default configuration

**eunox sends no telemetry and never phones home.** It opens no analytics,
usage-reporting, or update-check connections of its own. The only outbound
connections it makes are the ones the operator configures: the upstream MCP
server (when it is a remote HTTP upstream), the JWKS endpoint (when `--jwks-uri`
is set), and Redis (when `--redis-addr` is set). Adding any background network
activity requires an explicit design discussion (see
[CONTRIBUTING.md](../CONTRIBUTING.md)).

In the default configuration, all data stays on the machine running the proxy:

| Data               | Location                             |
| ------------------ | ------------------------------------ |
| Audit records      | `~/.eunox/audit.jsonl` (local file)  |
| HMAC signing key   | `~/.eunox/audit.key` (local file)    |
| Kill-switch state  | In-process memory                    |
| Call counter state | In-process memory                    |
| JWKS cache         | In-process memory                    |
| Policy manifest    | Local file path provided by operator |

When `--redis-addr` is configured, kill-switch and call-counter state are persisted to the Redis instance at that address. When a remote `upstreamUrl` is configured, tool call requests are forwarded to that URL (with the `upstreamAuthHeader` if provided). The remote-upstream HTTP client does **not** follow redirects: an MCP JSON-RPC POST has no legitimate redirect, and Go strips only `Authorization`/`Cookie` on a cross-host redirect, so a custom-named `upstreamAuthHeader` (e.g. `X-Api-Key`) would otherwise be replayed verbatim to whatever host a compromised upstream named in a `30x` `Location` — leaking the credential. A `30x` from the upstream is surfaced as an error instead. No other data is transmitted externally by the proxy.

### 6.5 Verified JWT claims at the policy-evaluator boundary

When a `policy` condition delegates to an external evaluator (the library-only `WithPolicyEvaluator` extension point — OPA/Cedar/etc.; the stock binary embeds none and denies `policy` conditions fail-closed), the proxy serializes the request into the standard Rego `input` document and hands it to that evaluator. `input.claims` carries the **entire** top-level claim set of the verified JWT — not only the four eunox-canonical fields (`sub`, `iss`, `task_id`, `agent_id`) but every other claim the IdP issued, including the nested `mcp` object and any PII the token happens to carry (`email`, `name`, group/role lists, …). A policy that restricts on an arbitrary IdP claim requires this; the trade-off is that whatever the IdP puts in the token now crosses the proxy→evaluator boundary on every evaluation, where before this change only the four fields did.

This is bounded and does not change the audit or data-residency posture:

- **Verification-gated.** The claim set is assembled only after the token's signature is verified, so an unsigned or invalid token contributes nothing.
- **Audit log unaffected.** Only the validated `agent_id`/`task_id`/`user_id` (the `sub` subject) reach an audit record (§6.1); `input.claims` is never written to `audit.jsonl`.
- **Stays where the evaluator runs.** A `PolicyEvaluator` is in-process operator code (§6.4 lists no policy-evaluator egress). Claims leave the host only if that operator-supplied evaluator itself forwards them — e.g. to an OPA sidecar. Operators wiring an external evaluator should treat `input.claims` as potentially PII-bearing and scope what their evaluator transmits accordingly.

| L-1 | Session binding       | No cryptographic binding between bearer JWT and session ID (§3.3). A periodic reconciliation timer now recovers kills whose pub/sub event was lost, even without a Redis outage. | Low      | Mitigated — by default the switch now fails **closed** during an outage (denies unconfirmable requests with `KILL_SWITCH_ERROR` until Redis recovers, ADR-0003); `--killswitch-fail-open` restores fail-open. | L-3 | Audit completeness    | Write failures produce a gap in the audit trail without blocking enforcement (§5.4). Mitigated by external log shipping. The loss is now observable: a distinct `eunox_audit_write_failures_total` metric (plus a one-shot stderr warning and a non-zero process exit when the failure persists to `Sync`/`Close`), separate from the queue-drop signal (§5.4). Queue-drop loss is made visible by a signed `AUDIT_RECORDS_DROPPED` chain marker (§3.6); drops during the graceful-shutdown window are counted-but-unchained, a known bounded gap (§3.6). | Info     | Accepted — documented tradeoff                                                                                                  |
| L-4 | SSE notifications     | SSE notifications from a remote `upstreamUrl` are not forwarded to the client (documented in `http_remote.go`). The same applies to server-initiated *requests*: a remote HTTP upstream's `sampling/createMessage` is never read back, so it cannot be enforced or audited. A manifest that grants `system:sampling/createMessage` on an `http` upstream is therefore rejected at load (fail closed, with a message pointing the operator at stdio) rather than silently accepted as inert. | Info     | Mitigated — remote sampling opt-in rejected at load; reach the upstream over stdio to enforce sampling |
| L-5 | X-Forwarded-For trust | When `--trust-forwarded-for` is enabled, the proxy honors `X-Forwarded-For` only from a peer whose RemoteAddr matches `listen.trustedProxyCIDRs`, and then resolves the client for `IPRange` conditions by **counting declared hops**: with `listen.trustedProxyHops` set to N (default 1), each of the N trusted proxies appends the address it saw, so the right-most N entries are proxy-written and the client is the N-th from the right. Entries further left are client-supplied and ignored, so a client behind the trusted proxies cannot forge its source IP. A chain that carries entries but fewer than N does not match the declared topology, so nothing in it is provably proxy-written and the source IP resolves empty — an `ipRange` condition then denies with `MISSING_CONTEXT`, making the mismatch loud instead of silently evaluating the proxy's own (in-range) address. A selected entry that is not a parseable host is likewise passed through unchanged so it fails closed downstream rather than falling back to the peer. The count is **declared, not inferred** from `trustedProxyCIDRs` membership: an entry inside that range is indistinguishable from a client whose own address falls in it, so inferring would skip the client's real entry and return a forged one to its left — a spoof in exactly the internal deployments where clients and proxies share a private supernet. A client that connects directly (outside the configured allowlist) gets its own RemoteAddr and cannot spoof the header at all; an empty allowlist makes the flag a no-op (XFF is never trusted). | Low | Mitigated — the immediate peer must match `listen.trustedProxyCIDRs`, and the chain depth is operator-declared rather than guessed. Set `listen.trustedProxyHops` to the real number of proxies in front of eunox; leaving it unset reads the right-most entry, correct for the single-proxy case. **Residual:** the declared count is trusted verbatim. Under-declaring is safe, but OVER-declaring points the read at a client-supplied entry and lets a client behind the proxies choose its own source IP; the count cannot be validated at runtime without reintroducing the CIDR inference this design rejects, so the proxy prints it as a startup `SECURITY` line whenever it exceeds 1 for an operator to check against the real topology. |
| L-6 | List-cache scope (forthcoming spec) | The 2026-07-28 revision (SEP-2549) adds `cacheScope` (`public`/`private`) and `ttlMs` to `*/list`, `resources/read`, and the discovery result. eunox filters `*/list` per caller identity, so every list it emits is authorization-context-specific; `filterListResult` preserves upstream sibling fields verbatim, so an upstream `cacheScope: public` would pass through unchanged on a personalized response, and a shared downstream cache honoring it could serve one identity's narrowed view to another. | Medium | Open — planned: override `cacheScope` to `private` on any filtered/personalized response (never preserve an upstream `public`); preserve `ttlMs` only as a freshness hint. Not yet applicable — eunox targets MCP 2025-11-25 (see `docs/conformance.md`). |
| L-7 | MCP Apps surface (forthcoming spec) | The 2026-07-28 revision (SEP-1865) adds server-rendered UI. UI templates are fetched via `resources/read` / `resources/list` (already gated and filtered) and UI-initiated tool execution is an ordinary `tools/call` (already enforced and audited); the `ui/*` methods run on the host↔iframe postMessage bridge, which never traverses the proxy. No new server-transport method exists today, so existing mediation covers it. | Info | Watch — a future Apps revision introducing a server-transport `app/*` method would hit the fail-closed unmapped path and need explicit classification. |
| L-8 | Enforcement-point interposition | eunox governs only traffic routed through it; a host that connects directly to the upstream bypasses all enforcement (§4.6). Interposition is a deployment property established by credential, network, and endpoint controls, not asserted by the proxy. | Info | Out of scope — established by deployment (see §4.6 and [deployment-hardening.md](./deployment-hardening.md)). Bypass is detectable by reconciling eunox audit records against the upstream's own audit log. |

### 7.3 Adversarial test coverage

The threat model sections cited in the table below — spanning the §3 attack
classes, the §4 out-of-scope threats, and the §2 verification invariants — and
the residual risks above are exercised by a published adversarial eval suite
(`TestAdv*` in `internal/transport/dispatch_test.go`, with the JWT∩manifest
intersection cases in `internal/pdp/jwt_test.go`), running against a mock
upstream. Each scenario has a **pass** sub-test (eunox blocks the
attack) and, where the threat model documents a residual risk, a **baseline**
sub-test showing what happens without eunox. The suite is the executable,
regression-protected counterpart to this document — enterprise evaluators can
run `go test -run TestAdv ./internal/...` to verify the claims independently.

| ID    | Scenario                          | What the suite asserts                                                                                                                                                                          | Threat model |
| ----- | --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| Adv-1 | Prompt injection / indirect       | A poisoned upstream tool **response** is forwarded to the host unmodified and never re-evaluated as a policy input; a host-issued `tools/call` to a denied tool is still blocked on its own merits. | §4.1, §2.3   |
| Adv-2 | Tool poisoning via description     | Denied tools are hidden from `tools/list`. `descriptionHash` pins both the description and the parameter descriptions; FM-6 + a closed `argumentSchema` catch and gate a changed parameter shape. **Residual:** the text is not semantically sanitized (a model-layer concern), and pins are opt-in. | §3.8         |
| Adv-3 | Read-then-exfiltrate               | An exfil `tools/call` issued after an allowed `resources/read` is denied when the tool is absent from the manifest; a `sequenceBlock` / `allowedValues` condition fires on the violating value.    | §3.2.1       |
| Adv-4 | Overbroad JWT claim                | A `*` capability claim is intersected with the manifest and cannot expand beyond it — both the call-time deny and the `tools/list` narrowing hold. This intersection applies when `--jwt-experimental-capabilities` is enabled; with the flag off the token is rejected at validation (fail closed). | §3.1, §2.2   |
| Adv-5 | Novel MCP method (fail-closed)     | An unmapped method (`tools/execute`, `resources/patch`, …) is denied `AUTHORIZATION_FAILED`, nothing is forwarded, and an audit record is written — on both the HTTP and stdio transports.        | §2.2         |
| Adv-6 | Rate-limit session-ID bypass       | **Residual:** a fresh `Mcp-Session-Id` resets the in-memory `maxCalls` counter. Redis shares the per-session counter across instances, but neither backend stops session rotation.                  | §3.6         |
| Adv-7 | Enforced method via notification framing | A manifest-granted `tools/call`/`resources/read`/`resources/subscribe`/`prompts/get` sent with no `id` (notification framing) is denied `INVALID_REQUEST`, never forwarded, and audited — on both the HTTP and stdio transports. | §3.10        |
